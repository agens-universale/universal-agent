# Конфигурация

## Конфиг клиента

- Требуется запущенный GigaCode Agent с API `v1/responses` или с режимом `backend_api_mode: chat_completions`. Адрес сервиса задаётся в `config.yml`.
- **Где ищется базовый `config.yml`** (первый найденный источник побеждает):
  1. путь из `--config` (если задан);
  2. иначе `config.yml` в каталоге «Config» из таблицы [«Где gc-cli хранит runtime-данные»](#где-gc-cli-хранит-runtime-данные) — `~/.config/gc/config.yml` на Linux/macOS, `%USERPROFILE%\.gc\config.yml` на Windows (учитывает `GC_CONFIG_DIR` / `XDG_CONFIG_HOME` / `GC_HOME`). Это **полная база** (кладите полный конфиг — частичный файл здесь потеряет пакетные дефолты);
  3. иначе `config.default.yml` из ассетов дистрибутива `gc-core` (в рабочей копии — `packages/core/assets/`, в установленном колесе — `gc_core/assets/`).

  Поверх выбранной базы дополнительно deep-merge'ится project-local `<cwd>/.gc/config.yml` (см. [«Project local config (опционально)»](#project-local-config-опционально)). Чтобы указать свой путь явно:
  ```commandline
  gc-cli -q "ваш вопрос" --config ./config.yml
  ```
- Пример конфигурации: `demo_config.yml`. Скопируйте в `config.yml` и отредактируйте под свой бэкенд и MCP-серверы.
- В конфиге можно задать количество шагов агента (`max_steps`), логирование и другие параметры.
- **`max_steps` / `subagent_max_steps` — число завершённых ходов модели**, не half-turn цикла. Один step ≈ «модель ответила + (если были) все tool calls из ответа исполнены» (или text/bounce/finish). Запрос к LLM (`user_ask` / `function_call_output`) сам по себе step не тратит. Батч из N tools в одном ответе = **1 step**. Проверка `step_limit` — только когда нет pending `function_call`: уже присланные моделью tools всегда дожимаются, затем на следующем ходе срабатывает лимит (`steps >= max_steps`).
- `session_token_limit` / `max_tool_calls` — необязательные per-run лимиты надёжности (по умолчанию выключены). Первый ограничивает суммарные input+output токены одного рана по всем категориям (включая summary/finish gate/сабагентов); второй — число вызовов инструментов за ран (каждый вызов в батче считается отдельно). При достижении ран мягко завершается (как при `max_steps`) с `terminal_outcome = token_limit / tool_call_limit`; тред сохраняется, следующий запрос получает свежий бюджет. Проверка выполняется между шагами, поэтому возможен перерасход токен-бюджета в пределах одного шага. `max_tool_calls` аналогично проверяется между шагами: батч из нескольких вызовов в одном шаге выполняется целиком, даже если лимит достигнут в его середине; попытки вызова, отклонённые валидацией аргументов, тоже расходуют счётчик. Сабагент наследует те же значения на свой собственный ран, и при этом оба бюджета считаются **по всему дереву**: и токены, и вызовы инструментов ребёнка вливаются в счётчики родителя, поэтому родитель тратит `1` (сам вызов `subagent_*`) плюс все вызовы, сделанные ребёнком.
- **`session_token_limit` зависит от провайдера.** Бюджет считается по блоку `usage` из ответа модели. Если провайдер его не возвращает, вызов учитывается в `calls` и `missing_usage_calls`, но токенов прибавляется ноль — израсходованное остаётся нулевым, и лимит не сработает вообще (ран остановится только по `max_steps` / `max_tool_calls`, они от провайдера не зависят). Признак в отчёте по завершении рана: строка `⚠ N вызов(ов) без usage не учтены` и поле `missing_usage_calls` (см. [usage_pricing.md](usage_pricing.md)). Если у вашего бэкенда так — полагайтесь на `max_tool_calls` и `max_steps`, а не на токен-бюджет.
- `agent.loop_detector.enabled` (по умолчанию `true`) — kill-switch напоминания о повторном вызове того же тула с теми же аргументами. Тул **всегда исполняется**; после батча в тред может уйти одно technical user-сообщение. В кольцо из 10 слотов попадают **все** вызовы; пороги (`consecutive` / `in_window`) считаются только у помеченных встроенных тулов (чтение, think, memory и т.п. — не write/exec/finish). Окно живёт только в рантайме, в тред и snapshot не пишется. `false` — не записывать окно и не слать notice. MCP по умолчанию не маркируются; opt-in — `mcp.servers.<name>.loop_control_tools` (см. [MCP-серверы](#mcp-серверы)).
- Для режима `backend_api_mode: chat_completions` можно передавать токен провайдера
  (например OpenRouter) через `chat_completions_auth_token` (или алиас `openrouter_api_key`);
  клиент сначала передаст настроенный формат заголовка в запрос к `completions_url`.
  Для голого ключа и Bearer после HTTP 401 (в том числе завёрнутого прокси в ответ 200)
  допускается одна попытка альтернативного формата на том же задании: её делает
  транспорт, до модели 401 не доходит, поэтому второй слот проверки зрения остаётся для
  новой картинки после неподтверждённого ответа. Basic и другие явные схемы передаются
  как есть. ENV/FILE не раскрываются при сохранении настроек.
  Транспорт помнит до конца процесса форму, с которой запрос к этой модели на этот URL
  прошёл успешно (отдельно для значений, заданных с `Bearer` и без), и начинает с неё —
  для рабочих запросов и пробы зрения одинаково: лишний 401 платят запросы, пока форма
  не подтверждена успешным ответом.
  В формах подключения и моделей успешная проба подставляет принятую форму
  текстового токена в черновик. Она записывается только при сохранении формы;
  ссылки ENV/FILE остаются исходными ссылками.
  Опционально для OpenRouter поддерживаются заголовки `openrouter_http_referer`
  и `openrouter_x_title` (в запросе это `HTTP-Referer` и `X-OpenRouter-Title`).
- `strip_tags_projection.strip_think`: кодовый дефолт (ключа нет) — `false`, скрытое поле мысли бэкенда (`reasoning_content`) копируется в историю. Поставляемый `config.default.yml` ставит `true`: поле в историю не копируется (следующий запрос с мыслью часть бэкендов, в том числе DeepSeek, отвергает с 400). `false` копирует поле; `true` вырезание включает. Salvage `<think>` при `true` — только если кроме ризонинга ничего нет (нет прозы и нет тулов): тогда мысль кладётся в историю как `<think>…</think>`. Смешанный ход (think + проза) кладёт только прозу. У записи реестра свой `models.<alias>.strip_think`: `true` вырезает, `false` копирует, отсутствие ключа оставляет глобальный флаг. Служебные вызовы от этого флага не зависят. История для сводки и патча памяти оставляет `<think>` в тексте ответа и дописывает обрезанное поле `reasoning_content`, если оно сохранено в истории; хвост `<last_dialog_steps>` для основной модели, intent, судьи и ответ служебной модели идут без мысли. Флаг модели действует в момент сохранения ответа: в режиме `level: auto` мысль, сохранённая моделью с `strip_think: false`, уходит и следующему запросу другой модели, даже если у той `strip_think: true`.
- Для хранения истории тредов:
  - по умолчанию используется папка `threads` в корне проекта (`mini-cli-pub/threads`);
  - опциональный параметр `threads_data_path` в `config.yml` должен быть **абсолютным путём** к директории хранения; если не задан — используется кросс-платформенный дефолт `<state>/projects/<project-slug>/threads/` (на Linux/macOS — `~/.local/state/gc/...`, на Windows — `~/.gc/...`);
  - параметры суммаризации в `chat_completions` задаются в секции `summary`:
    - `summary.chat_completions_summary_trigger_chars`:
      - `<= 0` (или отсутствует) — символьный порог выключен (дефолт в коде: `0`); если выключен и токенный порог, суммаризация не работает; рекомендуемое значение для моделей с контекстом ~131k — `180000`;
      - `> 0` — при достижении/превышении порога тред архивируется (`data_*`/`meta_*` с суффиксом `__summarized_<YYYYMMDD_HHMMSS>`) и продолжается от compact summary;
    - `summary.chat_completions_summary_trigger_tokens` — токенный порог рядом с символьным (дефолт `0` — выключен). Оценка — `prompt_tokens` (или `input_tokens`) последнего главного запроса плюс сообщения, добавленные после него, по курсу два символа на токен. Сработал любой из двух порогов — один проход сжатия. Ограничения:
      - число провайдера включает системный промпт, схемы тулов (вместе с MCP) и сводку — и основной, и turn-end порог держать заметно выше этой постоянной части, иначе сжатие повторяется каждый шаг или каждый ход — рантайм это не отслеживает;
      - без `usage` в ответе провайдера порог не срабатывает; когда история по символам уже выше порога, а числа нет, в лог уходит предупреждение `summary_token_trigger_no_prompt_tokens`;
      - порог рассчитан как дополнение к символьному: в пользовательских конфигах символьный держать включённым, режим «только токены» — для бенчей;
    - `summary.chat_completions_summary_turn_end_trigger_chars` и `summary.chat_completions_summary_turn_end_trigger_tokens` — пороги уборки после принятого `turn_finish`; нет ключа — 60% от mid-turn порога той же шкалы, явный `0` выключает;
    - `summary.incremental_batch_chars` — размер батча для кумулятивной суммаризации; если не задан, используется `int(summary.chat_completions_summary_trigger_chars * 1.2)`, а при выключенном символьном пороге — `int(summary.chat_completions_summary_trigger_tokens * 2 * 1.2)`;
    - `summary.chat_completions_summary_prompt_path` (опционально), по умолчанию `prompts/chat_completions_summary_prompt.md`;
    - `summary.max_message_chars` — максимум символов на одно сообщение при подготовке истории к суммаризации (по умолчанию `50000`);
    - `summary.max_dialogue_chars` — максимум символов на весь диалог для суммаризации (по умолчанию `1000000`, берется хвост целыми сообщениями);
    - `summary.max_accumulated_summary_chars` — лимит длины накопленного summary; при превышении запускается дополнительное сжатие summary-of-summary (по умолчанию `20000`);
    - `summary.original_user_messages_max_chars` — лимит символов для `meta.user_messages_log` (единственный источник user-запросов для суммаризации); сохраняются последние сообщения целиком (по умолчанию `20000`);
    - `summary.last_dialog_steps_count` — сколько последних сообщений включать;
    - `summary.last_dialog_step_message_max_chars` — максимум символов на одно сообщение (лишнее обрезается).
  - **Пороги на модели:** у `models.<alias>` можно задать `summary_trigger_chars` / `summary_trigger_tokens` (mid-turn). Читаются при проверке для модели, которая ведёт историю: и в ручном режиме, и в AUTO — модель подготовленного вызова, у субагента — его модель. `/level` меняет модель и её пороги со следующего нового вызова; уже подготовленный запрос и его повторы сохраняют прежний выбор. Это не снимок со старта `run`. Оба `0` — глобальный `summary`; иначе режим модели (см. таблицу ключей алиаса ниже). Батч и лимит диалога модели действуют при любом сжатии её истории: автоматическом, по команде `/compact` и из тула `session_compact`.
  - **Поток суммаризации** (только при `backend.api_mode: chat_completions` и положительном mid-turn пороге — глобальном или на модели истории):
    - перед первым запросом выполняется **pre-run** compaction после выбора модели и её порогов (если объём диалога уже достиг порога); текущая задача и батч сохраняются при сжатии;
    - после шага с исходящим результатом инструмента (**post-step**, сразу после обработки `function_call_output`) снова проверяется порог и при необходимости запускается compaction;
    - источник данных для решения «суммаризировать или нет» — только текущие сообщения сессии (`state.messages`); при запуске с `-t` после успешного compaction дополнительно обновляются файлы треда через `thread_store` (архив старых `data_*/meta_*` и запись compact-истории).
    - пользовательская картинка-вложение добавляет к объёму истории 4000 символов, снимок инструмента — 200: в тексте пикселей нет, а контекст модели они занимают. Так их видят порог в символах и индикатор контекста TUI в символьной шкале; порог в токенах берёт число токенов у бэкенда, где картинки уже учтены, а этим весом оценивает только хвост после последнего запроса.
    - после сжатия тело сводки перечисляет ваши картинки из свёрнутой части блоком `<images>` (подпись, размер, путь к файлу) — агент может вернуться к ним тулом `fs_view_image`; сами файлы не удаляются.
  - `gc-cli -q "..." -t my-thread` — продолжить диалог по треду;
  - `gc-cli -q "..." -t my-thread -n` (или `--new`) — начать тред заново с тем же id и удалить старые файлы этого треда (`data_*`/`meta_*`);
  - `-n/--new` можно использовать только вместе с `-t/--thread-id`.
  - в директории для тредов создаются файлы `data_<thread_id>.jsonl` (сообщения) и `meta_<thread_id>.json` (метаданные, включая `previous_response_id`).
- По умолчанию логи будут сохраняться в той папке, из которой запущена команда.
- **TUI**: секция `tui` управляет поведением интерфейса:
  - `tui.stream` (по умолчанию `true`) — мастер-переключатель live-стриминга ответа в TUI.
    При `false` ответ ждётся целиком; при `true` — чанки поступают по мере генерации.
    **Флаг задействован ТОЛЬКО в TUI:** на CLI/server/swarm не влияет — там всегда
    non-stream (стрим гейтится наличием `on_stream_delta`, который ставит только TUI).
    Legacy: если `tui.stream` не задан, читается старый `backend.stream` (backward-compat).
  - `tui.stream_display` (`minimal | answer | answer_reasoning`, по умолчанию `minimal`) —
    что показывать во время стриминга (`minimal` — только индикатор, `answer` — прогрессивный
    текст ответа, `answer_reasoning` — + однострочный «глазок» рассуждения).
    Актуально только при `backend_api_mode: chat_completions` и `tui.stream: true`.
  - `tui.text_answer_mode` (`deny | judge | allow`, по умолчанию `judge`) — как поступать
    с текстовым ответом агента без вызова инструмента:
    `deny` — всегда bounce (как CLI), `judge` — intent_guard решает, `allow` — принять текст.
    Только TUI копирует это в рабочий ключ `text_answer_mode`.
  - `acp.text_answer_mode` (`deny | judge | allow`, по умолчанию `allow`) — то же для
    канала `gc-acp` (IDE). По умолчанию проза разрешена без судьи.
  - `acp.finish_gate_mode` (`on | off | smart`, по умолчанию `off`) — судья на
    `turn_finish` в ACP; в IDE человек сам видит ответ и сверяет с интентом.
  - `acp.todo_reminder_steps` (число, по умолчанию `0`) — technical reminder про
    `session_todo`; `0` = выкл. В IDE-чате иначе легко толкает к реализации вопреки обсуждению.
  - `acp.confirm_timeout_sec` (число, по умолчанию `600`) — ожидание ответа IDE
    на `session/request_permission`. По таймауту операция отклоняется.
  - Канал ACP также подставляет bundled special instructions
    (`chat_completions_acp_special_instructions.md`: discussion ≠ implementation).
    Пример профиля — `packages/acp/profiles/acp.yml`. Гайд по процессу — [acp.md](acp.md).
  - `tui.file_view.enabled` / `max_file_bytes` / `page_lines` (`null` = авто по высоте)
    — постраничный просмотр `/view` в TUI (см. [tui.md](tui.md#просмотр-файла-view)).
  - `tui.theme` (`auto | gigacode`, по умолчанию `auto`) — тема TUI: `auto` берёт фон
    терминала, если на нём читается текст палитры, иначе — `gigacode`, собственная тёмная
    палитра. Выбирается при старте; переключатель — `/settings` → «Внешний вид»
    (см. [tui-design-code.md](tui-design-code.md)).
- **Правки агента**: секция `agent_edits` — журнал правок, снимки для отката, дифф в ленте
  и экран изменений. Журнал ведётся по режиму запуска: `agent_edits.record.tui` (по умолчанию
  `true`), `record.cli` и `record.server` (по умолчанию `false` — включите, чтобы правки из
  `gc-cli` или сервера попадали в журнал треда). Все ключи — в
  [tui.md](tui.md#конфигурация-tui).
- **Обновление**: секция `update` управляет самообновлением агента:
  - `update.check` (`auto | off`, по умолчанию `auto`) — проверять ли при запуске, вышла ли
    новая версия. Вердикт виден в TUI (`/settings` → Обновление) и по `gc-cli --check-update`.
  - `update.extra_args` (список, по умолчанию пустой) — дополнительные аргументы к
    `uv tool install` при обновлении. **В корпоративной сети обязателен**
    `["--system-certs"]`: без него установка упирается в TLS-перехват и падает —
    как из `/settings`, так и по `gc-cli --update`.
- **Слои инструкций** (`paths.agent_md_path`, `tui.agentsmd_override`) — см. раздел
  [«Слои инструкций (AGENTS.md)»](#слои-инструкций-agentsmd) ниже.

## Секреты и env-интерполяция (`${ENV:VAR}`)

В любом строковом значении конфига можно использовать плейсхолдер `${ENV:VAR}` — он
подставляется из переменной окружения **до валидации** (и в file-конфиге, и в CLI-override).
Удобно, чтобы не держать секрет в файле:

```yaml
backend:
  chat_completion_headers:
    Authorization: "Bearer ${ENV:GC_API_KEY}"   # затем: export GC_API_KEY=sk-...
mcp:
  servers:
    github:
      token: "${ENV:GITHUB_TOKEN}"
```

- Поддерживается несколько плейсхолдеров в одной строке (`"Bearer ${ENV:A}/${ENV:B}"`).
- **Ссылка обязательна.** Незаданная переменная — отказ старта (`gc-cli`, `gc-ua`,
  сервер, native-воркер Temporal) со списком **всех** незаданных переменных сразу и
  местом каждой ссылки: файл + dotted-ключ (`~/.gc/config.yml: voice.token`). Раньше
  подставлялась пустая строка, и ошибка всплывала позже — отказом авторизации у
  бэкенда или сервером без `auth_token`. Значение переменной в сообщения не попадает.
- **Необязательное значение — с умолчанием:** `${ENV:VAR:-умолчание}`. Умолчание
  подставляется, если переменная не задана **или пуста** (как `${VAR:-x}` в shell);
  `${ENV:VAR:-}` — пустое умолчание. Умолчание не может содержать `}`.
- Переменная, заданная пустой строкой, у обязательной ссылки подставляется как есть, без ошибки.
- Аналогично работает `${FILE:/путь/к/файлу}` — подставляет содержимое файла (хвостовые CR/LF срезаются, пробелы и табы — нет); поддерживается `~`. Строгость та же: файла нет, он нечитаем или больше лимита — отказ старта с путём файла и ключом; `${FILE:/путь:-умолчание}` делает его необязательным. Рекомендуется `chmod 600`: на POSIX файл, доступный group/other, даёт отдельный warning (как у ssh).
- **Лимит размера — 64 KiB (65536 байт).** Файл больше лимита считается нечитаемым (см. выше).
- Отказ — только по ссылкам, чьё значение дошло до итогового конфига: если
  верхний слой (проект, профиль) перекрывает ключ своим значением, незаданная
  переменная нижнего слоя ни на что не влияет и загрузку не роняет.
- Строгость касается **загрузки** — старта, `--param`, `config_server.yml`, JSON-конфига
  native-воркера. Проверка перед записью из `/settings` и мастера, витрины и пробы
  соединения TUI остаются мягкими (пустая строка + warning в лог): ссылку на
  переменную, заданную в окружении сервиса, а не текущего терминала, записывать
  законно.
- Относительный путь в `${FILE:}` резолвится **от текущего рабочего каталога процесса**, а не от каталога конфига (в отличие от ключей `paths.*`) — надёжнее указывать абсолютный путь или `~`.
- `${ENV:}` подставляется раньше `${FILE:}`, поэтому `${FILE:${ENV:SECRET_DIR}/token}` работает, а обратная вложенность — нет.
- Подстановка применяется к file-конфигу и к generic CLI-override'ам; в значении **объявленного** флага (например `--trace-id`) placeholder не разворачивается — там значение берётся буквально, раскрывать его должна оболочка.

### Версия формата (`config_version`)

Корневой ключ `config_version` — версия формата **этого файла** (сейчас `1`; нет
ключа — тоже `1`). Ведёт его приложение: шаблон первого запуска уже содержит
`config_version: 1`, править руками не нужно. Версия своя у каждого файла стека
(база, `~/.gc/config.local.yml`, проектный `.gc/config.yml`, профили). Когда формат
сменится, загрузчик сам поднимет старый файл до текущей версии в памяти (файл на
диске не меняется) и скажет об этом стартовым уведомлением. Файл с версией
**новее**, чем понимает установленное приложение, отвергается («конфиг записан более
новой версией приложения»): читать его по старой схеме значит молча потерять
настройки.

Переименования ключей внутри версии 1 по-прежнему обрабатывает compat-слой
(уведомление «… переименован в …, обновите config.yml: gc-cli --sync-config»).

### Проверки сочетаний полей

Однозначные поломки — отказ загрузки с dotted-путём поля:

- пустой или пробельный элемент в `security.write_guard.extra_paths`,
  `security.read_guard.allowed_read_roots`/`allowed_read_paths`/`denied_read_paths`,
  `security.protected_paths.extra` — пустая строка раскрылась бы в текущий каталог
  процесса (в `allowed_read_paths` это снимало все запреты на чтение для него);
- негодное регулярное выражение в `logging.redact_secrets.extra_patterns` (раньше
  шаблон молча пропускался, и секрет уходил в лог).

Бессмысленные, но рабочие сочетания — стартовое уведомление: половина пары
`cert_path`/`key_path` (в `backend`, у записи `models.*.backend` с учётом общего
`backend`, `client-cert`/`client-key` у MCP-сервера), MCP-сервер без `command`
(stdio) или без `url` (http/sse), `chat_completions_min_response_tokens` больше
`chat_completions_max_tokens`, порог компакции конца хода не меньше порога середины
хода, `project_memory.max_append_chars` больше `max_chars`.

### Лишние и недостающие ключи

- **Лишний ключ** (опечатка, устаревшее поле, поле из более новой версии) не
  роняет загрузку: он отбрасывается, а стартовое уведомление называет файл,
  ключ и ближайшее известное имя — «неизвестный ключ «agent.max_stps»
  проигнорирован — возможно, «max_steps»». Так же судит проверка перед записью
  из TUI/мастера. Строгими остаются программные правки (`--param`,
  `override_settings`): там опечатка — ошибка сразу.
- **Нет ключа с умолчанием** — действует умолчание; пустой файл тоже загружается.
- **Нет обязательного поля записи** (у сервера MCP — `transport`, у правила
  `tool_usage_notice` — `tool_name`/`notice_message`, у тарифа — `input`/`output`,
  у пресета — `name`/`url`) — отказ загрузки с путём поля, как и при неверном
  значении. Адрес бэкенда и модель проверяет не схема, а онбординг: TUI
  открывает мастер, CLI печатает инструкцию.

## Проверка и разбор конфига: `config explain | validate | schema`

`gc-cli config …` и `gc-ua config …` — одна и та же команда. Агент, TUI, MCP и сеть
не запускаются: конфиг собирается тем же загрузчиком, что и на старте (слои base →
managed → project → профиль, `${ENV:…}`). Общие параметры — `--config PATH` и
`--profile NAME`, с тем же смыслом, что у основной команды. Коды выхода: `0` — успех,
`1` — конфиг не загружается, `2` — ошибка вызова (неизвестная настройка, флаг).

```bash
gc-cli config explain                    # заданные настройки (не умолчания), по секциям
gc-cli config explain agent.max_steps    # одна настройка; секция (agent) тоже, плоское имя (max_steps) — ошибка с подсказкой пути
gc-cli config explain --all --show-defaults --json
gc-cli config validate                   # ok + notices загрузки, иначе объяснение и код 1
gc-cli config schema --output config.schema.json
```

- **`explain`** печатает значение и **источник**: слой (`base`, `managed`, `project`,
  `profile:<имя>`, `env` для `SWARM_*`), файл и переменную, если значение пришло из
  `${ENV:VAR}` — например `base (/home/u/.config/gc/config.yml) ← ${ENV:GC_API_KEY}`;
  `default` — значение по умолчанию. В шапке — действующий профиль и файлы слоёв.
  Без `KEY` выводятся только заданные настройки, `--all` добавляет умолчания,
  `--show-defaults` показывает умолчание рядом с заданным значением. Опечатка в ключе
  даёт код 2 и близкие варианты; прежнее плоское имя (`max_steps`) — тоже, с подсказкой пути (`agent.max_steps`). Флаги командной строки (`--param`, `--model`, `--level`)
  и правки сессии в выводе не учитываются — показан конфиг уровня файлов и окружения.
- **Секреты** (поля с флагом `secret` в схеме: токены, заголовки, `agent_auth`…)
  всегда заменяются на `***`, в том числе в `--json`; у словаря-секрета (заголовки)
  видны ключи, но не значения. Пустой секрет остаётся видимым — «не задан».
- **`validate`** — `ok: <путь>` и сообщения загрузки (compat, профили), либо то же
  объяснение, что на сломанном старте (что не так, какие файлы участвуют, что сделать).
  `--json` — `{"ok", "config", "profile", "notices", "error"}`.
- **`schema`** — JSON Schema `config.yml` (ключи — как в файле, с алиасами);
  метаданные полей (`secret`, `worker_only`, `expert`, `restart`) — под `x-gc`.
  Вывод стабилен: ключи отсортированы. Можно подключить к редактору, например через
  `# yaml-language-server: $schema=./config.schema.json` в начале `config.yml`.

## Логи: формат, уровень, редакция секретов

- `logging.format` (`text | jsonl`, по умолчанию `text`):
  - `text` — человекочитаемый вывод (историческое поведение);
  - `jsonl` — один JSON-объект на строку (`{"event": ...}`): `agent_start`,
    `backend_request/response`, `dialog_message`, `final_answer`, `run_usage`, `summary_*` и др.
    В jsonl-режиме человекочитаемый рендер в консоль **подавляется** — на stdout идёт только
    event-поток (удобно для парсеров/оркестраторов, напр. Task2PR-врапера).
- `logging.log_level` (`debug | info | warning | error`, по умолчанию `info`) — уровень per-run
  логгера (актуален для jsonl). На `debug` добавляются объёмные события
  `backend_request` / `backend_response` / `agent_tools`.
- `logging.redact_secrets` — маскировка секретов (Bearer/JWT/`sk-`/PEM/AWS/GCP/GitLab/npm/Slack)
  перед записью в лог и stdout → `***REDACTED***`. По умолчанию **выключено** (поведение как раньше):
  - `enabled: true|false`;
  - `extra_keys: []` — доп. подстроки имён чувствительных ключей (к встроенным);
  - `extra_patterns: []` — доп. value-regex (к встроенным).

  Счётчики токенов (`prompt_tokens`, `completion_tokens`, `max_tokens`) не маскируются;
  одиночное слово-ключ `token` / `*_token` — маскируется.

  **Важно — text vs jsonl:** маскировка **по имени ключа** (`extra_keys` и встроенные имена)
  работает только в `format: jsonl` — там редактируется структурный словарь события, и значение
  поля с совпавшим именем целиком становится `***REDACTED***`. В `format: text` редактируется
  финальная строка (словаря нет), поэтому применяются только **value-regex** (`extra_patterns`
  + встроенные Bearer/`sk-`/JWT/PEM/…), а `extra_keys` **не действует**. Для гарантированного
  маскирования в обоих режимах используй `extra_patterns` (по формату значения).
- Картинки в логи не пишутся: в событии `backend_request` (оба режима API) и в логе промпта служебных вызовов
  каждый data-URL заменяется на `data:<mime>;base64,<N bytes>` (N — длина данных base64). Маскировка включена
  всегда и от `logging.redact_secrets` не зависит; в сам запрос картинка уходит полностью.

## Внешний trace_id

`trace_id` связывает один ран агента с шагом воркфлоу внешнего оркестратора.
Значение приходит снаружи; если его не передали — не меняется ничего.

### Как передать

- `gc-cli --trace-id <id>` — обычный запуск.
- поле `trace_id` в теле `POST /events/webhook` — серверный режим. Поле снимается
  из payload до того, как payload уходит в сообщение модели, поэтому в промпт оно
  не попадает.

Значение — не длиннее 200 символов и без управляющих символов (CR, LF, tab).
Невалидное отклоняется до начала работы, по-разному в зависимости от интейка:
`gc-cli` падает на старте (traceback и ненулевой код возврата — так же, как на любой
ошибке валидации конфига), а `POST /events/webhook` и `POST /swarm/run` отвечают
`400` с телом `{"status": "error", "payload": "invalid trace_id: ..."}`, при этом
агент не стартует, а сервер продолжает работать. Пустая или состоящая только
из пробелов строка означает отсутствие trace_id — и тогда не меняется ничего.

Флаг принимается в обоих написаниях — `--trace-id` и `--trace_id`, это один и тот же
параметр. Значение берётся **буквально**: объявленные флаги идут в конфиг напрямую,
минуя и подстановку плейсхолдеров, и коэрсию типов (поэтому трейс `00123` останется
строкой `"00123"`, а не станет числом). Переменную окружения раскрывает шелл —
`--trace-id "$WORKFLOW_ID"`; написанный в значении `${ENV:...}` уйдёт как есть,
литеральной строкой.

### Что происходит при наличии trace_id

| Куда | Что именно |
|---|---|
| Имя лог-файла | `agent_main_<trace>_<run_id>.<ext>` и `summary_trace_main_<trace>_<run_id>.jsonl`. Расширение основного лога следует формату: `.log` при `logging.format: text` и `.jsonl` при `logging.format: jsonl` — то есть в рекомендованном для оркестратора jsonl-режиме глоб `*.log` файл не найдёт. В имя идёт безопасная производная (только `A-Za-z0-9_-`, до 64 символов), `run_id` остаётся. |
| Записи логов | jsonl — поле `trace_id` в каждой записи; text — префикс `[trace=<id>]`. Значение сырое, не производная. |
| Запрос к модели | только при `agent.trace_header_enabled: true` (дефолт — `false`): заголовок `x_trace_id` (переопределяется `agent.trace_id_header_name`) на каждом вызове — главный цикл, суммаризация, finish gate, модерация команд, project memory, intent scope, генерация роли сабагента. Без флага заголовка нет, но в лог-файл и записи трейс попадает как обычно. |
| MCP | только серверам с явным `trace_header_enabled: true` (дефолт — `false`, см. «Ключи конфига»): заголовок `trace_id` (то же переопределение) для транспортов `http`, `sse`, `stream_http`, `stream_sse`; переменная окружения `TRACE_ID` для `stdio` и `stream_stdio`. |
| Мета треда | `runtime.trace_ids` — список всех trace, которые трогали тред, в порядке появления. Пишется только когда у рана есть тред: серверный режим (тред всегда есть) или `gc-cli -t`. Без треда (`gc-cli` без `-t`) значение нигде не сохраняется. |
| Старт рана | событие `trace_binding` — под какими именами этот ран шлёт trace в модель и в MCP. Поля: `trace_id`, `model_header`, `mcp_header`. |

`trace_binding` передаёт свои поля только через `extra=` логгера — их рендерит
`JsonlFormatter`. При `logging.format: text` (дефолт) в строке остаётся имя события и стандартный
текст записи, поля из `extra` в вывод не попадают.

> **Для интеграции с оркестратором:** выставьте `logging.format: jsonl`. Без этого событие в
> стоковой конфигурации не несёт машиночитаемых данных — только имя.

Сабагенты наследуют trace родителя дословно: у ребёнка свой `run_id` и свой файл
лога, но тот же trace — так родитель и дети группируются в один шаг оркестратора.

### Ключи конфига

```yaml
agent:
  # Имя заголовка. Не задано — x_trace_id для модели, trace_id для MCP.
  # Задайте X-Trace-Id, если между агентом и бэкендом стоит nginx: он по
  # умолчанию выбрасывает заголовки с подчёркиванием.
  trace_id_header_name: X-Trace-Id
  # Разрешить отправку trace_id в заголовке к бэкенду модели. Дефолт — false:
  # без этой строки заголовка не будет, даже если trace_id у рана есть.
  trace_header_enabled: true
mcp:
  servers:
    internal_srv:
      transport: http
      url: https://mcp.internal/mcp
      # То же для конкретного MCP-сервера. Дефолт — false: без этой строки
      # сервер не получает ни заголовка, ни переменной окружения.
      trace_header_enabled: true
```

### Оговорки

- Заголовок `x_trace_id` больше **не** содержит внутренний `state_id`. Сам
  `state_id` продолжает уходить как `x-session-id`.
- Per-run trace выигрывает у `backend.chat_completion_headers` с тем же именем.
- Рассылка trace наружу — строго opt-in, и для модели, и для MCP: по умолчанию
  заголовок не уходит никуда. Так внутренний корреляционный id не утекает ни в
  бэкенд модели, ни на сторонние эндпойнты, которые могут оказаться в
  `mcp.servers`. Обратная сторона: забытый `trace_header_enabled: true` означает,
  что trace молча не ушёл — если принимающая сторона его ждёт, флаг нужно
  проставить явно. Проверить, что именно уходит, можно по событию
  `trace_binding` в начале рана.
- Охвачены записи per-run логгера. Модульные логгеры (часть MCP-дискавери,
  транспортные ретраи) идут мимо и trace не несут.
- `gc-cli --init` флаг не читает: это не оркестрируемый ран.
- Swarm-раны трассируются: `POST /swarm/run` принимает `trace_id` тем же полем тела, снимает его из payload и передаёт в песочницу через `SWARM_TRACE_ID`, откуда обёртка добавляет `--trace-id`. Внутри песочницы дальше всё как в обычном ране. Через конфиг трейс передать нельзя — ребёнку материализуется сырой YAML, и неизвестный верхнеуровневый ключ будет отвергнут валидацией.
- При `logging.redact_secrets.enabled` trace, похожий на секрет (`sk-…`, `eyJ…`),
  будет замаскирован в записях логов, но не в имени файла и не в `summary_trace_*.jsonl` —
  этот сток пишется сырым `open()`/`json.dumps`, мимо фильтра и форматтера.
- Второй вебхук по тому же `(system, task_id)` подмешивается в уже идущий ран,
  чьи логи и заголовки зафиксированы: сохраняется первый trace, а про
  проигнорированный пишется событие `trace_id_ignored`.

## Backend TLS / mTLS

- `backend.use_ssl` — `true | false | "/path/ca-bundle.pem"`. Строка трактуется как путь к
  CA-bundle (self-signed / корпоративный CA); `bool` — как раньше (обратно совместимо).
- `backend.cert_path` / `backend.key_path` — клиентский сертификат (mTLS). Заданы **оба** →
  клиент предъявляет `(cert, key)`; ни одного → без клиентского сертификата (дефолт). Пути
  раскрывают `~` и env-переменные. (Опционально; не обязательны для работы бэкенда.)
- `backend.request_timeout_sec` — HTTP-таймаут одного запроса к LLM (секунды), по умолчанию
  `600` (10 минут). Для стрима лимит действует на connect и на паузу между чанками, а не на
  длительность всего ответа. Не путать с `mcp.meta.request_timeout_sec` (таймаут MCP).
- `backend.claude_prompt_cache` — разметка prompt cache в запросах главного цикла; действует только
  в режиме `chat_completions` и только для запросов главного цикла (служебные вызовы — судьи,
  суммаризация — не размечаются). Не задано — автоматически для моделей, в чьём id есть
  `claude`; `true` — включить принудительно (claude под чужим именем за корп-шлюзом); `false` —
  выключить (прокси отвергает разметку). Переопределяется на одну модель через
  `models.<alias>.backend.claude_prompt_cache`. У сообщения с картинками метка хвоста ставится на его последнюю
  текстовую часть.
- `backend.vision` — `false` запрещает пробу и отправку изображений этому маршруту.
  Без значения или при `true` зрение проверяется автоматически перед первым использованием картинки.
  Обычно настройку задают для одной модели: `models.<alias>.backend.vision`.
  `true` разрешает проверку, но не подтверждает зрение. Подробнее — раздел «Изображения».
- `agent.exec_timeout_sec` — дефолтный таймаут `execute_command` / `run_python_code`
  (секунды), если модель не передала `timeout`. По умолчанию `200`. Для длинных
  контейнерных сборок (Harbor) обычно поднимают до `600`.
- `agent.harbor_exec_init` — инициализация окружения перед model-facing
  `execute_command` при `os_backend: harbor`. По умолчанию `null`: команда уходит в
  сырой shell без profile. Значение `bashrc` включает встроенный типовой bootstrap
  (`/etc/profile` и `~/.bashrc` с обходом non-interactive guard). Любая другая
  непустая строка выполняется как custom shell-префикс перед командой. Внутренние
  FS/search/capability/MCP-вызовы всегда используют raw-канал и этот ключ игнорируют.
- `agent.runtime_probe_ttl_sec` — сколько секунд не повторять пробу живости
  Harbor и Remote (`docker` / `ssh` / `exec`) после успешного `echo` суммы.
  По умолчанию `10`. `0` — проба перед каждым действием. Неудачная проба не
  запоминается: следующий вызов проверяет оболочку сразу.
- `agent.exec_output_capture_max_chars` — потолок захвата stdout/stderr на поток
  (decoded UTF-8 chars) для exec. По умолчанию `40000`: первые `floor(L/2)` символов
  головы и последние `L - floor(L/2)` символов настоящего хвоста, середина необратимо
  отбрасывается (процесс не убивается; чтение pipe продолжается, но результат снимается
  после ограниченного ожидания читателей, поэтому у команды, оставившей трубу открытой в
  потомке, хвост — снимок на момент ожидания). Точные `total_chars` и `omitted_chars`
  возвращаются в объектах `stdout` / `stderr` ответа тулы.
- `agent.exec_output_preview_edge_chars` — размер каждого края front-loaded preview
  длинного потока. По умолчанию `3000`: блок `preview` идёт в ответе раньше расширенных
  `stdout` / `stderr`, поэтому первая страница `stored_tool_output` показывает начало и
  настоящий конец обоих потоков. Поток длиной `<= 2P` в preview не дублируется. `0`
  отключает preview. Значение не должно превышать хвост capture
  (`exec_output_capture_max_chars - floor(exec_output_capture_max_chars / 2)`).
- `agent.walk_output_max_chars` — общий потолок внутренних exec-каналов бэкенда
  (decoded chars), не model-facing вывода: обход дерева в Harbor (`find -printf` для
  walk/listdir), нативный grep и MCP-carrier под `execute_on: os_backend` (http и
  stdio). По умолчанию `50000000`. Переполнение везде fail-closed: обход завершается
  ошибкой `walk_too_large` с советом сузить путь, MCP-вызов — `McpExecCarrierError`
  («response truncated by the exec output cap»). Понижение ради листингов молча
  уронит большие ответы MCP-серверов.

## Слои инструкций (AGENTS.md)

Системные инструкции агента формируются из нескольких файлов, мерджимых в порядке broad→narrow
(каждый следующий слой уточняет/перекрывает предыдущий):

| Слой | Файл | Описание |
|------|------|----------|
| L0 (shipped) | `paths.agent_md_path` | Базовые инструкции из пакета (или кастомный путь) |
| L1 (global) | `~/.gc/AGENTS.md` (Linux/macOS: `~/.config/gc/AGENTS.md`) | Глобальные инструкции пользователя |
| L2 (project) | `<cwd>/AGENTS.md` | Инструкции проекта |
| L3 (project) | `<cwd>/.gc/AGENTS.md` | Уточнения для конкретного проекта |

- `paths.agent_md_path` (по умолчанию — shipped `prompts/demo_cli_agent.md`) задаёт L0.
  Укажите свой файл, если хотите заменить базовые инструкции.
- `tui.agentsmd_override` (`false` по умолчанию) — только TUI; при `true` оставить лишь
  корневой `AGENTS.md` (L3), отбросив глобальный (L1) и `.gc/AGENTS.md` слои.
  Игнорируется, если задан `paths.agent_md_path` (путь главнее флага).
  Из CLI: `--agentsmd-override`.
- Файл `AGENTS.md` генерируется командой `gc-cli --init` (агент сканирует репозиторий и
  создаёт/обновляет `AGENTS.md` через `write_to_file`).

## Security policy

Клиент поддерживает несколько независимых слоёв безопасности для файловых изменений,
чтения файлов, запуска команд/кода и сетевых запросов. Все слои включены по умолчанию
с режимом `ask` (secure-by-default), **кроме `protected_paths`** — он включён с режимом
deny (floor-защита: служебные пути — отказ без подтверждения; файлы инструкций, `.git`, скиллы и настройки инструментов — вопрос).

```yaml
security:
  command_moderation:
    enabled: true        # on/ask по дефолту
    mode: ask            # allow | ask | deny
    allowed_command_examples: []
  write_guard:
    enabled: true        # on/ask по дефолту
    mode: ask            # allow | ask | deny
    extra_paths: []
  read_guard:
    enabled: true        # on/ask по дефолту
    mode: ask            # allow | ask | deny
  url_policy:
    enabled: true        # on/ask по дефолту
    mode: ask            # allow | ask | deny
    allowed_schemes: ["http", "https"]
    url_blacklist: []
  protected_paths:
    enabled: true        # false снимает пол защищённых путей целиком
    extra: []
```

**Контракт режимов:**

- `ask` (дефолт) — при нарушении периметра (out-of-perimeter операция):
  - **TUI** — показывает confirm-баннер; пользователь подтверждает или отменяет.
  - **Headless** (CLI/server/swarm без интерактивного confirmer) — fail-closed **deny**
    с инструктивным сообщением агенту: операция заблокирована, нужно выбрать другой путь.
  - In-perimeter операции (запись/чтение внутри `launch_root`) проходят молча в любом режиме.
- `deny` — всегда блокировать, без запроса подтверждения.
- `allow` — всегда пропускать, записать в audit log как `out_of_perimeter`.

**Escape-hatch:** `mode: allow` или `enabled: false` — отключают enforcement для конкретного слоя.

### `security.permissions` (режимы разрешений)

Режим разрешений — одна ручка поверх слоёв выше: он решает, что агент делает сам,
а о чём сначала спрашивает.

```yaml
security:
  permissions:
    default_mode: edit        # edit | manual | plan | auto
    readonly_commands: []     # дополнение списка команд без проверки
```

| Действие | `edit` (по умолчанию) | `manual` | `plan` | `auto` |
|---|---|---|---|---|
| Запись в проекте | без вопроса | вопрос | запрет | без вопроса |
| Запись вне проекта | решает `write_guard` (по умолчанию вопрос) | вопрос | запрет | судья действий |
| Чтение в проекте | без вопроса | без вопроса | без вопроса | без вопроса |
| Чтение вне проекта | решает `read_guard` | вопрос | вопрос | судья действий |
| Команда из списка только-чтения | без проверки | без проверки | без проверки | без проверки |
| Остальные команды и код | судья команд (`command_moderation`) | вопрос, судья не вызывается | запрет | судья действий |
| MCP-инструменты, скрипты скиллов | без вопроса | вопрос | запрет | судья действий |
| Запуск субагента | без вопроса | без вопроса | без вопроса | судья действий |
| Сетевой запрос (`exec_fetch_url`, `download_file`) | без вопроса | вопрос | без вопроса | судья действий |
| Адрес из `url_blacklist` | решает `url_policy` (по умолчанию вопрос) | вопрос | вопрос | судья действий |
| Запись в защищённые пути: `AGENTS.md` (проектный, `.gc/`, глобальный), каталоги `.git`, скиллы, настройки инструментов | вопрос | вопрос | запрет | судья действий |
| Память проекта (`project_memory`): запись | без вопроса | вопрос | запрет | без вопроса |

`edit` не проверяет MCP-инструменты, скрипты скиллов и сетевые запросы на обычные адреса:
это поведение агента до появления режимов. Для работы с внешними сервисами строже
`manual` и `auto`.

**Режим `plan`.** Агент исследует задачу и ничего не меняет, а готовый план предлагает
инструментом `turn_propose_plan` — он есть только в этом режиме. План показывается в
ленте, под ним — выбор: исполнить в `edit`, автономно в `auto`, с подтверждениями в
`manual` или доработать план. После одобрения режим меняется и агент сам продолжает исполнение.
План лежит и отдельным файлом для человека — `plans/plan_<system>_<сессия>.md` в каталоге сессий
(`paths.threads_data_path`): один файл на сессию, новый план пишется поверх прежнего, удаляется
вместе с сессией. Программа его не читает, агент к нему не обращается.
Запреты `plan` — жёсткие: их не снимает ни данное раньше «разрешить в этой сессии», ни
явный `security.write_guard.mode: allow`. Память проекта (`project_memory`) в `plan`
только читается: она переживает сессию, и запись в неё — изменение. План хранится в сессии
и переживает сжатие истории. Субагенты наследуют запреты, но план не предлагают — они
возвращают выводы родителю: в `plan` у субагента нет инструмента плана, и ему сообщают
«исследуй и верни находки текстом».

`edit` ведёт себя так же, как агент без режимов, с одним отличием: команды из списка
только-чтения исполняются без судьи.

**Режим `manual` и сеть.** Перед сетевым запросом агент спрашивает. Ответ «в этой
сессии» запоминается для сайта целиком, а не для точного адреса, и действует во всех
режимах, включая `auto`. Вопрос про адрес из `url_blacklist` — отдельный: он
запоминается только для точного адреса, и разрешение сайта его не покрывает.

**Переход на другой хост.** В `manual` и `auto` разрешённый или одобренный судьёй
адрес не уводит на другой хост: запрос с таким редиректом не выполняется, агент
получает адрес перехода и запрашивает его отдельно — новый запрос проходит новый
вопрос (в `manual`) или судью (в `auto`). Переходы в пределах того же хоста (`http` на
`https`, другой путь, другой порт) идут как раньше. Хосты сравниваются точно:
`example.com` и `www.example.com` — разные, и переход с одного на другой — отдельный
запрос. Так что скачивание релиза, которое перенаправляет на хост хранилища, в `manual`
задаёт второй вопрос. В `edit` и `plan` редиректы ведут себя как раньше; правило
действует для `exec_fetch_url` (и его упрощённого варианта) и `download_file`.

**Режим `auto`.** Автономная работа: вопросов подтверждения нет. Там, где другие режимы
спросили бы человека, действие перед выполнением проверяет **судья действий** —
отдельный запрос к вспомогательной модели (слот `assign.command_judge`, тот же, что у
судьи команд; без привязки — уровень `default`, если слот `default` задан, иначе активный
уровень, в том числе выбранный автовыбором, — см. [«Реестр»](#реестр-models-slots-assign)). Чтение,
правки в проекте и команды из списка только-чтения идут без проверки. Чтение файла из чёрного
списка чтения (`.env`, ключи, `~/.ssh`) судья проверяет строго: только если вы прямо просили
именно этот файл.

Судья отвечает на один вопрос: опасно ли действие и разрешал ли его пользователь. По
умолчанию действие разрешено. Отказ — если оно рискованно (удаление невосстановимого,
отправка данных наружу, общие и боевые системы, ослабление защиты, правка `AGENTS.md`),
а вы о нём не просили, либо если оно нарушает границу, которую вы назвали («не пушь»,
«без новых зависимостей»). Пуш, о котором не просили, — отказ; просьба открыть или
обновить PR покрывает пуш этой ветки. Запрещённые в конфиге команды
(`denied_command_examples`) и пути блокируются, даже если вы о них просили. Запрос к
сервису метаданных облака (`169.254.169.254` и подобные) без вашей просьбы — отказ;
локальные и частные адреса из `url_blacklist` судья проверяет как обычный запрос.

Судья видит ваши сообщения и ответы на вопросы агента, утверждённый план, то, что
агент говорил вам, и его прежние действия с аргументами. Вывод инструментов —
содержимое прочитанных файлов и страниц — он не видит: подложенная туда инструкция до
него не доходит. Разрешить рискованное могут только ваши слова; текст агента, задание
субагенту и содержимое файлов — нет.

Длинные тексты судья видит не целиком: длинное сообщение, прежнее действие или проверяемый
скрипт режутся по середине — начало и конец остаются, середина нет. Слова, ушедшие в
сводку при сжатии истории, судья знает только по журналу намерений (он переживает сжатие).
Служебное сообщение (например, вставленная в чат ошибка проверки
аргументов инструмента или блок текущего контекста) судье не показывается, но
распознаётся оно **по началу текста**: если ваше сообщение начинается со вставленной
служебной разметки, оно по-прежнему считается служебным и скрыто; вставка в середине
или в конце слов человека не прячет.

**Сервер, swarm и A2A.** Там слова «пользователя» приходят от внешней системы (JSON
вебхука или задачи swarm, сообщение пира-агента), и судья считает их не волей человека, а **запросом внешней
системы**: описание задачи и запреты из него учитываются, а разрешением на рискованное
или на выход за пределы задачи оно не служит. Признак действует на весь прогон —
сообщения, ответы на вопросы агента, слова из журнала намерений после сжатия и слова,
переданные судье субагента. В CLI и TUI запрос и правила судьи остаются прежними. `auto`
на сервере поэтому подходит для доверенных источников вебхуков.

При отказе агент получает причину и не повторяет действие: идёт более безопасным
путём или делает остальную часть задачи и сообщает вам. Ответьте, что действие нужно, —
судья увидит это как ваше разрешение.

- **Три отказа подряд или двадцать за сессию.** Проверка встаёт на паузу: следующие
  спорные действия агент спрашивает у вас обычным вопросом, пока вы не разрешите одно, —
  тогда auto работает дальше. Счёт общий для сессии и её субагентов и сохраняется в
  треде; при параллельных субагентах счёт приблизителен, признак паузы — точен. Без
  человека (см. список ниже) спорные действия на паузе отклоняются без вызова судьи;
  агент делает остальное и сообщает, что осталось. Паузу снимает и **ваше следующее
  сообщение** — судья снова проверяет; это верно во всех каналах, в том числе когда
  вопрос паузы остался без ответа.
  Ограничение: сообщение, отданное работающему субагенту в его очередь, паузу не
  снимает до следующего прогона корня.
- **Проверка не сработала** (сбой запроса, негодный ответ модели, несколько JSON-блоков
  вместо одного). Действие не выполняется; о самом действии это ничего не говорит,
  агент может повторить вызов. У судьи свой бюджет запроса: повторы клиента выключены,
  есть один собственный повтор, запрос ждёт не больше 60 секунд (настроенный таймаут
  короче — действует он); до остановки хода уходит не больше 20 запросов. Сбой судьи не
  выключает основную модель: она остаётся доступной для следующих ходов.
- **Десять сбоев подряд** либо **нет канала вспомогательной модели**. Ход
  останавливается: «проверка действий недоступна». Повторите позже или смените режим.

Явные настройки сильнее судьи: `mode: deny` у защиты — отказ, `mode: allow` — действие
идёт без проверки. Исключение — `command_moderation: allow`: в `auto` оно судью действий
не снимает, команды вне списка только-чтения он проверяет всегда; `deny` у команд остаётся
отказом. Значение `ask` из поставки в `auto` означает «решает судья». Выключенная защита
(`enabled: false`) судью не отменяет. Запрет и разрешение, данные вами «в этой сессии»,
сильнее судьи.

`auto` убирает вопросы, но безопасность не гарантирует:

- качество проверки зависит от модели судьи. Быстрая модель без скрытого рассуждения
  отвечает за 1–2 секунды; модель с рассуждением точнее на редких пограничных случаях,
  но ждать её в несколько раз дольше. Одна проверка — около 2 тысяч токенов и больше на
  длинной сессии;
- то, что агент читает, до него никто не проверяет: подложенная инструкция может
  заставить его сделать вредную правку внутри проекта, а правки в проекте судья не
  проверяет;
- после сжатия истории судья не видит прежних действий агента (ваши сообщения
  сохраняются в журнале намерений, но выдержками);
- середина длинного скрипта или длинного сообщения судье не видна (см. выше), как и
  содержимое запускаемого файла проекта, которого агент в этой сессии не записывал;
- отчёт субагента не проверяется; запуск субагента и его действия — проверяются.

Каждое решение судьи пишется в журнал аудита (`security_policy_decision`): исход,
причина словами судьи (`reason`) и идентификатор вызова (`call_id`). По этим записям
разбирают ложные отказы и пропуски.

**Команды только-чтения.** `ls`, `dir`, `pwd`, `stat`, `du`, `df`, `wc`, `which`, `where`,
`whoami`, `echo`; `git status` и `git rev-parse`; `git branch` и `git remote` — только без
аргументов. Команда с любым метасимволом оболочки (`;`, `|`, `&`, `>`, `<`, `$` и другие
подстановки) или с переменными окружения в вызове в список не попадает и идёт обычным
путём. git с явным каталогом исполнения (`cwd`) — тоже: он исполнит конфиг и хуки того
репозитория. Сам `.git` — защищённый путь (см. `protected_paths`), поэтому подложить
команду в его конфиг файловым тулом молча нельзя.

Встроенные `wc`, `du` и `git status` признаются безобидными **только с перечисленными
флагами** (белый список), а не «с любыми, кроме запрещённых»: `wc` — `-l -w -c -m -L` и
полные `--lines --words --bytes --chars --max-line-length`; `du` — `-s -h -a -c -k -m -b -x`,
`-d N`, полные `--summarize --human-readable --all --total --apparent-size
--one-file-system --max-depth=N`; `git status` — флаги вывода состояния (`-s`, `-b`, `-z`,
`-u`, `--porcelain`, `--ignored` и подобные). Любой другой флаг, в том числе сокращение
длинного (`wc --files0=файл`, `du -sX файл`: они печатают строки файла в тексте ошибки),
делает команду «не безобидной», и она идёт путём режима. Пути как аргументы разрешены;
после `--` всё считается аргументами. `cat`, `grep`, `git diff` и `git log` в списке
нет намеренно: они читают содержимое файлов, в том числе секреты, а `git diff --output` и
подобные флаги ещё и пишут.

Свои команды добавляет `readonly_commands` — слово или пара «команда подкоманда»:
запись `tree` признаёт команду с любыми аргументами, запись `git log` — подкоманду
`git log` с любыми аргументами (это ваш выбор, флаги не проверяются). Слишком широкие
записи конфиг не принимает и при загрузке сообщает, что поправить: однословная команда
с подкомандами (`git` — это и `git push`; укажите `git log`) или с подкомандой запуска
кода (`uv`, `npm`, `pnpm`, `yarn`, `docker`, `cargo`, `poetry` и другие — одним словом это и
`uv run …`; укажите, например, `npm ls`), оболочка или
интерпретатор первым словом в любой записи (`sh`, `bash`, `python`, `node`, `env` и
другие — с ними исполняется любой код, в том числе `bash -c`), запускатель другой команды
(`sudo`, `xargs`, `npx`, `timeout`, `nohup`, `stdbuf`, `busybox`, `ssh` и другие), пара, у
которой второе слово флаг (`git -c`) или подкоманда, исполняющая произвольный код
(`uv run`, `npm exec`, `pnpm dlx`, `docker exec`), запись из трёх слов и больше (укажите команду или пару «команда
подкоманда»). Имя сравнивается без пути, `.exe`, регистра и хвоста версии или варианта
сборки: `/usr/bin/python3.12`, `python3.13t`, `python3.12-dbg`, `Python.exe` — тоже `python`;
`python3-config` и `php8.2-fpm` — нет. Списки интерпретаторов, запускателей и команд с
подкомандой запуска неполны: запись в `readonly_commands` остаётся вашим решением. Команды
с подкомандами, которых нет в этих списках, однословной записью открываются целиком —
указывайте подкоманду. Пара, которая запускает скрипты проекта (`npm test`, `yarn build`,
`cargo build`, `make`), исполняет код, который агент мог перед этим изменить, — добавляйте
её, только если вас это устраивает.

`readonly_commands` берётся только из вашего `config.yml`, managed-слоя и профилей рядом с
ним. В конфиге проекта (`<cwd>/.gc/config.yml`) и в профилях из `<cwd>/.gc/profiles` ключ не
действует, при загрузке об этом выводится уведомление: списки проекта склеиваются с вашими,
и чужой репозиторий иначе сам дописал бы себе, например, `make` — произвольный код
Makefile без вопроса в plan и manual.

**Что сильнее режима.**

1. Защищённые пути (`protected_paths`) — в любом режиме, пока не выключены ключом
   `enabled: false`. Исключение: в `auto` запись в `AGENTS.md`, `.git`, скиллы и
   настройки инструментов решает судья, а не вопрос; служебные каталоги агента закрыты
   всегда (при включённой защите).
2. Ответы, запомненные в сессии. Запрет «до конца сессии» действует и после
   переключения режима: то же действие будет отклонено без вопроса.
3. Явно заданный `security.write_guard.mode` / `security.read_guard.mode` — для
   действий вне проекта: `deny` — отказ в любом режиме; `allow` снимает проверку судьёй
   в `auto`, но не вопрос `manual` — его вы выбрали в сессии сознательно.

**Ответы на вопрос подтверждения.** «Разрешить / запретить разово» действует на один
вызов инструмента: следующий такой же вызов спросит снова. «Разрешить / запретить в
этой сессии» запоминается для этого действия (файла, команды, инструмента) до конца
сессии и сохраняется вместе с ней. Запрет в сессии сильнее режима: он действует и после
смены режима, а снимает его только новая сессия. Поэтому `Esc` на вопросе в TUI, а в
консоли `Enter`, конец ввода и любой непонятный ответ — «запретить разово»; запрет в
сессии выбирают явно, клавишей `N`.

В `edit` ответ на вопрос о команде ещё и подсказка судье команд — поэтому вариант
звучит «команду и подобные»: похожую команду судья пропустит сам. В `manual` и `auto`
судьи команд нет, и вариант звучит «эту команду»: запоминается ровно она.

Для команды «то же действие» — тот же текст, тот же проект и то же окружение. Вопрос
показывает, кроме команды, каталог исполнения, имена переменных окружения и пометку
о фоновом запуске (процесс продолжит работать после ответа агента). Запуск в
подкаталоге проекта или в фоне — та же команда: разрешение на неё действует. В
каталоге вне проекта или с другими переменными окружения — новое действие, вопрос
будет задан снова. Значения переменных в запомненный ответ не попадают — только их
отпечаток.

**Откуда берётся режим**, от сильного к слабому: флаг запуска `--permission-mode`;
выбор, сохранённый в сессии (в TUI — `Shift+Tab`, в ACP — выбор режима в IDE); `default_mode`
из конфига; встроенный `edit`. Режим — выбор **сессии**: он сохраняется в её метаданных и
действует при следующем открытии, а флаг запуска перебивает сохранённый. Сессия без
сохранённого режима открывается в `default_mode` из конфига, а не в режиме окна, из
которого её открыли (новая сессия окна режим окна наследует). В TUI `default_mode`
правится и в Настройках → «Режимы работы», строка `mode`.

**Без человека** спросить некого, и вопрос становится отказом «спросить некого»: в
`manual` запись, команды вне списка только-чтения и сетевые запросы запрещены, а запись в
каталог `.git`, скиллы и настройки инструментов — отказ и в `edit`. Это `gc-cli` без
терминала (и бенчмарк), сервер `gc-serve`, A2A, `gc-chat` (у HTTP-процесса терминала
нет), swarm и воркер Temporal без канала ответа человека. Канал объявляет это о себе сам:
сервер, swarm (обёртка запускает `gc-cli --external-request`) и A2A — «человека нет», ACP —
«человек есть» (вопросы уходят в IDE), TUI и `gc-cli` без этого флага не объявляют, и ядро проверяет порт ответа, TUI или терминал при включённом
`turn_ask_human`. Если человек есть, но ответа не пришло (таймаут, отмена, клиент не умеет
отвечать), модель слышит «не ответил вовремя», а не «отказал». Поэтому встроенный режим —
`edit`. `auto` без человека работает: судья зовётся как обычно, предохранитель «три
отказа» вопросов не задаёт.

### `security.write_guard` (файловый периметр)

- `enabled` (по умолчанию `true`) — при `false` периметр выключен, запись в любой путь разрешена.
- `extra_paths` — дополнительные директории, куда разрешена запись помимо `launch_root`.
  Относительные пути разрешаются от директории `config.yml`.
- `mode` (`allow | ask | deny`, по умолчанию `ask`) — реакция на нарушение периметра.

Включить/выключить из CLI: `--write-guard true|false` или `--no-write-guard`.

### `security.command_moderation` (LLM judge для команд)

- `enabled` (по умолчанию `true`) — при `false` judge не вызывается, все команды проходят.
- `mode` (`allow | ask | deny`, по умолчанию `ask`) — управляет только `execute_command` и `run_python_code`:
  - `allow` — выполнять без judge (эквивалент `enabled: false`); в режиме разрешений `auto` не снимает судью действий — команды вне списка только-чтения он проверяет всегда;
  - `ask` — опасные команды: TUI → confirm-баннер; headless → fail-closed deny с сообщением;
  - `deny` — опасные команды блокировать без запроса.
- `allowed_command_examples` — positive examples для LLM judge; не строгий allowlist,
  а ориентир безопасного профиля команд проекта.
- `denied_command_examples` — negative examples (операторный deny-list). Явное совпадение
  (или тривиальная вариация: флаги/пути/кавычки/пробелы) → verdict `potentially_dangerous`
  + risk-флаг `operator_denied`, даже если команда сама по себе выглядит безобидно.
  Операторный интент главнее собственной оценки судьи. Работает при `mode: ask|deny`.
- **Трейдофф:** LLM-судья вызывается на каждую команду — добавляет задержку. При недоступности
  судьи: `deny` → fail-CLOSED; `ask` → headless deny, TUI → confirm-баннер.
  Отключить: `enabled: false`.

Переключить режим из CLI: `--command-moderation allow|ask|deny`.

### `security.read_guard` (периметр на чтение)

- `enabled` (по умолчанию `true`) — при `false` чтение файлов не ограничивается.
- `mode` (`allow | ask | deny`, по умолчанию `ask`) — реакция на нарушение.
- Дополнительные поля: `allowed_read_roots`, `allowed_read_paths`, `denied_read_paths`,
  `denied_file_patterns`, `denied_extensions`.

Включить/выключить из CLI: `--read-guard true|false` или `--no-read-guard`.
Режим: `--read-guard-mode allow|ask|deny`.

### `security.url_policy` (URL-политика)

- `enabled` (по умолчанию `true`) — при `false` проверки URL не выполняются.
- `mode` (`allow | ask | deny`, по умолчанию `ask`) — реакция на нарушение.
- `allowed_schemes` и `url_blacklist` проверяются для исходного URL
  в `fetch_url`/`simple_fetch_url` до сетевого запроса. Redirect targets повторно не проверяются.

### `security.protected_paths` (floor-защита)

Floor-защита операционного каталога `.gc` и системных путей gc от записи и чтения
действует, даже когда остальные guard'ы выключены; снять её целиком можно только ключом
`enabled: false` (см. ниже). Детерминированный tripwire: команды вроде `rm -rf .gc`
блокируются до запуска subprocess, без обращения к LLM-судье.

- `enabled` — `false` снимает пол защищённых путей целиком, вместе со списком `extra`:
  вопрос и запрет защищённых путей (инструкции, `.git`, скиллы, настройки инструментов,
  служебные каталоги), отказ служебных каталогов и отсечение команд вроде `rm -rf .gc`.
  Запреты и вопросы режимов разрешений остаются. По умолчанию `true`; `false` ставят
  конфиги бенчмарка.
- `extra` — дополнительные пути, которые агенту трогать нельзя: команда
  (`execute_command`, `run_python_code`), упоминающая такой путь, запрещается
  (`~` раскрывается). Не путать с `security.write_guard.extra_paths` — это,
  наоборот, каталоги, куда писать МОЖНО; команды с ними идут обычной модерацией
  (`command_moderation`).
- Каталоги `.git` — в корне проекта и во вложенных репозиториях (отдельного ключа нет):
  там конфиг и хуки, которые git исполняет сам (`core.fsmonitor` при `git status`, хуки
  при `git commit`). Как файлы инструкций: чтение свободно, запись файловыми тулами
  спрашивает подтверждение «Защищённый путь», в `auto` её проверяет судья действий, в `plan`
  запись запрещена режимом. Команды, где встречается такой путь (`grep --exclude-dir .git`),
  пол не трогает: в `edit` судья команд видит `.git` проекта среди неприкосновенных путей и
  о записи в него спросит, в `manual` спрашивается любая такая команда, в `auto` её
  проверяет судья действий. Служебные пути с `.git` внутри (`.gc/.git`, `extra`) остаются
  запретом. Без человека (сервер, A2A, запуски без терминала, бенчмарк) запись в `.git`
  — отказ.
- Скиллы — проектные (`.gc/skills`) и глобальные (в каталоге данных gc). Запись в них
  файловыми тулами спрашивает в `edit` и `manual` (ответ «в этой сессии» снимает
  повторы), в `auto` её проверяет судья действий (пропустит, только если вы просили), в
  `plan` она запрещена, без человека — отказ. Чтение скиллов и запуск их скриптов не
  меняются и идут без вопроса.
- Настройки инструментов — файлы и каталоги, которые потом исполняет или читает другая
  программа мимо агента: конфигурация git (`.gitconfig`, `.gitmodules`, `.config/git`),
  профили оболочки (`.bashrc`, `.zshrc`, `.profile`, `.envrc` и соседние), менеджеры
  пакетов и сборки (`.npmrc`, `.yarnrc`, `.cargo`, `.mvn`, `.bazelrc`, `bunfig.toml` и
  другие), хуки и проверки (`.husky`, `.pre-commit-config.yaml`, `lefthook.yml`), редакторы
  и окружения (`.vscode`, `.idea`, `.devcontainer`), настройки других агентов (`.claude`,
  `.claude.json`, `.mcp.json`, `.codex`). Исходы те же, что у скиллов: запись спрашивает в
  `edit` и `manual`, в `auto` решает судья, в `plan` запрещена, без человека — отказ.
  Сравнение — по имени: каталог по частям пути, файл по имени. Внутри проекта смотрятся
  только части пути **ниже его корня** (корень проекта сам может лежать в каталоге из
  списка — рабочая копия другого инструмента), вне проекта — все части (`~/.bashrc`,
  `~/.cargo/config.toml`). Регистр различается по правилу файловой системы. Явное
  `allow` у защиты этот пол не снимает. **Ограничения:** список неполон по природе — все
  инструменты не предусмотреть; запись в эти файлы командой оболочки этим классом не
  ловится (в `edit` команду видит судья команд, в `auto` — судья действий), а чтение и
  `cat .envrc` идут без вопроса.
- Символические ссылки не разворачиваются ни в одной проверке путей — как класс (ссылка
  внутри проекта на файл снаружи проходит как внутренний путь). Это известное
  ограничение, закрывается отдельным изменением.
- Класс `media` (отдельного ключа нет) — файлы, которые агент получает сам: копии вложенных
  изображений (`<threads_data_path>/images/`; если каталог тредов не задан —
  `<системный temp>/gc-images-<uid или имя пользователя>/`), собственный карман процесса
  `…/images/_staging/<pid>/` и
  картинки/аудио из ответов MCP-тулов (`<gc_cache>/mcp-media/`, не настраивается).
  - Чтение — без вопроса: пол их пропускает, периметр `read_guard` разрешает, как каталог
    скиллов (`denied_*` и `allowed_read_roots` на них не действуют).
  - Запись файловыми тулами — отказ `protected_path_denied`.
  - Команда оболочки, где встречается такой путь (скопировать вставленный скриншот в проект,
    удалить картинку), — подтверждение «Защищённый путь»; без интерактивного подтверждения
    (CLI без терминала, сервер) — отказ. После подтверждения команда, как обычно, идёт к
    LLM-судье (`command_moderation`).
  - Карманы других процессов (`_staging/<другой pid>`) в класс не входят: при каталоге тредов
    по умолчанию (под `<gc_state>`) они остаются операционными. Через класс агент может читать
    картинки других тредов того же проекта.

### Основные policy-ошибки

- `write_guard_violation` — файловое изменение вне разрешённых roots (write_guard);
- `unsafe_command_blocked` — опасная команда/код заблокированы в `deny`;
- `unsafe_command_cancelled_by_user` — пользователь не подтвердил опасное действие в `ask`;
- `url_validation_failed` — URL не прошёл схему/формат;
- `url_blocked_by_policy` — URL совпал с blacklist.

Все policy-решения пишутся в run logger как `security_policy_decision` без полного payload команды/кода.

## Профили и уровни моделей

Агент умеет работать не с одной моделью, а с **реестром именованных моделей** и тремя
**уровнями** сложности задачи. Уровень выбираете вы (ключ конфига, флаг CLI или
переключатель в TUI), а какая модель за ним стоит — решает конфиг:

- **light** — быстрая и дешёвая: простые задачи;
- **default** — основная рабочая: повседневные задачи;
- **max** — самая сильная: сложные задачи.

Есть и четвёртое значение — **`auto`**: уровень выбирает сам агент перед каждым
вызовом. По умолчанию — политикой двух уровней: всё, что меняет файлы и память
или закрывает ход, исполняет сильная модель пары, наблюдение — слабая; ход начинается
с сильной. Подробности, что видно в футере и палитре, и как устроен алгоритм —
[«Автовыбор уровня модели»](auto-routing.md).

Ничего из этого не обязательно. Пока секция `models` пуста (или её нет), агент работает
в **легаси-режиме** — модель берётся из `agent.model`, адрес из
`backend.completions_url`, как раньше.

### Реестр: `models`, `slots`, `assign`

Три секции. Они допустимы и в `config.yml`, и в файле профиля, и на любом слое конфига —
мержатся вместе, а ссылки между ними проверяются уже по итоговому (смерженному) результату.

```yaml
models:                                  # реестр: алиас → провайдерская модель
  glm-local:
    url: http://127.0.0.1:8014/v1/chat/completions
  flash:
    model: qwen/qwen-2.5-flash           # провайдерский id
    url: https://openrouter.ai/api/v1/chat/completions
    token: "${ENV:OPENROUTER_API_KEY}"
    main:                                # kwargs диалога и субагентов
      temperature: 1.0
      top_p: 1.0
      tool_choice: auto
      chat_template_kwargs:
        enable_thinking: true
    auxiliary:                           # summary, судьи, finish_gate, intent_scope
      temperature: 1.0
      top_p: 1.0
      chat_template_kwargs:
        enable_thinking: false

# В models.<alias>.backend нет api_mode, stream, send_tool_strict и
# openai_strict_tools_schema: они действуют на весь бэкенд и задаются в общей
# секции backend (на модели ключ проигнорируется с уведомлением).

slots:                                   # уровни — указатели на алиасы, не копии
  light: flash
  default: glm-local
  max: flash

assign:                                  # привязки отдельных потребителей
  command_judge: default                 # явная привязка; без неё тоже default
  finish_gate: max                       # явная привязка: финал судит max (уровень ИЛИ алиас); без неё — default
  summary: default                       # явная привязка; без неё тоже default
  subagents:
    subagent_critic: max
    "*": default                         # все остальные субагенты
```

Цены задаются в `pricing.models` по имени модели провайдера (`model` записи реестра)
или общим тарифом `pricing.input/output`. Поле `models.<алиас>.pricing` в расчёт пока
не попадает: учёт ведётся по модели провайдера, а не по алиасу. Если ставки заданы,
но для части расхода цены нет, стоимость отмечается «?»; если ставок нет совсем,
стоимость скрыта. При старте, когда цены есть лишь у части моделей, показывается
уведомление со списком моделей без ставки. Подробнее — [usage_pricing.md](usage_pricing.md).

**`models`** — ключ словаря это **алиас**, ваш собственный язык для `slots` и `assign`,
а не провайдерский id. Правила записи одной модели:

- `model` не задан → провайдерским id становится сам алиас (удобно для локальных сборок);
- **адрес и токен — пара**: модель работает либо через общее подключение, либо через своё.
  Не заданы оба → оба наследуются из эффективной секции `backend`. Задан один без второго →
  **ошибка валидации**: свой адрес без токена унёс бы общий ключ на чужой хост, а свой токен
  без адреса уехал бы вслед за сменой общего адреса. Правило действует и внутри одного файла,
  и по слоям — слой (проектный `config.yml`, профиль), перекрывший у записи только адрес,
  отвергается с путём своего файла;
- «свой адрес» — это `url` или `backend.completions_url`. «Свой
  токен» — `token` или `backend.chat_completion_headers.Authorization`.
  `backend.proxy` в пару не входит: это строка транспорта эндпоинта, она
  применяется и без своего адреса или токена;
- `backend.use_ssl` / `backend.cert_path` / `backend.key_path` в пару **не входят** — адрес
  они не меняют, и своего токена не требуют. Но у записи, работающей через общее подключение,
  они ослабляют защиту запроса, который уходит с **общим токеном**, — про это при старте
  выводится предупреждение (предупреждение, не ошибка: сетап с самоподписанным сертификатом
  законен);
- `token: ""` — «сервер не требует авторизации»; это **заданный** токен, пара с ним полна
  (штатная форма локального сервера). Непустое значение уходит как задано; если сервер
  ответил 401, следующая попытка — другая форма (`Bearer <token>` или голый ключ), и
  принятую форму рабочие запросы шлют первой, пока она не получит 401;
- «тот же провайдер, другой ключ» — законный случай: повторите тот же адрес явно и добавьте
  свой `token`;
- имена `light`, `default`, `max`, `auto` зарезервированы и алиасом быть не могут;
- одно и то же нельзя задать дважды: `token` вместе с
  `backend.chat_completion_headers.Authorization`, а `url` вместе с
  `backend.completions_url` — ошибка валидации;
- `main` и `auxiliary` читаются одинаково и друг в друга не подставляются.
  Агент поставляется без предзаданных vendor-схем: в шаблоне первого запуска
  `backend.chat_completion_kwargs` и
  `chat_completions.auxiliary_llm.completion_kwargs` равны `null`. Дефолт любого
  запроса — серверные дефолты модели. Сэмплинг и диалекты thinking собираются
  в профиле, per-алиас (рабочий референс — `demo_profile.yml`).

**Диалекты thinking.** Словарь `main` / `auxiliary` уходит в тело запроса
**как есть** — агент не переводит один вендорный диалект в другой. Непонятный
бэкенду ключ часто принимается с HTTP 200 и **молча игнорируется**; у моделей,
где thinking включён по умолчанию (DeepSeek V4 и др.), рассуждение остаётся
включённым. Ориентир при проверке — `usage.completion_tokens_details.reasoning_tokens`
в ответе (0 ≈ выключено). `strip_think` на это не влияет: он только решает,
класть ли мысль в историю, а не генерировать ли её.

| Стек | Выключить | Включить / усилить |
|---|---|---|
| Qwen / vLLM | `separate_reasoning: false` + `chat_template_kwargs.enable_thinking: false` | `separate_reasoning: true` + `enable_thinking: true` |
| GLM / DeepSeek на vLLM-подобных | `chat_template_kwargs: {thinking: false, reasoning_effort: none}` | `thinking: true` + `reasoning_effort: low\|high` |
| Native DeepSeek Chat Completions | `thinking: {type: disabled}` | `thinking: {type: enabled}` (+ при необходимости `reasoning_effort: low\|high\|max`) |
| OpenAI-like | `reasoning_effort: none` | `reasoning_effort: low\|medium\|high` |
| **OpenRouter** и совместимые прокси (LiteLLM → OpenRouter) | `reasoning: {effort: none}` | `reasoning: {effort: low\|medium\|high\|…}` |

OpenRouter **не** понимает Qwen/`chat_template_kwargs` и native DeepSeek
`thinking.type` как способ выключить reasoning: запрос проходит, модель
продолжает думать. Для части моделей (например часть GLM на OpenRouter)
`effort: none` даёт 400 «Reasoning is mandatory» — тогда ставьте
`effort: minimal` или `low` (на практике часто даёт 0 reasoning tokens).
Документация OpenRouter: [Reasoning Tokens](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

Пример выключения на OpenRouter-прокси:

```yaml
models:
  deepseek-v4:
    model: openrouter/deepseek/deepseek-v4-flash
    url: https://openrouter.ai/api/v1/chat/completions
    token: "${ENV:OPENROUTER_API_KEY}"
    main:
      reasoning:
        effort: none
    auxiliary:
      reasoning:
        effort: none
```

На каждом слое непустая секция и `{}` заменяют нижнюю целиком. Отсутствующий
ключ сохраняет значение нижнего слоя; YAML `null` явно его сбрасывает.
Если после наложения слоёв секции нет или она равна `null`, берётся глобальный
словарь своей роли (`backend.chat_completion_kwargs` для диалога и цикла субагента,
`chat_completions.auxiliary_llm.completion_kwargs` для summary, судей,
finish_gate, intent и черновика роли). Явный `{}` заменяет глобаль пустым
набором: эти ключи в запрос не класть, даже если глобаль непустая (старый
конфиг или свои kwargs). Секция с ключами заменяет глобальный словарь целиком,
без слияния. При пустой глобали поставки обе ветки дают payload без
vendor-ключей; это следствие пустой глобали, а не слияние семантик.

Что задаётся на алиасе:

| Ключ | Где |
|---|---|
| `main` | kwargs диалога и цикла субагента |
| `auxiliary` | kwargs summary, судей, finish_gate, intent, черновика роли |
| `strip_think` | вырезание мысли из истории. В поставке глобально `strip_tags_projection.strip_think: true` (нестрогий бэкенд отвечает 400 на мысль в истории). `false` на алиасе сохраняет скрытое поле; ключа нет — остаётся глобальный флаг |
| `summary_trigger_chars` / `summary_trigger_tokens` | mid-turn пороги сжатия на алиасе, который ведёт историю. `0` / нет ключа — шкала не задана. Оба нуля — весь набор из глобального `summary`. Хотя бы одно `> 0` — режим модели: незаданная шкала mid и turn-end = `0`; turn-end = 60% mid; `incremental_batch_chars` = ×1.2 и `max_dialogue_chars` = ×5 от символьного основания (если символы выкл — от `токены × 2`) |
| `backend.use_max_tokens_param` | `true` — в тело `max_tokens`, `false` — `max_completion_tokens`. Нет ключа — глобальный `backend`. Профиль может перекрыть и сам глобальный ключ своей секцией `backend` |
| `backend.openai_strict_tools_schema` | проекция схемы тулов в `chat_completions`: `true` — все properties в `required`. Нет ключа — глобальный `backend` |
| `backend.send_tool_strict` | слать ли `function.strict`. `false` снимает поле с копии на отправке. Нет ключа — глобальный `backend` |
| `backend.chat_completions_max_tokens` | потолок ответа этой модели |
| `backend.request_timeout_sec` | таймаут одного запроса |
| `backend.proxy` | HTTP/SOCKS-прокси |
| `backend.use_ssl` | TLS / путь к CA-bundle |
| `backend.cert_path`, `backend.key_path` | клиентский сертификат (mTLS) |
| `backend.use_retry` | ретраи транспорта |
| `backend.retry_embedded_choice_errors` | ошибка внутри HTTP-200 |
| `backend.claude_prompt_cache` | разметка prompt cache |
| `backend.chat_completion_headers` | дополнительные заголовки |
| `backend.completions_url` | свой адрес (пара с токеном) |

В `main`, `auxiliary` и в overrides нельзя писать ключи, которые рантайм ставит
сам: `model`, `messages`, `tools`, `max_tokens`, `max_completion_tokens`. Форма
их отклоняет, обе воронки режут их безусловно — иначе пользовательский словарь
затёр бы историю, список тулов или лимит ответа. При включённой разметке
prompt cache к этому набору добавляется `cache_control`: его пишет разметка,
чужое значение на проводе даёт 400. `api_mode` и `stream` остаются глобальными:
один ран — один протокол. `openai_strict_tools_schema` и `send_tool_strict`
можно задать на алиасе; ключа нет — берётся глобальный `backend`. В
`chat_completions` схема тулов проецируется на каждый запрос под резолвнутую
модель. В `responses` per-alias этих флагов нет: на провод идёт проекция
глобальных.

Старый `models.<alias>.backend.chat_completion_kwargs` при загрузке переносится
в `main` с предупреждением. Явно заданный `main` имеет приоритет. Сохранение карточки
модели записывает новый формат; служебные параметры задаются отдельно в `auxiliary`.

**`slots`** — какой алиас стоит за каким уровнем. Не заданный слот резолвится **матрицей
фоллбэков**: `light` → `light, default, max`; `default` → `default, max, light`;
`max` → `max, default, light`. Частный случай: слоты не заданы вовсе, а в реестре ровно
одна модель — она и работает на всех уровнях. Если моделей две и больше, а ни один слот
не задан, конфиг не загрузится с требованием указать `slots.default`.

**`assign`** — привязка отдельного служебного вызова к уровню или прямо к алиасу.
Потребители, которые можно привязать:

| Ключ `assign` | Кто это |
|---|---|
| `finish_gate` | судья завершения хода (самопроверка) |
| `text_answer_judge` | судья текстового ответа (`/answers` в TUI) |
| `command_judge` | судья команд в `edit` (`security.command_moderation`) и действий в `auto` |
| `routing_judge` | судья начальной пары при `agent.auto_routing_safe_level: auto` |
| `summary` | суммаризация истории и `/compact` |
| `intent_scope` | выжимки intent-scope |
| `memory_compaction` | компакция проектной памяти |
| `vision` | «глаза»: описывают изображение, когда модель хода его не видит (тул `fs_view_image`) |
| `subagents` | словарь `имя_субагента: уровень-или-алиас`, плюс `"*"` — все остальные |

- Без привязки `finish_gate`, `text_answer_judge`, `command_judge`, `summary` и
  `routing_judge` работают уровнем **`default`**, если слот `default` задан: судьи
  и суммаризация не опускаются и не дорожают вместе с исполнителем. Слот `default`
  не задан — они идут как остальные потребители, а не фоллбэком уровня `default`
  (иначе при слотах `light` и `max` судьи ручного `light` уходили бы на `max`).
  Остальные потребители без привязки идут **активным уровнем** (в том числе
  выбранным автовыбором, если активен `level: auto` — см. [«Автовыбор уровня
  модели»](auto-routing.md)).
- Явная привязка сильнее. У субагента, привязанного через `assign.subagents`,
  служебные вызовы без своей привязки тоже идут по этому правилу: `finish_gate`,
  `text_answer_judge`, `command_judge`, `summary` и `routing_judge` — `default`,
  если его слот задан; остальные потребители (`intent_scope`, `memory_compaction`,
  `vision`), а без слота `default` и судьи — моделью субагента.
- Поставляемые шаблоны привязок не задают. Старый ключ `assign.auto_judge`
  снимается при загрузке с уведомлением.
- Значение `auto` справа запрещено: это политика выбора уровня, а не модель.
- Ключ **`assign.main` запрещён** — основной трейс управляется уровнем
  (`level` / `--level` / `/level`), а не привязкой.
- Имена в `assign.subagents` сверяются с каноническим реестром субагентов: опечатка в
  имени — ошибка загрузки конфига, а не молчаливо неработающая строка.
- `assign` без реестра моделей ни на что не влияет — об этом приходит предупреждение
  (`привязки без реестра моделей не действуют`), а не тишина.
- `assign.vision` («глаза») зовёт только тул `fs_view_image`, когда модель хода картинку
  не видит: одна картинка, вопрос агента и текущая просьба пользователя (до 1500
  символов), `temperature: 0.1`, ответ до 1500 токенов, расход — в категории `vision`.
  Если модель для зрения отвечает, что картинок не принимает, она помечается до
  перезапуска агента: тул отвечает агенту, что смотреть некому, а в ленте TUI
  появляется серая строка `[изображение] Модель для зрения … не работает с
  изображениями`. Предохранитель и откат на активную модель такой отказ не включает.

### Указатели `profile` и `level`

Два топ-уровневых ключа `config.yml`:

```yaml
profile: ""        # какой профиль активен ("" или отсутствие ключа — без профиля)
level: default     # уровень по умолчанию: light | default | max | auto
```

`level` принимает четыре значения: три фиксированных уровня и `auto` — уровень
меняется автоматически по ходу работы, подробнее —
[«Автовыбор уровня модели»](auto-routing.md). Если `auto` выбран, а фича недоступна
(выключена `agent.auto_routing`, режим API `responses`, легаси-форс `--model` или в
уровнях, из которых выбирает политика, одна модель — в том числе без реестра
`models`) — уведомление с причиной, работает `default`.

Оба ключа выставляются с трёх поверхностей, по возрастанию приоритета: ключ в
конфиге → CLI (`--profile`, `--level`) → сессионные переключатели TUI
(`/profiles`, `/level`) — последние живут только в текущей сессии. Экран
`/settings` — это не отдельный приоритет, а запись того же ключа в файл конфига:
`profile` правит секция «Профили», `level` — секция «Режимы работы», рядом с
прочими глобальными переключателями.

Сам файл выбирается по правилу «пишем туда, где ключ уже задан»: обычно это
базовый `config.yml`, но если ключ задаёт проектный `.gc/config.yml`, запись идёт
в него — иначе проектный слой перекрыл бы её. Значение может перекрывать и слой,
в который экран не пишет (файл активного профиля, machine-managed
`~/.gc/config.local.yml`); тогда экран сообщает, что действует на самом деле, и
называет перекрывший слой.

Руками файлы ниже писать не обязательно: секция «Профили» умеет создавать,
переименовывать и удалять профили, а секция «Модели» — править `models` / `slots` /
`assign` (и в основном конфиге, и внутри профиля). Клавиши и поведение экрана —
[TUI режим](tui.md#настройки-settings).

### Настройки автовыбора уровня

| Ключ | Тип | По умолчанию | Что делает |
|---|---|---|---|
| `agent.auto_routing` | `bool` | `true` | рубильник фичи: `false` — `level: auto` работает как `default` |
| `agent.auto_routing_safe_level` | `default` \| `max` \| `auto` | `auto` | сильная модель пары: `default` — `light`+`default`, `max` — `default`+`max`; при `auto` начальную пару выбирает судья, затем пара меняется по сигналам и окнам. Судья используется, только когда в обеих парах разные модели; иначе выбирается обычная пара из двух разных моделей |
| `agent.auto_routing_two_level` | `{weak_steps, strong_steps, pair_threshold}` | `{10, 2, 3}` | `weak_steps` — шагов подряд на слабой модели до подъёма на сильную, `strong_steps` — шагов на сильной после важного вызова, сигнала и в начале хода. Оба числа — целые ≥ 1. `pair_threshold` — порог судьи для пары `default`+`max`, целое 2–5; сбой судьи также выбирает эту пару |

AUTO требует различающихся эффективных основных запросов. Два алиаса с одинаковой моделью, адресом, авторизацией и параметрами исполнителя считаются одним запросом для маршрутизации. Различия только тарифа, auxiliary-параметров и порогов сжатия не создают отдельную ступень; сами настройки по-прежнему применяются при исполнении и учёте.

Автовыбор использует пару моделей: важные вызовы выполняет сильная модель,
наблюдение — слабая. Настройка судьи пары — `assign.routing_judge`; без привязки
он использует уровень `default`, независимо от текущего уровня исполнителя, если
слот `default` задан, иначе — активный уровень.

Инструкцию судьи пары можно заменить через
`paths.chat_completions_routing_pair_judge_prompt_path`. По умолчанию берётся
`prompts/chat_completions_routing_pair_judge_prompt.md` рядом с конфигом, иначе
поставляемый файл. Когда начальную пару должен выбирать судья, локальный запуск
без файла инструкции или с пустым файлом отказывает до запуска ресурсов агента.

Настройки автовыбора состоят из рубильника, безопасного уровня и параметров пары.

Подробнее — [«Автовыбор уровня модели»](auto-routing.md).

### Профили — файлы-оверлеи

Профиль — обычный YAML-файл, **частичный конфиг**: любые секции `config.yml` (гварды,
суммаризация, `agent`, …) плюс, при желании, секции `models` / `slots` / `assign`.
Имя профиля — имя файла: `work.yml` → профиль `work`.

Ищутся в двух корнях, проектный первым:

1. `<проект>/.gc/profiles/<имя>.yml` — проектный (при совпадении имён выигрывает он);
2. `profiles/` рядом с базовым `config.yml` (на Windows — `~/.gc/profiles/`, на
   Linux/macOS — `~/.config/gc/profiles/`; при запуске с `--config` — каталог указанного
   файла).

Порядок сборки конфига: базовый `config.yml` → `config.local.yml` (то, что пишет
`gc-mcp`) → проектный `<cwd>/.gc/config.yml` → **контент профиля** → CLI-аргументы →
сессионные переключатели TUI. То есть профиль перекрывает все файловые слои, но сам
уступает CLI и сессии.

Ещё несколько правил:

- `${ENV:VAR}` и `${FILE:путь}` работают и внутри профиля;
- ключ `profile:` **внутри** профиля запрещён — цепочек профилей нет;
- файл с зарезервированным именем (`light.yml`, `default.yml`, `max.yml`, `auto.yml`)
  игнорируется с предупреждением;
- литеральный токен в **проектном** профиле даёт предупреждение — такой файл обычно
  лежит в репозитории, храните секрет через `${ENV:VAR}`.

Полный референс всех полей — [`demo_profile.yml`](../demo_profile.yml) в корне репозитория.

### Когда модель недоступна

Если модель не отвечает и обычные ретраи исчерпаны, её **алиас** попадает в сессионный
предохранитель. Дальше в этой сессии любой резолв этого алиаса отказывает сразу, не
ходя в транспорт, — у всех потребителей, не только у того, кто наткнулся первым.
Состояние живёт до конца сессии и переживает пересборку агента внутри неё (в TUI —
хранится в метаданных треда). Смена профиля предохранитель **сбрасывает**: модели
прежнего профиля больше не считаются сломанными.

Отказ модели принять изображение недоступностью **не считается**. Слепая модель
отвечает на картинку по-разному — vLLM «At most 0 image(s) may be provided» или
«… is not a multimodal model», OpenAI «image_url is only supported by certain models»,
OpenRouter даже `404` «No endpoints found that support image input», — но это факт о
модели, а не сбой: такой отказ не повторяется ни транспортом, ни адаптивным циклом, не
даёт уведомления «Ошибка LLM» и алиас в предохранитель не ставит.

Дальше поведение зависит от того, кто наткнулся на недоступность:

- **основной трейс в ручном режиме** — модель выбрана явно, подмены нет: ход завершается
  честной ошибкой, которая называет модель, алиас, адрес и причину, и подсказывает
  переключить уровень (`/level`) или профиль (`/profiles`);
- **основной трейс в AUTO** — тот же такт повторяется на ближайшем живом уровне, сначала
  вверх (см. [«Недоступная модель»](auto-routing.md)); честная ошибка — только когда
  живых уровней не осталось;
- **служебные вызовы** (то, что привязано через `assign`, — судьи, суммаризация и
  прочие) — один повтор активной моделью плюс уведомление о подмене; упал и он —
  ошибка уходит наверх как обычно;
- **субагент в собственном AUTO** — то же правило внутри его хода: замена ближайшим
  живым уровнем;
- **субагент с привязкой** (`assign.subagents`) — прежний запасной путь: переезжает на
  модель родителя; если запуск не успел сделать ни шага, он начинается заново, иначе
  продолжается с текущего шага.

В двух последних случаях подмена возможна, только если есть на что подменять: когда
привязка ведёт на ту же модель, что и активный уровень (или активная сама уже в
предохранителе), деградировать некуда — ошибка уходит наверх сразу, без повтора и без
уведомления.

### Уровень меняется со следующего нового вызова

`/level` меняет выбранный уровень сразу. Ручной → ручной, ручной → AUTO и AUTO →
ручной действуют со следующего нового LLM-вызова, независимо от стартового режима
хода. Модель, адрес, токен, тариф, строгость схем инструментов и пороги сжатия
берутся из одного решения при подготовке вызова до сжатия истории. Уже
подготовленный/отправленный запрос и его повторы сохраняют этот комплект;
смена уровня во время ожидания не переключает их посередине. Штатная смена формы
raw/Bearer или обновление токена при 401 допустимы внутри того же alias/URL/model: это
восстановление доступа, а не новое решение маршрутизации.

Футер показывает фактическую модель подготовленного вызова. Если следующий выбор
отличается, он отображается отдельно; будущий AUTO показан режимом `auto`, поскольку
его конкретную модель ещё предстоит выбрать. История и граница пользовательского
хода от `/level` не сбрасываются. Явная привязка субагента имеет приоритет.

Смена профиля или реестра моделей отличается от `/level`: она требует пересборки
раннера. Работающий executor сохраняет снимок конфигурации, реестра и доступности AUTO;
новые подключения и реестр профиля используются после завершения текущей задачи
при сборке следующего `RunContext`. Сам выбранный уровень, в том числе уровень
из session-profile при отсутствии явного `/level`, читается сразу и действует со
следующего нового вызова в пределах текущего снимка. Если текущий контекст
легаси/принудительно одномодельный или AUTO в нём недоступен, переключение уровня
не превращает его в новый реестр: новые возможности профиля ждут пересборки.

## Переопределение настроек из CLI

Любую настройку можно переопределить при запуске дополнительными аргументами
командной строки — **путём настройки через точку** (`--agent.max_steps 50`,
`--security.read_guard.mode ask`). Путь — тот же, что в `config.yml` и в
`gc-cli config explain`.

Тот же контракт у `gc-cli`, `gc-acp` и `gc-chat`: путь через точку и флаги
`--model`, `--completions_url`, `--level`. Свои флаги ACP и chat — ещё
`--config` и `--profile`. `gc-acp` пропускает чужие флаги клиентов без точки
(JetBrains — позиционный `acp`, `--experimental`) с пометкой в stderr;
`gc-chat` на них отвечает ошибкой.

- Прежние плоские имена (`--max_steps`, `--summary_params`) **не принимаются**:
  это ошибка при старте. Если у схемы есть настройка с тем же последним сегментом
  имени, сообщение подсказывает путь:
  `неизвестная настройка --max_steps (возможно, --agent.max_steps)`.
- Объявленные флаги CLI остаются флагами: `--model` (`agent.model`),
  `--completions_url` (`backend.completions_url`), `--profile`, `--level`,
  `--write-guard`/`--no-write-guard`, `--read-guard`/`--no-read-guard`,
  `--read-guard-mode`, `--command-moderation`, `--trace-id` и др. (`gc-cli --help`).

- Значения из CLI **всегда имеют приоритет** над файлами и профилем; в
  `config explain` их источник — слой `cli`.
- Поддерживаются формы `--param value`, `--param=value` и `--flag` (без
  значения — `true`).
- Значение приводится к типу через `yaml.safe_load` и проходит ту же
  валидацию, что и файл: `--agent.max_steps 50` → `agent.max_steps == 50`,
  `--agent.verbose true` → `agent.verbose is True`,
  `--agent.client_name "my_client"` → `agent.client_name == "my_client"`.
- В отличие от файла, **неизвестное имя или негодное значение — ошибка**
  сразу при старте: опечатка в команде не должна молча ничего не менять.
- Значение **заменяет** настройку целиком, а не сливается с файлом: список
  (`--security.read_guard.allowed_read_roots '[/repo]'`) сужает, словарь
  `--mcp.servers '{}'` отключает все серверы, запись `--models` заменяется
  вместе с адресом и токеном. Словарь на месте секции схемы раскладывается на
  её поля: `--security.read_guard '{"mode": "ask"}'` меняет только режим и не
  сбрасывает остальные поля секции к умолчаниям. Адрес записи реестра без
  токена (`--models.ds.url URL`) — ошибка правила пары: токен из файла не уйдёт
  на новый адрес. Так же работают `agent_overrides` сервера и swarm и
  сессионные правки TUI. Объединение списков — только у файловых слоёв.
- Имена флагов не сокращаются: `--mod` не превращается в `--model`.

**Примеры:**

- Отключить файловый периметр записи для разового запуска:
  ```bash
  gc-cli -q "..." --no-write-guard
  ```

- Переключить режим command moderation:
  ```bash
  gc-cli -q "..." --command-moderation ask
  ```

- Переопределить существующие ключи:
  ```bash
  gc-cli -q "..." --paths.agent_md_path "my path" --agent.max_steps 50
  ```
  В рантайме будет использовано `paths.agent_md_path == "my path"` и
  `agent.max_steps == 50`, даже если в `config.yml` заданы другие значения.

### Профиль и уровень: `--profile`, `--level`

```bash
gc-cli -q "..." --profile work            # активировать профиль work на этот запуск
gc-cli -q "..." --level max               # уровень на этот запуск: light | default | max | auto
```

Оба флага перекрывают одноимённые ключи `config.yml` (в том числе указатель
`profile:`), см. [«Профили и уровни моделей»](#профили-и-уровни-моделей). Профиля с
таким именем нет — запуск падает с сообщением, где искали и что нашли; `--level` кроме
этих четырёх значений ничего не принимает.

### Режим разрешений: `--permission-mode`

```bash
gc-cli -q "..." --permission-mode manual   # edit | manual | plan | auto
gc-ua --permission-mode manual
```

Режим сессии: он сохраняется в ней и действует при следующем открытии. Флаг перебивает
режим, сохранённый в сессии, которую вы продолжаете (`-t`), и ключ
`security.permissions.default_mode`; сессия без сохранённого режима открывается в
`default_mode`. Подробности — в разделе
[`security.permissions`](#securitypermissions-режимы-разрешений).

### `--model` и `--completions_url` при непустом реестре моделей

Флаги старые, но при **заполненной** секции `models` у них появляется отдельный смысл —
**легаси-форс**: на этот запуск резолв уровней и алиасов выключается целиком, и агент
(вместе с судьями и субагентами) идёт указанной моделью. Об этом сообщает нотис
`--model: уровни отключены на этот запуск (легаси-форс)`.

Что при этом **не** отключается: профиль остаётся в стопке слоёв как обычный оверлей —
гварды, суммаризация и прочие его секции продолжают действовать. Форс решает только
вопрос «какой моделью идёт вызов».

Если реестр пуст, ничего особенного не происходит: это обычное переопределение
`agent.model` и `backend.completions_url`, как и раньше.

## Изображения (`images:`)

Картинки во вводе: вставка в TUI или `--image` в CLI. В тексте сообщения картинка —
плашка `[Изображение #N]`, а сам файл (ужатый: длинная сторона не больше 1568 px, PNG
или JPEG) хранится рядом с тредом. Пикселями картинку видит только модель, которая
умеет работать с изображениями, и только при `backend_api_mode: chat_completions`; в
остальных случаях модель получает текстовую записку со ссылкой на файл.

| Ключ | Значение | По умолчанию |
|---|---|---|
| `max_per_message` | Картинок в одном сообщении: больше — отказ при вставке (TUI), ошибка старта (CLI) | `10` |
| `live_user_images` | Сколько ваших картинок уходит модели пикселями — самые свежие, в последних 10 ходах; остальные уходят запиской «вне контекста». Не меньше `max_per_message`, иначе конфиг не загрузится | `10` |
| `live_tool_images` | Сколько снимков агента (тул `fs_view_image`) уходит пикселями — только в текущем ходе. Не меньше `1`, иначе конфиг не загрузится: снимок, которого модель не видит, заставлял бы её звать тул снова | `3` |

Живая картинка стоит токенов на каждом шаге хода, поэтому окна ограничены. Картинка
вне окна не теряется: модель видит записку с путём и может посмотреть файл тулом.

**Как картинки уходят модели.** Пикселями картинки получает только подтверждённая основная модель в режиме
`backend_api_mode: chat_completions` — это chat_completions-only механика, как суммаризация, судья и обновление
памяти. На каждый запрос пикселями уходят ваши картинки — не больше `images.live_user_images` самых свежих за
последние 10 ходов, снимки агента — не больше `images.live_tool_images` за текущий ход (снимок, который модель
ещё не видела, остаётся живым и после вашей реплики посреди запуска — до ответа модели), и всего не больше 8 МБ
в base64 (не влезло — первыми выпадают самые старые). Остальные картинки уходят модели текстовой запиской:
подпись, размер, путь к файлу и как посмотреть (`fs_view_image`, если тул доступен и есть модель, которая видит).
В режиме `responses` основная модель всегда получает записки, и ни одна картинка не попадает в цепочку
`previous_response_id`. Файл картинки удалён вручную — модель получает записку «file unavailable», ход не
прерывается. Картинки лежат в `<threads_data_path>/images` (без `threads_data_path` — во временном каталоге
системы) и у своего хранилища тредов встраивающего SDK тоже.

**Автоматическая проверка зрения.** Неизвестный маршрут перед первым использованием изображения
получает отдельную маленькую PNG с шестью случайными символами и короткую просьбу прочитать код.
В пробе нет ваших изображений, истории, системного промпта агента и инструментов.
При точном ответе проверка занимает один запрос. После неправильного завершённого чтения допустима
одна вторая, более крупная PNG с другим кодом. Бюджет ответа обеих попыток — 512 токенов;
усечение без полного правильного кода останавливает проверку и не означает слепоту.

Результат сохраняется в процессе для фактического адреса, модели, доступа и маршрутизирующих настроек.
Другой токен или настроенный заголовок маршрутизации означает другой маршрут и новую пробу;
автоматические id запросов и тредов не разделяют кэш. Смена треда и субагенты используют общий результат,
перезапуск приложения очищает его. Успех подтверждает чтение этой пробы, а не распознавание любых картинок.
Обычные текстовые запросы проверку не запускают. Расход пробы учитывается в категории `vision`,
с меткой `vision_probe`; ожидающие общую проверку не оплачивают её повторно.

Пользовательские пиксели уходят только после подтверждения. Неизвестной модели может быть доступен
`fs_view_image`, чтобы лениво проверить зрение при просмотре файла проекта. В режиме `responses`
нативные пиксели запрещены; инструмент использует отдельный служебный вызов `chat_completions`.
Назначенная `assign.vision` сохраняет собственную авторизацию. Если рабочий вызов переключается
на активную модель из-за недоступности, новый адресат тоже проходит проверку до отправки картинки.

После временного сетевого сбоя, 5xx или 429 повтор возможен только по потребности в новом корневом
пользовательском ходе и не раньше чем через 30 секунд; для 429 соблюдается также `Retry-After`.
Повтор инструмента, внутренний шаг и компакция не создают новый ход. Ошибки доступа 401/403,
постоянная ошибка параметров и 413 маленькой пробы блокируют проверку до изменения доступа/настроек
или перезапуска; это не пометка слепоты. Неправильное чтение, усечение и явный отказ поддержки
тоже запоминаются до смены маршрута или перезапуска. При отказе или сбое появляется одно уведомление
на причину и маршрут в ходе, а история честно сообщает, что изображение не просмотрено.
Текстовые запросы при этом продолжают работать.

Сколько картинок подтверждённая модель принимает за запрос, агент узнаёт по факту. Явный отказ
от поддержки изображений запрещает пиксели этому эффективному маршруту; шаг повторяется с записками.
Названный предел числа картинок (например, «At most N image(s)…») запоминается на процесс.
Предел без числа или HTTP 413 рабочего запроса уменьшают число картинок вдвое, вплоть до записок вместо всех.
Успешно подобранное ограничение сохраняется на текущий ход для того же маршрута, набора живых изображений
и состояния истории: следующий шаг начинает с него, без повторной лесенки отказов. Это не пометка слепоты.
Новый ход, смена живых изображений или сжатие истории снимают ограничение; самые свежие картинки остаются.
Если не прошёл даже запрос без картинок, его ошибка обрабатывается обычным путём.

`backend.vision: false` явно запрещает пробу и пиксели; настройка одной модели имеет приоритет над общей.
`true` и отсутствие значения разрешают автопроверку. Штатные текстовые профили Harbor запрещают зрение
и исключают `fs_view_image` у основного агента и субагентов; эксперимент со зрением требует снять оба запрета.

## Голосовой ввод (`voice:`)

Диктовка в TUI (`Ctrl+T` / `/voice`): запись с микрофона уходит на STT-сервис, текст
возвращается в поле ввода. Настраивается мышкой — секция «Голосовой ввод» в `/settings`
(там же проверка связи и установка локального сервиса); ниже — те же ключи для правки
руками.

| Ключ | Значение | По умолчанию |
|---|---|---|
| `provider` | Пока одно значение — `openai` (endpoint, совместимый с `/v1/audio/transcriptions`) | `openai` |
| `url` | Полный адрес endpoint'а — вместе с `/v1/audio/transcriptions` | `""` |
| `token` | Bearer-токен endpoint'а | `""` |
| `model` | Имя модели распознавания (только `openai`) | `whisper-1` |
| `language` | Язык распознавания, ISO-код | `ru` |
| `max_seconds` | Предохранитель: запись сама останавливается через столько секунд | `120` |
| `timeout_seconds` | HTTP-таймаут запроса к STT | `60` |
| `verify-ssl` | `true \| false \| "/path/ca-bundle.pem"` — как `backend.use_ssl` | `true` |

Фича включается самим фактом настройки: достаточно `url` — токен не обязателен,
локальный сервис и открытые endpoint'ы его не спрашивают. Пусто — `Ctrl+T` молчит.

**Ключ пишется через дефис — `verify-ssl`**, в отличие от остальных ключей секции.
Форма с подчёркиванием конфиг не пройдёт.

Наружу голос ходит по тем же правилам, что запросы к модели: прокси берётся из
`backend.proxy` (или переменных окружения), `~/.netrc` игнорируется. Локальный сервис —
исключение: к нему всегда напрямую, мимо прокси.

Облачный endpoint:

```yaml
voice:
  url: "https://api.groq.com/openai/v1/audio/transcriptions"
  token: "${ENV:GROQ_API_KEY}"
  model: "whisper-large-v3-turbo"
  language: "ru"
```

Локальный сервис («батарейка», ~0.9 ГБ на диске) ставится командой `gc-voice install`
или из `/settings` и поднимается сам при старте `gc-ua`. Свою секцию он пишет не в ваш
`config.yml`, а в машинный `config.local.yml`, и она **мёржится поверх** вашей: пока
батарейка подключена, `voice:` из `config.yml` не действует. Про такой конфликт агент
предупреждает при установке и на старте.

Поэтому вписать свой endpoint руками мало — нужно ещё отключить локальный слой:
`/settings` делает это само при сохранении своего endpoint'а, вручную —
`gc-voice remove` (снос сервиса) либо удаление секции `voice:` из `config.local.yml`.

## Пресеты адресов (`endpoint_presets`, `voice_endpoint_presets`)

Выпадающий список под полем адреса. **По умолчанию ключа в конфиге нет** — работает
каталог из кода, и он обновляется вместе с версией агента. В шаблоне блок лежит
закомментированным как образец формата.

Задайте ключ, если нужен свой список: он перекроет кодовый — и с обновлениями
меняться уже не будет, новые провайдеры в него сами не приедут. Голосовые адреса
(`voice_endpoint_presets`) устроены так же.

```yaml
# адрес API-сервера агента (мастер первого запуска и /settings → «Подключение»)
endpoint_presets:
  - name: OpenRouter
    url: https://openrouter.ai/api/v1/chat/completions
  - name: Cloud.ru
    url: https://foundation-models.api.cloud.ru/v1/chat/completions
  - name: RouterAI
    url: https://routerai.ru/api/v1/chat/completions

# адрес STT-сервиса (/settings → «Голосовой ввод» → «Свой endpoint»)
voice_endpoint_presets:
  - name: OpenAI
    url: https://api.openai.com/v1/audio/transcriptions
  - name: Groq
    url: https://api.groq.com/openai/v1/audio/transcriptions
  - name: Mistral
    url: https://api.mistral.ai/v1/audio/transcriptions
```

Битый список (не тот формат) тоже откатывается на кодовый — молча, но целиком.

Свой адрес вписывается прямо в поле — список ему не мешает и не подставляется поверх.
Голосовые пресеты годятся для сервисов, говорящих на протоколе
`/v1/audio/transcriptions` (`voice.provider: openai`); у сервисов со своим API
(Deepgram, AssemblyAI, SpeechKit) другой протокол, и одним адресом они не настраиваются.

Порядок значим ровно в одном месте. Список фильтруется по подстроке имени и адреса,
а курсор при раскрытии встаёт на пункт, совпадающий с текущим значением поля; первым
он оказывается, только когда поле пустое — то есть на первом экране мастера. Проще
говоря, первый пресет — предложение тому, кто ничего не набрал, остальное человек
находит фильтром.

## Кастомные сабагенты

Сабагентов можно описывать файлами: `.md` с YAML-frontmatter в папке, путь к которой
задан в конфиге. Они появляются рядом со встроенными семью, и каждому можно сузить
набор инструментов.

```yaml
agent:
  use_local_subagents: true       # без этого сабагентов нет вообще
  subagents_dir: ./agents         # нет ключа → только встроенные
  subagents_max_count: 20         # опционально, дефолт 20
```

| Ключ | Дефолт | Смысл |
|---|---|---|
| `agent.use_local_subagents` | `false` | `true`/`false` либо **список имён**. Список выбирает кастомных; встроенные семь доступны всегда, пока значение не `false`. Пустой список = только встроенные |
| `agent.subagents_dir` | `null` | Папка с определениями. Не задана — папка не читается вовсе |
| `agent.subagents_max_count` | `20` | Предел числа подхватываемых определений. Лишние перечисляются в варнинге |

Работает только при `backend_api_mode: chat_completions`. Формат файла, правила по
инструментам и разбор коллизий — в `docs/subagents.md`.

## MCP-серверы

Клиент поддерживает MCP (Model Context Protocol): агент может вызывать инструменты
внешних MCP-серверов (поиск, RAG, файловая система, выполнение кода и т.д.).

Настройка — в `config.yml`, секция `mcp:` → `servers:` (литеральный верхнеуровневый
`mcp-servers:` конфиг отвергнет — это внутреннее имя ключа, не входное). Каждый сервер
задаётся ключом-именем (например `rag`, `search`, `python`); этот ключ служит частью имён
инструментов: тул `web_search` сервера `search` регистрируется как `mcp_search_web_search`
— именно это имя видит модель и его же принимает `agent.stop_tools`, тогда как
`whitelist.tools` берёт базовые имена без префикса (см. ниже). Используйте короткие имена
из латинских букв, цифр и символов `-_`, без пробелов.

Поддерживаются шесть типов транспорта MCP:

**Сессионные транспорты** (один запрос — один ответ, при необходимости используется `mcp-session-id`):

- **http** — запросы по HTTP. Обязательно: `transport: http`, `url`, `description`, `server-name`. Опционально: `token`, `verify-ssl`.
- **sse** — обмен через Server-Sent Events. Обязательно: `transport: sse`, `url`, `description`, `server-name`. Опционально: `token`, `verify-ssl`.
- **stdio** — MCP-сервер как локальный процесс (stdin/stdout); процесс запускается на каждый запрос. Обязательно: `transport: stdio`, `command`, `description`, `server-name`. Опционально: `args`, `cwd`, `env`.

**Стриминговые транспорты** (через MCP SDK, без сессий; подходят для серверов, поддерживающих streamable-протокол):

- **stream_http** — Streamable HTTP (MCP 1.26+). Обязательно: `transport: stream_http`, `url`, `description`, `server-name`. Опционально: `token`, `verify-ssl`. Endpoint обычно `.../mcp`; при 404 пробуется базовый URL.
- **stream_sse** — SSE в формате MCP SDK. Обязательно: `transport: stream_sse`, `url`, `description`, `server-name`. Опционально: `token`, `verify-ssl`.
- **stream_stdio** — stdio через MCP SDK (процесс на каждый запрос). Обязательно: `transport: stream_stdio`, `command`, `description`, `server-name`. Опционально: `args`, `cwd`, `env`.

**Общие параметры:** для любого транспорта можно задать `verify-ssl: true` (по умолчанию) или `verify-ssl: false` (отключить проверку SSL, например для self-signed сертификатов).

`whitelist` — ограничение набора тулов сервера: `enabled: true` + `tools: [имя, ...]` — модель видит строго перечисленные тулы (имена базовые, как их отдаёт сервер в `tools/list`, без префикса `mcp_<сервер>_`; пустой список = ноль тулов). **`enabled: true` без ключа `tools` (или с `tools: null`) — это тоже ноль тулов:** список нормализуется в пустой, и сервер молча остаётся без инструментов. Если нужны все тулы — не включайте `enabled` вовсе или поставьте `enabled: false`. Блок отсутствует или `enabled: false` — доступны все тулы. Имена, которых сервер не отдал, логируются warning'ом. Вызов не-whitelisted тула структурно невозможен: тул отсутствует в реестре, модель получает ошибку unknown tool, запрос до сервера не доходит.

`loop_control_tools` — opt-in loop detector для тулов этого MCP-сервера (профиль `generic`). По умолчанию детектор на MCP **выключен**: одинаковые аргументы у polling/mutating тулов могут намеренно давать новый результат, и транспорт не должен решать это за конкретный инструмент. Значения: список базовых имён из `tools/list` (без префикса `mcp_<сервер>_`) — контроль только на них; `"all"` — на все тулы сервера. Пустой список / отсутствие ключа — ни один MCP-тул сервера не маркируется. Глобальный выключатель всего контура — `agent.loop_detector.enabled` (см. [Конфиг клиента](#конфиг-клиента)): при `false` notice не шлётся и для MCP, даже если `loop_control_tools` задан.

**Внимание при layered-конфиге:** списки `whitelist.tools` из разных слоёв (base → `~/.gc/config.local.yml` → project `.gc/config.yml`) при deep-merge объединяются (concat + dedup) — сузить whitelist в project-слое нельзя, только расширить. Задавайте весь блок `whitelist` в одном слое; выключить целиком можно через `enabled: false` в верхнем слое.

**Кроссплатформенность (stdio / stream_stdio):** в `command` и `args` указывайте команду, доступную в PATH на вашей ОС (например, на Windows — `python` или `py`, а не только `python3`). Пути к скриптам в `args` лучше задавать в формате, принятом на целевой ОС, или использовать переменные окружения в `env`.

В секции `mcp-meta` можно задать:
- `tools-cache-ttl` — время жизни кэша списка инструментов (секунды);
- `request_timeout_sec` — таймаут запроса к MCP (секунды).

Полные примеры для http, sse, stdio и комментарии по stream_http/stream_sse/stream_stdio — в `demo_config.yml`. Скопируйте нужный блок, подставьте свои `url` или `command`/`args`.

### Встроенные интеграции — дистрибутив `gc-mcp`

Курируемые рецепты подключения MCP едут отдельным дистрибутивом `gc-mcp`
(пакет `recommended_mcp`, исходники — `packages/mcp/src/recommended_mcp/`).
Его тянут все профили, ставить отдельно не нужно. В корне репозитория каталога
`recommended_mcp/` больше нет — он переехал 18.08.2026 вместе с выделением
дистрибутива.

**Основной способ — `gc-mcp install`** (ставит пакет в отдельный venv агента и
сам прописывает сервер в `~/.gc/config.local.yml`):

```bash
gc-mcp install computer   # пример: установить computer MCP
gc-mcp install            # весь рекомендованный набор (кроме optional-рецептов)
gc-mcp list               # доступные / установленные / подключённые
gc-mcp remove computer    # отключить и удалить
```

**Фолбэк — `gc-mcp-install`**: та же установка отдельной точкой входа
(back-compat алиас `gc-mcp install`). Из рабочей копии репозитория работает и
запуск модулем:

```bash
uv run python -m recommended_mcp.install
```

`install.py` только ставит пакеты, в конфиг он ничего не пишет — этим и
отличается от `gc-mcp install`. После него сниппеты переносятся руками:
скопировать `packages/mcp/src/recommended_mcp/<name>/agent_config.snippet.yml`
в секцию `mcp-servers:` своего `config.yml`. Доступны:

- **`computer`** — управление Windows GUI через UI Automation (запуск
  приложений, клики, ввод, чтение состояния окон). Только Windows
  (`platforms: [win32]`). Исходники: `packages/mcp/external/vendor/computer-mcp/`.
- **`office`** — чтение офисных документов (pdf, docx, xls, xlsx, pptx,
  csv, html, msg) → markdown. Кросс-платформенно. Исходники:
  `packages/mcp/external/vendor/office-mcp/`.
- **`science`** — научные данные и вычисления, поднимается HTTP-daemon'ом.
  Исходники: `packages/mcp/external/vendor/science-mcp/`.
- **`duckduckgo_search`** — веб-поиск. Исходники: `packages/mcp/external/vendor/ddgs-mcp/`.
- **`browser_playwright`** — автоматизация браузера через `@playwright/mcp`
  (npx или Docker). Помечен `optional: true`: при установке без имени
  пропускается, ставится только явным `gc-mcp install browser_playwright`.

Подробности про каждую интеграцию — в её
`packages/mcp/src/recommended_mcp/<name>/README.md`. Общая документация по
`install.py` / `run.py` / структуре каталога —
в `packages/mcp/src/recommended_mcp/README.md`.

Для итеративной разработки наших MCP в `packages/mcp/external/vendor/`:

```bash
gc-mcp install --editable
```

### Ручная установка (для MCP не из курируемого набора)

Если нужный MCP не входит в набор `gc-mcp` — ставь как обычный пакет

```bash

```

## Секция `os_backend` — где живут файлы и команды тулов

Готовые YAML-блоки для каждого `kind` — в [os_backends.md](os_backends.md).

`kind`: `local` (по умолчанию) | `harbor` (только из Harbor-адаптера) | `docker` | `ssh` | `exec` | `sandbox`.
Голая строка `os_backend: docker` эквивалентна `{kind: docker}`.

| Ключ | Назначение |
|---|---|
| `cwd` | стартовый каталог на той стороне; `null` → `pwd` там при сборке контекста |
| `env` | переменные для каждой команды модели |
| `docker.name` / `docker.user` / `docker.binary` | `docker exec -i [-u USER] NAME`; `binary: podman` для podman |
| `ssh.host` / `port` / `user` / `key_path` / `options` / `control_master` | `ssh -T -o BatchMode=yes …`; `key_path: null` → ssh-agent; пароль не поддерживается |
| `exec.argv_prefix` | произвольный префикс (`kubectl exec -i -n NS POD --`, `container exec -i NAME`) |
| `sandbox.workdir` | `null` → изолируем текущий `launch_root`; `auto` → `<GC_STATE_DIR>/sandboxes/<slug папки запуска>/` — один на папку, общий для запусков и тредов |
| `sandbox.network` | `true` по умолчанию; `false` режет сеть у shell-команд |
| `sandbox.extra_ro` | дополнительные read-only пути (Linux) |
| `fetch_url_execute_on` | `agent` (по умолчанию) — `exec_fetch_url` качает с хоста; `os_backend` — GET делает `python3` среды исполнения (сеть только там), редиректы и `url_policy` проверяются на хосте, разбор текста — на хосте. Для `local`/`sandbox` игнорируется |
| `provision_skills` | `true` по умолчанию: для `docker`/`ssh`/`exec` скиллы (system + user + project) копируются на старте рана в `<launch_root>/.gc/skills_runtime/<слой>/`, реестр и `skills_run_script` работают по этим путям; повторный ран с тем же набором ничего не копирует (манифест sha256). `false` — скиллы не загружаются |

`agent.harbor_exec_init` действует и для `docker` / `ssh` / `exec` (профиль перед командой модели).
`agent.runtime_probe_ttl_sec` — срок годности успешной пробы живости той же оболочки (по умолчанию 10 с, `0` — перед каждым действием).
`sandbox` требует `bwrap` (Linux) или `sandbox-exec` (macOS); без них запуск падает, тихого отката в `local` нет. Windows не поддерживается. Изолируются только shell-команды модели и только на запись; MCP с `execute_on: os_backend` идёт под той же обёрткой, `download_file` работает как при `local` (файлы хостовые). `workdir: auto` — подмена рабочей области: файлы проекта, его `.git` и проектные скиллы тулам не видны.
Удалённой стороне нужны GNU `stat`/`find`, `sh`, `cat`, `base64`, `sha256sum`; `python3` — для `run_python_code`, MCP `execute_on: os_backend` и `fetch_url_execute_on: os_backend`; `bash` — для фоновых команд (`run_in_background`), как и в Harbor.
Правило разделения: хост — панель управления агента (конфиг, AGENTS.md, `project_memory`, треды и логи, MCP с `execute_on: agent`); среда исполнения — всё, с чем работает модель (`fs_*`, `exec_*`, фон, скиллы, MCP с `execute_on: os_backend`, при `fetch_url_execute_on: os_backend` — и сеть `exec_fetch_url`). `download_file` для remote-kind снят: он писал бы на хост.
Чистка `sandboxes/`: `python -m gc_server.swarm.cleanup … --core-sandboxes-dir ~/.local/state/gc/sandboxes`.

## Где gc-cli хранит runtime-данные

Кросс-платформенная раскладка. По умолчанию:

| ОС | Логи / треды / swarm | Cache (пока не используется)          | Config |
|---|---|---------------------------------------|---|
| Linux | `~/.local/state/gc/projects/<slug>/` | `~/.cache/gc/` *(резерв)*             | `~/.config/gc/` |
| macOS | `~/.local/state/gc/projects/<slug>/` *(как Linux)* | `~/.cache/gc/` *(резерв)*             | `~/.config/gc/` |
| Windows | `%USERPROFILE%\.gc\projects\<slug>\` | `%USERPROFILE%\.gc\cache\` *(резерв)* | `%USERPROFILE%\.gc\` |

`<slug>` — путь к проекту с заменой `/`, `\`, `:` на `-`, в стиле `~/.claude/projects/`.

Override через переменные окружения: `GC_HOME` (корневой), `GC_STATE_DIR` / `GC_CONFIG_DIR` / `GC_CACHE_DIR` / `GC_DATA_DIR` (точечные). На Linux/macOS дополнительно работают `XDG_STATE_HOME` / `XDG_CONFIG_HOME` / `XDG_CACHE_HOME` / `XDG_DATA_HOME`.

Каталог «Config» — это где `gc-cli` ищет базовый `config.yml` (tier между `--config` и пакетным дефолтом; подробнее — [«Где ищется базовый config.yml»](#конфиг-клиента) в начале страницы).

Каталог «Cache» — зарезервирован в кросс-платформенной XDG-раскладке, но `gc-cli` **пока не использует файловый кэш**: путь вычисляется (и переопределяется `GC_CACHE_DIR` / `XDG_CACHE_HOME`), но каталог не создаётся и в него ничего не пишется.

См. также пояснения в `demo_config.yml` (секция `paths`).

## Project local config (опционально)

Если в корне проекта есть файл `<your-repo>/.gc/config.yml`, gc-cli мерджит его поверх глобального `config.yml` через layered loading:

- **scalar** (число, строка, bool) — project переопределяет global.
- **dict** — рекурсивный deep merge: project расширяет/переопределяет ключи внутри.
- **list / array** — конкатенация + dedup: project только **расширяет** список, не сбрасывает (важно для security-полей вроде `agent.stop_tools` или `command_moderation.url_policy.url_blacklist`).

Пример проектного `<your-repo>/.gc/config.yml`:

```yaml
agent:
  max_steps: 200             # этот проект — длиннее цепочки рассуждений
  stop_tools: [browse_url]    # добавить локальный запрет (к глобальному списку)
mcp:
  servers:
    my_local_db:               # MCP только для этого проекта
      transport: stdio
      command: psql
```

Файл `.gc/config.yml` следует той же схеме, что и глобальный `config.yml` — указывайте только те поля, которые хотите переопределить или дополнить. Папка `.gc/` создаётся автоматически при первом запуске `gc-cli` (та же папка, что и для project-скиллов).

CLI-флаги (`--agent.max_steps 999` и т.п.) перебивают и global, и project. Файл опционален; если его нет — используется только global.

Если через `--config` явно передан тот же файл, что и `<repo>/.gc/config.yml` — gc-cli применяет его как обычный config без второго слоя (особый случай для запусков с явным путём).

## Temporal runtime

Opt-in интеграция: агент с теми же настройками исполняется воркером
Temporal — см. [Temporal](temporal.md).
