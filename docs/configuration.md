# Конфигурация

## Конфиг клиента

- Требуется запущенный GigaCode Agent с API `v1/responses` или с режимом `backend_api_mode: chat_completions`. Адрес сервиса задаётся в `config.yml`.
- **Где ищется базовый `config.yml`** (первый найденный источник побеждает):
  1. путь из `--config` (если задан);
  2. иначе `config.yml` в каталоге «Config» из таблицы [«Где gc-cli хранит runtime-данные»](#где-gc-cli-хранит-runtime-данные) — `~/.config/gc/config.yml` на Linux/macOS, `%USERPROFILE%\.gc\config.yml` на Windows (учитывает `GC_CONFIG_DIR` / `XDG_CONFIG_HOME` / `GC_HOME`). Это **полная база** (кладите полный конфиг — частичный файл здесь потеряет пакетные дефолты);
  3. иначе `config.default.yml` из ассетов дистрибутива `gc-core` (в рабочей копии — `packages/core/assets/`, в установленном колесе — `gc_core/assets/`).

  Поверх выбранной базы дополнительно deep-merge'ится project-local `<cwd>/.gc/config.yml` (см. [«Project local config (опционально)»](#project-local-config-опционально)). Чтобы указать свой путь явно:
  ```commandline
  gc-cli -q "ваш вопрос" --config ./config.yml
  ```
- Пример конфигурации: `demo_config.yml`. Скопируйте в `config.yml` и отредактируйте под свой бэкенд и MCP-серверы.
- В конфиге можно задать количество шагов агента (`max_steps`), логирование и другие параметры.
- **`max_steps` / `subagent_max_steps` — число завершённых ходов модели**, не half-turn цикла. Один step ≈ «модель ответила + (если были) все tool calls из ответа исполнены» (или text/bounce/finish). Запрос к LLM (`user_ask` / `function_call_output`) сам по себе step не тратит. Батч из N tools в одном ответе = **1 step**. Проверка `step_limit` — только когда нет pending `function_call`: уже присланные моделью tools всегда дожимаются, затем на следующем ходе срабатывает лимит (`steps >= max_steps`).
- `session_token_limit` / `max_tool_calls` — необязательные per-run лимиты надёжности (по умолчанию выключены). Первый ограничивает суммарные input+output токены одного рана по всем категориям (включая summary/finish gate/сабагентов); второй — число вызовов инструментов за ран (каждый вызов в батче считается отдельно). При достижении ран мягко завершается (как при `max_steps`) с `terminal_outcome = token_limit / tool_call_limit`; тред сохраняется, следующий запрос получает свежий бюджет. Проверка выполняется между шагами, поэтому возможен перерасход токен-бюджета в пределах одного шага. `max_tool_calls` аналогично проверяется между шагами: батч из нескольких вызовов в одном шаге выполняется целиком, даже если лимит достигнут в его середине; попытки вызова, отклонённые валидацией аргументов, тоже расходуют счётчик. Сабагент наследует те же значения на свой собственный ран, и при этом оба бюджета считаются **по всему дереву**: и токены, и вызовы инструментов ребёнка вливаются в счётчики родителя, поэтому родитель тратит `1` (сам вызов `subagent_*`) плюс все вызовы, сделанные ребёнком.
- **`session_token_limit` зависит от провайдера.** Бюджет считается по блоку `usage` из ответа модели. Если провайдер его не возвращает, вызов учитывается в `calls` и `missing_usage_calls`, но токенов прибавляется ноль — израсходованное остаётся нулевым, и лимит не сработает вообще (ран остановится только по `max_steps` / `max_tool_calls`, они от провайдера не зависят). Признак в отчёте по завершении рана: строка `⚠ N вызов(ов) без usage не учтены` и поле `missing_usage_calls` (см. [usage_pricing.md](usage_pricing.md)). Если у вашего бэкенда так — полагайтесь на `max_tool_calls` и `max_steps`, а не на токен-бюджет.
- Для режима `backend_api_mode: chat_completions` можно передавать токен провайдера
  (например OpenRouter) через `chat_completions_auth_token` (или алиас `openrouter_api_key`);
  тогда клиент отправит `Authorization: Bearer <token>` в запрос к `completions_url`.
  Опционально для OpenRouter поддерживаются заголовки `openrouter_http_referer`
  и `openrouter_x_title` (в запросе это `HTTP-Referer` и `X-OpenRouter-Title`).
- Для хранения истории тредов:
  - по умолчанию используется папка `threads` в корне проекта (`mini-cli-pub/threads`);
  - опциональный параметр `threads_data_path` в `config.yml` должен быть **абсолютным путём** к директории хранения; если не задан — используется кросс-платформенный дефолт `<state>/projects/<project-slug>/threads/` (на Linux/macOS — `~/.local/state/gc/...`, на Windows — `~/.gc/...`);
  - параметры суммаризации в `chat_completions` задаются в секции `summary_params`:
    - `summary_params.chat_completions_summary_trigger_chars`:
      - `<= 0` (или отсутствует) — суммаризация выключена (дефолт в коде: `0`); рекомендуемое значение для моделей с контекстом ~131k — `180000`;
      - `> 0` — при достижении/превышении порога тред архивируется (`data_*`/`meta_*` с суффиксом `__summarized_<YYYYMMDD_HHMMSS>`) и продолжается от compact summary;
    - `summary_params.incremental_batch_chars` — размер батча для кумулятивной суммаризации; если не задан, используется `int(summary_params.chat_completions_summary_trigger_chars * 1.4)`;
    - `summary_params.chat_completions_summary_prompt_path` (опционально), по умолчанию `prompts/chat_completions_summary_prompt.md`;
    - `summary_params.max_message_chars` — максимум символов на одно сообщение при подготовке истории к суммаризации (по умолчанию `50000`);
    - `summary_params.max_dialogue_chars` — максимум символов на весь диалог для суммаризации (по умолчанию `1000000`, берется хвост целыми сообщениями);
    - `summary_params.max_accumulated_summary_chars` — лимит длины накопленного summary; при превышении запускается дополнительное сжатие summary-of-summary (по умолчанию `20000`);
    - `summary_params.original_user_messages_max_chars` — лимит символов для `meta.user_messages_log` (единственный источник user-запросов для суммаризации); сохраняются последние сообщения целиком (по умолчанию `20000`);
    - `summary_params.last_dialog_steps_count` — сколько последних сообщений включать;
    - `summary_params.last_dialog_step_message_max_chars` — максимум символов на одно сообщение (лишнее обрезается).
  - **Поток суммаризации** (только при `backend_api_mode: chat_completions` и положительном `summary_params.chat_completions_summary_trigger_chars`):
    - перед стартом цикла агента выполняется **pre-run** compaction (если объём диалога в `state.messages` уже достиг порога);
    - после шага с исходящим результатом инструмента (**post-step**, сразу после обработки `function_call_output`) снова проверяется порог и при необходимости запускается compaction;
    - источник данных для решения «суммаризировать или нет» — только текущие сообщения сессии (`state.messages`); при запуске с `-t` после успешного compaction дополнительно обновляются файлы треда через `thread_store` (архив старых `data_*/meta_*` и запись compact-истории).
  - `gc-cli -q "..." -t my-thread` — продолжить диалог по треду;
  - `gc-cli -q "..." -t my-thread -n` (или `--new`) — начать тред заново с тем же id и удалить старые файлы этого треда (`data_*`/`meta_*`);
  - `-n/--new` можно использовать только вместе с `-t/--thread-id`.
  - в директории для тредов создаются файлы `data_<thread_id>.jsonl` (сообщения) и `meta_<thread_id>.json` (метаданные, включая `previous_response_id`).
- По умолчанию логи будут сохраняться в той папке, из которой запущена команда.
- **TUI**: секция `tui` управляет поведением интерфейса:
  - `tui.stream` (по умолчанию `true`) — мастер-переключатель live-стриминга ответа в TUI.
    При `false` ответ ждётся целиком; при `true` — чанки поступают по мере генерации.
    **Флаг задействован ТОЛЬКО в TUI:** на CLI/server/swarm не влияет — там всегда
    non-stream (стрим гейтится наличием `on_stream_delta`, который ставит только TUI).
    Legacy: если `tui.stream` не задан, читается старый `backend.stream` (backward-compat).
  - `tui.stream_display` (`minimal | answer | answer_reasoning`, по умолчанию `minimal`) —
    что показывать во время стриминга (`minimal` — только индикатор, `answer` — прогрессивный
    текст ответа, `answer_reasoning` — + однострочный «глазок» рассуждения).
    Актуально только при `backend_api_mode: chat_completions` и `tui.stream: true`.
  - `tui.text_answer_mode` (`deny | judge | allow`, по умолчанию `judge`) — как поступать
    с текстовым ответом агента без вызова инструмента:
    `deny` — всегда bounce (как CLI), `judge` — intent_guard решает, `allow` — принять текст.
  - `tui.file_view.enabled` / `max_file_bytes` / `page_lines` (`null` = авто по высоте)
    — постраничный просмотр `/view` в TUI (см. [tui.md](tui.md#просмотр-файла-view)).
- **Обновление**: секция `update` управляет самообновлением агента:
  - `update.check` (`auto | off`, по умолчанию `auto`) — проверять ли при запуске, вышла ли
    новая версия. Вердикт виден в TUI (`/settings` → Обновление) и по `gc-cli --check-update`.
  - `update.extra_args` (список, по умолчанию пустой) — дополнительные аргументы к
    `uv tool install` при обновлении. **В корпоративной сети обязателен**
    `["--system-certs"]`: без него установка упирается в TLS-перехват и падает —
    как из `/settings`, так и по `gc-cli --update`.
- **Слои инструкций** (`paths.agent_md_path`, `tui.agentsmd_override`) — см. раздел
  [«Слои инструкций (AGENTS.md)»](#слои-инструкций-agentsmd) ниже.

## Секреты и env-интерполяция (`${ENV:VAR}`)

В любом строковом значении конфига можно использовать плейсхолдер `${ENV:VAR}` — он
подставляется из переменной окружения **до валидации** (и в file-конфиге, и в CLI-override).
Удобно, чтобы не держать секрет в файле:

```yaml
backend:
  chat_completion_headers:
    Authorization: "Bearer ${ENV:GC_API_KEY}"   # затем: export GC_API_KEY=sk-...
mcp:
  servers:
    github:
      token: "${ENV:GITHUB_TOKEN}"
```

- Поддерживается несколько плейсхолдеров в одной строке (`"Bearer ${ENV:A}/${ENV:B}"`).
- Отсутствующая переменная → пустая строка + один warning с именем переменной (само значение не логируется).
- Переменная, заданная пустой строкой, подставляется как есть, без warning.
- Аналогично работает `${FILE:/путь/к/файлу}` — подставляет содержимое файла (хвостовые CR/LF срезаются, пробелы и табы — нет); поддерживается `~`. Нечитаемый файл → пустая строка + warning. Рекомендуется `chmod 600`: на POSIX файл, доступный group/other, даёт отдельный warning (как у ssh).
- **Лимит размера — 64 KiB (65536 байт).** Файл больше лимита тоже даёт пустую строку, с отдельным warning `credential file too large`; на этом пути проверка прав не выполняется. То есть пустой кред получается в трёх случаях: файла нет, он нечитаем, он слишком большой — во всех агент не падает, а продолжает с пустым значением, поэтому ошибка проявится уже как отказ авторизации у бэкенда.
- Относительный путь в `${FILE:}` резолвится **от текущего рабочего каталога процесса**, а не от каталога конфига (в отличие от ключей `paths.*`) — надёжнее указывать абсолютный путь или `~`.
- `${ENV:}` подставляется раньше `${FILE:}`, поэтому `${FILE:${ENV:SECRET_DIR}/token}` работает, а обратная вложенность — нет.
- Подстановка применяется к file-конфигу и к generic CLI-override'ам; в значении **объявленного** флага (например `--trace-id`) placeholder не разворачивается — там значение берётся буквально, раскрывать его должна оболочка.

## Логи: формат, уровень, редакция секретов

- `logging.format` (`text | jsonl`, по умолчанию `text`):
  - `text` — человекочитаемый вывод (историческое поведение);
  - `jsonl` — один JSON-объект на строку (`{"event": ...}`): `agent_start`,
    `backend_request/response`, `dialog_message`, `final_answer`, `run_usage`, `summary_*` и др.
    В jsonl-режиме человекочитаемый рендер в консоль **подавляется** — на stdout идёт только
    event-поток (удобно для парсеров/оркестраторов, напр. Task2PR-врапера).
- `logging.log_level` (`debug | info | warning | error`, по умолчанию `info`) — уровень per-run
  логгера (актуален для jsonl). На `debug` добавляются объёмные события
  `backend_request` / `backend_response` / `agent_tools`.
- `logging.redact_secrets` — маскировка секретов (Bearer/JWT/`sk-`/PEM/AWS/GCP/GitLab/npm/Slack)
  перед записью в лог и stdout → `***REDACTED***`. По умолчанию **выключено** (поведение как раньше):
  - `enabled: true|false`;
  - `extra_keys: []` — доп. подстроки имён чувствительных ключей (к встроенным);
  - `extra_patterns: []` — доп. value-regex (к встроенным).

  Счётчики токенов (`prompt_tokens`, `completion_tokens`, `max_tokens`) не маскируются;
  одиночное слово-ключ `token` / `*_token` — маскируется.

  **Важно — text vs jsonl:** маскировка **по имени ключа** (`extra_keys` и встроенные имена)
  работает только в `format: jsonl` — там редактируется структурный словарь события, и значение
  поля с совпавшим именем целиком становится `***REDACTED***`. В `format: text` редактируется
  финальная строка (словаря нет), поэтому применяются только **value-regex** (`extra_patterns`
  + встроенные Bearer/`sk-`/JWT/PEM/…), а `extra_keys` **не действует**. Для гарантированного
  маскирования в обоих режимах используй `extra_patterns` (по формату значения).

## Внешний trace_id

`trace_id` связывает один ран агента с шагом воркфлоу внешнего оркестратора.
Значение приходит снаружи; если его не передали — не меняется ничего.

### Как передать

- `gc-cli --trace-id <id>` — обычный запуск.
- поле `trace_id` в теле `POST /events/webhook` — серверный режим. Поле снимается
  из payload до того, как payload уходит в сообщение модели, поэтому в промпт оно
  не попадает.

Значение — не длиннее 200 символов и без управляющих символов (CR, LF, tab).
Невалидное отклоняется до начала работы, по-разному в зависимости от интейка:
`gc-cli` падает на старте (traceback и ненулевой код возврата — так же, как на любой
ошибке валидации конфига), а `POST /events/webhook` и `POST /swarm/run` отвечают
`400` с телом `{"status": "error", "payload": "invalid trace_id: ..."}`, при этом
агент не стартует, а сервер продолжает работать. Пустая или состоящая только
из пробелов строка означает отсутствие trace_id — и тогда не меняется ничего.

Флаг принимается в обоих написаниях — `--trace-id` и `--trace_id`, это один и тот же
параметр. Значение берётся **буквально**: объявленные флаги идут в конфиг напрямую,
минуя и подстановку плейсхолдеров, и коэрсию типов (поэтому трейс `00123` останется
строкой `"00123"`, а не станет числом). Переменную окружения раскрывает шелл —
`--trace-id "$WORKFLOW_ID"`; написанный в значении `${ENV:...}` уйдёт как есть,
литеральной строкой.

### Что происходит при наличии trace_id

| Куда | Что именно |
|---|---|
| Имя лог-файла | `agent_main_<trace>_<run_id>.<ext>` и `summary_trace_main_<trace>_<run_id>.jsonl`. Расширение основного лога следует формату: `.log` при `logging.format: text` и `.jsonl` при `logging.format: jsonl` — то есть в рекомендованном для оркестратора jsonl-режиме глоб `*.log` файл не найдёт. В имя идёт безопасная производная (только `A-Za-z0-9_-`, до 64 символов), `run_id` остаётся. |
| Записи логов | jsonl — поле `trace_id` в каждой записи; text — префикс `[trace=<id>]`. Значение сырое, не производная. |
| Запрос к модели | только при `agent.trace_header_enabled: true` (дефолт — `false`): заголовок `x_trace_id` (переопределяется `agent.trace_id_header_name`) на каждом вызове — главный цикл, суммаризация, finish gate, модерация команд, project memory, intent scope, генерация роли сабагента. Без флага заголовка нет, но в лог-файл и записи трейс попадает как обычно. |
| MCP | только серверам с явным `trace_header_enabled: true` (дефолт — `false`, см. «Ключи конфига»): заголовок `trace_id` (то же переопределение) для транспортов `http`, `sse`, `stream_http`, `stream_sse`; переменная окружения `TRACE_ID` для `stdio` и `stream_stdio`. |
| Мета треда | `runtime.trace_ids` — список всех trace, которые трогали тред, в порядке появления. Пишется только когда у рана есть тред: серверный режим (тред всегда есть) или `gc-cli -t`. Без треда (`gc-cli` без `-t`) значение нигде не сохраняется. |
| Старт рана | событие `trace_binding` — под какими именами этот ран шлёт trace в модель и в MCP. Поля: `trace_id`, `model_header`, `mcp_header`. |

`trace_binding` передаёт свои поля только через `extra=` логгера — их рендерит
`JsonlFormatter`. При `logging.format: text` (дефолт) в строке остаётся имя события и стандартный
текст записи, поля из `extra` в вывод не попадают.

> **Для интеграции с оркестратором:** выставьте `logging.format: jsonl`. Без этого событие в
> стоковой конфигурации не несёт машиночитаемых данных — только имя.

Сабагенты наследуют trace родителя дословно: у ребёнка свой `run_id` и свой файл
лога, но тот же trace — так родитель и дети группируются в один шаг оркестратора.

### Ключи конфига

```yaml
agent:
  # Имя заголовка. Не задано — x_trace_id для модели, trace_id для MCP.
  # Задайте X-Trace-Id, если между агентом и бэкендом стоит nginx: он по
  # умолчанию выбрасывает заголовки с подчёркиванием.
  trace_id_header_name: X-Trace-Id
  # Разрешить отправку trace_id в заголовке к бэкенду модели. Дефолт — false:
  # без этой строки заголовка не будет, даже если trace_id у рана есть.
  trace_header_enabled: true
mcp:
  servers:
    internal_srv:
      transport: http
      url: https://mcp.internal/mcp
      # То же для конкретного MCP-сервера. Дефолт — false: без этой строки
      # сервер не получает ни заголовка, ни переменной окружения.
      trace_header_enabled: true
```

### Оговорки

- Заголовок `x_trace_id` больше **не** содержит внутренний `state_id`. Сам
  `state_id` продолжает уходить как `x-session-id`.
- Per-run trace выигрывает у `backend.chat_completion_headers` с тем же именем.
- Рассылка trace наружу — строго opt-in, и для модели, и для MCP: по умолчанию
  заголовок не уходит никуда. Так внутренний корреляционный id не утекает ни в
  бэкенд модели, ни на сторонние эндпойнты, которые могут оказаться в
  `mcp.servers`. Обратная сторона: забытый `trace_header_enabled: true` означает,
  что trace молча не ушёл — если принимающая сторона его ждёт, флаг нужно
  проставить явно. Проверить, что именно уходит, можно по событию
  `trace_binding` в начале рана.
- Охвачены записи per-run логгера. Модульные логгеры (часть MCP-дискавери,
  транспортные ретраи) идут мимо и trace не несут.
- `gc-cli --init` флаг не читает: это не оркестрируемый ран.
- Swarm-раны трассируются: `POST /swarm/run` принимает `trace_id` тем же полем тела, снимает его из payload и передаёт в песочницу через `SWARM_TRACE_ID`, откуда обёртка добавляет `--trace-id`. Внутри песочницы дальше всё как в обычном ране. Через конфиг трейс передать нельзя — ребёнку материализуется сырой YAML, и неизвестный верхнеуровневый ключ будет отвергнут валидацией.
- При `logging.redact_secrets.enabled` trace, похожий на секрет (`sk-…`, `eyJ…`),
  будет замаскирован в записях логов, но не в имени файла и не в `summary_trace_*.jsonl` —
  этот сток пишется сырым `open()`/`json.dumps`, мимо фильтра и форматтера.
- Второй вебхук по тому же `(system, task_id)` подмешивается в уже идущий ран,
  чьи логи и заголовки зафиксированы: сохраняется первый trace, а про
  проигнорированный пишется событие `trace_id_ignored`.

## Backend TLS / mTLS

- `backend.use_ssl` — `true | false | "/path/ca-bundle.pem"`. Строка трактуется как путь к
  CA-bundle (self-signed / корпоративный CA); `bool` — как раньше (обратно совместимо).
- `backend.cert_path` / `backend.key_path` — клиентский сертификат (mTLS). Заданы **оба** →
  клиент предъявляет `(cert, key)`; ни одного → без клиентского сертификата (дефолт). Пути
  раскрывают `~` и env-переменные. (Опционально; не обязательны для работы бэкенда.)
- `backend.request_timeout_sec` — HTTP-таймаут одного запроса к LLM (секунды), по умолчанию
  `600` (10 минут). Для стрима лимит действует на connect и на паузу между чанками, а не на
  длительность всего ответа. Не путать с `mcp.meta.request_timeout_sec` (таймаут MCP).
- `agent.exec_timeout_sec` — дефолтный таймаут `execute_command` / `run_python_code`
  (секунды), если модель не передала `timeout_seconds`. По умолчанию `120`. Для длинных
  контейнерных сборок (Harbor) обычно поднимают до `600`.
- `agent.exec_output_capture_max_chars` — потолок RAM-буфера stdout/stderr на поток
  (decoded UTF-8 chars) для exec. По умолчанию `60000`. После cap вывод сливается и
  отбрасывается без kill процесса; page полного captured — через stream refs в ответе тулы.

## Слои инструкций (AGENTS.md)

Системные инструкции агента формируются из нескольких файлов, мерджимых в порядке broad→narrow
(каждый следующий слой уточняет/перекрывает предыдущий):

| Слой | Файл | Описание |
|------|------|----------|
| L0 (shipped) | `paths.agent_md_path` | Базовые инструкции из пакета (или кастомный путь) |
| L1 (global) | `~/.gc/AGENTS.md` (Linux/macOS: `~/.config/gc/AGENTS.md`) | Глобальные инструкции пользователя |
| L2 (project) | `<cwd>/AGENTS.md` | Инструкции проекта |
| L3 (project) | `<cwd>/.gc/AGENTS.md` | Уточнения для конкретного проекта |

- `paths.agent_md_path` (по умолчанию — shipped `prompts/demo_cli_agent.md`) задаёт L0.
  Укажите свой файл, если хотите заменить базовые инструкции.
- `tui.agentsmd_override` (`false` по умолчанию) — только TUI; при `true` оставить лишь
  корневой `AGENTS.md` (L3), отбросив глобальный (L1) и `.gc/AGENTS.md` слои.
  Игнорируется, если задан `paths.agent_md_path` (путь главнее флага).
  Из CLI: `--agentsmd-override`.
- Файл `AGENTS.md` генерируется командой `gc-cli --init` (агент сканирует репозиторий и
  создаёт/обновляет `AGENTS.md` через `write_to_file`).

## Security policy

Клиент поддерживает несколько независимых слоёв безопасности для файловых изменений,
чтения файлов, запуска команд/кода и сетевых запросов. Все слои включены по умолчанию
с режимом `ask` (secure-by-default), **кроме `protected_paths`** — он включён с режимом
deny (floor-защита без подтверждения).

```yaml
security:
  command_moderation:
    enabled: true        # on/ask по дефолту
    mode: ask            # allow | ask | deny
    allowed_command_examples: []
  write_guard:
    enabled: true        # on/ask по дефолту
    mode: ask            # allow | ask | deny
    extra_paths: []
  read_guard:
    enabled: true        # on/ask по дефолту
    mode: ask            # allow | ask | deny
  url_policy:
    enabled: true        # on/ask по дефолту
    mode: ask            # allow | ask | deny
    allowed_schemes: ["http", "https"]
    url_blacklist: []
  protected_paths:
    enabled: true        # floor-защита — всегда on
    extra: []
```

**Контракт режимов:**

- `ask` (дефолт) — при нарушении периметра (out-of-perimeter операция):
  - **TUI** — показывает confirm-баннер; пользователь подтверждает или отменяет.
  - **Headless** (CLI/server/swarm без интерактивного confirmer) — fail-closed **deny**
    с инструктивным сообщением агенту: операция заблокирована, нужно выбрать другой путь.
  - In-perimeter операции (запись/чтение внутри `launch_root`) проходят молча в любом режиме.
- `deny` — всегда блокировать, без запроса подтверждения.
- `allow` — всегда пропускать, записать в audit log как `out_of_perimeter`.

**Escape-hatch:** `mode: allow` или `enabled: false` — отключают enforcement для конкретного слоя.

### `security.write_guard` (файловый периметр)

- `enabled` (по умолчанию `true`) — при `false` периметр выключен, запись в любой путь разрешена.
- `extra_paths` — дополнительные директории, куда разрешена запись помимо `launch_root`.
  Относительные пути разрешаются от директории `config.yml`.
- `mode` (`allow | ask | deny`, по умолчанию `ask`) — реакция на нарушение периметра.

Включить/выключить из CLI: `--write-guard true|false` или `--no-write-guard`.

### `security.command_moderation` (LLM judge для команд)

- `enabled` (по умолчанию `true`) — при `false` judge не вызывается, все команды проходят.
- `mode` (`allow | ask | deny`, по умолчанию `ask`) — управляет только `execute_command` и `run_python_code`:
  - `allow` — выполнять без judge (эквивалент `enabled: false`);
  - `ask` — опасные команды: TUI → confirm-баннер; headless → fail-closed deny с сообщением;
  - `deny` — опасные команды блокировать без запроса.
- `allowed_command_examples` — positive examples для LLM judge; не строгий allowlist,
  а ориентир безопасного профиля команд проекта.
- `denied_command_examples` — negative examples (операторный deny-list). Явное совпадение
  (или тривиальная вариация: флаги/пути/кавычки/пробелы) → verdict `potentially_dangerous`
  + risk-флаг `operator_denied`, даже если команда сама по себе выглядит безобидно.
  Операторный интент главнее собственной оценки судьи. Работает при `mode: ask|deny`.
- **Трейдофф:** LLM-судья вызывается на каждую команду — добавляет задержку. При недоступности
  судьи: `deny` → fail-CLOSED; `ask` → headless deny, TUI → confirm-баннер.
  Отключить: `enabled: false`.

Переключить режим из CLI: `--command-moderation allow|ask|deny`.

### `security.read_guard` (периметр на чтение)

- `enabled` (по умолчанию `true`) — при `false` чтение файлов не ограничивается.
- `mode` (`allow | ask | deny`, по умолчанию `ask`) — реакция на нарушение.
- Дополнительные поля: `allowed_read_roots`, `allowed_read_paths`, `denied_read_paths`,
  `denied_file_patterns`, `denied_extensions`.

Включить/выключить из CLI: `--read-guard true|false` или `--no-read-guard`.
Режим: `--read-guard-mode allow|ask|deny`.

### `security.url_policy` (URL-политика)

- `enabled` (по умолчанию `true`) — при `false` проверки URL не выполняются.
- `mode` (`allow | ask | deny`, по умолчанию `ask`) — реакция на нарушение.
- `allowed_schemes` и `url_blacklist` проверяются для исходного URL
  в `fetch_url`/`simple_fetch_url` до сетевого запроса. Redirect targets повторно не проверяются.

### `security.protected_paths` (floor-защита)

- `enabled` (по умолчанию `true`) — защищает операционный каталог `.gc` от записи и чтения
  даже когда остальные guard'ы выключены. Также ставит детерминированный tripwire:
  команды вроде `rm -rf .gc` блокируются до запуска subprocess, без обращения к LLM-судье.
- `extra` — дополнительные пути с floor-защитой.

### Основные policy-ошибки

- `write_guard_violation` — файловое изменение вне разрешённых roots (write_guard);
- `unsafe_command_blocked` — опасная команда/код заблокированы в `deny`;
- `unsafe_command_cancelled_by_user` — пользователь не подтвердил опасное действие в `ask`;
- `url_validation_failed` — URL не прошёл схему/формат;
- `url_blocked_by_policy` — URL совпал с blacklist.

Все policy-решения пишутся в run logger как `security_policy_decision` без полного payload команды/кода.

## Профили и уровни моделей

Агент умеет работать не с одной моделью, а с **реестром именованных моделей** и тремя
**уровнями** сложности задачи. Уровень выбираете вы (ключ конфига, флаг CLI или
переключатель в TUI), а какая модель за ним стоит — решает конфиг:

- **light** — быстрая и дешёвая: простые задачи;
- **default** — основная рабочая: повседневные задачи;
- **max** — самая сильная: сложные задачи.

Ничего из этого не обязательно. Пока секция `models` пуста (или её нет), агент работает
в **легаси-режиме** — модель берётся из `agent.model`, адрес из
`backend.completions_url`, как раньше.

### Реестр: `models`, `slots`, `assign`

Три секции. Они допустимы и в `config.yml`, и в файле профиля, и на любом слое конфига —
мержатся вместе, а ссылки между ними проверяются уже по итоговому (смерженному) результату.

```yaml
models:                                  # реестр: алиас → провайдерская модель
  glm-local:
    url: http://127.0.0.1:8014/v1/chat/completions
  flash:
    model: qwen/qwen-2.5-flash           # провайдерский id
    url: https://openrouter.ai/api/v1/chat/completions
    token: "${ENV:OPENROUTER_API_KEY}"
    pricing: {input: 12, output: 48}     # тариф этой модели (формат секции pricing)
    backend:                             # частичный backend поверх эффективного
      chat_completion_kwargs: {temperature: 0.2}

slots:                                   # уровни — указатели на алиасы, не копии
  light: flash
  default: glm-local
  max: flash

assign:                                  # привязки отдельных потребителей
  finish_gate: light                     # значение — уровень ИЛИ алиас
  summary: light
  subagents:
    subagent_critic: max
    "*": default                         # все остальные субагенты
```

**`models`** — ключ словаря это **алиас**, ваш собственный язык для `slots` и `assign`,
а не провайдерский id. Правила записи одной модели:

- `model` не задан → провайдерским id становится сам алиас (удобно для локальных сборок);
- **адрес и токен — пара**: модель работает либо через общее подключение, либо через своё.
  Не заданы оба → оба наследуются из эффективной секции `backend`. Задан один без второго →
  **ошибка валидации**: свой адрес без токена унёс бы общий ключ на чужой хост, а свой токен
  без адреса уехал бы вслед за сменой общего адреса. Правило действует и внутри одного файла,
  и по слоям — слой (проектный `config.yml`, профиль), перекрывший у записи только адрес,
  отвергается с путём своего файла;
- «свой адрес» — это `url`, `backend.completions_url` **или** `backend.proxy`: прокси решает,
  куда физически уходит запрос вместе с токеном, поэтому тоже требует своего токена. «Свой
  токен» — `token` или `backend.chat_completion_headers.Authorization`;
- `token: ""` — «сервер не требует авторизации»; это **заданный** токен, пара с ним полна
  (штатная форма локального сервера). Непустое значение нормализуется в `Bearer <token>`
  (уже с префиксом — не дублируется);
- «тот же провайдер, другой ключ» — законный случай: повторите тот же адрес явно и добавьте
  свой `token`;
- имена `light`, `default`, `max`, `auto` зарезервированы и алиасом быть не могут;
- одно и то же нельзя задать дважды: `token` вместе с
  `backend.chat_completion_headers.Authorization`, а `url` вместе с
  `backend.completions_url` — ошибка валидации.

**`slots`** — какой алиас стоит за каким уровнем. Не заданный слот резолвится **матрицей
фоллбэков**: `light` → `light, default, max`; `default` → `default, max, light`;
`max` → `max, default, light`. Частный случай: слоты не заданы вовсе, а в реестре ровно
одна модель — она и работает на всех уровнях. Если моделей две и больше, а ни один слот
не задан, конфиг не загрузится с требованием указать `slots.default`.

**`assign`** — привязка отдельного служебного вызова к уровню или прямо к алиасу.
Потребители, которые можно привязать:

| Ключ `assign` | Кто это |
|---|---|
| `finish_gate` | судья завершения хода (самопроверка) |
| `text_answer_judge` | судья текстового ответа (`/answers` в TUI) |
| `command_judge` | судья модерации опасных команд (`security.command_moderation`) |
| `summary` | суммаризация истории и `/compact` |
| `intent_scope` | выжимки intent-scope |
| `memory_compaction` | компакция проектной памяти |
| `auto_judge` | классификатор уровня (ключ легален, но пока инертен) |
| `subagents` | словарь `имя_субагента: уровень-или-алиас`, плюс `"*"` — все остальные |

- Потребитель без привязки идёт **активным уровнем**. Исключение — `auto_judge`: без
  привязки он статически резолвится в `default`.
- Значение `auto` справа запрещено: это политика выбора уровня, а не модель.
- Ключ **`assign.main` запрещён** — основной трейс управляется уровнем
  (`level` / `--level` / `/level`), а не привязкой.
- Имена в `assign.subagents` сверяются с каноническим реестром субагентов: опечатка в
  имени — ошибка загрузки конфига, а не молчаливо неработающая строка.
- `assign` без реестра моделей ни на что не влияет — об этом приходит предупреждение
  (`привязки без реестра моделей не действуют`), а не тишина.

### Указатели `profile` и `level`

Два топ-уровневых ключа `config.yml`:

```yaml
profile: ""        # какой профиль активен ("" или отсутствие ключа — без профиля)
level: default     # уровень по умолчанию: light | default | max
```

`level` принимает только три значения. Значение `auto` отклоняется отдельной ошибкой
(«появится с функцией авто-выбора») — этой функции пока нет.

Оба ключа выставляются с трёх поверхностей, по возрастанию приоритета: ключ в
конфиге → CLI (`--profile`, `--level`) → сессионные переключатели TUI
(`/profiles`, `/level`) — последние живут только в текущей сессии. Секция «Профили»
экрана `/settings` — это не отдельный приоритет, а запись того же ключа в файл конфига.

### Профили — файлы-оверлеи

Профиль — обычный YAML-файл, **частичный конфиг**: любые секции `config.yml` (гварды,
суммаризация, `agent`, …) плюс, при желании, секции `models` / `slots` / `assign`.
Имя профиля — имя файла: `work.yml` → профиль `work`.

Ищутся в двух корнях, проектный первым:

1. `<проект>/.gc/profiles/<имя>.yml` — проектный (при совпадении имён выигрывает он);
2. `profiles/` рядом с базовым `config.yml` (на Windows — `~/.gc/profiles/`, на
   Linux/macOS — `~/.config/gc/profiles/`; при запуске с `--config` — каталог указанного
   файла).

Порядок сборки конфига: базовый `config.yml` → `config.local.yml` (то, что пишет
`gc-mcp`) → проектный `<cwd>/.gc/config.yml` → **контент профиля** → CLI-аргументы →
сессионные переключатели TUI. То есть профиль перекрывает все файловые слои, но сам
уступает CLI и сессии.

Ещё несколько правил:

- `${ENV:VAR}` и `${FILE:путь}` работают и внутри профиля;
- ключ `profile:` **внутри** профиля запрещён — цепочек профилей нет;
- файл с зарезервированным именем (`light.yml`, `default.yml`, `max.yml`, `auto.yml`)
  игнорируется с предупреждением;
- литеральный токен в **проектном** профиле даёт предупреждение — такой файл обычно
  лежит в репозитории, храните секрет через `${ENV:VAR}`.

Полный референс всех полей — [`demo_profile.yml`](../demo_profile.yml) в корне репозитория.

### Когда модель недоступна

Если модель не отвечает и обычные ретраи исчерпаны, её **алиас** попадает в сессионный
предохранитель. Дальше в этой сессии любой резолв этого алиаса отказывает сразу, не
ходя в транспорт, — у всех потребителей, не только у того, кто наткнулся первым.
Состояние живёт до конца сессии и переживает пересборку агента внутри неё (в TUI —
хранится в метаданных треда). Смена профиля предохранитель **сбрасывает**: модели
прежнего профиля больше не считаются сломанными.

Дальше поведение зависит от того, кто наткнулся на недоступность:

- **основной трейс** — никакой подмены молча: ход завершается честной ошибкой, которая
  называет модель, алиас, адрес и причину, и подсказывает переключить уровень
  (`/level`) или профиль (`/profiles`);
- **служебные вызовы** (то, что привязано через `assign`, — судьи, суммаризация и
  прочие) — один повтор активной моделью плюс уведомление о подмене; упал и он —
  ошибка уходит наверх как обычно;
- **субагенты** — тоже переезжают на активную модель: если запуск не успел сделать ни
  шага, он начинается заново, иначе продолжается с текущего шага.

В двух последних случаях подмена возможна, только если есть на что подменять: когда
привязка ведёт на ту же модель, что и активный уровень (или активная сама уже в
предохранителе), деградировать некуда — ошибка уходит наверх сразу, без повтора и без
уведомления.

### Уровень фиксируется на ход

Уровень снимается один раз в начале хода, и весь ход идёт на нём: переключение `/level`
или профиля посреди работы применится со **следующего** хода. Иначе смена уровня уводила
бы модель, адрес и токен на другой слот прямо в середине цикла вызовов инструментов.

## Переопределение настроек из CLI

Любой параметр из `config.yml` (или новый, которого там нет) можно переопределить при запуске через дополнительные аргументы командной строки.

- Значения из CLI **всегда имеют приоритет** над значениями из `config.yml`.
- Поддерживаются следующие формы:
  - `--param value`
  - `--param=value`
  - `--flag` (без значения, в конфиг уйдёт `true`)
- Значения автоматически приводятся к типам с помощью `yaml.safe_load`, поэтому:
  - `--max_steps 50` → `config_dict["max_steps"] == 50` (число),
  - `--verbose true` → `config_dict["verbose"] == True` (булево),
  - `--client_name "my_client"` → `config_dict["client_name"] == "my_client"` (строка).

**Примеры:**

- Отключить файловый периметр записи для разового запуска:
  ```bash
  gc-cli -q "..." --no-write-guard
  ```

- Переключить режим command moderation:
  ```bash
  gc-cli -q "..." --command-moderation ask
  ```

- Переопределить существующие ключи:
  ```bash
  gc-cli -q "..." --agent_md_path "my path" --max_steps 50
  ```
  В рантайме будет использовано:
  - `config_dict["agent_md_path"] == "my path"`,
  - `config_dict["max_steps"] == 50`,
  даже если в `config.yml` заданы другие значения.

- Добавить новый параметр, которого нет в `config.yml`:
  ```bash
  gc-cli -q "..." --my_custom_flag true --extra_param "some value"
  ```
  В `config_dict` появятся:
  - `config_dict["my_custom_flag"] == True`,
  - `config_dict["extra_param"] == "some value"`.

### Профиль и уровень: `--profile`, `--level`

```bash
gc-cli -q "..." --profile work            # активировать профиль work на этот запуск
gc-cli -q "..." --level max               # уровень на этот запуск: light | default | max
```

Оба флага перекрывают одноимённые ключи `config.yml` (в том числе указатель
`profile:`), см. [«Профили и уровни моделей»](#профили-и-уровни-моделей). Профиля с
таким именем нет — запуск падает с сообщением, где искали и что нашли; `--level` кроме
трёх значений ничего не принимает.

### `--model` и `--completions_url` при непустом реестре моделей

Флаги старые, но при **заполненной** секции `models` у них появляется отдельный смысл —
**легаси-форс**: на этот запуск резолв уровней и алиасов выключается целиком, и агент
(вместе с судьями и субагентами) идёт указанной моделью. Об этом сообщает нотис
`--model: уровни отключены на этот запуск (легаси-форс)`.

Что при этом **не** отключается: профиль остаётся в стопке слоёв как обычный оверлей —
гварды, суммаризация и прочие его секции продолжают действовать. Форс решает только
вопрос «какой моделью идёт вызов».

Если реестр пуст, ничего особенного не происходит: это обычное переопределение плоских
ключей, как и раньше.

## Голосовой ввод (`voice:`)

Диктовка в TUI (`Ctrl+T` / `/voice`): запись с микрофона уходит на STT-сервис, текст
возвращается в поле ввода. Настраивается мышкой — секция «Голосовой ввод» в `/settings`
(там же проверка связи и установка локального сервиса); ниже — те же ключи для правки
руками.

| Ключ | Значение | По умолчанию |
|---|---|---|
| `provider` | Пока одно значение — `openai` (endpoint, совместимый с `/v1/audio/transcriptions`) | `openai` |
| `url` | Полный адрес endpoint'а — вместе с `/v1/audio/transcriptions` | `""` |
| `token` | Bearer-токен endpoint'а | `""` |
| `model` | Имя модели распознавания (только `openai`) | `whisper-1` |
| `language` | Язык распознавания, ISO-код | `ru` |
| `max_seconds` | Предохранитель: запись сама останавливается через столько секунд | `120` |
| `timeout_seconds` | HTTP-таймаут запроса к STT | `60` |
| `verify-ssl` | `true \| false \| "/path/ca-bundle.pem"` — как `backend.use_ssl` | `true` |

Фича включается самим фактом настройки: достаточно `url` — токен не обязателен,
локальный сервис и открытые endpoint'ы его не спрашивают. Пусто — `Ctrl+T` молчит.

**Ключ пишется через дефис — `verify-ssl`**, в отличие от остальных ключей секции.
Форма с подчёркиванием конфиг не пройдёт.

Наружу голос ходит по тем же правилам, что запросы к модели: прокси берётся из
`backend.proxy` (или переменных окружения), `~/.netrc` игнорируется. Локальный сервис —
исключение: к нему всегда напрямую, мимо прокси.

Облачный endpoint:

```yaml
voice:
  url: "https://api.groq.com/openai/v1/audio/transcriptions"
  token: "${ENV:GROQ_API_KEY}"
  model: "whisper-large-v3-turbo"
  language: "ru"
```

Локальный сервис («батарейка», ~0.9 ГБ на диске) ставится командой `gc-voice install`
или из `/settings` и поднимается сам при старте `gc-ua`. Свою секцию он пишет не в ваш
`config.yml`, а в машинный `config.local.yml`, и она **мёржится поверх** вашей: пока
батарейка подключена, `voice:` из `config.yml` не действует. Про такой конфликт агент
предупреждает при установке и на старте.

Поэтому вписать свой endpoint руками мало — нужно ещё отключить локальный слой:
`/settings` делает это само при сохранении своего endpoint'а, вручную —
`gc-voice remove` (снос сервиса) либо удаление секции `voice:` из `config.local.yml`.

## Пресеты адресов (`endpoint_presets`, `voice_endpoint_presets`)

Выпадающий список под полем адреса. **По умолчанию ключа в конфиге нет** — работает
каталог из кода, и он обновляется вместе с версией агента. В шаблоне блок лежит
закомментированным как образец формата.

Задайте ключ, если нужен свой список: он перекроет кодовый — и с обновлениями
меняться уже не будет, новые провайдеры в него сами не приедут. Голосовые адреса
(`voice_endpoint_presets`) устроены так же.

```yaml
# адрес API-сервера агента (мастер первого запуска и /settings → «Подключение»)
endpoint_presets:
  - name: OpenRouter
    url: https://openrouter.ai/api/v1/chat/completions
  - name: GigaCode
    url: https://litellm-proxy.sberai-rnd.ru/v1/chat/completions

# адрес STT-сервиса (/settings → «Голосовой ввод» → «Свой endpoint»)
voice_endpoint_presets:
  - name: OpenAI
    url: https://api.openai.com/v1/audio/transcriptions
  - name: Groq
    url: https://api.groq.com/openai/v1/audio/transcriptions
  - name: Mistral
    url: https://api.mistral.ai/v1/audio/transcriptions
```

Битый список (не тот формат) тоже откатывается на кодовый — молча, но целиком.

Свой адрес вписывается прямо в поле — список ему не мешает и не подставляется поверх.
Голосовые пресеты годятся для сервисов, говорящих на протоколе
`/v1/audio/transcriptions` (`voice.provider: openai`); у сервисов со своим API
(Deepgram, AssemblyAI, SpeechKit) другой протокол, и одним адресом они не настраиваются.

Порядок значим ровно в одном месте. Список фильтруется по подстроке имени и адреса,
а курсор при раскрытии встаёт на пункт, совпадающий с текущим значением поля; первым
он оказывается, только когда поле пустое — то есть на первом экране мастера. Проще
говоря, первый пресет — предложение тому, кто ничего не набрал, остальное человек
находит фильтром.

## Кастомные сабагенты

Сабагентов можно описывать файлами: `.md` с YAML-frontmatter в папке, путь к которой
задан в конфиге. Они появляются рядом со встроенными семью, и каждому можно сузить
набор инструментов.

```yaml
agent:
  use_local_subagents: true       # без этого сабагентов нет вообще
  subagents_dir: ./agents         # нет ключа → только встроенные
  subagents_max_count: 20         # опционально, дефолт 20
```

| Ключ | Дефолт | Смысл |
|---|---|---|
| `agent.use_local_subagents` | `false` | `true`/`false` либо **список имён**. Список выбирает кастомных; встроенные семь доступны всегда, пока значение не `false`. Пустой список = только встроенные |
| `agent.subagents_dir` | `null` | Папка с определениями. Не задана — папка не читается вовсе |
| `agent.subagents_max_count` | `20` | Предел числа подхватываемых определений. Лишние перечисляются в варнинге |

Работает только при `backend_api_mode: chat_completions`. Формат файла, правила по
инструментам и разбор коллизий — в `docs/subagents.md`.

## MCP-серверы

Клиент поддерживает MCP (Model Context Protocol): агент может вызывать инструменты
внешних MCP-серверов (поиск, RAG, файловая система, выполнение кода и т.д.).

Настройка — в `config.yml`, секция `mcp:` → `servers:` (литеральный верхнеуровневый
`mcp-servers:` конфиг отвергнет — это внутреннее имя ключа, не входное). Каждый сервер
задаётся ключом-именем (например `rag`, `search`, `python`); этот ключ служит частью имён
инструментов: тул `web_search` сервера `search` регистрируется как `mcp_search_web_search`
— именно это имя видит модель и его же принимает `agent.stop_tools`, тогда как
`whitelist.tools` берёт базовые имена без префикса (см. ниже). Используйте короткие имена
из латинских букв, цифр и символов `-_`, без пробелов.

Поддерживаются шесть типов транспорта MCP:

**Сессионные транспорты** (один запрос — один ответ, при необходимости используется `mcp-session-id`):

- **http** — запросы по HTTP. Обязательно: `transport: http`, `url`, `description`, `server-name`. Опционально: `token`, `verify-ssl`.
- **sse** — обмен через Server-Sent Events. Обязательно: `transport: sse`, `url`, `description`, `server-name`. Опционально: `token`, `verify-ssl`.
- **stdio** — MCP-сервер как локальный процесс (stdin/stdout); процесс запускается на каждый запрос. Обязательно: `transport: stdio`, `command`, `description`, `server-name`. Опционально: `args`, `cwd`, `env`.

**Стриминговые транспорты** (через MCP SDK, без сессий; подходят для серверов, поддерживающих streamable-протокол):

- **stream_http** — Streamable HTTP (MCP 1.26+). Обязательно: `transport: stream_http`, `url`, `description`, `server-name`. Опционально: `token`, `verify-ssl`. Endpoint обычно `.../mcp`; при 404 пробуется базовый URL.
- **stream_sse** — SSE в формате MCP SDK. Обязательно: `transport: stream_sse`, `url`, `description`, `server-name`. Опционально: `token`, `verify-ssl`.
- **stream_stdio** — stdio через MCP SDK (процесс на каждый запрос). Обязательно: `transport: stream_stdio`, `command`, `description`, `server-name`. Опционально: `args`, `cwd`, `env`.

**Общие параметры:** для любого транспорта можно задать `verify-ssl: true` (по умолчанию) или `verify-ssl: false` (отключить проверку SSL, например для self-signed сертификатов).

`whitelist` — ограничение набора тулов сервера: `enabled: true` + `tools: [имя, ...]` — модель видит строго перечисленные тулы (имена базовые, как их отдаёт сервер в `tools/list`, без префикса `mcp_<сервер>_`; пустой список = ноль тулов). **`enabled: true` без ключа `tools` (или с `tools: null`) — это тоже ноль тулов:** список нормализуется в пустой, и сервер молча остаётся без инструментов. Если нужны все тулы — не включайте `enabled` вовсе или поставьте `enabled: false`. Блок отсутствует или `enabled: false` — доступны все тулы. Имена, которых сервер не отдал, логируются warning'ом. Вызов не-whitelisted тула структурно невозможен: тул отсутствует в реестре, модель получает ошибку unknown tool, запрос до сервера не доходит.

**Внимание при layered-конфиге:** списки `whitelist.tools` из разных слоёв (base → `~/.gc/config.local.yml` → project `.gc/config.yml`) при deep-merge объединяются (concat + dedup) — сузить whitelist в project-слое нельзя, только расширить. Задавайте весь блок `whitelist` в одном слое; выключить целиком можно через `enabled: false` в верхнем слое.

**Кроссплатформенность (stdio / stream_stdio):** в `command` и `args` указывайте команду, доступную в PATH на вашей ОС (например, на Windows — `python` или `py`, а не только `python3`). Пути к скриптам в `args` лучше задавать в формате, принятом на целевой ОС, или использовать переменные окружения в `env`.

В секции `mcp-meta` можно задать:
- `tools-cache-ttl` — время жизни кэша списка инструментов (секунды);
- `request_timeout_sec` — таймаут запроса к MCP (секунды).

Полные примеры для http, sse, stdio и комментарии по stream_http/stream_sse/stream_stdio — в `demo_config.yml`. Скопируйте нужный блок, подставьте свои `url` или `command`/`args`.

### Встроенные интеграции — `recommended_mcp/`

В корне репозитория есть каталог `recommended_mcp/` с готовыми рецептами
подключения нескольких MCP.

**Основной способ — `gc-mcp install`** (автоматически ставит пакет и прописывает в `~/.gc/config.local.yml`):

```bash
gc-mcp install computer   # пример: установить computer MCP
gc-mcp list               # список установленных
gc-mcp remove computer    # удалить
```

**Фолбэк — ручная установка** (если `gc-mcp` недоступен):

```bash
python recommended_mcp/install.py
```

После ручной установки нужно скопировать сниппеты из
`recommended_mcp/<name>/agent_config.snippet.yml` в секцию `mcp-servers:`
своего `config.yml`. На момент написания доступны:

- **`computer`** — управление Windows GUI через UI Automation (запуск
  приложений, клики, ввод, чтение состояния окон). Только Windows.
  Исходники: `external/computer-mcp/`.
- **`office`** — чтение офисных документов (pdf, docx, xls, xlsx, pptx,
  csv, html, msg) → markdown. Кросс-платформенно. Исходники:
  `external/office-mcp/`.

Подробности про каждую интеграцию — в её `recommended_mcp/<name>/README.md`.
Общая документация по `install.py` / `run.py` / структуре каталога —
в `recommended_mcp/README.md`.

Для итеративной разработки наших MCP в `external/`:

```bash
python recommended_mcp/install.py --editable
```

### Ручная установка (для MCP не из `recommended_mcp/`)

Если нужный MCP не входит в `recommended_mcp/` — ставь как обычный пакет
и подключай через `mcp-servers:`. Пример с DDGS-поиском:

```bash
python3 -m pip install ddgs-mcp
ddgs-mcp --http
```

В `config.yml` агента укажи нужный транспорт (`http`, `stream_http` и т.д.)
и endpoint подключения (см. раздел [MCP-серверы](#mcp-серверы) выше).

## Где gc-cli хранит runtime-данные

Кросс-платформенная раскладка. По умолчанию:

| ОС | Логи / треды / swarm | Cache (пока не используется)          | Config |
|---|---|---------------------------------------|---|
| Linux | `~/.local/state/gc/projects/<slug>/` | `~/.cache/gc/` *(резерв)*             | `~/.config/gc/` |
| macOS | `~/.local/state/gc/projects/<slug>/` *(как Linux)* | `~/.cache/gc/` *(резерв)*             | `~/.config/gc/` |
| Windows | `%USERPROFILE%\.gc\projects\<slug>\` | `%USERPROFILE%\.gc\cache\` *(резерв)* | `%USERPROFILE%\.gc\` |

`<slug>` — путь к проекту с заменой `/`, `\`, `:` на `-`, в стиле `~/.claude/projects/`.

Override через переменные окружения: `GC_HOME` (корневой), `GC_STATE_DIR` / `GC_CONFIG_DIR` / `GC_CACHE_DIR` / `GC_DATA_DIR` (точечные). На Linux/macOS дополнительно работают `XDG_STATE_HOME` / `XDG_CONFIG_HOME` / `XDG_CACHE_HOME` / `XDG_DATA_HOME`.

Каталог «Config» — это где `gc-cli` ищет базовый `config.yml` (tier между `--config` и пакетным дефолтом; подробнее — [«Где ищется базовый config.yml»](#конфиг-клиента) в начале страницы).

Каталог «Cache» — зарезервирован в кросс-платформенной XDG-раскладке, но `gc-cli` **пока не использует файловый кэш**: путь вычисляется (и переопределяется `GC_CACHE_DIR` / `XDG_CACHE_HOME`), но каталог не создаётся и в него ничего не пишется.

См. также пояснения в `demo_config.yml` (секция `paths`).

## Project local config (опционально)

Если в корне проекта есть файл `<your-repo>/.gc/config.yml`, gc-cli мерджит его поверх глобального `config.yml` через layered loading:

- **scalar** (число, строка, bool) — project переопределяет global.
- **dict** — рекурсивный deep merge: project расширяет/переопределяет ключи внутри.
- **list / array** — конкатенация + dedup: project только **расширяет** список, не сбрасывает (важно для security-полей вроде `agent.stop_tools` или `command_moderation.url_policy.url_blacklist`).

Пример проектного `<your-repo>/.gc/config.yml`:

```yaml
agent:
  max_steps: 200             # этот проект — длиннее цепочки рассуждений
  stop_tools: [browse_url]    # добавить локальный запрет (к глобальному списку)
mcp:
  servers:
    my_local_db:               # MCP только для этого проекта
      transport: stdio
      command: psql
```

Файл `.gc/config.yml` следует той же схеме, что и глобальный `config.yml` — указывайте только те поля, которые хотите переопределить или дополнить. Папка `.gc/` создаётся автоматически при первом запуске `gc-cli` (та же папка, что и для project-скиллов).

CLI-флаги (`--max_steps 999` и т.п.) перебивают и global, и project. Файл опционален; если его нет — используется только global.

Если через `--config` явно передан тот же файл, что и `<repo>/.gc/config.yml` — gc-cli применяет его как обычный config без второго слоя (особый случай для запусков с явным путём).
