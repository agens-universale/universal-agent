# Хранилище тредов: как подставить своё

История диалога по умолчанию лежит в `data_*.jsonl` рядом с `meta_*.json`. Это
реализация, а не устройство ядра: встраивающий может положить тред в базу и
передать своё хранилище агенту при создании.

Через конфиг оно **не настраивается** и настраиваться не может — хранилище
передаётся объектом. В YAML есть только `paths.threads_data_path`, и он нужен
единственному хранилищу, которое работает с файлами.

---

## Где что лежит

| файл | что |
|---|---|
| `gc_core/thread_store_base.py` | `ThreadStoreBase` / `AsyncThreadStoreBase` — **единственное объявление контракта**: ABC с 11 абстрактными методами и общими инвариантами. Отсюда же выводится `CONTRACT_METHODS` |
| `gc_core/thread_store_types.py` | Типы обмена: `ThreadState`, `SubagentTraceRecord`, `TraceKind`, `MessageKey` |
| `gc_core/thread_store_async.py` | `AsyncThreadStore` — те же 11 с приставкой `a`. Плюс `SyncThreadStoreAdapter` и фабрика `athread_store()` |
| `gc_core/thread_store_file.py` | `FileThreadStore` — реализация поверх `data_*.jsonl`. Образец для своей |
| `gc_core/thread_store.py` | файловый слой и `ThreadSession`. Внутренности; встраивающему сюда не нужно |
| `gc_testkit/memory_thread_store.py` | `MemoryThreadStore` — вторая реализация, целиком в памяти. Второй образец, 230 строк |
| `gc_testkit/thread_store_conformance.py` | `assert_conforms` / `assert_conforms_async` — проверка своей реализации |

### Наследовать базу или совпасть по сигнатурам

Оба пути рабочие, но по умолчанию — **наследуйте `ThreadStoreBase`**:

```python
from gc_core.thread_store_base import ThreadStoreBase


class PostgresThreadStore(ThreadStoreBase):
    def load_messages(self, system_id, thread_id): ...

    # ...остальные десять
```

Что это даёт помимо автодополнения:

* **отказ на месте.** Забыли метод — объект не создастся, `TypeError` назовёт
  какой. У протокола это обнаруживалось поздно: молчали все, пока агент не
  доходил до проводки;
* **общие инварианты даром** — `stamp_meta`, `apply_runtime_flag`,
  `merge_runtime_meta`. Это не удобства, а поведение, одинаковое для всех
  реализаций и не выводимое из сигнатур. Пока держать его было негде, две
  НАШИ реализации разъехались ровно на нём: файловая штамповала meta на каждом
  пути записи, in-memory — только в `save_meta`. Обе проходили конформанс,
  потому что и он проверял штампы лишь у `save_meta`. Цена ошибки для чужого
  хранилища: без `state_schema_version` следующий прогон откажется читать
  тред, и заметно это на ВТОРОМ прогоне — первый проходит нормально.

Наследование не обязательно: хранилище, совпавшее по именам и сигнатурам,
принимается как прежде. Это нужно тем, кому наследовать нельзя, — объекту из
чужого DI-контейнера, обёртке на `__getattr__`. Проверка при проводке
(`athread_store`) структурная и на наследование не смотрит; закреплено тестом.

Раньше для этого пути существовал ещё и `ThreadStore` (`Protocol`) — те же
одиннадцать методов второй копией, — и отдельный кортеж имён третьей. **Копии
сняты**: контракт объявлен один раз, абстрактными методами `ThreadStoreBase`,
а список имён `CONTRACT_METHODS` выводится из них же. Копии никто не сверял, а
расходятся они молча: метод, добавленный в ABC и забытый в кортеже, ядро
начало бы звать у хранилищ, которые о нём не знают.

Что изменилось на практике: утиный путь **работает как раньше** (проводка
структурная), но аннотироваться такому объекту больше не против чего. Нужен
тип в сигнатурах — наследуйте `ThreadStoreBase`. Оба свойства стережёт
`test_thread_store_one_contract.py`.

Оговорка про `FsBackend`, которая раньше стояла здесь как довод против ABC:
он и правда ABC с тридцатью абстрактными методами, и добавить туда
async-двойники было бы больно. Но дело не в ABC как таковом, а в размере
контракта — одиннадцать методов против тридцати, — и в том, что у `FsBackend`
нет ни конформанс-набора, ни проверки при проводке.

## Как прокинуть store

Пять точек, все проверены. Обычному встраивающему нужна первая.

### 1. SDK — `AsyncAgent.create`

```python
from gc_core.aio import AsyncAgent

agent = await AsyncAgent.create(cfg, thread_store=MyStore())
answer = await agent.run("привет", thread_id="t1")
```

Дальше ничего делать не нужно: хранилище доезжает до `RunContext`, оттуда до
`ThreadSession`, и весь ввод-вывод треда идёт через него.

### 2. Контекст напрямую

```python
from gc_core.run_context import acreate_run_context

ctx = await acreate_run_context(cfg, thread_store=MyStore())
```

### 3. Исполнитель

```python
from gc_core.agent_executor import AgentExecutor

executor = AgentExecutor(
    ctx
)  # берёт хранилище из ctx, отдельно передавать не нужно
```

### 4. Сессия треда — если работаете с историей мимо агента

```python
from gc_core.thread_store import ThreadSession

session = await ThreadSession.afrom_config(
    config_dict=cfg,
    system_id="cli",
    thread_id="t1",
    store=MyStore(),
)
```

Ядро зовёт только эту форму (`agent_executor`, `manual_compaction`), и она
ЕДИНСТВЕННАЯ: синхронного `from_config` больше нет. Он был удобством для
вызывающего без своего loop, но из-под живого loop заводил второй и морозил
поток, а производственных вызывающих у него не было ни одного. Нужен вход без
loop — поднимайте его сами: `asyncio.run(ThreadSession.afrom_config(...))`.

Это не касается КОНТРАКТА хранилища: одиннадцать синхронных методов
`ThreadStoreBase` на месте, и обещание «своё хранилище можно синхронное»
в силе.

### 5. `system_id` — не забыть

Читать тред надо тем же `system_id`, каким его писали. У SDK он **`"sdk"`**, у
CLI — `"cli"`:

```python
await agent.run("привет", thread_id="t1")
store.load_messages("sdk", "t1")  # не "cli"
```

Частая ошибка при первом чтении из своего хранилища: тред «пустой», хотя всё
записано.

И `thread_id` — только латинские буквы, цифры, `_` и `-`. Кириллица падает
`ValueError` на валидации.

## Что реализовать: одиннадцать методов

```python
class MyThreadStore:
    # чтение
    def load_messages(self, system_id, thread_id) -> list[dict]: ...
    def load_thread_state(self, system_id, thread_id) -> ThreadState: ...
    def load_meta(self, system_id, thread_id) -> dict: ...

    # запись
    def append_messages(
        self, system_id, thread_id, messages, *, known_keys=None, start_seq=0
    ) -> int: ...
    def save_meta(self, system_id, thread_id, meta) -> None: ...
    def patch_runtime_flag(
        self, system_id, thread_id, flag, *, active, session_meta=None
    ) -> None: ...
    def update_runtime_meta(self, system_id, thread_id, patch) -> None: ...
    def discard_message(self, system_id, thread_id, message_id) -> bool: ...
    def reset(self, system_id, thread_id) -> list[str]: ...

    # трассы субагентов
    def append_subagent_trace(
        self,
        system_id,
        thread_id,
        *,
        parent_call_id,
        child_run_id,
        kind,
        payload,
    ) -> SubagentTraceRecord: ...
    def read_subagent_trace(
        self, system_id, thread_id
    ) -> list[SubagentTraceRecord]: ...
```

Образцы: `FileThreadStore` (185 строк) и `MemoryThreadStore` (233 строки).

## Проверить себя

```python
from gc_testkit.thread_store_conformance import assert_conforms


def test_my_store():
    assert_conforms(lambda: MyThreadStore(dsn=TEST_DSN))
```

Пятнадцать проверок: три структурных (методы на месте, синхронны, сигнатуры
совпали) и двенадцать поведенческих. Отказ называет, что именно разошлось.

**`isinstance(store, ThreadStore)` гейтом не является.** `runtime_checkable`
сверяет только наличие атрибутов: у класса, где все одиннадцать методов
объявлены `async def`, проверка проходит, а восемь свойств нарушены. Ошибка
симметрична — законное прокси-хранилище на `__getattr__` `isinstance` не
пройдёт, потому что в 3.12 проверка идёт через `getattr_static`.

## Восемь свойств, которые легко нарушить

Это не общие пожелания. Каждое — место, где разошлись **две наши собственные**
реализации, оставаясь зелёными на всём прежнем наборе тестов.

**Идемпотентность `append_messages`.** Батч персистится ДВАЖДЫ — сразу после
исполнения тулов и ещё раз на выходе цикла. Повтор не должен задваивать
историю.

**`known_keys` мутируется НА МЕСТЕ и только записанным.** Вызывающий держит тот
же объект и снимает снимок ДО вызова, чтобы по приросту понять, что записалось.
Защитная копия — совершенно естественное решение — молча задваивает историю на
следующем батче. Досыпать туда заодно всё содержимое треда тоже нельзя: это
ломает ту же разницу с другой стороны.

**Третий элемент `load_thread_state` — НОМЕР последнего `seq`, а не количество
записей.** Расходятся после `discard_message`: удалили среднее из трёх —
количество 2, номер по-прежнему 3. Оба `int`, и подмену не поймает ни одна
проверка типов. `seq` — это ordering key хвостового читателя TUI: на записи с
меньшим номером тот отдаёт `stream_reset` и перестраивает живой трейс.

**`id` проставляется на чтении.** Без него ключ идемпотентности уходит в ветку
`payload:<json>` — нестабильную к любому изменению формы сообщения. Готовая
функция: `gc_core.thread_store.ensure_message_id`.

**Meta штампуется при записи:** `state_schema_version`, `created_at`,
`updated_at`. Самое коварное из восьми: без версии схемы следующий прогон
ОТКАЖЕТСЯ читать тред (`StateSchemaError`), но ПЕРВЫЙ проходит нормально —
юнит-тесты первого прогона такое не ловят. Готовое значение даёт
`ThreadMetaMapper.ensure_v2_meta(meta)`.

**Снятие последнего флага убирает секцию `runtime` ЦЕЛИКОМ.** «Нет флагов» и
«пустой словарь» обязаны читаться одинаково: расхождение означало бы, что
переезд на другое хранилище меняет форму meta, а её читают и TUI, и сервер.

**Запись трассы субагента — шесть полей**, включая `ts` и `seq`, которые
проставляет хранилище, а не вызывающий.

**Форма meta ОТКРЫТАЯ.** Секцией `tui` владеет другой процесс, сервер отдаёт
meta наружу дословно — незнакомые ключи хранятся как есть, а не отбрасываются.

Отсутствующий тред читается пустотой, а не исключением.

## Асинхронный клиент

`ThreadStore` синхронный, и это правильный контракт по умолчанию: файлы и
локальная база отвечают за микросекунды. Но у `redis.asyncio` и `asyncpg`
синхронного клиента нет вовсе.

```python
class RedisThreadStore:
    async def aload_messages(self, system_id, thread_id): ...
    async def aload_thread_state(
        self, system_id, thread_id
    ) -> ThreadState: ...

    # ...остальные девять с приставкой a


agent = await AsyncAgent.create(cfg, thread_store=RedisThreadStore(url))
```

Передаётся туда же. Ядро само разбирается — вся развилка в одной функции
(`gc_core.thread_store_async.athread_store`):

```python
if is_async_thread_store(store):
    return store  # нативное — ждём напрямую
return SyncThreadStoreAdapter(store)  # синхронное — заворачиваем
```

Внутри ядро знает только асинхронный порт и всюду пишет
`await port.aload_meta(...)`. Так у async-пути не может быть «второго,
забытого» вызывающего — он единственный.

Проверить себя: `assert_conforms_async(factory)` — тот же набор свойств.
Свойства от корутинности не зависят, поэтому набор один на обе формы.

**Смешивать формы нельзя.** Либо все одиннадцать методов синхронные, либо все
одиннадцать корутинные. Половинчатая реализация отвергается при создании
агента:

```
Половинчатое: часть методов объявлена async def под СИНХРОННЫМИ именами: load_meta.
  Смешивать нельзя: синхронные вызывающие отбросят корутину без ошибки,
  и часть записей треда потеряется молча.
```

## Синхронное СЕТЕВОЕ хранилище: будет работать, но

Адаптер зовёт синхронные методы **инлайн**, не через поток — и это не
недосмотр. `asyncio.to_thread` здесь ошибка, проверенная запуском:
`save_thread_meta` пишет во фиксированный путь `{meta_path}.tmp`, и два потока
на одном треде дают `FileNotFoundError`; а дефолтный пул общий с синхронными
чужими тулами.

Значит адаптер даёт совместимость, но неблокирующим хранилище не делает: цикл
честно стоит на каждом обращении. Замеренный закон:

```
худший разрыв цикла ≈ 16 × RTT + 20 мс
```

25 обращений за прогон ложатся в два куска подряд без возврата в цикл — 11 и
14 обращений; закон — по крупнейшему. Замерено прогретым пульсом приёмки
(`gc_testkit.LoopPulse`) на ходах `test_acceptance_sdk_thread_store.py` с
настоящим `exec_sleep`; судит `gc_testkit.assert_loop_was_free`:

| RTT на вызов | худший разрыв | разрывов от 20 мс | приёмка |
|---|---|---|---|
| 0 (файлы, память) | 14–17 мс | 0 | проходит |
| 1 мс | 28–38 мс | 2 | **не проходит**: два пропуска при допуске в один |
| 5 мс (локальный Redis) | ~100 мс | 2 | **не проходит**: два пропуска |
| 10 мс | ~185 мс | 2 | **не проходит**: и потолок 150 мс |
| 20 мс (облако, другая зона) | ~340 мс | 2 | **не проходит**: и потолок |

Числа машинозависимы. Потолок пробивается около 8 мс на вызов, но приёмка
отвергает синхронное хранилище раньше — по правилу пропусков: уже при 1 мс оба
куска длиннее 20 мс. Прежняя таблица («5 мс — 79 мс, проходит») снималась
пульсом, не видевшим начала хода, и судила по одному худшему разрыву.

Отличить быстрое локальное хранилище от сетевого статически нельзя, поэтому
адаптер меряет первые восемь обращений и один раз пишет предупреждение:

```
thread_store_blocking_loop store=MyStore slowest_method=append_messages
    median_ms=6.2 threshold_ms=2 samples=8
    hint=implement_AsyncThreadStore_for_network_backed_storage
```

Судит по **медиане** окна, а не по отдельному вызову: у `FileThreadStore`
медиана 0,29 мс при отдельных всплесках до 2,8 мс (запись меты, конкуренция за
диск между агентами), и порог по одному вызову советовал владельцу обычных
файлов переписать хранилище на асинхронное.

## Необязательная способность: архив перед компакцией

Если у хранилища есть метод `archive_and_replace(system_id, thread_id,
messages)` — или его асинхронная форма `aarchive_and_replace`, — компакция
зовёт его. Если нет, история замещается через `replace_messages` — отдельной
операцией вместо `reset` + `append_messages`.

Разница существенная: `reset` по контракту сносит и трассу субагентов, а между
ним и `save_meta` было окно, в котором meta отсутствовала целиком — падение
процесса там теряло `created_at`, `tui` и `shared`.

`replace_messages` в контракт НЕ входит: он объявлен умолчанием базы, а
контракт — это абстрактные методы. У хранилища, принятого «по сигнатурам», его
может не быть вовсе; тогда компакция идёт прежней парой, но трассу спасает
сама — читает до `reset` и возвращает после, предупреждая об этом в лог. Цена
спасения — штампы: `append_subagent_trace` ставит свежее время и следующий
номер, так что вся трасса получит дату компакции. Хранилищу, которое умеет
заместить историю одной операцией (SQL `DELETE … INSERT` в транзакции), стоит
объявить `replace_messages` и в этот путь не попадать.

Так и задумано: «отложить прежнюю историю рядом» осмысленно для файлов, а у
базы это либо отдельная таблица, либо не нужно вовсе. В основные одиннадцать
метод не входит — реализация без него полноценна.

## Картинки треда

В историю картинка не пишется: у сообщения есть ключ `attachments` — ссылки на
нормализованные файлы (хеш, mime, размеры, путь; `source` — откуда картинка: полный
путь исходного файла или `clipboard`), а `content` остаётся строкой с
плашками `[Изображение #N]`. Хранилищу для этого ничего делать не нужно: форма
записи та же, ключ едет в `payload` как есть.

Номер `N` сквозной по треду. Счётчик — `meta.runtime.image_seq`, секция ядра: при
записи батча сессия (`ThreadSession`, как и `live_*`) поднимает его до наибольшего
номера среди новых сообщений и только вверх. Компакция уносит записи в архив, но не
meta, откат реплики удаляет запись, но не номер, — счётчик не уменьшается. Ключ
появляется у треда с первой картинкой; фронт выдаёт следующий номер от него.

Файлы лежат в `<threads_dir>/images/` плоско, по образцу `data_`/`meta_`/`touched_`:
`<system>_<thread>_<sha16>.png` или `.jpg` (имя короткое из-за MAX_PATH на Windows).
У хранилища без каталога (`threads_dir == ""`) — во временном каталоге системы,
`gc-images-<uid или имя пользователя>/`; после перезапуска такие ссылки ведут в пустоту, и модель получает на
месте картинки записку «file unavailable». На POSIX этот каталог обязан быть своим: его создаёт сам агент с правами
только владельцу; занятое другим пользователем имя (его каталог или ссылка в общем `/tmp`) не принимается — тогда
корень — свой приватный каталог процесса, иначе охрана чтения пустила бы агента по чужой ссылке без вопроса.

Карман процесса — `images/_staging/<pid>/`: там вставленная картинка ждёт отправки,
там же живёт картинка `gc-cli --image` без `-t`. Копию в тред делает ядро, когда
сообщение получает тред: на старте хода — после сброса `-n`, иначе сброс снёс бы
свежую копию; сообщение посреди хода — когда агент его принимает. Карман чистится
на выходе процесса (в TUI — и при аварийном выходе, когда умер терминал: хуком atexit) и
на старте следующего TUI или CLI (каталоги мёртвых процессов).

Картинки живут столько же, сколько тред: `delete_thread` (удаление сессии в TUI,
серверный уборщик) и сброс `-n` (`reset_thread_files`) удаляют
`images/<system>_<thread>_*`. Компакция их не трогает — она идёт через
`archive_and_replace`, и архив `__pre_summary__` ссылается на те же файлы. В swarm
картинки агента живут в песочнице (`/work/.gc/threads/images`) и уходят вместе с
ней. Своё хранилище без каталога картинки не удаляет: его `reset` о них не знает.

---

## Единственный ключ конфига

```yaml
paths:
  threads_data_path: /абсолютный/путь
```

Нужен ТОЛЬКО файловому хранилищу и обязан быть абсолютным. Своей реализации он
не нужен: `ThreadSession` берёт каталог как `getattr(store, "threads_dir", "")`,
и у хранилища без файлов там пустая строка.

CLI и TUI делят этот путь намеренно — тред, начатый в `gc-cli -t …`,
открывается в TUI. В swarm он перекрывается последним слоем конфига
(см. [swarm.md](swarm.md)).
