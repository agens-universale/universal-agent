# Session context & status UX — Design

**Дата:** 2026-06-23
**Статус:** согласовано, готово к плану
**Ветка:** feat/agent-instructions-and-gc-guard

## Цель

Три связанные TUI-доработки вокруг состояния сессии (делят шапку + `meta` + суммаризацию):

1. **Индикатор заполненности контекста** — сколько осталось до следующей авто-суммаризации.
2. **Команда `/compact`** — принудительно сжать сессию, не дожидаясь порога (с антиспам-защитой по контенту).
3. **Точные статусы сессии** — различать «работает / ждёт ответа / завершил / прервал ты / упал» цветом и подписью (сейчас всё кроме running/asking → серый `[stopped]`).

Все три — слой `src/tui/` + одна точка в executor (персист метрик/терминального статуса в `meta`). Server/swarm не трогаем.

---

## Компонент 1 — Индикатор контекста

### Поведение
- **Размещение:** хвост левого сегмента шапки, после чипа модели:
  `Сессия: 25d6c08e  [running]  модель: M · chat  ·  контекст ▓▓▓▓▓▓░░░░ 58%`
- **Формат:** слово `контекст` + бар (8 ячеек, `▓` заполнено / `░` пусто) + процент. Без абсолютного счётчика.
- **Цвет порогами:** `<60%` зелёный (`OK`), `60–90%` золотистый (`RUN_COLOR` — тот же amber, что у `[running]` и плашки «думаю»), `>90%` красный (`ERR`).
- **Смысл:** `fill = round(100 * context_chars / context_threshold)`, где `context_threshold = chat_completions_summary_trigger_chars`, `context_chars = calc_history_chars_for_trigger(state.messages)`. При `fill ≥ 100` показываем `100%` красным (сам акт сжатия отражает нижняя плашка «сжимаю контекст…»).
- **Скрыт**, когда: `backend_api_mode != chat_completions`, либо `context_threshold <= 0`, либо метрик нет в `meta` (старый тред / ещё не было шага).

### Данные (single source of truth)
Executor пишет в `meta` две метрики при персисте треда (точка, где уже формируется meta-payload — `persistence/thread_meta_mapper` → `state_repository`): `context_chars`, `context_threshold`. TUI читает их в `_poll_active` (тик 250 мс) через `file_store.get_task_meta` и перерисовывает шапку. TUI **не** дублирует расчёт объёма — берёт готовое из `meta`.

> Почему meta, а не пересчёт в TUI: TUI видит тред через jsonl-поллинг, а не `state.messages`; единственный, кто знает каноничный trigger-volume, — executor (он же считает его для порога). Дублировать `calc_history_chars_for_trigger` на стороне TUI = второй источник истины и расхождения.

## Компонент 2 — Команда `/compact` (алиас `/сжать`)

### Поведение
Принудительная суммаризация текущей сессии «здесь и сейчас», не дожидаясь порога.

- Регистрируется в реестре команд (`src/tui/commands.py`) с описанием «сжать контекст сессии сейчас», алиас `/сжать`.
- Выполнение **off-thread** (как обычный прогон): worker-поток вызывает существующий `run_summary_compaction(ctx, state, trigger_reason="manual", …)` на `ctx`/`state` активного runner'а; на время сжатия взводится флаг `tui_summarizing` → нижняя плашка показывает «сжимаю контекст…». После — трейс реконсилит новый маркер «контекст сжат» (механика уже есть).

### Гарды (проверяются в `_cmd_compact` до запуска)
1. **Режим:** только `chat_completions`. Иначе сообщение в трейс: «/compact недоступен в режиме responses (суммаризацию ведёт бэкенд)».
2. **Простой:** только когда нет активного прогона. Если статус `[running]`/`[asking]` → «/compact: дождитесь паузы или остановите (/stop)».
3. **Антиспам по контенту:** отказ, если `context_chars < 0.20 * context_threshold`. Сообщение: «/compact: контекст ещё небольшой (NN% порога) — сжимать нечего». Объективно и без таймера: после сжатия объём падает до preserved-batch (сводка + последние шаги) → повторный `/compact` сразу естественно отклоняется тем же правилом. Метрики берутся из тех же `meta`-полей, что и индикатор.

Нет активной задачи / нет runner'а → «/compact: нет активной сессии».

### Механика runner
`AgentRunner.compact_now()` — публичный метод: если worker занят → False; иначе спавнит daemon-поток, который вызывает `run_summary_compaction` на `self._executor`/`state`, выставляя/снимая `tui_summarizing` в `meta` и персистя результат. Ошибка → через `_on_error` (как у `run`).

## Компонент 3 — Статусы сессии

### Набор (EN-подписи)
**Живые** (из рантайма, приоритет сверху вниз):
| статус | цвет | когда |
|---|---|---|
| `[running]` | золотистый (`RUN_COLOR`) | агент активно работает |
| `[asking]` | teal (акцент confirm-баннера) | ждёт твоего ответа: ask_human **или** confirm |

**Терминальные** (пишутся в `meta.status`, видны после завершения и при переоткрытии сессии):
| статус | цвет | когда |
|---|---|---|
| `[completed]` | зелёный (`OK`) | завершил ход штатно (turn_finish / submit_solution) |
| `[stopped]` | серый (`DIM`) | прервал ты (Ctrl+C / /stop) посреди работы |
| `[failed]` | красный (`ERR`) | прогон упал (рантайм / обрыв бэкенда) |

`compacting` — **не** отдельный статус: остаётся `[running]`, факт сжатия показывает нижняя плашка.

### Деривация и персист
- **Живые** — как сейчас: `ask_human_state → [asking]`; `runner.is_running() → [running]`.
- **Терминальные** — исход прогона фиксируется в worker-потоке по завершении `_target`: `_stop_requested → "stopped"`; пойманное исключение → `"failed"`; иначе → `"completed"`. Исход персистится в `meta.status` (через `file_store.write_task_meta` / executor-персист — точную точку определяет план), чтобы при переоткрытии сессии бейдж был корректным. Конкретно: `completed`/`stopped` знает executor (нормальное завершение vs `stop_run`), `failed` — ловит AgentRunner (`_on_error`).
- **Бейдж** (`_task_status_badge`): живые приоритетнее; иначе — из `meta.status` (маппинг `running→[running]`, `completed→[completed]`, `failed`/`unknown_failed→[failed]`, прочее/пусто→`[stopped]`).

### Цвет бейджа
Новый чистый хелпер презентационного слоя (`src/tui/services/`): `status_badge_style(badge: str) -> str` → цвет из палитры. Шапка рендерит бейдж как rich-сегмент с этим цветом (сейчас бейдж — простой текст без цвета). Хелпер используется и в шапке, и (при необходимости) в экране сессий.

### Охват
Только TUI-бейдж + персист терминального статуса из TUI/CLI-рантайма. Server (`completed`/`failed`/`unknown_failed`) и swarm (`lifecycle.py`) — свою семантику `meta.status` сохраняют; маппинг бейджа их корректно отображает (`unknown_failed → [failed]`), но их код не меняем.

## Тестирование (pytest; TUI — `uv run pytest`)

1. **Индикатор:** `fill→(проценты, цвет)` табличный (0/59 зелёный · 60/90 золотистый · 91/100/над-порогом красный); видимость (`responses`/threshold=0/нет метрик → скрыт; chat+метрики → показан); рендер сегмента шапки содержит `контекст` + `NN%`.
2. **Статусы:** маппинг `meta.status`+живое-состояние → бейдж (running/asking/completed/stopped/failed); `status_badge_style` → правильный цвет; AgentRunner-исход (`stop_requested→stopped`, исключение→failed, норм→completed) персистится в `meta`.
3. **`/compact`:** реестр содержит `compact` (+алиас); guard режима (responses→отказ); guard простоя (running→отказ); content-guard (объём <20% порога → отказ с NN%, ≥20% → запуск); `compact_now` спавнит сжатие и взводит `tui_summarizing`.
4. Где трогаем суммаризацию — прогон `test_summary_*`, `test_thread_summarizer*`.

## Слои и ответственность
- Форматирование индикатора, маппинг/цвет статусов — `src/tui/services/` (чистая презентация).
- Чтение метрик/статуса — `_poll_active`/`_task_status_badge`/шапка в `src/tui/screens/main.py`.
- `compact_now` — `src/tui/services/agent_runner.py`; вызывает существующий `run_summary_compaction` (домен суммаризации не дублируем).
- Персист `context_chars`/`context_threshold`/терминального `meta.status` — в executor/координаторе, в точке, где `meta` уже пишется.
- `/compact` оркестрация — `_cmd_compact` в `main.py` (контроллерный слой TUI).

## Вне scope
- Изменение порогов/логики самой суммаризации (`run_summary_coordinator`) — только читаем метрики и зовём существующий compaction.
- Статусы server/swarm — не трогаем.
- Индикатор в `responses`-режиме (скрыт) — отдельная идея «оценки размера без порога» отклонена (вводила бы в заблуждение).
- Таймерный кулдаун на `/compact` — отклонён в пользу content-guard.
