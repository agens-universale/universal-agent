# Дизайн: prose-first унификация рендера ответа (стрим ↔ финал)

Дата: 2026-06-26
Статус: дизайн (ожидает ревью)

## Проблема

После V1 (прогрессивный показ ответа) на живых прогонах видны **два расхождения**
между стримом и финальной (канонической) версией ответа:

1. **Пустые строки.** Стрим (`render_stream_answer`) хранит пустые строки между
   абзацами (читаемо); финал (`render_block` → по-строчные `TraceRow`) их **роняет**
   ([markdown_render.py:117-119](../../src/tui/services/markdown_render.py#L117)) →
   на финале абзацы схлопываются.
2. **Отступ.** Стрим — один `StreamBlock` (Static без колонки префикса) → flush-left,
   без висячего отступа. Финал — `TraceRow` (двух-колоночный: `● ` + content-колонка с
   авто-wrap и hanging indent) → на финале текст «сдвигается» вправо и получает `● `.

Корень обоих — **два разных прозовых пути** (стрим vs финал), которые расходятся.
Цель: единый прозовый рендер, чтобы для прозы на финале **не было ни одного визуального
изменения** (вариант A — полный паритет с первого токена).

## Граница (prose-first)

Унифицируем **только прозовый путь** (контент + хост). Код-блоки и таблицы остаются
отдельными виджетами (плоский текст в стриме → бокс/сетка на финале — согласованная
prose-first граница; полную parity для них оставляем на будущее). Reasoning-«глазок»
`⠇ …` (режим `answer_reasoning`) — не трогаем, это отдельная сущность.

## Решения

- **Вариант A** — полный паритет с первого токена: стрим-проза сразу с `● ` + висячим
  отступом + пустыми строками, идентично финалу.
- **Переименовать** `render_stream_answer` → `render_prose` (он становится общим, больше
  не «stream-only»). Семантика без изменений (blank-preserving + inline `**bold**`/
  `` `code` ``/heading/bullet; fenced/таблицы — plain).
- Хост для прозы в обоих контекстах — существующий `TraceRow` (его двух-колоночный
  layout и даёт правильный отступ).

## Архитектура и компоненты

### 1. `render_prose` — единый источник истины контента прозы
`src/tui/services/markdown_render.py`: переименовать `render_stream_answer` → `render_prose`
(тело без изменений). Используется И стримом, И финалом.

### 2. `TraceRow.set_content` — обновление контента после монтирования
`src/tui/widgets/trace_row.py`: добавить `set_content(self, content)` (зеркало
существующего `set_prefix`) — обновляет `.trace-content` Static. Нужно для пер-тик
апдейта прозы в стриме.

### 3. Стрим-сторона (`src/tui/screens/main.py`, стрим-ветка `_poll_active`)
- `kind=="answer"` → эфемерная строка ответа = `TraceRow(prefix="● ",
  content=render_prose(clean), kind_class="line-agent", focusable=False)`; пер-тик —
  `set_content(render_prose(clean))`.
- `kind=="reasoning"` → как сейчас, `StreamBlock` (muted italic `⠇ …`).
- **Единый эфемерный слот.** Чтобы не плодить пути снятия, ответный `TraceRow` и
  reasoning-`StreamBlock` хранятся в ОДНОМ слоте (текущий `self._stream_block` или
  переименованный `self._stream_widget`); все существующие `_clear_stream_block`/clear-пути
  работают по слоту без изменений (тип-агностично: `.remove()` + слот=None). При смене
  `kind` (редко) слот пересоздаётся под нужный тип.
- Автоскролл (#2, уже реализован) применяется к слоту независимо от типа.

### 4. Финал-сторона (`src/tui/services/trace_render.py::build_block_widgets`) ⚠️ нагруженная
Вместо по-строчных `TraceRow` — группировать **прозовые прогоны**: подряд идущая проза
между code/table-блоками (пустые строки **сохранены внутри прогона**), каждый прогон →
**один** `TraceRow` с `content=render_prose(run_text)`. Code/table-ветки — без изменений.
Префиксы как сейчас: первый прогон — `bullet` (`● `/`· `/`""` по `prose_bullet`/kind),
прогоны после code/table — `  ` (продолжение). Сегментацию «прогон | code | table»
получаем эволюцией `render_block` (единственный потребитель — `build_block_widgets`) или
отдельным сегментатором (решит план).

Затрагивает единообразно всех потребителей `build_block_widgets`: `build_agent_widgets`,
`build_intermediate_widgets`, `ask_human_banner` — всем проза получает сохранённый «воздух».

## Поведение по режимам `stream_display`

- **Стрим-сторона (§3)** касается только режимов, где стрим-ответ показывается
  (`answer`/`answer_reasoning`). В `minimal` стрим-ответный `TraceRow` НЕ монтируется
  (`select_stream_render` → `none`) — во время генерации всё как раньше (индикатор + счётчик).
- **Финал-сторона (§4)** — это каноничный рендер `build_block_widgets`, **общий для всех
  режимов** (+ превью + старые треды). Срабатывает на коммите ответа независимо от
  `stream_display`. Поэтому улучшение прозы (сохранённые пустые строки + `● `-отступ)
  получают ВСЕ режимы, включая `minimal`. Это намеренно: #1 — дефект финального рендера,
  чинится в общем месте → выгода всем; регресса нет (фиксируется snapshot-тестами). Затронут
  только TUI-рендер (CLI/server рисуют иначе — не трогаем).

## Регресс-поверхности (что НЕ сломать)

- **Превью (read-only).** `trace_render._dispatch_readonly` → `build_agent_widgets`/
  `build_intermediate_widgets` → тот же `build_block_widgets`. Паритет превью с главным
  трейсом сохраняется автоматически; покрыть тестом.
- **ask_human-баннер.** `prose_bullet=False` (без `● `) — прогоны прозы тоже без буллета;
  проверить, что баннер не сломан.
- **Все clear-пути эфемерного слота:** шов `_render_event`:804 (mount-then-clear),
  task-switch `_reset_render_state`, idle/terminal, run-not-running, `minimal`-режим
  (`reset_sink=False`). Все должны снимать новый ответный `TraceRow` так же, как раньше
  `StreamBlock` — существующие тесты на это (`test_stream_block_render.py`) мигрировать на
  новый виджет (см. ниже), не ослабляя проверок.
- **Focus/Tab.** Контракт «1 событие = 1 Tab-стоп» (`focusable=not focus_set` — только
  первый виджет события). Прогоны вместо по-строчных строк уменьшают число виджетов, но
  фокус и так был пер-событийный → без регресса; проверить.
- **CSS-маржины/вид.** `.line-agent`/`.line-agent-cont`/`.line-intermediate` и межсобытийные
  отступы — поведение margin на уровне `TraceRow` (kind_class на самом ряду). Переход
  по-строчно→по-прогонно меняет число рядов → **snapshot/структурные тесты** на регресс вида.
- **Нейминг.** `render_stream_answer` → `render_prose`: обновить потребителя
  (`main.py`) и тесты (`tests/tui/test_render_stream_answer.py` → `test_render_prose.py`).

## Критерий паритета и тесты

- **Чистая проза:** стрим-`TraceRow` и финал-`TraceRow` строятся идентично (один
  `render_prose`, один `● `+отступ) → на финале НОЛЬ визуальных изменений.
- **Смешанный ответ:** прозовые части идентичны; код/таблицы «защёлкиваются» в бокс на
  финале (prose-first граница).

Тесты:
- `render_prose` (переименованные существующие): blanks сохранены, inline-стили, fenced
  plain, пустой → пустой.
- `TraceRow.set_content`: обновляет content-Static после монтирования.
- Финальная группировка прогонов: многоабзацный ответ → один `TraceRow` на прогон, пустые
  строки сохранены; ответ с code-блоком → [прогон-`TraceRow`, code-панель, прогон-`TraceRow`].
- **Парити-тест:** для чистой прозы content стрим-ряда == content финал-ряда (оба
  `render_prose(text)`).
- Миграция `test_stream_block_render.py`: answer-режимные тесты → запрос нового ответного
  `TraceRow` (вместо `StreamBlock`), проверка `● ` + контент; reasoning-режимные — остаются
  на `StreamBlock`. Clear-тесты (canonical/task-switch/not-running) → на новый слот.
- Превью-паритет: read-only многоабзацный ответ рендерит прогоны так же, как трейс.
- Регресс: code/table/ask_human/intermediate — вид не изменился (snapshot/структурно).

TUI-тесты — `uv run pytest`.

## Вне scope

- Полная true-parity для **кода/таблиц** (живые боксы по мере стрима / единый renderable) —
  отдельный будущий заход; здесь они остаются «защёлкивающимися» на финале.
- Reasoning-«глазок» `⠇ …` — без изменений.
- Поведение агента/finish-gate/суммаризации — не трогаем.
