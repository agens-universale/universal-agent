# Разбиение на модули: `gc_core` / `gc_cli` / `gc_tui` / `gc_server`

Ядро — SDK с собственным пространством имён; фронтенды `cli`, `tui`, `server` и
рецепты MCP — отдельные дистрибутивы над ним. Раздельная установка профилей сделана
раньше, в 0.4.0, четырьмя манифестами над общим `src/`; переезд её не отменяет, а
добавляет к ней границу имён.

## Что это даёт

Ядро — **SDK**: пакет с собственным пространством имён, который импортируется из
чужого приложения, не конфликтуя с его модулями. Фронтенды (`cli`, `tui`, `server`)
и рецепты MCP — отдельные пакеты-потребители этого SDK.

Это **не** про раздельную установку файлов: она сделана в 0.4.0 четырьмя
манифестами над общим `src/`, без единой правки импортов, и переездом не отменена.

## Зачем

Ядро занимает **45 имён верхнего уровня** в `site-packages`:

```
config  tools  utils  states  security  instructions  constants  backends
persistence  summarize  updater  usage  onboarding  model_picker  app_version
```

Любое приложение со своим `config.py` или пакетом `utils/` конфликтует с
агентом. Namespace-префикс — единственное, что это лечит.

Прочие мотивы отпадают, зафиксировано, чтобы к ним не возвращаться:

| Мотив | Статус |
|---|---|
| Раздельная установка файлов | сделано в 0.4.0 без переезда |
| Размер установки | дают разные зависимости профилей |
| Принудительная граница | даёт разделение дистрибутивов |
| Независимые релизные циклы | даёт разделение дистрибутивов |

## Раскладка

```
universal-agent/
  pyproject.toml                 # мета gc-ua (чисто метаданные) + корень uv-workspace
  packages/core/
    pyproject.toml               # дистрибутив gc-core — БЕЗ [project.scripts]
    src/gc_core/                 # 279 модулей SDK
    assets/                      # prompts/, skills/, config.default.yml
  packages/cli/
    pyproject.toml               # gc-cli   → gc-core, gc-mcp
    src/gc_cli/                  # cli.py, arg_parser.py, onboarding_wizard.py
  packages/tui/
    pyproject.toml               # gc-tui   → gc-core, gc-mcp
    src/gc_tui/                  # экраны, редакторы, diff_tui, голос
  packages/server/
    pyproject.toml               # gc-server → gc-core, gc-mcp
    src/gc_server/               # server.py, rest_api/, swarm/
  packages/mcp/
    pyproject.toml               # gc-mcp   → gc-core
    src/recommended_mcp/         # рецепты MCP + runtime: cli, установка, автозапуск
  packages/testkit/
    pyproject.toml               # gc-testkit — только dev, в колёса не попадает
    src/gc_testkit/              # раскладка, фикстуры, pytest-плагин
  external/                      # сторонние батарейки: vendor/ (MCP), litellm/
  integrations/                  # стенды бенчмарков: harbor/, bench_configs/
  tests/                         # только общерепозиторное: колёса, MCP
```

Наборы тестов лежат в `packages/*/tests` — по одному на дистрибутив.

Каталог называется `packages/`, а не `packaging/`: там теперь лежит код, а не
только манифесты. Хвост в командах установки меняется соответственно —
`#subdirectory=packages/tui`.

### Дистрибутивы

| Дистрибутив | Пакеты | Зависит от | Команды |
|---|---|---|---|
| `gc-core` | `gc_core` | — | **нет** |
| `gc-cli` | `gc_cli` | `gc-core`, `gc-mcp` | `gc-cli` |
| `gc-tui` | `gc_tui` | `gc-core`, `gc-mcp` | `gc-ua`, `gc-voice` |
| `gc-server` | `gc_server` | `gc-core`, `gc-mcp` | `gc-serve` |
| `gc-mcp` | `recommended_mcp` | `gc-core` | `gc-mcp`, `gc-mcp-install` |
| `gc-ua` (мета) | — | все четыре | все шесть |

Каждый профиль объявляет ТОЛЬКО свою команду: имя команды принадлежит одному
дистрибутиву, иначе два профиля не ставятся рядом. Подробности и цена ошибки —
`docs/packaging.md`.

`gc-core` — библиотека, поэтому **не объявляет точек входа** и ставится иначе:

```bash
uv pip install "gc-core @ git+URL#subdirectory=packages/core"   # в своё приложение
uv tool install "gc-cli @ git+URL#subdirectory=packages/cli"    # как инструмент
```

Фронтенды друг от друга не зависят: проверено — `cli`, `arg_parser` и
`onboarding_wizard` не импортирует никто, кроме самих себя.

### Границы, посчитанные по графу импортов

| Пакет | Модулей | Что внутри |
|---|---|---|
| `gc_core` | 279 | 45 имён верхнего уровня: конфиг, тулы, память, безопасность, MCP-клиент |
| `gc_cli` | 4 | `cli`, `arg_parser`, `onboarding_wizard` |
| `gc_tui` | 137 | экраны, редакторы, `diff_tui`, `voice`, `voice_runtime` |
| `gc_server` | 15 | `server`, `server_cleanup_threads`, `rest_api`, `swarm` |
| `recommended_mcp` | 14 | рецепты и `runtime/`: cli, установка, автозапуск daemon'ов |

### Осознанный долг: оболочка приложения в SDK

Десять пакетов нужны cli и tui, но не нужны server:

```
onboarding, onboarding_config_writer, onboarding_fields, updater, upgrade_gate,
app_version, config_sync, config_raw, config_origin, model_picker
```

Это мастер первого запуска, самообновление и редактирование конфига — не логика
агента. **Решено класть их в `gc_core`** (2026-08-17), чтобы не плодить пятый
пакет. Цена: SDK носит механизм самообновления через `uv tool install`, который
встраивающему не нужен.

Долг ограничен этими десятью. Автозапуск MCP-daemon'ов в него НЕ входит: он живёт
у рецептов (`recommended_mcp.runtime.daemon_autostart`), потому что потребителей в
ядре у него нет — зовут его `gc_cli` и `gc_tui`.

Шимов точек входа в ядре тоже нет. Команда целится прямо в свой пакет
(`gc-ua = "gc_tui:main"`), а не в охранника, который поймал бы отсутствие профиля:
после разведения имён команд «команда есть, а пакета нет» в здоровой установке не
случается. Свою третью сторону охраняет тот, кому она принадлежит: `gc_tui.main()`
сам ловит отсутствие `textual` и печатает однострочную подсказку
(`packages/tui/tests/test_runner_no_textual.py`). Цена решения: у `gc-cli` и
`gc-serve` вручную сломанная установка даёт трейсбек, а не строку с командой.

Если долг начнёт мешать, выделяется пакет `gc_app` — граница посчитана и проходит
ровно по этим десяти пакетам.

### Ассеты

В репозитории ассеты лежат в `packages/core/assets/`, в колесе — внутри пакета,
в `gc_core/assets/`. `bundled_root()` знает обе раскладки и считает путь от
своего `__file__`.

Внутрь пакета они переехали 18.08.2026, вторым заходом. Первый (переезд из корня
репозитория в `packages/core/assets/`) чинил только рабочую копию: в колесе
ассеты по-прежнему распаковывались РЯДОМ с пакетом, прямо в `site-packages`, и
дистрибутив занимал там родовые имена `prompts`, `skills`, `external`,
`recommended_mcp`. Проверено в чистом venv: `import prompts` у встраивающего
резолвился в наши промпты. То есть заявленная цель «одно имя вместо 45» была
достигнута лишь наполовину — стало четыре. Сейчас два, и оставшиеся два уносит
задача про вынос MCP.

Промпт TUI и `server_agent.md` остаются в ассетах ядра: `bundled_root()`
резолвится от `__file__` ядра, и фронтенды дотягиваются оттуда — проверено на
установленном профиле 0.4.0.

Следствие: встраивающий получает вместе с SDK ~400 КБ промптов и скиллов. Это
правильно — без системного промпта агент не работает.

## Что из этого следует держать в уме

Правила и страховки, оставшиеся от переезда. Не история — они действуют.

**Компат-шимов под старыми именами нет и не будет.** Модуль под дореформенным
именем вернул бы пересечение путей между колёсами и разрушил инвариант, на котором
держится раздельная установка: три дистрибутива не заявляют ни одного общего пути
(`tests/test_packaging_wheel.py`).

**Пути к исходникам считаются через `gc_testkit.paths`, а не арифметикой
`Path(__file__).parents[N]`.** Такая арифметика ломается при каждом переезде молча:
полтора десятка тестов уже так протухли, а один считал корень от `cwd`.

**Обход исходников обязан доказывать, что что-то нашёл.** `test_memory_cutover_invariants`
сканировал `<repo>/src`; каталог исчез, `rglob` стал возвращать пустоту — и проверка
**молча проходила на любом коде**. Страховка — `test_scan_actually_covers_sources`,
падающая на пустом обходе.

**Зелёный набор сам по себе не доказывает, что имена не разъехались.** Имя модуля
живёт не только в узлах `import`: три с половиной сотни мест называют его СТРОКОЙ —
`monkeypatch.setattr("mod.attr")`, `sys.modules[...]`, `types.ModuleType`, фильтры
`startswith("mod.")`. Часть из них при устаревшей строке краснеет, а часть — нет:
цикл выселения просто становится пустым, заглушки текут между тестовыми файлами, и
набор остаётся зелёным. Границы применимости разобраны в докстринге
`gc_testkit/module_literals.py`.

Отсюда **три сетки** в корневом наборе, дополняющие друг друга:
`test_import_health` (битые имена и потерянные связывания), `test_module_literals`
(имена модулей, записанные строкой), `test_test_ownership` (набор пакета не
импортирует пакеты выше себя). Ни одна не полна сама по себе — и ни одна не ловит
двух вещей, на которых уже спотыкались: подмену подмодуля через `sys.modules` без
атрибута на пакете и зашитый в строку файловый путь.

**Ядро не зависит ни от кого.** У `gc_core` ноль импортов `gc_cli`, `gc_tui`,
`gc_server` и `recommended_mcp`. Это не самоцель, а то, ради чего затевался переезд:
пока ядро тянуло фронтенды, «SDK» оставался словом. Держится проверкой глазами и
правилом владения тестов; отдельной сетки на это пока нет.
