# No fabricated approval — Design

**Дата:** 2026-06-24
**Статус:** согласовано, готово к плану
**Ветка:** feat/agent-instructions-and-gc-guard

## Цель

Не дать агенту **действовать по согласию, которого пользователь не давал**. Корневой
кейс (сессия `31a0a127`): агент попросил одобрение прозой, контракт отбил прозу
(no-tool-call), и агент на отбивке **выдумал** одобрение («пользователь уже выбрал
минимум → начинаю») и пошёл действовать без согласия.

Два дополняющих изменения, оба промпт-слой (системный промпт не трогаем, рантайм-
детекторов нет, `turn_ask_human` не мандатим):

1. **Анти-фабрикация в bounce-сообщении** — несгораемое ядро, все режимы.
2. **Тюнинг turn-handoff-правила судьи** — чтобы искренний запрос одобрения принимался
   как чистый конец хода (до отбивки часто даже не доходим).

---

## Проблема (анализ сессии 31a0a127)

Цепочка (записи 48→51):
- **[48]** пользователь: `минимум` — выбор **уровня** (ответ на «Уточняющий вопрос #2»).
- **[49]** агент: проза + «**Одобряешь? Напиши 'ок' — начну делать**», **без tool-call**.
- **[50]** рантайм: no-tool-call bounce. Путь: проза → `text_response` →
  `should_return_text_answer` → режим `judge` + finish-gate включён → **прозо-судья**
  (переиспользует finish-gate) вернул reject/ошибку → механизм отбивки выдал [50].
- **[51]** агент: `<think>Пользователь уже одобрил дизайн ("минимум")…</think> Ок, начинаю!`
  → начал читать/менять файлы. **Действие по неполученному согласию.**

### Нестыковка в существующих промптах

`prompts/chat_completions_system_prompt.md`:
- **§5:** «every assistant turn must contain at least one appropriate tool call».
- **§9:** «finalize … **not for questions, brainstorming, or mid-task status**».

Система сама считает вопрос/брейншторм отдельным легитимным случаем (его нельзя
finalize'ить). Штатный канал «закончить ход открытым вопросом» — `turn_ask_human`
(его описание: *«Finalizes turn: no. Request user input and wait»*). Модель выразила
легитимное намерение **голой прозой** (нештатный канал) → §5 требует tool → судья не
принял прозу как yield → bounce → фабрикация.

### Корень

Механизм наказал правильное намерение (закончить ход вопросом), потому что оно
пришло не тем каналом и судья его не спас; а на отбивке слабая модель закрыла разрыв
**галлюцинацией одобрения**. Катастрофа — не «не вызвал `turn_ask_human`», а
**действие по согласию, которого не было**.

### Почему НЕ мандатим turn_ask_human (рассмотрено и отклонено)

- Тул-зависимо: при `ask_human` в `stop_tools` (headless) совет сломан.
- Противоестественно для casual-диалога: «привет → привет, чем помочь?» не требует
  `turn_ask_human`; мандат загонял бы обычную болтовню в ask_human.
- Широкое вмешательство в системный промпт во всех режимах.

Поэтому ядро — **тул-агностичный запрет фабрикации**, а не «используй такой-то тул».

## Компонент 1 — анти-фабрикация в bounce-сообщении (ядро, все режимы)

### Где
`src/message_policy/no_tool_call_bounce.py` — в **обе** формы сообщения
(`NO_TOOL_CALL_BOUNCE_MESSAGE` и `format_no_tool_call_bounce`), после существующих
двух буллетов «finalize / call the next tool». (Реализация может вынести общий хвост
в одну константу — это решает план; смысл: клауза присутствует в обоих вариантах.)

### Почему здесь
- Срабатывает ровно в момент риска (агент выдал прозу без tool-call — это [50]).
- Общее сообщение → покрывает CLI/server/swarm/TUI без правки системного промпта
  (зовётся из `processing_responses.run_agent`: exception-путь и text_response-путь).
- Тул-агностично; casual-диалог не задевает (в TUI на «привет» прозу принимает судья,
  bounce не возникает; клауза живёт только внутри bounce).

### Текст (выверенный черновик — добавляется после двух существующих буллетов)

> If your prose asked the user a question, requested approval, or awaited their decision, their reply has NOT arrived — it is not in this conversation. Do not assume, invent, or act on a user response that has not actually arrived. If you need their input to proceed, wait for it: ask via the user-input tool if one is available, otherwise finalize the turn as blocked / needing input. A prior user choice is not standing approval for a later action.

Точки точности:
- **«their reply has NOT arrived … not in this conversation»** — прямо отрицает наличие
  ответа (бьёт по «пользователь уже одобрил»).
- **«ask via the user-input tool if one is available, otherwise finalize as blocked»** —
  тул-агностично; работает в headless без `ask_human`.
- **«A prior user choice is not standing approval for a later action»** — точечно про
  наш кейс: выбор «минимум» ≠ одобрение последующего действия.

## Компонент 2 — тюнинг turn-handoff-правила судьи (TUI-путь + мягко finish-gate)

### Где
`prompts/chat_completions_intent_guard_prompt.md`, в **уже существующую** секцию
`## Interactive turn-handoff (Axis A clarification)` (добавлена коммитом 9664e417) —
дописываем одну фразу. Новой зоны поражения не вводим: правило уже общее.

### Зачем
В сессии судья отбил запрос одобрения, вероятно сочтя его stalling'ом («юзер выбрал
минимум → иди делай, чего опять спрашиваешь») — сработал гард «could proceed on its
own / near-repeat». Нужно явно вывести **подтверждение-перед-действием** из-под этого
гарда: спросить «одобряешь?» перед последствием — это не отлынивание.

### Охват (честно)
- **Приём прозы как ответа** (ход закрывается на прозе) — **TUI-only** (`text_answer_mode`
  ставит только TUI; CLI/server/swarm прозу бунсят). Это грань, где живёт баг.
- **Само правило** — в общем промпте → его читает и настоящий finish-gate (`turn_finish`)
  → во всех chat_completions режимах оценка `turn_finish`-хэндоффа с запросом одобрения
  станет мягче. Это **благо и единообразно** (интерактивный CLI тоже вправе уступить ход
  на одобрение); в headless правило само не выстрелит (интент не интерактивен, гард
  оставляет такие случаи gap'ом). Строго-TUI потребовал бы флаг «прозо-путь vs
  turn_finish» в payload судьи — дублирование + расхождение поведения, сознательно
  избегаем.

### Текст (выверенный черновик — добавляется в конец секции turn-handoff)

> A request for explicit confirmation or approval **before** a consequential, irreversible, or plan-committing action is itself a legitimate hand-off — not stalling — even if the user already made a related choice earlier.

Точки точности:
- Выводит approval-перед-действием из-под гарда «could proceed on its own / near-repeat».
  «even if the user already made a related choice earlier» прямо снимает рассуждение
  судьи «юзер выбрал минимум → иди делай → stalling».
- «consequential, irreversible, or plan-committing» — узко: не открывает лазейку для
  «спрашиваю вместо тривиальной работы» (это остаётся gap по прежнему гарду).
- **Сознательно НЕ дублируем тут «прежний выбор ≠ согласие действовать»** — это про
  *право действовать* (забота агента/bounce, Компонент 1), а судья решает только
  *классификацию хода* (хэндофф vs stalling). Своя ось — чище фокус.

## Связка компонентов

- **Норма (casual-диалог):** не трогаем — проза, ход закрывается (в TUI судьёй), ты
  отвечаешь. `turn_ask_human` не навязываем.
- **Approval-перед-действием, TUI:** Компонент 2 — судья принимает запрос одобрения как
  чистый yield → ход закрывается → ты реально отвечаешь → до bounce не доходим.
- **Остаток (судья всё же отбил / CLI-strict / любой режим):** Компонент 1 — bounce
  запрещает действовать по неполученному согласию. Несгораемая страховка.

## Тестирование

Обе правки текстовые (решения принимают LLM/модель), поэтому детерминированно
проверяем **присутствие** клауз; поведение — живой реплей.

1. **Bounce (Компонент 1):** `format_no_tool_call_bounce("любая проза")` и
   `NO_TOOL_CALL_BOUNCE_MESSAGE` содержат маркеры: `their reply has NOT arrived`,
   `Do not assume, invent, or act on`, `not standing approval`. (Дописать в
   существующий `tests/test_no_tool_call_bounce.py`.)
2. **Судья (Компонент 2):** `_load_guard_prompt()` содержит маркер новой фразы:
   `explicit confirmation or approval before a consequential`.
   (Дописать в `tests/test_intent_guard_final_report_consistency.py`.)
3. **Регресс:** существующие тесты политики сообщений + intent_guard/finish-gate.
4. **Поведенческая валидация (ручная/живая):** реплей сессии 31a0a127 — запрос
   одобрения должен закрывать ход (судья принимает) ИЛИ, если отбит, агент **не**
   фабрикует согласие и **не** действует. Негатив: «спрашиваю вместо тривиальной
   работы» при actionable-интенте по-прежнему bounce/gap.

## Слои и ответственность

- Компонент 1 — `src/message_policy/no_tool_call_bounce.py` (политика сообщений; чистые
  функции, без бизнес-логики). Код `processing_responses` не трогаем.
- Компонент 2 — ассет `prompts/chat_completions_intent_guard_prompt.md`. Код
  `intent_guard/*` не трогаем.
- Системный промпт `chat_completions_system_prompt.md` — **не трогаем**.
- Конфиг — **не трогаем** (sync в demo/default не требуется).

## Вне scope

- Мандат `turn_ask_human` для вопросов (отклонён: тул-зависимо + ломает casual-диалог).
- Правка системного промпта / §5/§9 (не требуется — анти-фабрикация живёт в bounce).
- Рантайм-детекторы «это вопрос к пользователю» (костыль, отклонён).
- Строго-TUI ветка judge-правила (дублирование + расхождение режимов).
- Предохранитель от петель (#2 из прошлой фичи) — отдельный документированный follow-up.
