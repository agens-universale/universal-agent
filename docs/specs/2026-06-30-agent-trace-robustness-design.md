# Дизайн: устойчивость трейса агента (TUI) и устранение зацикленных tool-call ошибок

Дата: 2026-06-30
Статус: дизайн утверждён, переход к плану реализации
Режим, к которому относится: общий (часть фиксов — `backend_api_mode: chat_completions`-adjacent, см. секции)

## Контекст

На живом прогоне (модель `vllm/Qwen3-Coder-Next-262k`, задача генерации тест-кейсов в SberTrack
через MCP) в TUI наблюдалось три класса некорректного поведения. Источник анализа — экспорт треда
(`23c413dd…`, 84 сообщения) + скриншоты трейса.

### Наблюдаемые проблемы

1. **Ошибки `[!]` отображаются неинформативно, а таймер «running» у вызова бежит бесконечно.**
   При невалидном tool-call строка-вызов продолжает тикать секундами, хотя агент уже перешёл
   к другим операциям; сама ошибка показана отдельной строкой, визуально не связанной с вызовом.

2. **После серии таких ошибок выполнение «встаёт»** — иногда с ложным «Выполнил за Nм»
   (хотя ничего не сделано), иногда без статуса; приходится «пинать» агента, чтобы продолжил.

3. **Постоянные ошибки чтения references/assets и MCP-вызовов** — неверные аргументы;
   правильный вызов получается со 2–4-й попытки, иногда модель уходит в `read_file` или падает.

## Корневые причины (верифицированы по коду)

### Проблема №1 — осиротевший таймер + несвязанная ошибка
- Отказ валидации аргументов эмитится как синтетическое **USER-сообщение**
  `<technical type="error_message">` с **новым id, без `call_id`**
  (`src/processing_responses.py:756-764`).
- TUI гасит таймер `ToolCallRow` **только** при приходе `function_call_output` с тем же `call_id`
  (`src/tui/screens/main.py:1035-1043`, `src/tui/widgets/tool_call_row.py:132-136`).
- Отказ — не `function_call_output`, а отдельная `[!]`-строка без `call_id`
  (`src/tui/services/trace_mapper.py:114-127`, `src/tui/screens/main.py:1074-1078`).
- Строка-вызов остаётся в `_active_calls` с `_result is None` → таймер бежит вечно.
  Финализация в `· прервано` происходит только когда **вся задача** уходит из running
  (`src/tui/screens/main.py:1494-1501`) — отсюда «всё разом превращается в прервано» при завершении.
- `repair_tool_call_pairing` синтетический output **не создаёт**, orphan-вызов **выбрасывает**
  из payload (`src/message_policy/chat_completions.py:20-87`) — конкурирующего терминального
  события для строки-вызова нет.

### Проблема №2 — ложный терминальный статус
- Терминальный статус решается **целиком в TUI** на спадающем фронте running
  (`src/tui/screens/main.py:1518-1545`): `last_runner_error → failed`,
  `last_stop_requested → stopped`, **иначе → completed**.
- TUI не инспектирует, *почему* закончился ран. Выход по `max_steps` / кап-у ошибок
  (`src/processing_responses.py:541-545`) не несёт ни error, ни stop-флага → TUI по умолчанию
  пишет `completed` → «Выполнил за…».
- Отдельной детекции зацикленных невалидных вызовов нет; единственный бэкстоп — `max_steps`,
  а штатный `no_tool_call_max_count` по умолчанию 0 (выключен).

### Проблема №3 — отказы аргументов
- **3a (skill_id):** `_lookup_skill` при наличии `:` делает строгий canonical-lookup и нормализует
  только хвост (`src/tools/skills/registry.py:515-533`); удвоённый/угаданный `pack:skill` для
  flat-скилла → сырой `KeyError "not found"` без подсказок-кандидатов.
- **3b (object-vs-string):** поле-объект приходит JSON-строкой; валидация — strict reject-only
  (`src/tools/connect_mcp/validation.py:27-48`); генератор «Correct call format» делает наивный
  `spec.get("type","any")` и игнорирует `anyOf`/`oneOf`, рисуя `<any>`
  (`src/tools/arguments_validation.py:77-89`). Существующий `json.loads` парсит только **внешний
  конверт** аргументов (`src/tools/arguments_validation.py:171-195`), но **не значения полей** —
  двойное кодирование на втором уровне не разворачивается. Фидбэк не сообщает требуемый тип →
  модель циклически шлёт ту же строку.

## Зафиксированные решения

- **3b:** коэрция двойного кодирования (строка→объект) на ветке провала валидации + честный фидбэк
  (раскрытие `anyOf`/`oneOf` вместо `<any>`).
- **№1:** проброс `call_id` соседним ключом message-dict → TUI финализирует строку-вызов и
  подавляет дублирующую `[!]`-строку.
- **3a:** узкая обработка удвоённого namespace + кандидаты в ошибке `_lookup_skill`.
- **№2:** честный терминальный статус (Вариант 2) — TUI отличает «завершил» от «остановлен по
  лимиту/ошибкам». **Детектор зацикленных повторов — отложен** (fast-follow по живым трейсам).

## Дизайн по секциям

### Секция 1 — №1: проброс `call_id` → финализация строки-вызова

**Слои:** `message_policy` + точка эмиссии в `processing_responses` (харнес); `tui` (mapper/main).

**Харнес:**
- При формировании technical-feedback по невалидному tool-call протащить `call_id` отказавшего
  вызова **соседним ключом** message-dict (рядом с `role/content/id`), **НЕ** внутри текста тега.
  > Обоснование: `_TECHNICAL_CONTENT_RE` (`src/message_policy/user_message_policy.py:10-13`) матчит
  > строго `<technical type="...">` без иных атрибутов и используется для идемпотентности
  > `wrap_technical_user_content`. Атрибут в теге сломал бы идемпотентность,
  > `is_technical_user_message_text` и извлечение типа в маппере.

**TUI:**
- `map_message`: ветка technical/`error_msg` читает `msg.get("call_id")` — **тот же паттерн**, что
  уже есть для tool-записей (`src/tui/services/trace_mapper.py:172,460`); прокинуть на `TraceEvent`.
- `main._render_event`, ветка `error_msg`: если `call_id` известен и есть активная `ToolCallRow` —
  вызвать `row.set_result(error=True, summary=<текст>)` (таймер стоп, ошибка inline `✗ <tool> → …`)
  и **подавить** отдельную `[!]`-строку (через `TraceEvent.hidden` либо пропуск mount — выбрать в
  плане). Если `call_id` нет или строка не найдена — текущий рендер `[!]` как есть.

**Поведение:** невалидный вызов сразу `✗ <tool> → <причина>` с зафиксированным временем; без
вечного «running»; без визуального дублирования ошибки.

**Тесты:** mapper — technical с `call_id` → событие несёт `call_id`, без — нет; main — `error_msg`
с `call_id` финализирует активную `ToolCallRow` и не плодит `[!]`-строку. На реальном payload `.jsonl`.

**Риск:** низкий, аддитивно. Старые треды без поля — fallback на текущий рендер.

### Секция 2 — №3a: lenient-резолв `skill_id` + кандидаты

**Слой:** только `src/tools/skills/registry.py`.

- В ветке «id содержит `:`»: если прямой и tail-нормализованный lookup промахнулись **и**
  `pack_part == tail` (удвоённый namespace, как `qa-tc-generation:qa-tc-generation`) — попробовать
  bare-lookup по `tail`. Однозначно и безопасно (не кросс-пак).
- `KeyError` от `_lookup_skill` обогатить **списком кандидатов** (id, чей хвост близок к запросу) —
  по образцу `AmbiguousSkillId`, чтобы модель чинилась за один шаг, а не гадала.
- Broad-резолв (любой `pack:skill` через хвост) **не делаем** — он мог бы молча разрешить чужой
  пак (маскировка ошибки).

**Поведение:** удвоённый namespace резолвится; иначе ответ содержит кандидатов.

**Тесты:** удвоённый `pack:skill` flat-скилла резолвится; несуществующий skill_id → кандидаты;
реально неоднозначный short → `AmbiguousSkillId` (как сейчас).

**Риск:** низкий; поведение строгого пути не меняется, fallback только после промаха.

### Секция 3 — №3b: коэрция двойного кодирования + честный фидбэк

**Слой:** только `src/tools/arguments_validation.py` (+ генератор фидбэка там же).

- **Коэрция** в `except` на `src/tools/arguments_validation.py:196` (recovery-проход перед
  `_raise_…`): для каждого **строкового** значения поля, которое **не проходит свою под-схему**,
  попробовать `json.loads`; принять, только если результат — `dict`/`list` **и** проходит под-схему;
  после правок — обязательная **полная ре-валидация** всего объекта. Не прошла — обычный отказ.
  - Контракт: срабатывает только на ветке провала; не трогает строки, валидные как есть
    (поэтому `"123"`→123 не случится: если строка валидна, до коэрции не доходим); коэрсим только
    в `dict`/`list`, не в number/bool.
- **Честный фидбэк:** генератор плейсхолдеров раскрывает `anyOf`/`oneOf` — показывает реальный
  требуемый тип (`<object>`/`<array>`/…), а не `<any>`. Диагностика для всех ошибок, где коэрция
  бессильна (неверный enum, отсутствует required).

**Поведение:** двойно закодированный объект чинится детерминированно и невидимо; умные модели не
затрагиваются (коэрция только после провала); прочие ошибки получают внятный фидбэк.

**Тесты:** строка→объект `anyOf` принимается; строка, чей `loads` всё равно невалиден — отказ;
строка, валидная как есть — не трогается; фидбэк для `anyOf` содержит конкретный тип, а не `<any>`.
На реальном формате аргументов.

**Риск:** по построению расширяет множество «принято-и-валидно», не меняя валидные/корректно-
отклонённые вызовы. Главное — узкий контракт (dict/list, обязательная ре-валидация).

### Секция 4 — №2: честный терминальный статус (Вариант 2)

**Слои:** `State` (поле) + точки терминирования (харнес); мост через app-флаг; `tui`
(индикатор + бейдж сессии). Детектор зацикленных повторов — **вне scope** (см. «Отложено»).

- **Харнес:** в точках терминирования `run_agent` (`src/processing_responses.py:541-545`) записать
  `state.terminal_outcome` (`completed` / `step_limit` / `tool_errors`). Поле в `State` (SoT), по
  образцу `finish_gate_rejection_count`. **Форму возврата `run_agent` не менять.**
- **Мост:** `AgentExecutor.run()` / `agent_runner` после прогона выставляет app-флаг (зеркало
  существующих `last_runner_error` / `last_stop_requested`) из `state.terminal_outcome`.
- **TUI — новое 4-е терминальное состояние индикатора.** Сейчас их три
  (`src/tui/widgets/thinking_indicator.py:206-226`): `done → «✓ Выполнил за N»`,
  `cancelled → «■ Отменено»`, `failed → «✗ Ошибка»`. Лимитный выход сейчас ошибочно идёт в `done`.
  Добавляем состояние **`stopped_incomplete`** с текстом **по причине** (глиф `⏹`, стиль `_DIM`):
  - `step_limit` → `⏹ Остановлено: превышен лимит шагов`
  - `tool_errors` → `⏹ Остановлено: превышен лимит ошибок`
  > Примечание: `tool_errors` срабатывает только при `no_tool_call_max_count > 0`
  > (`src/processing_responses.py:544-545`); по умолчанию 0 → неактивен, реальный исход —
  > `step_limit`. Текст `tool_errors` обрабатываем для полноты (когда кап включён).
- **Точки правки TUI:**
  - `src/tui/widgets/thinking_indicator.py` — новая `_STATE_*`-константа + ветка рендера; текст
    выбирается по причине (причина приходит в `frozen`/последнем индикаторе).
  - спадающий фронт `src/tui/screens/main.py:1521-1545` — ветка: `state.terminal_outcome in
    (step_limit, tool_errors)` → `outcome = "stopped_incomplete"`, в `last_indicator` пишем
    `{kind, reason}` (reason нужен для выбора текста). **Порядок ветвей важен:** новая ветка
    проверяется **после** `last_runner_error`/`last_stop_requested` и **перед** дефолтом
    `completed` — иначе лимитный исход уйдёт в `completed` (тот же баг, что чиним).
  - маппинги `_KIND` (`src/tui/screens/main.py:1537`) и `_TERMINAL_STATE`
    (`src/tui/screens/main.py:1659`) + восстановление `_restore_terminal_indicator`
    (`src/tui/screens/main.py:671-685`) — распознать новый kind, без `elapsed`.
    > ВАЖНО (выяснилось на финальном review): `_TERMINAL_STATE` на 1659 — это **живой
    > idle-рендер** `_poll_active`, а не только legacy-restore. Он читает схлопнутый
    > `status`, поэтому для лимитного стопа показывал бы `■ Отменено` на живом прогоне.
    > Решение: чистый хелпер `resolve_live_terminal_indicator_state`, idle-ветка
    > предпочитает `last_indicator.kind` (commit `72d9a1d3`).
  - тип `Status` в `src/tui/models.py:9` (`running/stopped/completed/failed`) — решить в плане:
    переиспользовать `stopped` для `TaskSummary.status` (список сессий), а различие нести в
    индикаторе через `last_indicator.kind`/reason (минимально), либо расширить `Status`.
    > Учесть при переиспользовании `stopped`: в списке сессий лимитный стоп и юзер-отмена
    > сольются в один статус; а legacy-восстановление через `_TERMINAL_STATE`
    > (`src/tui/screens/main.py:1659`) при **отсутствии** `last_indicator` отрендерит лимитный
    > стоп как `■ Отменено`. Приемлемо как legacy-fallback (reason не сохранён), но должно быть
    > осознанным решением плана, а не случайностью.

**Поведение:** пользователь видит честное «⏹ Остановлено: превышен лимит шагов / превышен лимит
ошибок» вместо ложного «✓ Выполнил за N». В трейсе при этом повторяющиеся невалидные вызовы уже
финализированы как `✗` (Секция 1) — картина согласована.

**Тесты:** `max_steps` → `state.terminal_outcome == "step_limit"`; кап ошибок → `tool_errors`;
нормальный finish → `completed`; рендер индикатора для каждой причины (`⏹ … превышен лимит шагов` /
`⏹ … превышен лимит ошибок`) — снапшот; восстановление терминального индикатора из
`last_indicator` после переоткрытия сессии.

**Риск:** контракт возврата `run_agent` не трогаем — потребители CLI/server/swarm не затронуты;
новое поле `State` и новое TUI-состояние аддитивны. В плане решить вопрос `Status`-литерала
(переиспользовать `stopped` vs расширить) — на остальной TUI не влияет.

## Чистота размещения (по слоям)

- №1 — `message_policy` + `tui` (mapper/main); без логики в `states.py`.
- 3a — только `tools/skills/registry.py`.

Ни одна правка не пишет презентацию/политику в доменную модель или контроллер «по месту»;

`demo_config.yml`/`config.default.yml` не требуется.

## Отложено / вне scope

- **Детектор зацикленных идентичных повторов** (ранняя остановка по счётчику подряд идущих
  идентичных вызовов/ошибок с эскалацией фидбэка). Решено отложить как fast-follow: 3b убирает
  главный триггер, №1 снимает «зависший» вид, №2 убирает ложный статус; остаточная стоимость цикла
  ограничена `max_steps`. Вернуться, если живые трейсы после 3b всё ещё показывают дорогие циклы.
  Фундамент (`state.terminal_outcome` + проводка статуса) при этом уже заложен Секцией 4.
- **Slug-нормализация** (срезание `skill_id:`/`assets/`/`references/` у over-qualified slug).
  Не включаем: лечит лишь случай существующего ресурса с переусложнённым slug.
- **Класс «галлюцинация несуществующего ресурса»** (модель просит asset/reference, которого у
  скилла нет; см. скрин supercoder:writing-plans). Отнесён к поведению модели — харнес уже даёт
  внятный фидбэк («Available …: (нет …)»), отсутствующий файл создать нельзя.

## Известное ограничение

2-цикл (модель чередует A,B,A,B — никогда не идентично подряд) детекцией не ловился бы и сейчас
не относится к scope; `max_steps` остаётся бэкстопом.
