# Спека B — Защита `.gc` + command-layer guard + бэкап памяти

Дата: 2026-06-20
Статус: design (готов к ревью)
Связанные: Спека A (слоистые инструкции + `/init`) — определяет `protected_paths()` фундамент и confirm-канал.
Фиксит баг: **TSKBCKGRNDGNT-2** «Агент удаляет свои папки» (`rm -rf .gc && git clone …` через `execute_command`).

---

## 1. Контекст и баг

Баг TSKBCKGRNDGNT-2: агент выполнил `rm -rf .gc && git clone --depth=1 … .` через `execute_command` и **снёс проектную `.gc/`** (project config overlay, project skills, long memory).

Почему случилось — разбор по факту кода:

- `execute_command` сторожит **только `command_moderation` (LLM-судья)**, а не path-policy. Судья (вероятностный) **пропустил** деструктивную команду — агент дал «разумный» reason.
- **У `execute_command` нет path-политики вообще.** `write_guard`/`read_guard` декорируют только fs-тулы.
- Дефолтный конфиг (`config.default.yml`) включает `write_guard: enabled, mode: deny` и `command_moderation: enabled, mode: deny`, но `read_guard: enabled: false`.
- **`.gc` ничем не защищена**: она внутри `launch_root` → write_guard-периметр её включает (fs-запись разрешена), read_guard выключен, command-layer не покрыт. Пример «`.gc` denied + `.gc/skills` allowed» в `demo_config.yml` — **закомментированный opt-in для read_guard**, не активный дефолт, и только про чтение.

## 2. Жёсткая правда (важно для приёмки)

**Детерминированно защитить in-tree пути от агента с shell-доступом нельзя.** `rm -rf .gc`, `python -c "import shutil; shutil.rmtree('.gc')"`, base64-обёртка, `find . -name .gc -delete` — распарсить произвольный shell и узнать, что он удалит, в общем случае неразрешимо.

Поэтому модель — **defense-in-depth + снижение радиуса поражения**, а не «железная стена». Самый надёжный рубеж — детерминированный fs-tool guard; для shell — эвристический tripwire + LLM-судья (вероятностно) + бэкап на случай прорыва.

## 3. Цели и не-цели

**Цели:**
1. Закрыть `.gc` (проектную и глобальную) и файлы инструкций от агентских egress на трёх дверях: read / write / execute.
2. Зафиксировать `.gc/skills` как исключение (туда легитимно ходит `skill-creator`).
3. Floor-защита в коде (всегда on, opt-out флагом) — закрывает дыру и для старых конфигов.
4. Бэкап long memory вне дерева проекта → переживает удаление `.gc`.
5. Фундамент `protected_paths()` (из Спеки A) как единый source-of-truth.

**Не-цели (вне scope):**
- Гарантированная защита от обфусцированного shell (невозможно — см. §2). Делаем best-effort + judge + бэкап.
- Sandbox/контейнеризация исполнения команд.
- Защита произвольных пользовательских путей (только floor + явный `extra`).

## 4. Модель защищаемых путей: два класса + исключение

`protected_paths()` (модуль `src/security/protected_paths.py`, см. Спека A §5.1/§7) вычисляет в коде набор, разбитый на **классы с разной политикой**. Один режим на всех неверен — пути разнородны.

| Класс | read | write | execute | Состав |
|---|---|---|---|---|
| **Инструкции** | allow | **ask** | ask | `AGENTS.md` (L2), `GIGACODE.md` (L1 глоб, L3 проект) |
| **Операционная `.gc`** | **deny** | **deny** | deny | вся `.gc/` (проектная и глобальная) **кроме** `skills/` и кроме файлов-инструкций |
| **Исключение `skills`** | allow | allow | allow | `<cwd>/.gc/skills/`, `<gc_data>/skills/` (`~/.local/share/gc/skills` или `~/.gc/skills`) |

Обоснование:
- **Операционная `.gc` — deny даже на чтение**: там `config.yml` с кредами (Bearer-токен бэкенда). Агенту незачем читать `.gc` напрямую — инструкции и список скиллов харнес сам кладёт в промпт, память идёт через спец-тул, тела скиллов — через исключение. Запрет чтения ничего легитимного не стоит, но закрывает утечку кредов и само-инспекцию.
- **Инструкции — ask на запись**: совместная доработка с подтверждением человека (Спека A §7). Чтение allow.
- **`skills` — полный allow**: `skill-creator` пишет скиллы **обычными fs-тулами** (`write_file`/`read_file` по абсолютным путям в `.gc/skills/`) и запускает скрипты через `execute_command` ([skills/skill-creator/SKILL.md](../../skills/skill-creator/SKILL.md)). Без исключения наша защита сломала бы skill-creator. Исключение действует на всех трёх дверях.

Глобальная и проектная `.gc` защищаются **обе**; срочная (баг) — проектная.

Уточнение «глобальной `.gc`» (на Linux это не буквально `.gc`): операционный класс глобально = каталоги `env_vars.gc_paths()` — `config` (креды в `config.yml`), `state` (треды, auth-токены), `cache`, и `data` **кроме** `data/skills/`. На Linux/macOS это `~/.config/gc`, `~/.local/state/gc`, `~/.cache/gc`, `~/.local/share/gc`; на Windows они схлопнуты в `~/.gc/`. Конкретные пути резолвит `protected_paths()` в коде. Файлы инструкций (L1 `GIGACODE.md` в `config`-каталоге) — класс «инструкции», поэтому из операционного deny **исключены** по имени.

## 5. Enforcement на трёх дверях

`protected_paths()` — один источник; три потребителя.

### 5.1 Write (`write_guard`)

Сейчас `write_guard` — только allow-периметр (`launch_root` + `extra_paths`), без внутренних исключений. Добавляем **deny-карв-аут**:

- путь в классе «операционная `.gc`» → **deny** (даже внутри периметра);
- путь в классе «инструкции» → **ask** (confirm-канал Спека A §8; headless → авто-deny);
- путь в `skills`-исключении → пропускаем как раньше.

Проверка идёт через тот же `protected_paths()`, не из конфигурации.

### 5.2 Read (`read_guard`)

`read_guard` уже умеет `denied_read_paths` + `allowed_read_paths`-override, и уже инжектит `skills_root` программно (`_resolve_skills_root`). Расширяем тем же приёмом:

- класс «операционная `.gc`» → инжектится в denied (программно, не из конфига);
- `skills`-исключение → инжектится в allowed-override (уже есть для skills);
- класс «инструкции» → allow (не в denied).

Нюанс: read_guard в дефолте `enabled: false`. Floor-защита **не должна** зависеть от этого тумблера (иначе дыра по дефолту). Решение — §6 (floor в коде, отдельный от `read_guard.enabled`).

### 5.3 Execute (`execute_command`, `run_python_code`) — НОВЫЙ guard

У команд path-политики нет. Вводим новый command-layer guard:

1. **Детерминированный pre-scan (tripwire):** перед запуском резолвим, какие protected-пути команда упоминает/затрагивает (по подстрокам/нормализованным путям). Нашли операционную `.gc` или инструкцию → **fail-closed (deny)**, для инструкций → ask. `skills`-исключение пропускаем. Это ловит очевидное (`rm -rf .gc`).
2. **Judge-правило:** в промпт `command_moderation` инжектится явный неперекрываемый список protected-путей с правилом «эти пути трогать/удалять нельзя» — ловит то, что tripwire пропустил.

Честная граница (в спеке зафиксирована как known limitation): pre-scan — эвристика, не гарантия; хитрую/обфусцированную команду детерминированно не поймать. Судья — обязательный второй рубеж, не замена. Финальная страховка — бэкап памяти §7.

Разделение ответственности с C1 (Спека A §8.3): эта секция — **вход** судьи (tripwire + инжект protected-путей в промпт); поведение при **поломке** судьи (невалидный вердикт → ask через confirm-канал или fail-closed deny) — выход судьи, описан в Спеке A §8.3. Они ортогональны и композируются: tripwire отсекает protected детерминированно до судьи, ask-на-поломке касается только не-protected периметра.

### 5.4 Привилегированные writers — в обход

Спец-тулы-владельцы пишут свои файлы прямым кодом, **не** через агентские egress, поэтому guard их не трогает:
- `project_memory` (read/append/write) → файл памяти в `.gc/` ([tools/project/project_memory.py](../../src/tools/project/project_memory.py));
- `/init` и онбординг → инструкции/конфиг (Спека A);
- `skill-creator` → через `skills`-исключение (а не привилегию).

## 6. Floor в коде + opt-out (без дублирования)

Floor-пути (операционная `.gc` кроме `skills` + файлы инструкций) **вычисляются в коде** (`protected_paths()`), а не вписываются в конфиг. Гарды берут вычисленный набор. Прецедент инжекта вычисленного пути уже есть — `_resolve_skills_root`.

Конфиг — **тонкий**, путей не дублирует:

```yaml
security:
  write_guard:  { enabled: true, mode: deny, extra_paths: [] }   # как сейчас
  read_guard:   { enabled: false, ... }                          # как сейчас
  protected_paths:                 # НОВЫЙ блок — floor
    enabled: true                  # opt-out тумблер; default on (вкл. старые конфиги — floor в коде)
    extra: []                      # доп. пути → класс «операционные» (hard deny)
```

- Файлы инструкций → **always ask** (headless → авто-deny). Отдельного `instructions_mode` нет (намеренно убран: «жёсткий deny поверх ask» не даёт ценности — если человек подтвердил, отказывать незачем; YAGNI).
- Операционная `.gc` → **always deny** (нет сценария, где агенту можно в свой конфиг с кредами).
- `extra` — что юзер добавит, трактуется как операционное (hard-deny).
- `enabled: false` — явный opt-out (его машина — его риск). Floor в коде ⇒ работает даже если блок в конфиге отсутствует.

`protected_paths.enabled` — **независим** от `write_guard.enabled`/`read_guard.enabled`: floor применяется всегда (пока не выключен явно), чтобы дефолт-выключенный read_guard не оставлял дыру.

## 7. Бэкап long memory (снижение радиуса)

Чтобы потеря пережилась даже при прорыве shell, копия памяти должна лежать **вне `.gc` и вне дерева проекта** — там, куда агент в норме не ходит.

- Локация: `gc_state`, где уже живут треды/логи — `<gc_state>/projects/<slug>/` (Linux `~/.local/state/gc/...`, Win `~/.gc/projects/<slug>` — вне `<cwd>/.gc`).
- Механика (в `project_memory`-владельце, не в агенте):
  - на `write`/`append` память **зеркалится** в state-копию;
  - на `read`, если проектный файл пропал, — **авто-восстановление** из state-копии.
- Основной файл памяти остаётся в `.gc/` (discoverability/commit), бэкап — страховка.

## 8. Тестирование

- `protected_paths()`: состав классов (операционная `.gc`, инструкции, `skills`-исключение); глоб + проектная `.gc`; `extra` → операционные.
- Write: операционная `.gc` → deny; инструкция → ask (headless авто-deny); `.gc/skills` → allow; `skill-creator`-сценарий не ломается.
- Read: операционная `.gc` → deny (в т.ч. `config.yml`); `.gc/skills` → allow; инструкции → allow; floor работает при `read_guard.enabled: false`.
- Execute (баг-репро): `rm -rf .gc` → deny tripwire'ом; `rm -rf .gc/skills/...` → allow; judge-правило содержит protected-пути; обфусцированный кейс → документирован как known limitation (бэкап страхует).
- Floor/opt-out: `enabled: true` (и отсутствие блока) → защита on; `enabled: false` → off.
- Бэкап памяти: зеркалирование на write/append; авто-restore при пропаже проектного файла.

## 9. Known limitations (зафиксировать в коде и доке)

- Command pre-scan — эвристика; обфусцированные/непрямые удаления (`python -c`, скрипты, перемещения) могут пройти. Судья + бэкап — компенсация, не гарантия.
- Защита не покрывает удаление через сторонние процессы вне инструментов агента.
- `protected_paths.enabled: false` полностью снимает floor — осознанный opt-out.

## 10. Порядок внедрения относительно Спеки A

`protected_paths()` и confirm-канал определяются в Спеке A (фундамент). Спека B — потребитель: добавляет deny-карв-ауты в три двери, floor-конфиг, бэкап памяти. Рекомендуемый порядок: A (фундамент + инструкции) → B (защита + фикс бага). Внедряются отдельными PR.
