# release-prep: автоматизированная подготовка обзора изменений и PR над master

**Дата:** 2026-07-01
**Статус:** дизайн утверждён, ждёт план реализации
**Скоуп:** новый Claude Code скилл `release-prep` + тонкая обёртка `/loop`, готовящие из рабочей ветки чистую release-ветку, свежий обзор изменений (`CHANGES-vs-master.md`) и заготовку PR — **не трогая рабочую ветку**.

---

## 1. Зачем

Над `master` накопился большой разноплановый объём работы (на момент дизайна — 461 коммит, 390 файлов, +33926/−2325, линейно: `master` → `feat/mcp-install-ux-stream` → `feat/agent-instructions-and-gc-guard`). Нужно:

- всегда иметь **свежий, информативный обзор** всех изменений над master — чтобы самому помнить «что/почему/зачем/как», и чтобы показать команде;
- иметь **готовую к PR** причёсанную ветку (сквошенная история, сгруппированная по темам);
- вести эту рутину **параллельно с разработкой**, автоматически, не отвлекаясь;
- при этом **рабочая ветка остаётся неприкосновенной** — никаких rewrite истории на ней.

Это решается одним скиллом, запускаемым по расписанию (`/loop`) или вручную.

## 2. Проверенные факты git (на момент дизайна)

- `master` (`a14b376`) — **полный предок** HEAD. Вливать из master **нечего** (подтверждено `git merge-base --is-ancestor master HEAD`). Скилл всё равно проверяет это каждый цикл.
- История **линейна**: независимые PR-«на master напрямую» без хирургии невозможны → стартуем с одного PR, харнесс с заделом под stacked (см. §10).
- `docs/CHANGES-vs-master.md` уже ведётся вручную и устарел ~вдвое — он становится автогенерируемым артефактом release-ветки.

## 3. Архитектура: три артефакта, один источник истины

```
рабочая ветка (feat/agent-instructions-and-gc-guard)   ← ЕДИНСТВЕННЫЙ источник; скилл НЕ трогает
        │  (скилл читает её закоммиченный HEAD из общего .git)
        ▼
release-ветка (release/agent-stack)                    ← производная, пересобирается с нуля каждый цикл
        │  • дерево == рабочей ТОЧЬ-В-ТОЧЬ (ИНВАРИАНТ, см. §5)
        │  • история сквошена в N коммитов по категориям (по важности)
        ▼
   push в remote (force, namespace release/*)           ← бэкап + видимость команде; PR открывает человек
        +
   CHANGES-vs-master.md  → untracked-файл в worktree + ТЕЛО PR (не коммитится в ветку, §7)
```

**Рантайм:**
- Скилл исполняет ВСЕ git-операции в **выделенном git worktree** (`../bg-release/`), создавая его при первом запуске. Он **никогда** не делает `checkout` в текущем рабочем каталоге пользователя → переключения веток и пересборка физически не могут задеть несохранённые правки.
- **Место вызова ≠ место исполнения:** скилл можно звать откуда угодно (из loop-терминала ИЛИ из обычного рабочего терминала) — исполнение всегда в worktree.
- `/loop 1h <вызов скилла>` в отдельном терминале — фоновый режим. Тот же скилл руками — on-demand режим.

## 4. Цикл из 5 фаз (каждая завершается verify)

1. **Sense.** `git fetch`. Сравнить закоммиченный HEAD рабочей ветки с `last_seen_head` из state. Не изменилось → **no-op + выход** (дёшево, токенов не тратит). Заодно: рабочая ветка запушена в remote? Нет → запушить (это и есть страховка данных). → verify: дельта реальна / её нет.
2. **Classify (инкрементально).** Классифицировать по категориям **только новые/изменённые файлы** с `last_rebuild_head` (`git diff <last_rebuild_head>..HEAD --name-only`, обычно 1–5 файлов); дописать в персистентную карту `file → category`. → verify: каждый файл из `master..working` ∈ ровно одной категории (нет сирот).
3. **Rebuild.** Пересоздать release-ветку (механизм §5). → verify: **`git diff working release/agent-stack` пуст** (инвариант). При непустом diff — **стоп, не пушить**, поднять ошибку.
4. **Document.** Регенерировать `CHANGES-vs-master.md` как **untracked-файл в worktree** (НЕ коммитить в ветку — он же тело PR; см. §7). → verify: цифры шапки == `git rev-list --count master..working` и `git diff --shortstat master..working`.
5. **Self-review (лёгкий, delta-scoped).** Качественная самопроверка того, что нельзя поймать механически (§7.1). Только новизна этого цикла; на no-op — пропускается. Один ограниченный fix-pass. → verify: чек-лист §7.1 пройден.
6. **Publish.** Force-push release-ветки в namespace `release/*`. Вывести готовую команду/текст для `gh pr create` (PR человек открывает сам). → verify: push exit 0; запушена **только** release-ветка, рабочая — никогда.

Масштаб усилий — по дельте; **жёсткие гейты — фаза 3 (инвариант дерева) и фаза 6 (push)** — не пропускаются никогда.

## 5. Механизм squash-by-category (даёт инвариант «дерево идентично»)

```sh
# в release-worktree:
git checkout -B release/agent-stack <working-HEAD>   # history+tree = рабочей
git reset master                                     # HEAD→master; рабочее дерево цело,
                                                     #   все отличия от master теперь unstaged
# для каждой категории по порядку важности:
git add <файлы категории>
git commit -m "<категория>: <саммари>"
# после всех категорий: git status чист; дерево верхушки == рабочей
```

Итог: N коммитов над master, верхушка **байт-в-байт** равна рабочей ветке. Меняется только история — содержимое файлов не трогается. **Никаких косметических правок кода скилл не делает**: это сломало бы инвариант. Любая косметика содержимого — задача человека на рабочей ветке.

Почему инвариант критичен: `git diff working release` == ∅ доказывает «поведение не изменилось» одной командой → ревью тривиально, класс рисков «случайно сломал в причёсывании» исключён.

### 5.1 Adaptive commit granularity

**Категории = секции таблицы = группы коммитов** — один и тот же раздел (partition), два рендера. Скилл строит ОДНУ карту `файл → категория`; из неё получаются и секции таблицы, и коммиты.

Гранулярность коммитов — производная от реальных данных, не фиксирована:

- **Коммит на каждую непустую категорию**, в порядке важности. Сколько тем реально затронуто — столько коммитов (461 коммит в 14 темах → ~14; 10 коммитов в одной теме → 1).
- **Floor = 1.** Всё в одной категории / изменений мало → один общий коммит, без церемоний «1 из 1».
- **Анти-пыль (`min_files_per_commit`, дефолт ~3):** крошечная категория (1–2 тривиальных файла) не плодит однострочный коммит — сворачивается в ближайшую родственную или в общий «Сопровождение/прочее».
- **Ceiling = таксономия таблицы.** Коммитов не больше, чем реальных тем; новая категория — только при реально новой теме.

**Таблица vs коммиты — намеренное небольшое расхождение:** таблица тяготеет к читаемости (мелкая тема может остаться отдельной строкой); коммиты тяготеют к чистой истории (мелкие темы сворачиваются по `min_files_per_commit`). Оба читают из одной карты — различие только в пороге сворачивания на стороне коммитов.

## 6. Состояние (персистентность)

`../bg-release/.release-prep/state.json` — **untracked** файл в worktree (переживает `git checkout -B`, т.к. не в индексе):

```json
{
  "working_branch": "feat/agent-instructions-and-gc-guard",
  "last_seen_head": "<sha>",
  "last_rebuild_head": "<sha>",
  "file_category_map": { "src/...": "3. Слои инструкций агента L0–L3 + /init" },
  "categories_order": ["...по важности..."],
  "last_rebuild_ts": "<iso>"
}
```

Это память для **инкрементальной классификации** — главный механизм экономии токенов: цена цикла пропорциональна новой работе, а не всем 390 файлам. Пересборка коммитов и регенерация таблицы — чистые git-операции, токенов не стоят.

## 7. Контракт содержимого таблицы (критерий приёмки, не пожелание)

`CHANGES-vs-master.md` сохраняет **существующую форму** (минимальная добавка к тому, что уже ведётся вручную; не ломать рабочий формат):

- Секции = категории; колонки: **Тип · Что · Функция (что даёт) · Зачем (мотивация) · Флаг·дефолт · Где**.
- Каждая строка обязана быть **самодостаточно понятной**: что это · что именно делает · зачем/почему сделано · как работает · нюансы флага/конфига. Ничего не выкидывать как «и так понятно».
- **Ясно, просто, без воды.** Информативность максимальна, раздувание недопустимо. Строка — одна агрегированная фича/улучшение/фикс по смыслу, не по коммитам.
- Шапка автогенерится: файлы/строки над master + **обе** цифры коммитов («461 коммит рабочей истории → ~14 логических коммитов release») + строка «дельта с прошлой пересборки: +X в категориях …».

**Где живёт (вариант B):** таблица **не коммитится ни в одну ветку**. Регенерится как **untracked-файл в worktree** (`<worktree>/CHANGES-vs-master.md` — тебе на просмотр / скинуть команде) и подаётся **телом PR** (`gh pr create --body-file`). Это держит инвариант §5 чистым (release ≡ рабочая точь-в-точь, без `~1`) и не засоряет master транзиентным файлом при мерже. Нынешняя трекаемая `docs/CHANGES-vs-master.md` на рабочей ветке — отдельный ручной снимок; loop её не трогает (правило «не писать в рабочую»).

**По важности:**
- Секции упорядочены по значимости (headline-фичи выше).
- Внутри секции строки — по важности.
- Лёгкий маркер важности в колонке Тип (напр. `Фича ⭐` для ключевых) — **без новой колонки**.

Таблица одновременно служит телом будущего PR.

### 7.1 Self-review (фаза 5) — чек-лист

Качественная проверка того, что механические verify не ловят. **Delta-scoped** (только новизна цикла), **пропускается на no-op**, **один bounded fix-pass**, bias «оставить» — правка только при нарушении пункта, без «улучшайзинга» ради стиля.

Конкретные фальсифицируемые проверки (размытое «хорошо ли?» исключено — агент сам себе зарубит штампом):

1. каждая новая/изменённая строка таблицы реально несёт *что · почему · зачем · как · нюанс флага* — не вода, не пусто;
2. каждый новоклассифицированный файл лежит в категории, которая ему **подходит** (ловим mis-bucketing);
3. сообщение коммита затронутой категории точно её описывает;
4. порядок по важности не поехал после добавления.

Нашёл конкретный дефект → правит (строку / реклассификацию / сообщение коммита) и пере-прогоняет дешёвый verify затронутой фазы (реклассификация → повтор §5-инварианта). Один проход, не рекурсия. Стоимость — пропорциональна новизне.

## 8. Режимы вызова

| Режим | Как | Поведение |
|---|---|---|
| Фоновый | `/loop 1h <вызов release-prep>` в отдельном терминале | каждый час: Sense → если рабочая продвинулась, полный цикл; иначе no-op |
| On-demand | `/release-prep` из любого терминала | немедленный полный цикл вне расписания (перед показом команде / нарезкой PR) |

При on-demand из рабочего терминала с несохранёнными правками скилл предупреждает: «таблица отражает только закоммиченное; закоммить, если хочешь включить».

## 9. Частота и автономность

- **Интервал:** `1h` (дефолт). Легко выкрутить до 2–3 ч. Свежесть до минуты не нужна — таблица регенерится детерминированно в любой момент.
- **Демпфер (опционально, тумблер, по умолчанию off):** «rebuild только если ≥N новых коммитов ИЛИ прошло ≥M ч» — чтобы не пересобирать на каждый мелкий коммит.
- **Автономность = «push ветки, без PR»:** скилл сам force-push'ит производную release-ветку (бэкап + видимость), но **не открывает и не обновляет PR** — это outward-facing жест человека. Отключаемо до «только локально».
- Реальная страховка данных — push **рабочей** ветки в фазе Sense, а не release-ветки (release одноразова и регенерится).

## 10. Задел под stacked PR (не реализуется сейчас)

Старт — один PR (коммиты по категориям). Карта `file → category` и группировка коммитов — та же структура, что нужна для будущей stacked-нарезки: позже добавляется режим, который вместо N коммитов в одной ветке раскладывает категории в цепочку зависимых веток (`release/p1` → `release/p2` → …) без переписывания контракта. YAGNI до явного запроса.

## 11. Безопасность и инварианты (сводка)

- Рабочая ветка **никогда** не модифицируется (ни история, ни рабочее дерево).
- Скилл видит только **закоммиченное** состояние рабочей ветки.
- Release-ветка: дерево ≡ рабочей; история сквошена; ветка disposable и force-push'ится только в `release/*`.
- Общий `.git` двух worktree → редкая краткая блокировка индекса; скилл переживает её одним ретраем.
- Verify фаз 3 (инвариант дерева) и 6 (push) — жёсткие гейты: при провале инварианта push не происходит.

## 12. Дом логики

- Новый скилл `~/.claude/skills/release-prep/SKILL.md` — 5 фаз + verify-гейты, инвариантный каркас в духе `reintegrating-master` (фазы-с-verify, durable state), но самостоятельный (другая задача — `reintegrating-master` вливает master В ветку; здесь master не трогается).
- `/loop` — тонкая обёртка, лишь зовущая скилл по интервалу.
- Скилл и `.claude/` в git проекта **не коммитятся** (правила репо). Коммитится только эта спека и автогенерируемый `CHANGES-vs-master.md`.

## 13. Рассмотренные и отклонённые альтернативы

- **Полный цикл прямо на рабочей ветке** — отклонено: rewrite истории на рабочей ветке опасен.
- **Squash в один коммит** — отклонено: теряется читаемость по категориям, которая и есть ценность обзора.
- **Независимые PR на master** — отклонено: линейная история не даёт независимости без хирургии.
- **Полный авто: push + открытие PR каждый цикл** — отклонено: outward-facing полусырое; PR открывает человек.
- **Косметические правки кода в скилле** — отклонено: ломает инвариант «дерево идентично».
- **Cloud cron-routine вместо `/loop`** — отклонено: не учит `/loop`, сложнее с локальным worktree/репо.
- **Частый интервал как рычаг экономии** — отклонено: настоящий рычаг — инкрементальная классификация, а не редкость опроса.
