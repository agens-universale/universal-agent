Universal Agent: локальный запуск и интеграция с Temporal

Общий агентский цикл и жизненный цикл сессии. Local остаётся по умолчанию; Temporal включается явно и исполняет внешние операции через activities.

Сначала показан обычный агент, затем фактическая интеграция: процессы, activities, ход, guards, MCP, субагенты, хранение и семантика ошибок.

Статус: реализовано в ветке feat/temporal-runtime. База — develop 8f43bf03 (влит 05.10.2026: изображения, gc-chat); эталон поведения local — трассы develop 824870f6. Документ описывает фактические классы, activities и поведение; итоги проверок — в разделе 12, порядок чтения кода — в разделе 13.

Основное решение: один AgentExecutor, один ThreadSession, один агентский цикл. Temporal меняет только исполнителя внешних операций: модель, внешние эффекты инструментов, I/O хранилища и подготовку контекста. Пакет gc-ua-temporalio связывает штатное ядро с workflow и activities; бизнес-правила остаются в gc_core. Тот же принцип у Pydantic AI (TemporalDurability) и у Deep Agents (temporalio.contrib.deepagents).

Temporal — опциональный backend. SDK, CLI, server и TUI по умолчанию работают локально и к Temporal Server не обращаются. TUI и gc-cli работают только локально; Temporal включается worker'ом gc-temporal-native-worker, клиентом gc-temporal-native или server backend execution_backend: temporal-native.

0. Как устроен штатный агент без Temporal

0.1. Основные классы

Клиент передаёт сообщения исполнителю. AgentExecutor открывает тред, создаёт состояние хода и запускает общий цикл. Модель предлагает текст или инструменты; цикл проверяет результат, исполняет действия и передаёт outputs следующему запросу. «Локальное исполнение» здесь означает процесс цикла: модель, MCP и workspace могут находиться удалённо.

Класс / функция Ответственность и связи
AsyncAgent SDK-фасад: создаёт контекст и исполнителя, принимает ввод, отдаёт ответ и события. CLI/TUI также используют ядро через свои фасады.
acreate_run_context, RunContext Подготовка config, logger, tools, router, skills, MCP, os_backend, workspace и callbacks. Уже поддерживает внедрение thread_store.
AgentExecutor Жизненный цикл: _aopen_thread_session, _abuild_run_state, persist/summary hooks, arun, teardown, aclose_run_accounting. Управление: add_message, stop_run, take_undelivered_messages.
State, SharedStateData Messages, usage, счётчики, intent, stop и общие memory/permissions. Новый State создаётся на каждый ход; сохраняемые поля восстанавливаются из треда.
arun_agent, AgentLoop Общий цикл: _astep, _aprepare_batch, _adispatch; pending messages, лимиты, hooks и завершение.
ExecutionPolicy aprocess_user_ask, aprocess_tool_calls, aprocess_tool_outputs: обработка batches, pairing вызовов и outputs, обратная связь, последовательность инструментов.

0.2. Один штатный ход

Схема показывает путь с подключённым тредом; без thread_id его сохранение отсутствует. Summary и finish judge могут обращаться к модели между основными шагами. Один проход цикла обрабатывает режим user_ask, function_call, function_call_output или text_response; он не равен всему запросу пользователя.

При обычном account_run=True исполнитель закрывает учёт сам. При дополнительном post-run шаге вызывающий использует account_run=False, затем вызывает aclose_run_accounting(). Отмена во время MCP teardown после завершившегося цикла не должна потерять его итог и usage; cancellation пробрасывается после сохранения.

Очередь поступает через add_message(), stop — через stop_run(). Необработанный хвост возвращает take_undelivered_messages(). Продолжение треда в локальном режиме создаёт новый ход на сохранённых данных; файловое хранилище не сохраняет стек Python, HTTP-запрос или живую MCP-сессию.

2. Порты операций: один код, два исполнителя

Ядро не импортирует Temporal. Порты заполняет assemble_native_context через штатный assemble_run_context; без портов (локально) ядро вызывает те же функции напрямую. Чистые инструменты (memory, todo, calculator) исполняются в workflow и activities не порождают.

Песочница workflow. Код workflow Temporal исполняет в песочнице: модуль workflow и всё, что он импортирует, загружаются заново, а сеть, файлы, время и urllib.request запрещены. Ядро импортирует httpx, MCP SDK, trafilatura и readability на уровне модулей, как в develop, хотя workflow ими не пользуется: модель, инструменты и MCP идут через activities. Поэтому модули workflow первым делом импортируют sandbox_passthrough: эти сторонние пакеты песочница берёт готовыми из процесса worker'а (тот же приём у temporalio.contrib.deepagents). Код самого ядра по-прежнему загружается в песочнице и проходит её проверки (test_executor_sandbox_import.py). Идентификаторы, которые локально берутся из uuid4 (ход, ключ проб зрения, сообщения), в workflow выдаёт среда исполнения (execution.environment.supplied_id).

Изображения. Вложения и снимки fs_view_image — ссылки на файлы ImageStore; пикселей в истории workflow нет. Проекция картинок в запрос и пробы зрения модели идут внутри agent.model.request (у worker'а есть хранилище картинок). fs_view_image исполняется в agent.tool.execute: срез состояния хода приходит в ToolStateView.vision, снимок возвращается в хвост батча через StateDelta.pending_tool_attachments. Картиночные отказы модели классифицируются на worker'е и приходят в workflow полями ModelFailure.image_*. Журнал правок (agent_edits) в durable-исполнении выключен: NativeContextProvider гасит agent_edits.record в профиле.

3. Один ход

Workflow не повторяет логику ядра: подготовку State, промпты, summary, finish gate и учёт делает AgentExecutor. Workflow отвечает за доставку сообщений, ожидания, stop/close и Continue-As-New.

Continue-As-New после каждого хода. Новый run получает только состояние доставки (NativeResume): принятые ID сообщений, ответы человека, недоставленные сообщения, эпоху владельца треда. Диалог уже лежит в ThreadStore, переносить его не нужно. Списки дедупликации ограничены последними 1000 записями. Простаивающая сессия держит почти пустую историю, поэтому релиз нового кода её не ломает; ход, идущий в момент релиза, доигрывается старым кодом — worker нужно останавливать мягко. Если несовместимый код всё же получил такой ход, недетерминизм роняет только workflow task: run остаётся RUNNING и продолжит ход на исправленном воркере (раздел 8).

Владение тредом. Тред принадлежит сессии (workflow ID): локальный TUI/CLI и workflow с другим ID в него не пишут. Сессия снимает владение сама — при закрытии (в том числе после Continue-As-New без хода), при ошибке и отмене. После terminate или падения процесса следующая сессия с любым ID проверяет workflow владельца: не RUNNING или не найден — владение снимается и тред захватывается; живой владелец не уступает.

4. Guards, подтверждение и эффект

Правила guards одни и те же для local и Temporal: генераторы path_policy, read_guard, command_moderation выполняются в workflow, а факты о файловой системе приносит evaluate_guard_probe. Probe вызывается только для файловых и командных инструментов и только для включённых проверок. Исключение — защита системных путей (protected_read, protected_write): она работает всегда, как в develop, и настройкой не выключается (security.protected_paths.enabled не действует). Поэтому Guard: protected_write виден в истории и при выключенных read_guard, write_guard, url_policy и command_moderation. Под защитой — ~/.gc, .gc проекта, каталоги состояния и все служебные пути воркера (треды, квитанции, payload; базы — вместе с -wal/-shm). Ожидание человека не занимает worker: это workflow.wait_condition.

5. MCP и фоновые процессы

Владелец живых ресурсов — один на ход, как begin/end run в local: WorkerResourceHost. Discovery, вызовы и teardown MCP идут в одной задаче, повторная доставка той же операции ждёт тот же результат. Ошибка вызова MCP — ошибка инструмента, сессия остаётся живой; закрывается владелец только при потере транспорта (McpSessionLostError). Ресурсы не переживают процесс: после перезапуска worker'а модель получает ResourceOwnerLost и может продолжить; внутреннее состояние MCP-сервера не восстанавливается. Фоновый владелец создаётся лениво. Владелец хода — <workflow ID>/<первый run цепочки>/turn-N: новая сессия на том же workflow ID не наследует кэш и квитанции прошлой. Контекст сессии, снятой terminate посреди хода, освобождает NativeMaintenance.

6. Субагент в child workflow

Одновременно активен один ребёнок, как в local. Сигнал ребёнка, пришедший раньше handle, ждёт его, а сигнал неактивного ребёнка игнорируется и родителя не роняет. Сообщение, пришедшее после конца цикла ребёнка или не доставленное ему сигналом, возвращается родителю. Вопрос человеку от ребёнка, который завершился, снимается. Ребёнок, снятый terminate или по таймауту, — ошибка инструмента subagent_interrupted (часть его действий могла выполниться), а не отказ сессии.

7. Хранение: тред, история Temporal и payload

Слой Что хранит Сколько живёт
ThreadStore История диалога — источник правды Постоянно
Event History Журнал выполнения одного run Пока run открыт + retention namespace
External storage Крупные payload этого журнала Нужно чистить: lifecycle S3 или prune_file_payloads

Durable-контракт хранилища. Повтор activity может прийти дважды, поэтому хранилище в Temporal реализует два метода поверх обычного ThreadStore: read_snapshot (meta, сообщения, revision, generation, владелец) и commit_operation (атомарная операция с operation_id, expected_revision, владельцем). Повтор той же операции возвращает исходную квитанцию; дедупликацию сообщений хранилище делает само, expected_revision гарантирует согласие с сессией. Свою реализацию (Postgres, S3) проверяют одной строкой: assert_durable_conforms(factory) из gc_testkit.durable_thread_store_conformance.

Хранилище Где Как устроено
FileThreadStore local по умолчанию Как в develop: data_*.jsonl, meta_*.json, без журнала. В тред, которым владеет Temporal, не пишет.
DurableFileThreadStore Temporal, один хост Те же файлы + .store/: квитанции, журнал прерванной записи, владелец.
SQLiteThreadStore Temporal Транзакции SQLite.

Когда писать тред — thread_store.persist в профиле:

Значение Когда пишем По умолчанию
step После каждого шага и в конце хода local (единственное допустимое)
turn В точках сброса: конец хода, перед компакцией, перед ожиданием человека (кроме вопроса субагента — тред родителя пишется в конце его хода), при stop/ошибке Temporal

В режиме turn шаги до сброса защищены историей workflow: после падения worker'а replay восстанавливает буфер; при сбое коммита буфер не очищается, и повторный сброс дописывает шаги. Шаги теряются из треда, только если workflow принудительно завершить (terminate) до сброса. Local без durable-исполнителя turn отклоняет.

Сброс треда в durable-хранилище убирает то же, что локальный: файлы истории, картинки треда, журнал правок. Квитанции прошлого поколения остаются (поздний повтор операции получает прежний исход), но без meta треда. Квитанции старше 7 дней удаляет NativeMaintenance.

8. Ошибки, повторы и неизвестный исход

Семантика как у Pydantic AI и как в local: ход продолжается, если модель может отреагировать на ошибку.

Ситуация Что видит модель / workflow
Доменная ошибка в activity (ValueError, OSError, …) Переносится значением (DomainError) и поднимается в workflow тем же типом — ядро возвращает модели internal_tool_error, как в local
Факты guard'а изменились до эффекта GuardPreconditionChanged — ошибка инструмента, эффект не исполнен
Запрос к модели упал вместе с worker'ом Temporal повторяет; если ответ пришёл, а квитанция нет — повторная оплата одного запроса
Сбой провайдера модели: обрыв, 5xx, 408/425/429 Temporal повторяет запрос по политике activities.model (по умолчанию без ограничения): ход ждёт и продолжается, run остаётся RUNNING
Чтение (fs-чтения, fetch_url, fs_view_image, чтение памяти проекта), подготовка, хранилище Повтор Temporal (до 5)
Эффект инструмента (запись, команда, MCP, project memory) Вторая попытка только читает квитанцию первой и никогда не исполняет эффект заново; квитанции нет — модель получает «исход неизвестен, проверьте состояние» (ToolOutcomeUnknown)
Потеря MCP или фонового владельца ResourceOwnerLost — ошибка инструмента
Инструмент дольше лимита activity ToolOutcomeUnknown «превысило лимит времени activity»
Хранилище треда недоступно, подготовка контекста, исчерпаны повторы модели Доменный отказ: run становится FAILED (ApplicationError)
Недетерминизм после деплоя, запрет песочницы, баг в коде workflow Падает только workflow task, run остаётся RUNNING и продолжает ход на исправленном воркере. Если сбой случился после того, как код запланировал уборку (finally с activity), replay исправленного кода может разойтись — тогда temporal workflow reset на событие до хода

Операторского восстановления нет: решение после неизвестного исхода принимает модель, как после падения процесса в local. Exactly-once внешних эффектов не обещается.

9. Сервер и клиент

execution_backend: temporal-native монтирует HTTP API http_api и переводит /events/webhook, /runs, /logs на Temporal. Сообщение отправляется через Update-With-Start: одна атомарная операция «доставить, при необходимости открыв сессию». Закрытая или упавшая сессия с тем же ID начинается новым run и продолжает тот же тред. Статусы: idle/completed → completed, stopped → cancelled, failed → failed.

Команды клиента: gc-temporal-native start | status | result | stop | answer | close | send | unlock (unlock снимает владение тредом у сессии, которой больше нет — для локального TUI/CLI); --config (JSON воркера) нужен, чтобы читать крупные payload из payload_storage. Ошибки update и query сессии (устаревший ход, сессия ещё не готова) API отдаёт как 409. Повтор сообщения с тем же message_id — duplicate: true, кроме сообщения, отброшенного остановкой хода: его повтор принимается заново.

11. Ограничения

  • Один процесс worker'а обслуживает все очереди и один workspace; раздельное развёртывание model/resource не поддержано этим entrypoint.
  • MCP-сессии и фоновые процессы не переживают процесс worker'а.
  • Внешний эффект — не более одного исполнения; после падения в середине исход может быть неизвестен, и модель должна проверить состояние сама.
  • Запрос к модели может быть оплачен дважды при падении после ответа.
  • Worker Versioning включается секцией versioning (по умолчанию выключен): ход закреплён за сборкой, где начался, следующий ход идёт на текущей; номер сборки — версия пакета gc-ua-temporalio. Без versioning ход, идущий в момент несовместимого релиза, ждёт исправленного воркера.
  • Настройки профиля воркер берёт из своего JSON при каждой activity: смена настроек или токена — перезапуск воркера, живые сессии продолжают работу.
  • Blob'ы external storage Temporal не удаляет — нужна очистка по сроку.
  • История Temporal не шифруется (PayloadCodec нет).
  • Файлы картинок (ImageStore, карман процесса _staging/<pid>) лежат на диске worker'а: несколько worker'ов на разных хостах требуют общего тома для каталога картинок, даже если тред хранится в БД.
  • Ответ человека с картинками (HumanAnswer.attachments) через Temporal не передаётся: ответ — строка.
  • Журнал правок агента (agent_edits: дифф, откат) в durable-исполнении не ведётся.
  • Одновременно активен один субагент.
  • Защиту системных путей (protected_*) конфигом не выключить.
  • Дедупликация message_id — последние 1000 ID в пределах сессии; после закрытия сессии повтор того же ID обрабатывается снова.
  • Workflow histories прежнего экспериментального протокола не поддерживаются и не мигрируются; этот протокол удалён.

  • Обслуживание воркера: контекст хода после terminate освобождается, квитанции исчезнувших workflow и старые квитанции тредов удаляются.

13. С каких файлов начинать

Быстрый путь — пять файлов в таком порядке:

  1. native_worker.py — build_native_runtime и worker_options: что поднимает worker, какие хранилища и activities на каких очередях.
  2. native_provider.py — NativeWorkerConfig/NativeProfile (конфиг worker'а) и NativeContextProvider: как профиль превращается в штатный RunContext на worker'е.
  3. native_workflow.py — NativeAgentWorkflow: run → _run_session → _run_turn → AgentExecutor.arun; signals/updates (submit_message, answer_human, stop, close_session).
  4. native_operations.py — NativeOperations: как порты ядра (модель, инструмент, guard, промпты) становятся вызовами activities.
  5. native_activities.py — NativeActivities: что исполняется на worker'е (_prepare, _model, _tool, _guard).
