# HTTP-фасад Responses (`gc-chat`)

Отдельный процесс `gc-chat`. Внешнее приложение открывает ход агента через `POST /v1/responses` и читает стрим прозы, рассуждения и коротких карточек тулов. Конверт близок к OpenAI Responses API. Петля тулов остаётся внутри ядра: клиент присылает текст и не исполняет тулы сам.

Тот же процесс и тот же порт отдают `POST /v1/chat/completions`. Клиент выбирает путь. У Chat Completions другой контракт: клиент каждый раз присылает `messages`, тред хода эфемерный, трейс уходит внутри `<think>`.

Это не `gc-serve`. У вебхука другой контракт: он отвечает `started` и просит опрашивать статус. Здесь соединение живёт, пока жив ход. Флага у `gc-cli` и маршрутов в `gc-serve` нет.

Один запрос — один ход. Продолжение диалога — `previous_response_id` прошлого хода, тот же тред (`system="responses"`).

## Установка и запуск

Зависимости FastAPI и uvicorn живут в дистрибутиве `gc-chat`. Базовая установка CLI их не ставит.

```bash
uv tool install -e packages/chat
# без клонирования репозитория:
uv tool install "gc-chat @ git+https://gitverse.ru/gigacode-ai/universal-agent#subdirectory=packages/chat"
```

В корпоративной сети к `uv tool install` добавляйте `--system-certs`.

```bash
gc-chat --config ./config.yml
gc-chat --config ./config.yml --profile <имя>
```

Без `--config` поиск конфига тот же, что у остальных команд: явный путь, затем `config.yml` в каталоге Config, затем пакетный шаблон. Конфиг не читается — сообщение в stderr, код выхода 1, порт не открывается.

`os_backend` обязан быть `local`. `harbor` и неизвестный бэкенд завершают процесс с кодом 1 до bind.

По умолчанию слушает `127.0.0.1:8090`. Логи — в stderr. Тело ответа в stderr не пишется. Пустой `chat_api.auth_token` даёт на старте строку: сервер без авторизации. Там же процесс перечисляет ручки: метод и адрес.

## Конфиг

Секция `chat_api` — часть общей схемы `config.yml`. Аннотированный образец — [`demo_config_chat.yml`](../demo_config_chat.yml) в корне репозитория: скопируйте блок в свой конфиг агента. В шаблон CLI (`config.default.yml`) и в справочник `demo_config.yml` секция не входит. Без неё схема подставляет дефолты, и процесс стартует.

Ключи читает только `gc-chat`. gc-cli и TUI их не применяют. Оба пути, Responses и Chat Completions, берут host, port, токен, CORS и режимы хода из этой секции.

| Ключ | Дефолт | Смысл |
|---|---|---|
| `chat_api.host` | `127.0.0.1` | Адрес bind. Пустая строка отклоняется при загрузке. |
| `chat_api.port` | `8090` | Порт, 1–65535. |
| `chat_api.auth_token` | `""` | Пусто — заголовок не проверяется. Иначе каждый запрос к `/v1/` несёт `Authorization: Bearer <token>`, иначе 401 `invalid_api_key`. |
| `chat_api.cors_origins` | `[]` | Пусто — любой origin (`Access-Control-Allow-Origin: *`). Непусто — только эти origin, методы `GET`, `POST`, `OPTIONS`, заголовок `Authorization`. `"*"` из списка выбрасывается. Preflight с `Access-Control-Request-Private-Network` получает `Access-Control-Allow-Private-Network: true`. Страница чата открывается с порта этого процесса и CORS не использует; заголовок нужен чужим клиентам. |
| `chat_api.launch_root` | `null` | Рабочий каталог нового хода, если в запросе нет абсолютного `metadata.cwd`. Относительный путь не используется: тогда берётся каталог процесса. |
| `chat_api.text_answer_mode` | `allow` | `deny`, `judge` или `allow`. После загрузки пишется в runtime-ключ `text_answer_mode`. |
| `chat_api.finish_gate_mode` | `off` | `off`, `on` или `smart`. Пишется в `strict_turn_finish_validation` (`true`, когда режим не `off`) и `finish_gate_smart` (`true` только для `smart`). |
| `chat_api.todo_reminder_steps` | `0` | Напоминания про `session_todo`. `0` — не напоминать. Сам тул остаётся. Значение пишется в `todo_params.reminder_steps` этого процесса. |

Значения `off` и `on` в yaml пишите в кавычках: без них YAML читает их как boolean, и загрузка конфига падает.

`agent.strict_turn_finish_validation` и уже лежащий в конфиге `text_answer_mode` на этом процессе не действуют: фасад перекрывает оба ключа после загрузки. Дефолт канала — проза без тула принимается, судья на `turn_finish` не зовётся. `session_todo` остаётся в схеме. Напоминания о нём этот процесс ставит в `0`, если в секции не задано другое число.

После загрузки режим дописывает в `stop_tools` имена `turn_ask_human` и `turn_intermediate_reply`: ни вопроса человеку, ни промежуточной реплики в схеме нет. Прогресс пишется прозой. Ролевая вставка ставится на копию конфига перед созданием агента, не в общий словарь процесса. У хода Responses это `chat_completions_responses_special_instructions.md`: вопрос пользователю — проза ответа, следующий запрос — ответ человека. У хода Chat Completions другой файл: следующий запрос не увидит трейс. Свой `paths.chat_completions_special_instructions_path` на этом процессе не читается. Порт `ask_human` остаётся и сразу возвращает пустую строку, чтобы случайный вызов не читал stdin.

Неизвестный ключ внутри `chat_api` загрузка отклоняет (`extra=forbid`).

Рабочий каталог хода, по порядку:

1. абсолютный `metadata.cwd` нового запроса;
2. иначе абсолютный `chat_api.launch_root`;
3. иначе каталог процесса.

На продолжении присланный `metadata.cwd` должен совпасть с каталогом, записанным у прошлого ответа. Чужой путь — 400, ход не стартует.

## Запрос

`POST /v1/responses`. Тело — объект. Обязательны непустые `model` и `input`.

`model` в объект ответа копируется как присланная строка. В роутер моделей фасад её не передаёт: модель хода — та, что в конфиге агента.

`stream: true` — ответ `text/event-stream`, поток закрывается на терминальном событии. Нет поля или `false` — процесс держит запрос до конца хода и отдаёт один объект Response.

`input` — строка или массив. Из массива в ход берётся только последний элемент, история перед ним игнорируется. Текст последнего элемента: сама строка; либо объект `role: user` (с `type: message` или без type) и `content` строкой; либо `content` — массив, и склеиваются через перевод строки только части `type: input_text`. Картинки, файлы и прочие части этого сообщения пропускаются. Последний элемент `assistant`, `function_call` или `function_call_output` текста не даёт. Пустой текст — 400, ход не стартует.

Без `previous_response_id` открывается новый тред. С ним ход продолжается на том же `thread_id`. Пока предыдущий ход этого треда не записал терминальный статус, второй `POST` — 409, новый ход не стартует. Клиент шлёт тот же текст ещё раз, когда первый ход закончился.

`instructions`, `tools`, `tool_choice`, `temperature`, `max_output_tokens`, `store`, `truncation` принимаются и на ход не влияют. `store: false` индекс всё равно пишет.

Ошибки запроса — JSON `{ "error": { "message", "type": "invalid_request_error", "code" } }`:

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `invalid_request` | тело не объект, нет `model` или `input`, у последнего элемента нет текста, чужой `metadata.cwd` на открытом треде |
| 401 | `invalid_api_key` | токен задан, заголовок не сошёлся |
| 404 | `not_found` | нет такого ответа |
| 409 | `conflict` | у этого треда ещё идёт ход |
| 500 | `server_error` | ход без стрима упал исключением. В теле при этом объект Response со `status: failed`, не конверт ошибки |

## Объект ответа

Поля: `id` (`resp_` и uuid), `object: "response"`, `created_at`, `status`, `model`, `previous_response_id`, `output`, `error`, `incomplete_details`, `metadata`, `usage` (`null`).

`status`: `completed` — обычный конец хода, в том числе `tool_errors`; `incomplete` — `token_limit`, `step_limit` или `tool_call_limit`, и тогда `incomplete_details.reason` равен этому исходу; `cancelled` — `POST …/cancel`, обрыв соединения или остановка хода; `failed` — исключение, `error.message` — его текст.

Элементы `output`: `message` (проза), `reasoning` (сплошная серия мыслей), `gc_tool_call`. Клиентского `function_call` фасад не пишет.

Карточка тула — имя, короткий заголовок и статус (`in_progress`, затем `completed` или `failed`). Сырых аргументов и тела результата в событии нет. `turn_ask_human`, `turn_intermediate_reply` и `session_think` наружу не выходят. Вложенный тул субагента — такая же карточка: `call_id` склеен как `{parent_call_id}/{call_id}` ребёнка, поле `parent_call_id` — вызов `subagent_*`. Проза субагента, служебный user и метка сводки в карточки не входят. Ход, закрытый `turn_finish` без прозы, отдаёт `task_report` и заметку: сырые аргументы, вердикт судьи и отклонённая попытка в ответ не попадают. Если тот же отчёт уже был в прозе хода, заметка повторно не дописывается.

`GET /v1/models` отдаёт один элемент: `id` — модель из конфига агента.

`GET /v1/responses/{id}` читает сохранённый объект, в том числе `in_progress`, и работает после перезапуска процесса. Нет файла — 404.

`POST /v1/responses/{id}/cancel` останавливает идущий ход, статус `cancelled`. Повтор после терминального статуса возвращает сохранённый объект и агента не трогает.

Индекс лежит рядом с каталогом тредов: `responses-index/<response_id>.json`. История хода — в обычном jsonl треда, `system="responses"`.

## Страница и диалоги

`GET /` отдаёт страницу чата, `Content-Type: text/html; charset=utf-8`. Токен на этот ответ не нужен: его вводят на странице, дальше он уходит заголовком `Authorization`. Запросы страницы — относительные `/v1/…` на тот же порт. Каталог хода этот маршрут не раздаёт.

`GET /v1/dialogs` — прошлые диалоги Responses, сначала недавно обновлённые. Один элемент на `thread_id`: `latest_response_id` (ход, на который не ссылается `previous_response_id` другого хода этого треда), `cwd` последнего хода, `created_at` первого, `updated_at` и `status` последнего, `title` — имя по правилу TUI. Сначала формулировка `task` из `turn_finish`: первая берётся всегда, следующая заменяет её только если в этом ходе был тул кроме финализатора и когнитивных (`session_think`, память). Иначе авто-имя из промптов: первый любой длины, следующий заменяет его только если после схлопывания пробелов длиннее 30 символов. Потолок 200. Нет промпта и нет `task` — пустая строка, страница пишет «Без названия». Треды Chat Completions и чужой `system` в список не входят. Битый файл индекса пропускается. Нет целого jsonl — тред остаётся с пустым `title`.

`GET /v1/dialogs/{thread_id}` — ходы по цепочке `previous_response_id`, от первого к последнему. У хода: `response_id`, `previous_response_id`, `created_at`, `status`, `text` пользователя из jsonl, `output` сохранённого ответа. Нет треда — 404.

`GET /v1/dialogs/{thread_id}/artifacts?path=` — один уровень каталога `cwd` хода. Пустой `path` — сам этот каталог. Ответ: `path` и `entries`. `path` относительный, разделитель `/`, в корне пустая строка. Элемент — `name`, `path`, `kind` (`dir` или `file`). У файла ещё `text`: первые 8 КиБ читаются как UTF-8 и не содержат нулевого байта. Пустой файл — текст. Символ, обрезанный границей этого окна, текстом остаётся. Страница даёт «Просмотреть» только при `text`. Сначала каталоги, потом файлы, внутри группы по имени без учёта регистра. В список входит обычный файл и каталог, реальный путь которых внутри `cwd`. Имена, начинающиеся с точки, не входят. `..`, абсолютный путь, обратная косая черта, отсутствующий путь, файл вместо каталога, симлинк наружу и путь со скрытым сегментом — 404. Нет треда — 404. Вызовы тулов этот список не читает.

`GET /v1/workspace/artifacts?path=` — тот же один уровень для корня нового хода, пока диалога ещё нет. Корень совпадает с первым `POST /v1/responses` без абсолютного `metadata.cwd`: абсолютный `chat_api.launch_root`, иначе каталог процесса. Ответ: `cwd` (абсолютный корень), `path` и `entries`. Отказы пути те же, сообщение 404 — `path not found`.

`GET /v1/workspace/artifacts/download?path=`, `POST /v1/workspace/artifacts` и `DELETE /v1/workspace/artifacts?path=` читают и пишут этот же корень. Тело создания, имя каталога и правила удаления совпадают с ручками диалога. Идущий ход эти ручки не блокирует: диалога ещё нет.

`GET /v1/dialogs/{thread_id}/artifacts/download?path=` отдаёт байты обычного файла внутри этого каталога. `Content-Type: application/octet-stream`, `Content-Disposition: attachment`. Пустой путь, каталог, чужой путь, `..`, симлинк наружу и путь со скрытым сегментом — 404. Тело файла в stderr не пишется.

`POST /v1/dialogs/{thread_id}/artifacts` с телом `{"path", "name"}` создаёт каталог `name` внутри уже открытого `path`. Пустой `path` — корень `cwd` хода. `name` — одно имя: без `/`, `\`, пустой строки и ведущей точки. Ответ: `path` созданного каталога и `kind: dir`. Такое имя уже занято — 409 `already exists`. Имя не годится — 400. Нет треда или родительского каталога — 404.

`DELETE /v1/dialogs/{thread_id}/artifacts?path=` удаляет файл или каталог по этому пути вместе с содержимым каталога. Пустой путь — это сам `cwd`, его ручка не снимает, 404. Симлинк внутри каталога снимается как ссылка, цель снаружи не удаляется. Чужой путь, `..` и скрытый сегмент — 404.

Пока ход этого треда идёт, `POST` и `DELETE` отвечают 409 `turn already running` и каталог не меняют.

Эти `GET /v1/dialogs…` и `GET /v1/workspace/artifacts…` проверяют Bearer так же, как остальные `/v1/`. Пустой `chat_api.auth_token` — проверки нет. `POST` и `DELETE` каталога тоже.

## Чего в этом релизе нет

Нет Conversations API, `background: true`, картинок и аудио во входе, клиентских `tools`, которые UI исполняет сам, `DELETE /v1/responses/{id}`, смены модели полем `model`, песочницы Harbor и загрузки файла с браузера в каталог хода. Вопрос человеку в канал отдельным событием не выходит: модель пишет его прозой и завершает ход.
