# Асинхронное ядро

Ядро `gc-core` асинхронное. У каждой операции **одна** форма, и она корутинная:
`AgentExecutor.arun(...)`, `gc_core.aio.AsyncAgent`, `aapply_tool` и так далее.

Синхронные точки входа существовали ради обратной совместимости и держались
на портале — приватном event loop в фоновом потоке. Обещание снято: два API
означали две формы у каждой операции и целый loop, живущий только ради того,
чтобы синхронное имя могло дождаться корутины.

## Как звать из синхронного кода

Своим `asyncio.run` — как это делают TUI и harbor-адаптер: они держат агента
в рабочем потоке, а внутри потока запускают собственный loop. Поток там нужен
не ядру, а фронтенду (не делить loop с интерфейсом; у мостящих бэкендов —
чтобы синхронный файловый API не заблокировал сам себя).

## Асинхронный агент

```python
from gc_core.aio import AsyncAgent
from gc_core.config import load_config

config = load_config("~/.gc/config.yml")

async with await AsyncAgent.create(config) as agent:
    answer = await agent.run("почини падающие тесты", thread_id="t1")
```

Живые дельты ответа:

```python
async with await AsyncAgent.create(config) as agent:
    async for kind, text in agent.stream("объясни этот модуль", thread_id="t1"):
        if kind == "answer":
            print(text, end="", flush=True)
        elif kind == "think":
            ...          # рассуждение модели, если провайдер его отдаёт
        elif kind == "reset":
            ...          # начать вывод заново: пошла повторная попытка запроса
```

Управление ходом снаружи:

```python
agent.send({"role": "user", "content": "стоп, сначала линтер"})   # подкинуть в идущий ход
agent.stop()                                                      # кооперативная остановка
```

Полный рабочий пример — [`packages/core/examples/async_embed.py`](../packages/core/examples/async_embed.py).

## Без фасада

Фасад ничего не прячет: то же самое доступно напрямую.

```python
from gc_core.agent_executor import AgentExecutor
from gc_core.run_context import acreate_run_context

ctx = await acreate_run_context(config, on_stream_delta=my_sink)
answer = await AgentExecutor(ctx).arun(["привет"], thread_id="t1", system="sdk")
```

## Как называются точки входа

Приставка `a` — не «асинхронный вариант», а единственное имя операции.
Синхронных двойников у ОПЕРАЦИЙ ЯДРА нет: то, что раньше стояло без
приставки, снято вместе с порталом.

Синхронные имена остались ровно в двух местах, и оба — не двойники:

* **контракт `ThreadStoreBase`** — одиннадцать методов хранилища
  (`load_messages`, `append_messages`, `save_meta` и остальные). Это ПУБЛИЧНАЯ
  поверхность для встраивающего с синхронным хранилищем; ядро её не зовёт — оно
  ходит через `a`-формы и адаптер `thread_store_async`. Убрать её значило бы
  отменить обещание «своё хранилище можно синхронное», ради которого контракт и
  задуман (см. `docs/thread-store.md`). Рядом стоит `AsyncThreadStoreBase` для
  встраивающего с `redis.asyncio` или `asyncpg` — это ВТОРОЙ контракт, а не
  двойник первого.

  Методы `ThreadSession` (`from_config`, `persist_batch`,
  `archive_and_compact_summary_payload`) в этом списке раньше стояли по ошибке:
  это не контракт хранилища, а фасад ядра, и синхронных форм у него больше нет
  — только `afrom_config`, `apersist_batch` и `aarchive_and_compact_summary_payload`;
* **долгоживущий stdio MCP** — `PersistentStdioSession.close`, `close_all` и
  построчное чтение в `transport`. Их зовёт `atexit`, где loop'а уже нет, а
  обмен с процессом блокирующий по существу. Плюс синхронные `list_tools` /
  `call_tool` у `AgentRuntimeClient`: они обслуживают ровно этот транспорт и
  всему остальному отказывают громко.

Исключений нет и у сборки контекста: `create_run_context` снят, осталась
одна `acreate_run_context`.

Держался он ради TUI, и здесь же стояло объяснение — «MCP-сессии привязаны к
loop'у, на котором заведены». Объяснение было неверным: синхронная сборка
уводила дискавери в `run_coro_blocking`, то есть на такой же одноразовый loop,
умиравший до первого хода. Настоящая причина была проще — фабрика исполнителя
в TUI обычная функция и своего loop не имеет; теперь она заводит его сама
(`asyncio.run`), ровно как уже делает на каждый ход.

Отложено: один долгоживущий loop в рабочем потоке TUI на всё приложение. Он
убрал бы и TLS-рукопожатие, которое TUI платит на каждое сообщение, закрывая
пул httpx после хода.

| Операция | Имя |
|---|---|
| собрать контекст | `acreate_run_context` |
| прогнать ход | `AgentExecutor.arun` |
| цикл шагов | `processing_responses.arun_agent` |
| позвать тул | `tools.aapply_tool` |
| запрос к бэкенду | `connect_backend.arequest_backend_chat_completions` |
| запрос с политикой ретраев | `request_backend_policy.arequest_chat_completions_with_policy` |
| одиночный chat/completions | `utils.llm_chat_client.arequest_chat_completion_text` |
| суммаризация | `summarize.llm.arequest_summary_text` |
| запуск процесса в бэкенде | `aexec`, `aexec_argv`, `arun_python` |

## Свои тулы и свои бэкенды

**У тула одна форма — `acall`.** Диспетчер зовёт только её; тул без `acall` —
жёсткая ошибка проводки, а не тихий уход в поток.

```python
class MyTool(AbstractSimpleTool):
    async def acall(self, x: str) -> str:
        ...
```

Асинхронность формы НЕ означает, что тело обязано что-то ждать: файловые и
короткие тулы исполняют его инлайн на loop, потому что у файлов нативной
асинхронной формы нет, а поход в пул стоит дороже самой работы.

Прежняя третья ступень диспетчера (синхронный `__call__` → `asyncio.to_thread`)
убрана. Она сторожила возможность, которой нет: зарегистрировать свой
Python-класс-тул извне нельзя — `build_tools_data` собирает набор из
`config_dict`, параметра у `acreate_run_context` нет, механизма плагинов нет.
Точка расширения для чужих тулов — **MCP**, и она асинхронна насквозь.

**Ограничение снято.** Раньше здесь стояло: у `FsBackend` есть асинхронные
двойники файловых операций, но тулы их не зовут — и под `HarborBackend` каждая
файловая операция тула была сетевым roundtrip'ом на заблокированном loop, так
что бюджет «разрыв < 150 мс» не держался. Двойников больше нет: файловые
операции порта САМИ корутинные (27 методов плюс четыре асинхронных генератора
`iter_lines` / `iter_walk` / `iter_files` / `iter_walk_entries`), примесь
`AsyncFileOps` с двадцатью восемью двойниками снята, и флага `bridges_to_loop`
тоже нет — развилки «инлайн или поток» не осталось. У Harbor операция ждёт
нативно через `_aawait`: корутина уходит на loop владельца, результат —
обычным `await`, без потока. У локального бэкенда тело осталось инлайн, и
`await` там стоит микросекунды.

**Чужой `FsBackend` обязан стать корутинным — это ломающая правка.** Для
файловых операций адаптера НЕТ, в отличие от запуска процессов: там синхронный
бэкенд по-прежнему заворачивается в `SyncExecAdapter`, а сами `exec` /
`exec_argv` / `run_python` остались на порте входом для чужих реализаций
(умолчание отказывает `SyncExecNotSupportedError`). Пробы возможностей
(`has_find`, `has_grep`, …) читают только КЭШ: прогрев `awarm_capabilities`
стал обязательным шагом, а холодное чтение отказывает
`CapabilitiesNotWarmedError` — вместо прежней тихой заморозки loop на четырёх
запусках процесса подряд.

Поток у адаптера БРОШЕННЫЙ, со своими слотами. Прервать чужой синхронный
`exec` нечем — команда доработает до своего таймаута в любом случае, — но
платить за это вызывающий не должен: с `asyncio.to_thread` отмена не
возвращала управление, потому что `asyncio.run` на выходе ждёт
`shutdown_default_executor`. Слоты не общие с MCP: команда идёт минутами и
заняла бы те, которыми пользуется дискавери соседних агентов.

### Файловые тулы ядра идут инлайн

`acall` объявляют не только асинхронные тулы. Четырнадцать встроенных файловых
объявляют его, чтобы исполняться **на loop**, а не в потоке из пула:

* девять из `tools/fs/` — `fs_read_file`, `fs_write_file`, `fs_append_file`,
  `fs_apply_file_edits`, `fs_search_and_replace`, `fs_search_files`,
  `fs_list_files`, `fs_file_info`, `fs_save_base64_file`;
* `project_memory` — `read_text` / atomic write / восстановление из бэкапа;
* четыре скилловых читателя — `skills_list`, `skills_load`,
  `skills_read_reference`, `skills_read_asset`. Они не наследуют
  `AbstractSimpleTool` и лежат не в `tools/fs/`, из-за чего первая правка их и
  пропустила; в файлы они ходят наравне с остальными, а `skills_list` вдобавок
  пересканирует все три корня скиллов на **каждый** вызов.

Причина в том, что у файлового I/O нет нативной асинхронной формы. Всё, что
выглядит как «async file», — обёртка над тем же пулом: у `anyio` каждый метод
`AsyncFile` это буквально `await to_thread.run_sync(self._fp.read, …)`, у
`aiofiles` — `run_in_executor`. Единственный настоящий нативный путь,
`io_uring`, есть только на Linux и требует C-расширения. Значит выбор не
«поток или корутина», а «поток или инлайн» — а обычные чтение и запись
отвечают за микросекунды, и передача в пул и обратно стоит дороже самой
операции. Замерено на записи 32 МиБ: 6.1 мс лага цикла инлайн против 2.7 мс в
потоке, при бюджете приёмки 150 мс.

По той же причине `download_file` пишет тело инлайн. Сеть в нём остаётся
нативно асинхронной (`httpx.AsyncClient`) — поток убран только с записи.

Два тула из этого списка не сводятся к «позвать `__call__` инлайн», и оба
случая стоит знать, прежде чем добавлять `acall` новому туду:

* **`project_memory`** на переполнении ужимает содержимое через LLM. Это
  единственное место в его `append`, которое ходит по сети, и `acall` ждёт
  `acompact_text` нативно — остальное (чтение, атомарная запись, откат из
  бэкапа) идёт инлайн.
* **`skills_run_script`** файлов почти не трогает — он запускает subprocess на
  весь таймаут. У запуска процесса нативная асинхронная форма ЕСТЬ, и его
  `acall` ждёт `backend.aexec_argv` (`asyncio.create_subprocess_exec`). Поток
  с этого пути ушёл совсем, а не переехал на loop.

Общее правило: инлайн уместен там, где операция короткая и нативной
асинхронной формы у неё нет. Если по пути есть сеть, subprocess или другое
долгое ожидание — нужен настоящий `await`, а не проброс.

### Где поток остаётся — и почему

Все двадцать пять встроенных тулов объявляют `acall` и в пул не уходят:
короткие идут инлайн, а у долгих есть нативная форма и они идут через неё —
`exec_command` через `backend.aexec`, `exec_python` через
`backend.arun_python`, `skills_run_script` через `backend.aexec_argv`,
`exec_sleep` через `asyncio.sleep`, `turn_ask_human` через
`await ctx.ask_human`.

У `exec_command` и `exec_python` есть тонкость. Оба обёрнуты
`moderate_command_execution`, а его тело синхронное и зовёт LLM-судью
(на конфиге по умолчанию — `enabled=True, mode="ask"`). Поэтому у `dual_wrap`
есть флаг `body_may_block`: тело этого одного гварда исполняется вне loop, на
собственном потоке через `run_abandonable` (не в общем пуле — иначе оно
вставало бы в очередь за чужой работой), а судью ждёт `run_coro_blocking`.
Сам запуск процесса при этом асинхронный: гвард ждёт тул через `await`.

Оставшиеся в ядре `asyncio.to_thread` — не недоделка, каждый замерен:

* **`backends/async_protocol.SyncExecAdapter`** — не «для гипотетического
  чужого бэкенда»: через него ходит `TrackingFsBackend` (TUI), инлайн там даёт
  1037 мс лага. `HarborBackend` из этого списка **вышел**: под ним всегда был
  нативный async (`env.exec` — корутина Harbor), просто бэкенд не объявлял
  порт и обёртка уводила каждый запуск команды в общий пул. Порт объявлен —
  запуск идёт на loop вызывающего, без потока.
* **`tools/exec/fetch_url.py`, разбор HTML** — нативной async-формы у разбора
  нет ни у одной библиотеки, а работы там секунды. Поток режет худший разрыв
  цикла: замерено на странице 1.2 МБ — 237 мс инлайн (один тик пульса за весь
  разбор) против 22 мс и 22 тиков в потоке.

  Механизма два, и работают оба сразу. lxml отпускает GIL примерно на
  четверти времени: два параллельных разбора идут 1.53× от одного, а не 2×.
  Остальное вытесняет переключение CPython каждые 5 мс — оно же спасает и
  чисто питоновскую часть обёртки. Контроль: чистый питоновский цикл даёт
  ровно 1.93×, то есть параллелизма нет вовсе, и всё равно в потоке loop
  тикает (22 мс медиана против 180 инлайн).

  Вывод опирается на замер ОТЗЫВЧИВОСТИ, а не на рассуждение о GIL: по
  отдельности ни «отпускает», ни «держит» решения не дают.
* **Легаси-транспорты MCP (`http`/`sse`)** из этого списка тоже **вышли**.
  Уходили в `run_abandonable` как «не имеющие асинхронной формы» — форма была
  всё это время: обмен идёт через `httpx`, а у него есть `AsyncClient`.
  В потоке осталась только долгоживущая stdio-сессия, и это сознательное
  ограничение. Причина именно в долгожительстве: сессию заводит дискавери,
  зовут тулы и закрывает `arun`, а TUI гоняет каждый ход своим `asyncio.run` —
  asyncio-подпроцесс столько не живёт (проверено запуском: на втором
  `asyncio.run` он отдаёт «Future attached to a different loop»). Поэтому
  процесс держится на `Popen`, который к loop не привязан вовсе, а обмен с ним
  идёт в потоке. Одноразовым stdio-вызовам это ограничение не касается.
* **`tools/turn/ask_human.py`, чтение stdin** — только когда порт
  `ctx.ask_human` не задан. У построчного `input()` нативной формы нет, а
  ждать человека на loop нельзя. Порт встраивающего, наоборот, ждётся
  нативно — на его же loop.
* **`processing_responses._acall_blocking_hook`** — ветка для вызывающих,
  передавших синхронный хук. Ядро передаёт только корутинные имена, это
  сторожит `test_loop_hooks_are_native.py`.

Цену стоит знать: на loop встают и гварды путей, а в режиме `security: ask`
они ждут подтверждения человека. Приложению с живым loop это заметно, если
оно включает `ask` и одновременно обслуживает других — тогда либо `ask` не
включают, либо агента держат в отдельном процессе.

## Порты приложения

Ядро — библиотека, и ресурсы приложения ей не принадлежат:

```python
ctx.ask_human = my_ask          # спросить пользователя: функция или корутина
ctx.on_stream_delta = my_sink   # живые дельты ответа
ctx.on_progress = my_progress   # прогресс подключения MCP при сборке контекста
```

`ask_human` не задан → тул `turn_ask_human` читает stdin, как раньше в CLI.

### Логи

Отдельной абстракции нет и не нужно: `ctx.logger` — обычный
`logging.Logger`, а лучшего контракта, чем стандартная библиотека, не
придумать. Нужен только способ подключиться:

```python
agent = await AsyncAgent.create(cfg, log_handlers=[MyHandler()])
```

Хендлер **добавляется** к файловому выводу ядра, а не заменяет его; отключить
файл по-прежнему можно через `save_logs: false`.

Цеплять хендлер к `ctx.logger` вручную ПОСЛЕ сборки тоже можно, но раньше это
был единственный способ, и об этом никто не знал: ядро делает
`logger.handlers.clear()` в начале сборки и стирает всё, подключённое заранее.

Если приложение настроило `logging` по-своему и хочет видеть жизнь агента у
себя, нужен ещё флаг — иначе оно не увидит ничего:

```yaml
logging:
  propagate: true     # дефолт false: ран пишет в свой файл и не засоряет чужие хендлеры
```

Осторожно с `ctx.logging_path` и `ctx.summary_trace_path`: это пути к **файлам**,
и при `save_logs: false` они пусты.

### Кэш MCP-дискавери

Дискавери — самая дорогая часть старта (866–1405 мс против 2.4–6.9 мс на всё
остальное). Один агент платит её один раз, но приложение, поднимающее агентов
пачками, заплатит за каждого. Кэшем владеет вызывающий:

```python
cache = ToolsCache(config_dict)
a1 = await AsyncAgent.create(cfg, tools_cache=cache)
a2 = await AsyncAgent.create(cfg, tools_cache=cache)   # уже бесплатно
```

Кэш достаётся и субагентам через `ctx` — иначе каждый спавн стоил бы секунду.
Процессным синглтоном он намеренно не сделан: скрытое время жизни, протечка
между арендаторами сервера с разными наборами серверов и переживание между
тестами. Разным наборам — разные кэши, это решает владелец.

### Живые дельты и финальный ответ

```python
async for kind, text in agent.stream("вопрос"):
    ...                       # kind: "answer" | "think" | "reset"
print(agent.last_answer)      # финальный ответ хода
```

Очередь заводится **на вызов**: два параллельных `stream()` не растаскивают
события друг у друга, а после обычного `run()` в следующем `stream()` не
всплывают старые дельты. Агент без подписчиков не копит ничего.

`last_answer` существует потому, что async-генератор не умеет вернуть значение
итерирующему. Раньше результат хода просто терялся, и приходилось склеивать
ответ из дельт — а это не то же самое: ход закрывается `turn_finish`, и прозы
перед ним может не быть вовсе.

Ограничение: два `stream()` на ОДНОМ агенте запускают два хода, а sink живёт на
`ctx` и о ходах не знает — каждый подписчик увидит дельты обоих. Для двух
независимых потоков событий нужны два агента.

### Хранилище тредов

```python
agent = await AsyncAgent.create(cfg, thread_store=MyDbStore())
```

Начинайте с `ThreadStoreBase` (`gc_core.thread_store_base`): ABC с
одиннадцатью абстрактными методами, общими инвариантами и отказом в
конструкторе, если метод забыт. Наследовать не обязательно — контракт
существует и как `Protocol`, и хранилище, совпавшее по сигнатурам,
принимается как прежде. Не передали ничего — файловое хранилище, ровно
прежнее поведение.

Для асинхронного клиента (`redis.asyncio`, `asyncpg`) есть `AsyncThreadStore`:
те же одиннадцать методов с приставкой `a`, ядро ждёт их нативно. Синхронные
хранилища оно заворачивает в адаптер само.

Всё остальное — одиннадцать методов, восемь свойств, которые легко нарушить,
конформанс-набор, таблица лага для синхронного сетевого клиента — вынесено в
отдельный документ: **[thread-store.md](thread-store.md)**.

## Хранилище с асинхронным клиентом

`ThreadStore` синхронный, и это правильный контракт по умолчанию: файлы и
локальная база отвечают за микросекунды. Но у `redis.asyncio` и `asyncpg`
синхронного клиента нет вовсе. Для них — `AsyncThreadStore`
(`gc_core.thread_store_async`): те же одиннадцать операций с приставкой `a` и
теми же свойствами.

```python
class RedisThreadStore:
    async def aload_messages(self, system_id, thread_id): ...
    async def aload_thread_state(self, system_id, thread_id): ...
    # ...остальные девять

agent = await AsyncAgent.create(cfg, thread_store=RedisThreadStore(url))
```

Ядро ждёт такое хранилище **нативно**; синхронное — заворачивает в
`SyncThreadStoreAdapter`. Проверить себя: `assert_conforms_async(factory)` —
тот же набор свойств.

**Смешивать формы нельзя.** Либо все одиннадцать методов синхронные, либо все
одиннадцать корутинные с приставкой `a`. Половинчатая реализация отвергается
при создании агента: иначе часть записей ушла бы в базу, а часть потерялась
молча — синхронные вызывающие корутину просто отбрасывают.

### Синхронное сетевое хранилище

Работать будет, но цикл агента блокируется на каждом обращении. Замеренный
закон:

```
худший разрыв цикла ≈ 16 × RTT + 20 мс
```

25 обращений за прогон ложатся в два куска подряд без возврата в цикл — 11 и
14 обращений; закон — по крупнейшему.

Замерено прогретым пульсом приёмки на ходах
`test_acceptance_sdk_thread_store.py` с настоящим `exec_sleep`; судит
`gc_testkit.assert_loop_was_free`:

| RTT на вызов | худший разрыв | разрывов от 20 мс | приёмка |
|---|---|---|---|
| 0 (файлы, память) | 14–17 мс | 0 | проходит |
| 1 мс | 28–38 мс | 2 | **не проходит**: два пропуска при допуске в один |
| 5 мс (локальный Redis) | ~100 мс | 2 | **не проходит**: два пропуска |
| 10 мс | ~185 мс | 2 | **не проходит**: и потолок 150 мс |
| 20 мс (облако, другая зона) | ~340 мс | 2 | **не проходит**: и потолок |

Числа машинозависимы: потолок пробивается около 8 мс на вызов, и на более
медленной машине граница сдвинется вниз. Но приёмка отвергает синхронное
хранилище раньше потолка — по правилу пропусков, уже при 1 мс.

Отличить быстрое локальное хранилище от сетевого статически нельзя, поэтому
адаптер меряет первые обращения и один раз пишет предупреждение
`thread_store_blocking_loop` с именем метода. Увидели его — реализуйте
`AsyncThreadStore`.

### Архив перед компакцией

Необязательная способность: если у хранилища есть метод `archive_and_replace`,
компакция зовёт его; если нет — история замещается через `reset` +
`append_messages`, без архива. Так и задумано — «отложить прежнюю историю
рядом» осмысленно для файлов, а у базы это либо отдельная таблица, либо не
нужно вовсе.

Два свойства обязательны, и они закреплены общим набором тестов на обе
реализации (`test_thread_store_contract.py`):

* **идемпотентность** `append_messages` — батч персистится дважды (после тулов
  и на выходе цикла), повтор не должен задваивать историю;
* снятие последнего флага убирает секцию `runtime` **целиком** — «нет флагов» и
  «пустой словарь» обязаны читаться одинаково.

Прямых обращений к файлам мимо этого контракта в ядре нет — это сторожит
`test_no_direct_file_calls_left_in_core`.

## Приёмка

Три критерия, которые сторожит
[`test_acceptance_non_blocking.py`](../packages/core/tests/test_acceptance_non_blocking.py):

1. **Изоляция.** Агент собирается там, где установлен только `gc-core`;
   `gc_cli`, `gc_tui`, `gc_server` в `sys.modules` не попадают.
2. **Неблокирование.** Соседняя корутина тикает с шагом 10 мс всё время
   жизни агента — от сборки до закрытия; пульс прогрет и стартует до сборки.
   Медиана разрыва — у шага, ни одного разрыва от 150 мс и не больше двух от
   20 мс: у хода два куска без уступки, в которых файловое хранилище тредов
   пишет инлайн. Окно замера — под заглушённым сборщиком мусора; критерий —
   `gc_testkit.assert_loop_was_free`.
3. **Параллельность.** Два агента через `asyncio.gather` укладываются
   быстрее, чем в 1.6× одиночного прогона.

Проверить на своей установке:

```bash
uv venv /tmp/gc-core-only && source /tmp/gc-core-only/bin/activate
uv pip install "gc-core @ ./packages/core"
python -c "import gc_core.aio, sys; print('gc_tui' in sys.modules)"   # False

cd packages/core && python -m examples.async_embed ~/.gc/config.yml \
    "посчитай 2+2" "назови столицу Франции"
```

## Что осталось за пределами loop

- **TUI** держит агента в своём daemon-потоке и запускает там собственный
  `asyncio.run`. Поток нужен не ядру, а интерфейсу: не делить loop с Textual.
  Пользователя TUI спрашивает через порт `ctx.ask_human`, а не через `input()`.
- **Тело `moderate_command_execution`** — единственный синхронный гвард,
  исполняется на своём потоке (`run_abandonable`), см. выше.

## HTTP-тулы

`exec_fetch_url`, `exec_simple_fetch_url` и `exec_download_file` переведены на
`httpx`:

- сеть — через `await`;
- разбор HTML — через `asyncio.to_thread` (trafilatura/lxml — чистый CPU, на
  большой странице это секунды).

Прокси эти тулы берут из окружения (`HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY`)
через `resolve_proxies`, а не через `trust_env`: включать `trust_env` нельзя —
вместе с прокси вернулось бы чтение `~/.netrc`, а URL сюда приходят от модели.

`requests` из зависимостей ядра **ушёл** — весь HTTP на httpx. Переезд был не
про асинхронность (у httpx есть синхронный `Client`), а про одну зависимость
вместо двух на один и тот же протокол.

Две тонкости, которые всплыли по дороге:

* `NO_PROXY` httpx применяет только сам, при `trust_env=True` — а он нам не
  подходит, потому что вместе с прокси включает чтение `~/.netrc`. Матчинг
  вынесен в `utils/no_proxy.py`; его эквивалентность
  `requests.utils.should_bypass_proxies` закреплена дифференциальным тестом на
  221 паре «URL × список».
* Ловушка с netrc, ради которой заводилась `NO_NETRC_SESSION`, у httpx
  отсутствует структурно: он **не читает** netrc сам, `NetRCAuth` нужно
  передавать явно. Имя переменной оставлено — на неё ссылаются вызывающие, —
  а `trust_env=False` по-прежнему значим: он отключает env-прокси и CA из
  окружения, которые мы передаём явно.

Откат сторожит `test_no_requests_dependency.py`: он проверяет и манифест, и
код (через AST, чтобы не спотыкаться о докстроки, где объяснено, как было).
