# A2A-фасад: `gc-serve a2a`

Поверхность `a2a` сервера `gc-serve` ([server.md](server.md)): `gc-serve a2a`
отдельно или вместе с другими поверхностями одним процессом. Другой агент
открывает этого агента по [Agent2Agent Protocol 1.0](https://a2a-protocol.org/v1.0.0/specification/)
и ставит задачу. Протокол ведёт официальный [`a2a-sdk`](https://github.com/a2aproject/a2a-python)
(1.2.x): разбор запросов, модели (proto `lf.a2a.v1`), стрим и push. Наше —
исполнитель задач и хранилища. Петля тулов остаётся внутри ядра: пир присылает
текст и получает либо ответ, либо вопрос.

Это не `gc-serve chat` и не `gc-acp`. Для HTTP-чата — [chat.md](chat.md), для
IDE — [acp.md](acp.md).

## Установка

SDK — extra пакета `gc-server`:

```bash
uv tool install "gc-server[a2a] @ git+https://gitverse.ru/gigacode-ai/universal-agent#subdirectory=packages/server"
```

Без extra `gc-serve a2a` не стартует: «поверхность a2a работает на a2a-sdk:
установите gc-server[a2a]».

## Операции

Два биндинга, оба объявлены в карточке:

| Биндинг | Адрес |
|---|---|
| JSON-RPC 2.0 | `POST /rpc` |
| HTTP+JSON (REST) | `/message:send`, `/message:stream`, `/tasks`, `/tasks/{id}`, `/tasks/{id}:cancel`, `/tasks/{id}:subscribe`, `/tasks/{id}/pushNotificationConfigs…` |

| Операция | Что делает |
|---|---|
| `SendMessage` | поставить задачу или ответить на её вопрос; ждёт конца хода или вопроса, с `configuration.returnImmediately` — возвращает задачу сразу |
| `SendStreamingMessage` | то же, события задачи — потоком (SSE) |
| `GetTask`, `ListTasks` | задача и список задач — с любого инстанса |
| `CancelTask` | отменить ход; задача — `TASK_STATE_CANCELED` |
| `SubscribeToTask` | события идущей задачи — на инстансе, который её ведёт |
| `…PushNotificationConfig…` | настройки push задачи (если push включён, см. ниже) |

Ошибки протокола (неизвестный метод, задача не найдена, неверные параметры,
версия протокола в заголовке `A2A-Version`) отдаёт SDK по таблице
спецификации.

## Карточка

`GET /.well-known/agent-card.json` — без авторизации.

```json
{
  "name": "GigaCode",
  "description": "Универсальный агент GigaCode",
  "supportedInterfaces": [
    {"url": "http://127.0.0.1:8091/rpc", "protocolBinding": "JSONRPC", "protocolVersion": "1.0"},
    {"url": "http://127.0.0.1:8091", "protocolBinding": "HTTP+JSON", "protocolVersion": "1.0"}
  ],
  "version": "0.4.0",
  "capabilities": {"streaming": true, "pushNotifications": false},
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "skills": [{"id": "agent", "name": "Агент", "description": "…", "tags": ["agent"]}]
}
```

`pushNotifications` — `true`, только если задан `a2a.push_allowed_hosts`. Адреса
интерфейсов — из `a2a.public_url` (адрес JSON-RPC с `/rpc` на конце, как раньше,
или корень, под которым висят оба), иначе из адреса сокета; при bind на
`0.0.0.0` задайте `public_url`. С токеном карточка объявляет схему `bearer`
(`httpAuthSecurityScheme`, `Bearer`) и требование к ней.

## Диалог, задача, ход

- **Диалог** — `contextId` и тред хранилища `system="a2a"` с тем же id. Агент
  помнит диалог: следующая задача в том же `contextId` продолжает историю.
- **Задача** — один ход агента. Первое сообщение без `taskId` создаёт задачу
  (`TASK_STATE_SUBMITTED` → `TASK_STATE_WORKING`).
- **Вопрос.** `turn_ask_human` агента становится вопросом задачи:
  `TASK_STATE_INPUT_REQUIRED`, текст — в `status.message`. Ход на вопросе
  завершается: тред свободен, агент ничего не держит, ожидание ответа не
  ограничено по времени и переживает перезапуск. Ответ — следующее
  сообщение с тем же `taskId` (и `contextId` задачи) на любом инстансе: ход
  продолжается с ответом. Отмена такой задачи освобождает диалог, а вопрос
  следующий ход закроет «без ответа».
- **Очередь задач в диалоге.** Пока в `contextId` идёт ход или задача ждёт
  ответа, новая задача в нём — `TASK_STATE_SUBMITTED`: она в очереди диалога
  (порядок — по времени приёма) и стартует, когда диалог освободится. Ждёт
  её тот же запрос `SendMessage` (с `returnImmediately` — в фоне): статусы,
  стрим и push — как у обычной задачи. `CancelTask` задачи из очереди —
  `TASK_STATE_CANCELED`, она не стартует.
- **Итог.** Ответ — артефакт `answer`, `TASK_STATE_COMPLETED`. Ход, закрытый
  предложенным планом, — `COMPLETED` с текстом плана (одобрения плана в A2A
  нет). Досрочная остановка (лимиты шагов, токенов, тулов; недоступный судья)
  и сбой — `TASK_STATE_FAILED` с текстом «Ход не выполнен.» без подробностей
  ядра.
- **Каталог хода** — `metadata.cwd` сообщения (или запроса): абсолютный путь
  **внутри** `a2a.launch_root` (без него — внутри каталога процесса).
  Симлинки и `..` раскрываются, ходу отдаётся раскрытый путь: это периметр
  записи агента, выйти за корень пир не может. Без `metadata.cwd` — сам
  корень. Каталог диалога запоминается: продолжение с другим `cwd` —
  `TASK_STATE_FAILED`.

## Несколько инстансов

Задачи и настройки push лежат в хранилище тредов (`storage` в config.yml,
[server.md](server.md#хранилище-storage-в-configyml)): задача — снимки в
потоке `a2a.tasks` треда диалога (снимок на каждое изменение), в состоянии
фронтенда `a2a` — номер последнего снимка задачи, очередь диалога и его
корень; `taskId` находит тред алиасом `a2a-task:<id>`. `GetTask` и
`ListTasks` отвечают одинаково на любом инстансе, занятость диалога (ход,
вопрос, очередь) видна всем. Стрим и `SubscribeToTask` идущей задачи — на
инстансе, который её ведёт (межинстансный стрим SDK не подключён).
`CancelTask` на другом инстансе останавливает ход через поток `control` треда:
владелец увидит отмену на следующем шаге.

**Восстановление.** Раз в 30 с каждый инстанс ищет задачи, чей ход или
ожидание в очереди умерли вместе с инстансом (отметка молчит дольше минуты,
аренды треда нет): такая задача — `TASK_STATE_FAILED` «Ход прерван:
инстанс, который вёл задачу, остановился.», её место в диалоге
освобождается, очередь идёт дальше. Push об этом статусе не уходит (его
некому отправить из запроса). Остановка сервера — тоже прерывание: идущие
задачи подберёт восстановление другого инстанса.

## Push-уведомления

Адрес push задаёт пир, а запрос по нему делает сервер — поэтому по умолчанию
push выключен. `a2a.push_allowed_hosts: [hooks.example.com]` включает его
только для этих хостов, и каждый адрес ещё проверяется валидатором SDK (не во
внутреннюю сеть, метаданные облака и т.п.). Без списка карточка не объявляет
push, а настройка push в запросе не действует. Настройки хранятся в треде
`a2a/push-<taskId>`.

## Транспорт и защита

- Непустой токен (`a2a.auth_token`, по умолчанию `server.auth_token`) —
  `Authorization: Bearer <token>` на всём, кроме карточки, иначе `403`.
  Адрес не loopback без токена — отказ старта.
- `POST` — только с `Content-Type: application/json`, иначе `415`: такой
  запрос браузер не шлёт без preflight. На loopback-бинде заголовок `Host` —
  только loopback-имя (DNS rebinding), иначе `400`.

## Режимы разрешений

Поверхность `a2a` объявляет канал «человека нет, слова внешние». Что из этого следует:

- Работают режимы разрешений `edit` (по умолчанию) и `auto` (не путать с уровнем модели
  `auto` — автовыбором). `plan` и `manual` здесь не функции, а
  ограничения: одобрить план и подтвердить действие некому (согласие пира — не согласие
  пользователя), поэтому `plan` не выходит из `plan`, а `manual` отклоняет всё, что
  требует подтверждения. Смены режима по протоколу нет. При старте с `default_mode: plan`
  или `manual` процесс пишет предупреждение в stderr и называет способ вернуть `edit`
  (флаг `--security.permissions.default_mode edit` или профиль); старт не прерывается.
- Слова пира для судьи действий в `auto` — **запрос внешней системы**: описание задачи и
  запреты из него учитываются, а разрешением на рискованное или на выход за пределы
  задачи оно не служит. Пауза судьи (три отказа подряд или двадцать за сессию) снимается
  следующим сообщением пира.
- Каталог хода (`metadata.cwd` внутри корня поверхности) и есть периметр проекта для
  режимов: в `auto` запись внутри него идёт без судьи.
- Запись в каталог `.git`, скиллы и настройки инструментов без человека — отказ.

## Секция `a2a` в config_server.yml

`os_backend` обязан быть `local`: рабочий каталог хода — путь на машине
процесса. Иной бэкенд — отказ старта до bind. Секция `a2a` в config.yml больше
не читается: `gc-serve a2a` при ней не стартует (её `auth_token` пропал бы
молча).

| Ключ | Дефолт | Смысл |
|---|---|---|
| `a2a.host` | `server.host` (`127.0.0.1`) | адрес bind |
| `a2a.port` | `8091` | порт |
| `a2a.public_url` | `null` | адрес в карточке (JSON-RPC с `/rpc` или корень); пусто — адрес сокета |
| `a2a.auth_token` | `server.auth_token` | пусто — без Bearer |
| `a2a.launch_root` | `null` | корень ходов: `metadata.cwd` пира — только внутри; пусто — каталог процесса |
| `a2a.push_allowed_hosts` | `[]` | хосты для push-уведомлений; пусто — push выключен |
| `a2a.name` | `GigaCode` | `name` карточки |
| `a2a.description` | краткое описание агента | `description` карточки и скилла |
| `a2a.text_answer_mode` | `allow` | проза без tool-call |
| `a2a.finish_gate_mode` | `off` | судья на `turn_finish` |
| `a2a.todo_reminder_steps` | `0` | напоминания `session_todo` |
| `a2a.agent_md_path` | — | роль агента этой поверхности (слой L0) |
| `a2a.agent_overrides` | `{}` | правки настроек агента поверх общих `agent_overrides` |

`turn_ask_human` остаётся в схеме: его текст становится вопросом задачи.
`turn_intermediate_reply` снимается — прогресс пиру не отдаётся. Подтверждения
в терминал сервера не уходят: канал объявлен «человека нет», и любой вопрос
режима разрешений или защищённых путей заканчивается отказом «спросить
некого». Остановка процесса снимает идущие ходы.
