# Серверный режим (REST-обёртка поверх gc-cli)

Существует серверный режим, который добавляет поверх CLI-агента REST‑слой на FastAPI.
Он позволяет принимать внешние события по вебхуку и запускать агента в фоне, используя те же конфиги и тулы.

## Установка зависимостей для сервера

Чтобы не тянуть FastAPI в чистый CLI‑режим, серверные зависимости живут за
дистрибутив `gc-server` — базовая установка их НЕ ставит:

```bash
uv tool install -e packages/server
# без клонирования репозитория:
uv tool install "gc-server @ git+https://gitverse.ru/gigacode-ai/universal-agent#subdirectory=packages/server"
```

Профиль добавляет `fastapi`, `uvicorn[standard]` и `psutil`, а также сами
`server.py`, `rest_api/`, `swarm/`. psutil нужен swarm-режиму (memory/cpu
enforcement); без него swarm деградирует до disk+timeout. Отдельного профиля у
swarm нет: он запускается только через `POST /swarm/run`, то есть без сервера
бесполезен.

> Раньше зависимости лежали в `server_requirements.txt`. Файл удалён — он пинил
> `uvicorn<0.31.0`, что **несовместимо** с `mcp==1.26.0` (тот требует
> `uvicorn>=0.31.1`). Конфликт не всплывал только потому, что файл ставили
> отдельно, мимо резолвера зависимостей.

## Конфиги и файлы для серверного режима

Для работы серверного режима необходимо подготовить:

- **CLI-конфиг агента**:
  - скопируйте `demo_config.yml` (или другой пример) в `config.yml` и настройте:
    - адрес бэкенда агента (API `v1/responses`);
    - параметры модели (`model`, `max_steps`, `system_prompt_id` и т.д.);
    - секцию `mcp-servers` (если вы используете MCP).

- **Конфиг сервера** `config_server.yml` (лежит в корне проекта):

  Пример (демо-конфиг, уже есть в репозитории):

  ```yaml
  server:
    host: "0.0.0.0"
    port: 8000
    log_level: "info"
    # Опциональный токен для простой авторизации на REST-слое.
    # Если задан непустой auth_token, все запросы к серверу должны содержать заголовок:
    #   Authorization: Bearer <auth_token>
    # Иначе вернётся 403.
    auth_token: null
    # Сколько секунд вебхук ждёт, пока контекст его задачи строит другой
    # запрос; по истечении — 503 (см. «Одна задача — один прогон» ниже).
    # Потолок у ожидания, а не у сборки: сама сборка не прерывается.
    context_build_wait_seconds: 120

  defaults:
    # Идентификатор системы по умолчанию, если во входном JSON нет поля system.
    system: "generic"

  agent:
    # Путь до файла с универсальными инструкциями агента. Абсолютный — как есть;
    # относительный ищется сначала рядом с ЭТИМ файлом (config_server.yml), затем
    # среди bundled-ассетов дистрибутива (packages/core/assets в репозитории,
    # site-packages/gc_core/assets в установке). Не нашёлся нигде — WARNING в лог
    # и агент работает без системных инструкций.
    server_agentmd_path: "./server_agent.md"

  # Набор аргументов, переопределяющих значения в конфиге cli клиента в серверном запуске.
  # Ключи — пути настроек через точку (как в config.yml и `gc-cli config explain`).
  agent_overrides:
    # Список simple-tools, запрещённых в серверном режиме (чтобы не портить файлы библиотеки).
    agent.stop_tools:
      - fs_write_file
      - fs_append_file
      - fs_read_file
      - fs_list_files
      - fs_find_files_by_name
      - fs_find_in_files
      - fs_search_and_replace
      - fs_view_image
      - exec_command
      - exec_python
      - turn_ask_human
  ```

  - Путь к этому файлу можно переопределить через переменную окружения `SERVER_CONFIG_PATH`.
  - Секция `agent_overrides` перекрывает соответствующие поля `config.yml`
    (аналогично тому, как CLI‑аргументы `--agent.max_steps` перекрывают конфиг в `packages/cli/src/gc_cli/cli.py`).
  - Ключ — **путь настройки через точку** (`agent.max_steps`, `backend.completions_url`)
    или вложенная секция (`agent: {max_steps: 100}`); заданные в секции поля перекрываются,
    остальные остаются из `config.yml`. Прежние плоские имена (`max_steps`, `stop_tools`)
    не принимаются: сервер не стартует, а сообщение подсказывает путь
    (`agent_overrides: неизвестная настройка max_steps (возможно, agent.max_steps)`).
  - **Унификация webhook ↔ swarm:** `agent_overrides` применяется и к webhook'у, и
    к swarm-режиму в одном и том же виде:
    ```yaml
    agent_overrides:
      agent.max_steps: 100
      backend:
        completions_url: "http://custom-llm:8011/v1/chat/completions"
    ```
  - **Автовыбор уровня:** `agent_overrides.level: auto` работает как любой другой
    оверрайд — включает автовыбор уровня модели (см.
    [«Автовыбор уровня модели»](auto-routing.md)) для запусков этого сервера. Если
    фича недоступна (`agent.auto_routing: false`, `backend.api_mode: responses`,
    легаси-форс `--agent.model`/`agent_overrides.agent.model`, во всех уровнях одна модель или — под
    политикой `two_level` — одна модель в паре: «в паре light+default одна модель; другая
    пара — auto_routing_safe_level: max»),
    при создании рана в лог прогона уходит тот же текст уведомления, что CLI и TUI
    показывают своим каналом, но уровнем `warning`; агент при этом работает уровнем
    `default`. Поля уровня в теле запроса нет: уровень задаёт только конфиг сервера.
    `agent_overrides.agent.auto_routing_safe_level` и
    `agent_overrides.agent.auto_routing_two_level` задают пару уровней, длительность
    слабой и сильной серий и порог начального судьи пары. Политика одна — `two_level`.
    Переигрыш важных вызовов, некорректного вызова и ответа без вызова инструмента
    работает тем же механизмом, что в CLI и TUI: ответ слабой модели отбрасывается,
    запрос повторяется на сильной модели пары. MCP-тулы по имени не классифицируются
    как важные. Ограничения инструментов действуют на весь собранный набор:
    `agent.stop_tools` снимает встроенные тулы, скиллы и MCP. Демо-конфиг сервера
    запрещает запись и правку файлов, команды оболочки и `turn_ask_human`.
    Запрещённый вопрос человеку от слабой модели даёт повод `invalid_call`
    для переигрыша, а от сильной — сигнал `tool_call_error`.


- **Файл инструкций агента для сервера**:
  - по умолчанию берётся bundled `prompts/server_agent.md` из ассетов `gc-core`;
  - путь задаётся в `config_server.yml` через `agent.server_agentmd_path`;
  - внутри `states.State` этот путь попадает в `agent_md_path`, и содержимое файла подмешивается
    в `promptVariables["userInstructions"]`.
  - **Слои инструкций L0–L3 работают в серверном режиме так же, как в CLI.** `server_agentmd_path` является аналогом L0 (системный промпт). Если в рабочем каталоге сервера присутствует `.gc/AGENTS.md` — он также подхватывается как project-level слой инструкций.

- **Папка для хранения тредов**:
  - на файловую персистентность отвечает тот же механизм, что и в CLI (`packages/core/src/gc_core/thread_store.py`);
  - по умолчанию используется папка `threads` в корне проекта (`mini-cli-pub/threads`);
  - опциональный параметр `threads_data_path` задаётся в `config.yml` и должен быть **абсолютным путём**; если не задан — используется дефолт `<state>/projects/<project-slug>/threads/`;
  - серверный режим НЕ переопределяет этот путь, он использует те же настройки, что и CLI.

- **Папка со скиллами**:
  - как и для CLI, пути к скиллам настраиваются в `config.yml`;
  - серверный режим использует ту же сборку тулов (`build_tools_data(settings)`) и `skills_registry`,
    но с учётом `agent.stop_tools` из `agent_overrides` (опасные FS‑тулзы вырезаются из реестра - чтобы не работать с файловой системой веб приложения).

## Запуск серверного режима

После установки профиля `gc-server` и настройки конфигов сервер запускается
точкой входа:

```bash
gc-serve
```

Из рабочей копии по-прежнему работает и запуск модулем:

```bash
uv run python -m gc_server.server
```

> Точка входа `gc-serve` появилась вместе с профилями установки. Тогда же
> починен запуск из установленного колеса: в `server.py` стояло
> `uvicorn.run("src.server:app", ...)`, а под колесом (`sources = ["src"]`)
> модуль называется `server`, поэтому строка резолвилась только из корня репо.

По умолчанию сервер стартует на `http://0.0.0.0:8000` (см. `config_server.yml` / секция `server`).

Основные эндпоинты:

- `GET /healthcheck` — простой health‑чек:

  ```json
  {"status": "ok"}
  ```

- `POST /events/webhook` — входящий вебхук:
  - тело запроса — произвольный JSON‑объект;
  - поле `task_id`:
    - если указано и непустое — используется как есть;
    - если нет — сервер генерирует `task_id` (GUID) и подставляет его в JSON;
  - поле `system`:
    - если указано — нормализуется (обрезка пробелов, нижний регистр);
    - если нет — берётся `defaults.system` из `config_server.yml` (по умолчанию `generic`);
  - при первом запросе по паре `(system, task_id)` сервер:
    - занимает ключ задачи (бронь) и строит `RunContext` на основе `config.yml` +
      `agent_overrides` из `config_server.yml` — асинхронно, не останавливая
      остальные запросы;
    - запускает прогон задачи — asyncio-задачу на loop сервера
      (`AgentExecutor.arun(...)`), тред — `task_id` — и отвечает
      `{ "status": "started", ... }`;
    - если сборка контекста упала — отвечает `500`, бронь снимается;
  - при последующих запросах с теми же `(system, task_id)` — см. «Одна задача —
    один прогон» ниже: `queued`, ожидание чужой сборки или `503`.

- `GET /runs/{system}/{task_id}` — статус прогона задачи:
  - `running` — прогон идёт; `started_at` — его старт, `last_activity_at` —
    последнее событие прогона: старт, принятое сообщение, конец каждого хода
    (в том числе хвостового, см. ниже);
  - `running` отдаётся и пока контекст задачи строится, а прогона ещё нет: тогда
    `started_at` и `last_activity_at` — время, когда взята бронь. Зависшая сборка
    поэтому стареет для сторожа по `last_activity_at` так же, как зависший
    прогон;
  - `completed` — `finished_at` и `result`. `result` — ответ **последнего** хода
    прогона: хвостовой ход идёт по тому же треду и отвечает с учётом всего, что
    было до него, поэтому это итог прогона задачи. Ответы прежних ходов — в
    `GET /logs/{system}/{task_id}`;
  - `failed` — прогон упал, `error` — `repr` исключения;
  - `cancelled` — прогон сняли (остановка сервера, отмена задачи). Это не отказ
    агента, поэтому и статус отдельный;
  - `404` — нет ни прогона, ни брони (или запись завершённого прогона уже
    вытеснена);
  - статусы **не персистентны**: после завершения хранятся только в памяти
    процесса (15 минут, не больше 500 записей); для долговременной истории
    используйте логи тредов.

- `GET /logs/{system}/{task_id}` — получение логов работы агента по треду:
  - в качестве `thread_id` используется `task_id`, с которым запускался агент;
  - при успехе возвращает JSON:
    - `status: "ok"`;
    - `system`, `task_id`;
    - `meta` — содержимое файла `meta_<thread_id>.json` (или `{}` если метаданных нет);
    - `messages` — список сообщений из `data_<thread_id>.jsonl` (payload каждого сообщения);
  - если для указанного `task_id` нет ни метаданных, ни сообщений — возвращает `404` с `{"status": "not_found"}`;
  - логи тредов **персистентны** в рамках выбранного хранилища (по умолчанию — файловая система приложения в директории `threads`).

### Одна задача — один прогон

У пары `(system, task_id)` в каждый момент не больше одного прогона, и
сообщение, которому ответили `queued`, до агента доходит — или его потеря
остаётся в логе.

**Пока строится контекст.** Ключ задачи занят бронью с первого вебхука, ещё до
сборки контекста. Вебхук, пришедший в это время, ждёт конца чужой сборки и
проходит путь заново: прогон стартовал — сообщение уходит в него (`queued`);
сборка упала — вебхук строит контекст сам (`started`). Ждёт он не дольше
`server.context_build_wait_seconds` (по умолчанию 120 с) — в сумме за запрос,
даже если чужих сборок по очереди было несколько. По истечении — `503`:

```json
{"detail": {"status": "error", "payload": "task context is still being built, retry later"}}
```

Сообщение при этом **не принято** — повторите запрос. Сборка, которую ждали,
продолжается: своего дедлайна у неё нет, медленная сборка законна. В лог
пишется `WARNING` с событием `context_build_wait_timeout`.

**Пока идёт прогон.** Сообщение кладётся в очередь идущего прогона, и сервер
сразу отвечает `queued`; цикл агента забирает очередь на следующем шаге. Если
модель только что вернула вызовы тулов, они сначала исполняются, и сообщение уходит
модели вместе с их ответами.
`trace_id` такого вебхука не применяется: контекст прогона уже собран — об этом
пишется событие `trace_id_ignored` (см. [configuration.md](configuration.md)).

**Хвост прогона.** Закрыв ход, прогон ещё сохраняет тред и закрывает
MCP-сессии, и всё это время он жив: вебхуки получают `queued`. Сообщения,
легшие в очередь после последнего её забора циклом, прогон доигрывает
**отдельным ходом** того же исполнителя по тому же треду — и так, пока хвост не
опустеет. Прогон задачи может поэтому состоять из нескольких ходов; `result` в
статусе — ответ последнего из них.

**Хвост, который доставить некуда.** Остановленный, упавший и снятый прогон
хвост не доигрывает: это отменило бы остановку или спрятало отказ за статусом
следующего хода. Такие сообщения пропадают, но не молча — `WARNING` с событием
`run_tail_dropped` и полями `system`, `task_id`, `ending`, `count`:

- `ending=failed` — прогон упал;
- `ending=cancelled` — прогон сняли (остановка сервера, отмена задачи);
- `ending=stopped` — прогон остановлен методом реестра `stop` (HTTP-ручки
  остановки нет).

В `count` входит и батч хвоста, с которым умер хвостовой ход, — даже если он
умер в сетапе, не дойдя до модели: упал на чтении треда или сборке состояния,
снят остановкой uvicorn.

### Автоматическая чистка тредов

По умолчанию **выключена**. Включается секцией в `config_server.yml`:

```yaml
threads_cleanup:
  enabled: true
  interval_seconds: 3600
  ttl_days: 7
```

Дефолт выключенный не из осторожности вообще, а по конкретной причине: сервер
чистит НЕ свой каталог. `threads_data_path` в серверном режиме не
переопределяется (см. выше), поэтому чистка удаляет треды из того же стора, куда
пишут `gc-cli` и TUI, — то есть историю интерактивной работы в этом проекте.
Сервер, поднятый в каталоге проекта, снёс бы её молча.

Тред удаляется целиком — тем же путём, что удаление сессии в TUI: история, meta,
картинки (`images/`), сайдкар субагентов, архивы компакции, журнал правок и lock.
Meta без `system` и `thread_id` (старый формат) удаляется по имени файла вместе со
своим `data_*.jsonl`.

Включённая чистка объявляется в логе: каталог, срок хранения, интервал, и
отдельная строка на каждый проход, который что-то удалил. Если этих строк нет —
чистка не работает, и это её штатное состояние.

Без секции ротацию настраивайте вне приложения — например, cron-джобой
(`python -m gc_server.cleanup_threads --threads-dir ... --ttl-days ...`).

## Поведение инструментов в серверном режиме

Важное отличие от CLI:

- В `config_server.yml` в `agent_overrides` под ключом `agent.stop_tools` перечислены simple‑tools,
  которые **отключаются** в серверном режиме (fs/командные тулзы).
- При построении настроек агента для сервера (`build_agent_settings_for_server`) эти поля ложатся в `agent.stop_tools`,
  и `packages/core/src/gc_core/tools/registry.py` (`_apply_stop_tools`) автоматически вырезает такие тулы из реестра.
- Это защищает директорию библиотеки и окружение сервера от нежелательных изменений файловой системы.
- Имена сверяются точно, шаблонов нет: тул, появившийся в новой версии, сервер получит, пока его
  не впишут в `stop_tools`. При обновлении сверяйте свой `config_server.yml` с `demo_config_server.yml` —
  например, `fs_view_image` (просмотр картинок с диска сервера) добавлен вместе с картинками.

## Swarm-режим (только Linux)

Помимо webhook-режима, REST-сервер умеет запускать CLI-агенты в изолированных
bubblewrap-песочницах (swarm). Каждая задача форкается в отдельный процесс с
собственным workspace, ресурсными лимитами и полной изоляцией от серверного
процесса; ручки — `POST /swarm/run`, `GET /swarm/status/{system}/{task_id}`,
`GET /swarm/logs/{system}/{task_id}`.

Доставка запроса симметрична webhook'у: в обоих режимах агенту передаётся
**JSON-payload** из тела запроса. В webhook это user-сообщение
(`json.dumps(payload)`), в swarm — аргумент `-q "<payload-json>"` запускаемого
`gc-cli` внутри песочницы (отдельный файл `payload.json` не пишется).

Единственное исключение — поле `trace_id`: оба режима **снимают** его из payload
до доставки, потому что payload становится текстом задачи для модели, и трейс в
нём попал бы в промпт. В webhook он уходит в конфиг рана, в swarm — в песочницу
переменной `SWARM_TRACE_ID`, из которой обёртка добавляет `gc-cli --trace-id`.
Невалидное значение (управляющие символы, длиннее 200 символов) обе ручки
отклоняют с `400` и телом `{"status": "error", "payload": "invalid trace_id: ..."}` —
агент не стартует, сервер продолжает работать. Подробнее о трейсе — в
[configuration.md](configuration.md).
