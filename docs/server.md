# Сервер: gc-serve

Пакет `gc-server` — все сетевые входы агента в одном процессе или по
отдельности. Каждая поверхность — своё приложение на своём адресе:

| Поверхность | Порт по умолчанию | Что это |
|---|---|---|
| `webhook` | 8000 | задачи внешних систем: `POST /events/webhook`, статус, логи треда |
| `chat` | 8090 | OpenAI-совместимые `/v1/responses` и `/v1/chat/completions`, страница чата на `/` ([chat.md](chat.md)) |
| `a2a` | 8091 | агент как пир A2A: карточка и JSON-RPC ([a2a.md](a2a.md)) |
| `swarm` | 8092 | ручки вебхука, но задача исполняется `gc-cli` в песочнице bubblewrap ([swarm.md](swarm.md), только Linux) |

## Установка

```bash
uv tool install -e packages/server
# без клонирования репозитория:
uv tool install "gc-server @ git+https://gitverse.ru/gigacode-ai/universal-agent#subdirectory=packages/server"
# с драйвером базы для storage: (см. ниже)
uv tool install "gc-server[postgres]" …   # [mysql] | [redis] | [s3] | [all]
```

Пакет приносит `fastapi`, `uvicorn[standard]`, `psutil` (лимиты памяти и CPU
песочниц swarm) и `gc-stores` — хранилища тредов и агента в базах. Драйверы
баз — extras; SQLite — без extra.

## Запуск

```bash
gc-serve                                  # поверхности из server.apis (по умолчанию webhook)
gc-serve chat a2a                         # перечисленные — первыми аргументами
gc-serve webhook --config ./config.yml --server-config ./config_server.yml
gc-serve chat --agent.max_steps 30        # флаги настроек, как у gc-cli
```

Из рабочей копии — `uv run gc-serve …` или `uv run python -m gc_server.cli …`.

Флаги: `--config` (config.yml), `--profile`, `--server-config`
(config_server.yml), флаги путей настроек (`--agent.max_steps 5`). Поверхности
перечисляются **до** флагов: иначе значение флага читалось бы поверхностью.

Каждая поверхность слушает свой адрес, поэтому `gc-serve chat` и
`gc-serve webhook`, запущенные двумя процессами, не мешают друг другу, а
`gc-serve webhook chat` поднимает то же самое одним процессом. Поверхности с
одинаковым `host:port` — одно приложение (общий сокет); `webhook` и `swarm` на
одном адресе — отказ старта: у них одинаковые ручки. Адреса занимаются до
старта поверхностей: занятый порт — отказ, а не наполовину поднятый сервер.

Остановка (Ctrl+C, SIGTERM): поверхности перестают принимать запросы, идущие
прогоны вебхука снимаются (`cancelled`), песочницы swarm получают SIGTERM, затем
SIGKILL; хранилища закрываются последними.

## config_server.yml

Один файл на процесс: какие поверхности поднимать, где они слушают, токены и
правки настроек агента поверх `config.yml`. Пример с комментариями —
`demo_config_server.yml` в корне репозитория.

Где ищется: `--server-config` или переменная `SERVER_CONFIG_PATH` — явный
путь, файла нет — отказ старта. Без явного пути — каталог запуска, корень
рабочей копии, ассеты пакета; не нашёлся ни один — умолчания. Неизвестный ключ —
отказ старта с названием ключа.

```yaml
server:
  host: "0.0.0.0"         # по умолчанию для всех поверхностей
  auth_token: null        # общий токен; у поверхности может быть свой
  apis: [webhook]         # что поднимает gc-serve без аргументов
  log_level: "info"
  logging: {console_trace: false, save_logs: false}   # правки logging.* агента

agent_overrides:          # правки настроек агента — всем поверхностям
  agent.max_steps: 100

webhook:
  port: 8000
  default_system: "generic"
  agent_md_path: "./prompts/server_agent.md"
  context_build_wait_seconds: 120
  threads_cleanup: {enabled: false, interval_seconds: 3600, ttl_days: 7}
  agent_overrides:        # только вебхуку, поверх общих
    agent.stop_tools: [fs_write_file, exec_command, turn_ask_human]

chat: {port: 8090, cors_origins: [], launch_root: null}
a2a: {port: 8091, public_url: null, name: "GigaCode"}
swarm: {port: 8092, max_concurrent: 10}
```

У каждой поверхности есть `host`, `port`, `auth_token`, `agent_overrides` и
(кроме swarm) `agent_md_path` — роль агента этой поверхности. Пустые `host` и
`auth_token` наследуются из `server`.

**Настройки агента поверхности** собираются так: `config.yml` (профиль, env,
флаги) → `server.logging` → роль поверхности (`agent_md_path`) → общий
`agent_overrides` → `agent_overrides` поверхности. Ключ правки — путь настройки
через точку (`agent.max_steps`, `backend.completions_url`) или вложенная секция
(`agent: {max_steps: 100}`); прежние плоские имена (`max_steps`) — отказ старта
с подсказкой пути. `agent_overrides.level: auto` включает автовыбор уровня
модели ([auto-routing.md](auto-routing.md)); недоступен — уведомление в лог
прогона уровнем `warning`, агент работает уровнем `default`.

**Токен.** Непустой `auth_token` — каждый запрос с
`Authorization: Bearer <token>`, иначе `403`. Пустой — без проверки, на старте
строка в stderr. `a2a` на адресе не loopback без токена не стартует.

### Переезд ключей

| Было | Стало |
|---|---|
| `server.port` | `webhook.port` (у каждой поверхности свой) |
| `defaults.system` | `webhook.default_system` |
| `agent.server_agentmd_path` | `webhook.agent_md_path` |
| `server.context_build_wait_seconds` | `webhook.context_build_wait_seconds` |
| `threads_cleanup` | `webhook.threads_cleanup` |
| `logging` | `server.logging` |
| `swarm.enabled` | `server.apis: [swarm]` или `gc-serve swarm` |
| `chat_api` в config.yml | секция `chat` в config_server.yml |
| `a2a` в config.yml | секция `a2a` в config_server.yml |
| команды `gc-chat`, `gc-a2a` | `gc-serve chat`, `gc-serve a2a` |
| `/swarm/run`, `/swarm/status/…`, `/swarm/logs/…` | ручки вебхука на порту swarm |

Прежний ключ в config_server.yml — отказ старта с новым местом. Секции
`chat_api` и `a2a` в config.yml больше не читаются: остальные фронтенды
показывают уведомление, а `gc-serve chat`/`gc-serve a2a` при такой секции не
стартуют — иначе её `auth_token` пропал бы молча и поверхность поднялась бы без
авторизации.

### Чьи треды видит вебхук

`system` хранит треды разных входов в одном хранилище. Занятые другими
поверхностями и интерактивными сессиями — `a2a`, `responses`, `completions`,
`acp`, `cli`, `tui` — вебхук не принимает (`400`), не читает (`/logs`,
`/runs` — `400`) и не показывает (`/logs/all`). Сверяется нормализованное имя:
`CLI!` и `.cli` — тот же тред `cli`.

## Хранилище: storage в config.yml

Где лежат треды и ресурсы агента (промпты, скиллы, память), задаёт секция
`storage` в **config.yml** — общая с `gc-cli`
([configuration.md](configuration.md#хранилище-storage)):

```yaml
storage:
  threads: {type: postgres, dsn: "${FILE:/run/secrets/pg_dsn}"}
  agent:   {type: postgres, dsn: "${FILE:/run/secrets/pg_dsn}", agent_id: coder}
  ensure_schema: false    # true — накатить схему при старте
```

Без секции всё на файлах, как раньше. `gc-serve` открывает хранилище один раз до
открытия портов и закрывает после остановки; все поверхности пишут в него, а
`/logs` читают из него. Схема не накатана или старая — отказ старта с
подсказкой `gc-stores migrate --config <config.yml>`; нет драйвера — какой extra
поставить. Песочница swarm пока хранит тред в своих файлах: подключение к базе в
её `config.yml` не передаётся.

## Режимы разрешений на сервере

На сервере всегда **спросить некого**: `gc-serve` объявляет канал «человека нет».
Вопросы режима и защиты получают ответ «спросить некого» и становятся отказом, а консоль
сервера не спрашивает никогда, даже если сервер запущен из терминала и `turn_ask_human`
включён. Запись в каталог `.git`, скиллы и настройки инструментов без человека —
отказ. Одобрить план и сменить режим через API сервера нельзя, поэтому на сервере
работают `edit` (по умолчанию) и `auto`. `plan` и `manual` здесь не функции, а
ограничения: с `default_mode: plan` сессия не выйдет из `plan`, а `manual` отклонит
всё, что требует подтверждения. При старте с таким режимом по умолчанию сервер пишет
предупреждение в лог (старт не прерывается) и называет способ вернуть `edit`: в
`config_server.yml` в `agent_overrides` задайте
`security.permissions.default_mode: edit`.

Задача swarm объявляет о себе то же самое: обёртка песочницы запускает
`gc-cli --external-request`, и задача swarm для судьи — такой же запрос внешней системы,
как вебхук. Режим разрешений swarm-ран берёт из своего конфига (базовый слой,
`agent_overrides`); предупреждения о `plan` и `manual` при старте сервера он не получает.

`auto` на сервере подходит для доверенных источников вебхуков. Судья действий считает
слова вебхука не волей пользователя, а **запросом внешней системы**: описание задачи и
запреты из него учитываются, а разрешением на рискованное действие или на выход за пределы
задачи оно не служит (это относится и к тексту в вебхуке, выдающему себя за слова
человека). После трёх отказов подряд или двадцати за сессию проверка встаёт
на паузу, и спорные действия отклоняются без вызова судьи; паузу снимает следующий
вебхук, потому что каждый вебхук — новая задача.

## Вебхук

Агенту вебхука нужны:

- **config.yml** — адрес модели, параметры агента, `mcp-servers`; тот же файл,
  что у `gc-cli` (`demo_config.yml` — пример).
- **Роль** — `webhook.agent_md_path` (по умолчанию bundled
  `prompts/server_agent.md` из ассетов `gc-core`). Абсолютный путь — как есть,
  относительный ищется рядом с config_server.yml, затем среди ассетов; не
  нашёлся — `WARNING`, агент работает без инструкций. Роль — слой L0 AGENTS.md;
  `.gc/AGENTS.md` каталога запуска подхватывается как слой проекта.
- **Треды** — в хранилище из `storage` (по умолчанию файлы в
  `paths.threads_data_path`, тот же каталог, что у `gc-cli` и TUI).
- **Скиллы** — как у CLI, из `config.yml`; запреты `agent.stop_tools` снимают
  и скиллы, и MCP.

Ручки (порт `webhook.port`, по умолчанию 8000):

- `GET /healthcheck` — простой health‑чек:

  ```json
  {"status": "ok"}
  ```

- `POST /events/webhook` — входящий вебхук:
  - тело запроса — произвольный JSON‑объект;
  - поле `task_id`:
    - если указано и непустое — используется как есть;
    - если нет — сервер генерирует `task_id` (GUID) и подставляет его в JSON;
  - поле `system`:
    - если указано — нормализуется (обрезка пробелов, нижний регистр);
    - если нет — берётся `webhook.default_system` (по умолчанию `generic`);
    - занятый другой поверхностью или интерактивными сессиями — `400` (см. выше);
  - при первом запросе по паре `(system, task_id)` сервер:
    - занимает ключ задачи (бронь) и строит `RunContext` из настроек поверхности
      (config.yml + `agent_overrides`) — асинхронно, не останавливая остальные
      запросы;
    - запускает прогон задачи — asyncio-задачу на loop сервера
      (`AgentExecutor.arun(...)`), тред — `task_id` — и отвечает
      `{ "status": "started", ... }`;
    - если сборка контекста упала — отвечает `500`, бронь снимается;
  - при последующих запросах с теми же `(system, task_id)` — см. «Одна задача —
    один прогон» ниже: `queued`, ожидание чужой сборки или `503`.

- `GET /runs/{system}/{task_id}` — статус прогона задачи:
  - `running` — прогон идёт; `started_at` — его старт, `last_activity_at` —
    последнее событие прогона: старт, принятое сообщение, конец каждого хода
    (в том числе хвостового, см. ниже);
  - `running` отдаётся и пока контекст задачи строится, а прогона ещё нет: тогда
    `started_at` и `last_activity_at` — время, когда взята бронь. Зависшая сборка
    поэтому стареет для сторожа по `last_activity_at` так же, как зависший
    прогон;
  - `completed` — `finished_at` и `result`. `result` — ответ **последнего** хода
    прогона: хвостовой ход идёт по тому же треду и отвечает с учётом всего, что
    было до него, поэтому это итог прогона задачи. Ответы прежних ходов — в
    `GET /logs/{system}/{task_id}`;
  - `failed` — прогон упал, `error` — `repr` исключения;
  - `cancelled` — прогон сняли (остановка сервера, отмена задачи). Это не отказ
    агента, поэтому и статус отдельный;
  - `404` — нет ни прогона, ни брони (или запись завершённого прогона уже
    вытеснена);
  - статусы **не персистентны**: после завершения хранятся только в памяти
    процесса (15 минут, не больше 500 записей); для долговременной истории
    используйте логи тредов.

- `GET /logs/{system}/{task_id}` — получение логов работы агента по треду:
  - в качестве `thread_id` используется `task_id`, с которым запускался агент;
  - при успехе возвращает JSON:
    - `status: "ok"`;
    - `system`, `task_id`;
    - `meta` — метаданные треда (`{}`, если их нет);
    - `messages` — сообщения треда (payload каждого);
  - если для указанного `task_id` нет ни метаданных, ни сообщений — возвращает `404` с `{"status": "not_found"}`;
  - логи тредов **персистентны** в рамках хранилища из `storage` (по умолчанию — файлы в каталоге тредов).
- `GET /logs/all` — треды вебхука (без тредов других поверхностей и
  интерактивных сессий), свежие первыми.

### Одна задача — один прогон

У пары `(system, task_id)` в каждый момент не больше одного прогона, и
сообщение, которому ответили `queued`, до агента доходит — или его потеря
остаётся в логе.

**Пока строится контекст.** Ключ задачи занят бронью с первого вебхука, ещё до
сборки контекста. Вебхук, пришедший в это время, ждёт конца чужой сборки и
проходит путь заново: прогон стартовал — сообщение уходит в него (`queued`);
сборка упала — вебхук строит контекст сам (`started`). Ждёт он не дольше
`webhook.context_build_wait_seconds` (по умолчанию 120 с) — в сумме за запрос,
даже если чужих сборок по очереди было несколько. По истечении — `503`:

```json
{"detail": {"status": "error", "payload": "task context is still being built, retry later"}}
```

Сообщение при этом **не принято** — повторите запрос. Сборка, которую ждали,
продолжается: своего дедлайна у неё нет, медленная сборка законна. В лог
пишется `WARNING` с событием `context_build_wait_timeout`.

**Пока идёт прогон.** Сообщение кладётся в очередь идущего прогона, и сервер
сразу отвечает `queued`; цикл агента забирает очередь на следующем шаге. Если
модель только что вернула вызовы тулов, они сначала исполняются, и сообщение уходит
модели вместе с их ответами.
`trace_id` такого вебхука не применяется: контекст прогона уже собран — об этом
пишется событие `trace_id_ignored` (см. [configuration.md](configuration.md)).

**Хвост прогона.** Закрыв ход, прогон ещё сохраняет тред и закрывает
MCP-сессии, и всё это время он жив: вебхуки получают `queued`. Сообщения,
легшие в очередь после последнего её забора циклом, прогон доигрывает
**отдельным ходом** того же исполнителя по тому же треду — и так, пока хвост не
опустеет. Прогон задачи может поэтому состоять из нескольких ходов; `result` в
статусе — ответ последнего из них.

**Хвост, который доставить некуда.** Остановленный, упавший и снятый прогон
хвост не доигрывает: это отменило бы остановку или спрятало отказ за статусом
следующего хода. Такие сообщения пропадают, но не молча — `WARNING` с событием
`run_tail_dropped` и полями `system`, `task_id`, `ending`, `count`:

- `ending=failed` — прогон упал;
- `ending=cancelled` — прогон сняли (остановка сервера, отмена задачи);
- `ending=stopped` — прогон остановлен методом реестра `stop` (HTTP-ручки
  остановки нет).

В `count` входит и батч хвоста, с которым умер хвостовой ход, — даже если он
умер в сетапе, не дойдя до модели: упал на чтении треда или сборке состояния,
снят остановкой uvicorn.

### Автоматическая чистка тредов

По умолчанию **выключена**. Включается в `config_server.yml`:

```yaml
webhook:
  threads_cleanup:
    enabled: true
    interval_seconds: 3600
    ttl_days: 7
```

**Треды в файлах.** Сервер чистит НЕ свой каталог: `threads_data_path` общий с
`gc-cli` и TUI, и чистка удаляет историю интерактивной работы в этом проекте.
Сервер, поднятый в каталоге проекта, снёс бы её молча — поэтому выключено.
Тред удаляется целиком — тем же путём, что удаление сессии в TUI: история, meta,
картинки (`images/`), сайдкар субагентов, архивы компакции, журнал правок и lock.
Meta без `system` и `thread_id` (старый формат) удаляется по имени файла вместе со
своим `data_*.jsonl`.

**Треды в базе** (`storage.threads`). Чистка идёт через хранилище и трогает
только треды вебхука: треды chat, a2a, ACP и интерактивных сессий в той же базе
остаются.

Включённая чистка объявляется в логе (где, срок хранения, интервал) и пишет
строку на каждый проход, который что-то удалил. Нет этих строк — чистка не
работает, и это её штатное состояние.

Без секции файловую ротацию настраивайте вне приложения — например, cron-джобой
(`python -m gc_server.cleanup_threads --threads-dir ... --ttl-days ...`).

## Поведение инструментов на сервере

- `agent.stop_tools` в `agent_overrides` (общих или поверхности) снимает
  встроенные тулы, скиллы и MCP из собранного набора. Демо-конфиг запрещает
  вебхуку запись и правку файлов, команды оболочки и `turn_ask_human` — это
  защищает каталог и окружение сервера.
- Имена сверяются точно, шаблонов нет: тул, появившийся в новой версии, сервер
  получит, пока его не впишут в `stop_tools`. При обновлении сверяйте свой
  `config_server.yml` с `demo_config_server.yml` — например, `fs_view_image`
  (просмотр картинок с диска сервера) добавлен вместе с картинками.

## Swarm (только Linux)

`gc-serve swarm` — те же ручки, что у вебхука (`POST /events/webhook`,
`GET /runs/{system}/{task_id}`, `GET /logs/{system}/{task_id}`, `GET /logs/all`,
`GET /healthcheck`), на своём порту (8092). Задача исполняется не в процессе
сервера, а `gc-cli` в bubblewrap-песочнице: свой workspace, лимиты памяти, диска
и CPU, таймаут. Статус — в той же форме, что у вебхука, плюс поле `swarm`
(песочница, pid, причина завершения).

Песочница одноразовая: запрос по задаче, которая ещё идёт, — `409 task is
running`; по завершённой — `409 task already finished — use a new task_id`.
Свободных слотов нет (`swarm.max_concurrent`) — `503`.

Доставка запроса та же, что у вебхука: агенту уходит **JSON-payload** тела
запроса — в вебхуке user-сообщением (`json.dumps(payload)`), в swarm —
аргументом `-q "<payload-json>"` для `gc-cli` внутри песочницы. Поле `trace_id`
оба режима **снимают** из payload до доставки: в вебхуке он уходит в конфиг
рана, в swarm — в песочницу переменной `SWARM_TRACE_ID` (обёртка добавляет
`gc-cli --trace-id`). Невалидное значение (управляющие символы, длиннее 200
символов) — `400` с телом `{"status": "error", "payload": "invalid trace_id: ..."}`.
Подробнее о трейсе — в [configuration.md](configuration.md).

> ⚠️ **Swarm работает только на Linux** (требует `bubblewrap` и `timeout` из
> GNU coreutils).

Установка, секция `swarm` в config_server.yml, жизненный цикл песочницы и
troubleshooting — в **[docs/swarm.md](swarm.md)**.
