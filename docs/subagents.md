# Кастомные сабагенты

## Что это

Сабагент — отдельный агент, которому оркестратор делегирует подзадачу: у него свой
системный промпт (роль), свой лог-файл и свой набор инструментов. Встроенных семь
(`subagent_worker`, `subagent_coder`, `subagent_planner`, `subagent_critic`,
`subagent_code_planner`, `subagent_code_reviewer`, `subagent_special_agent`).

Кастомные добавляются файлами: кладёте `.md` в папку, указываете путь в конфиге —
и агент видит их как обычные инструменты рядом со встроенными.

Работает только при `agent.use_local_subagents: true` и
`backend_api_mode: chat_completions`. Без них папка не читается вовсе.

## Конфиг основного агента

```yaml
agent:
  use_local_subagents: true       # без этого сабагентов нет вообще
  subagents_dir: /absolute/path/agents         # папка с определениями; нет ключа → только встроенные
  subagents_max_count: 20         # опционально, дефолт 20
  subagent_max_steps: 100         # общий лимит шагов на любого сабагента
  stop_tools: [turn_ask_human]    # глобальный запрет; файлы могут только добавить к нему

backend_api_mode: chat_completions
```

Если `subagents_dir` не задан или папки нет — ничего не ломается, работают встроенные
семь. Про отсутствующую папку будет один варнинг на старте.

### Выбор состава: `use_local_subagents` списком

Поле принимает не только `true`/`false`, но и список имён — тогда оркестратор увидит
**только** их. Встроенные и кастомные тут на равных:

```yaml
agent:
  use_local_subagents: [db_migrator, worker]   # только эти два
```

| Значение | Что видит оркестратор |
|---|---|
| `true` | всех: семь встроенных + всех из папки |
| `false` | никого |
| `[db_migrator, worker]` | только `subagent_db_migrator` и `subagent_worker` |
| `[]` | никого — пустой список это «ни одного», а не «все» |

Префикс `subagent_` можно не писать: `worker` и `subagent_worker` — одно и то же.
Имя, которого нет ни среди встроенных, ни в папке, попадает в варнинг
`use_local_subagents_unknown` со списком доступных — старт не прерывается.

Отфильтрованный сабагент не только не показывается модели, но и не может быть вызван
напрямую: диспетчер проверяет список отдельно.

`use_server_subagents` остаётся строго булевым — состав server-сабагентов определяет
бэкенд, а не мы.

## Файл сабагента

`<subagents_dir>/db-migrator.md` — имя файла произвольное, важно только расширение:

```markdown
---
name: subagent_db_migrator
description: Пишет и проверяет миграции БД. Вызывать, когда нужна схема или откат.
tools:
  - fs_read_file
  - fs_write_file
  - exec_command
stop_tools:
  - exec_python
---
Ты — инженер по миграциям базы данных.

Работаешь по шагам:
1. Читаешь текущую схему и последние миграции.
2. Пишешь миграцию и обратный откат.
3. Проверяешь, что откат возвращает схему в исходное состояние.

Никогда не удаляй данные без явного указания в задаче.
```

Минимальный валидный файл — три строки frontmatter и тело:

```markdown
---
name: subagent_doc_writer
description: Пишет и правит документацию по коду.
---
Ты — технический писатель. Пишешь кратко, по делу, с примерами.
```

### Поля

| Поле | Обяз. | Смысл |
|---|---|---|
| `name` | да | Имя инструмента. Должно матчить `^subagent_[a-z0-9_]+$`, не длиннее 64 символов |
| `description` | да | По нему модель решает, звать ли этого сабагента. Пишите, **когда** его вызывать. Не длиннее 1024 символов |
| `tools` | нет | Allowlist инструментов. Ключа нет → доступны все |
| `stop_tools` | нет | Blocklist. Применяется после `tools` |
| тело | да | Системная роль. Пустое тело — файл отвергается |

Неизвестный ключ во frontmatter — ошибка, файл пропускается с варнингом. Так опечатка
`discription:` не проглатывается молча.

Лимиты длины не декоративные: имя не длиннее **64** символов, потому что столько
позволяют OpenAI-совместимые бэкенды для имени функции, и потому что имя без префикса
попадает в имя лог-файла (`agent_<kind>_<run_id>.jsonl`), а тот ограничен 255 байтами.
Описание не длиннее **1024**, потому что оно уходит в схему инструментов на каждом
запросе к модели — у встроенных сабагентов это 220–280 символов. Тело-роль не
ограничено: оно попадает в системный промпт один раз за запуск сабагента.

## Что наследует сабагент

По умолчанию — всё, что есть у родителя, кроме самих сабагентов:

| | Наследуется |
|---|---|
| Встроенные инструменты | все (минус глобальный `agent.stop_tools`) |
| Скиллы | все, тот же 3-слойный дискавери и тот же `disable_skills` |
| MCP-серверы | все, вместе с их `whitelist` |
| Модель | модель родителя |
| Рабочая память, notes, кэш URL | общие с родителем |
| Тред | тот же, если у родителя он есть |
| `subagent_*` | **никогда** — сабагент не может вызывать сабагентов |

Лимиты (`subagent_max_steps`, `subagent_finish_gate_max_iterations`) общие на всех.

MCP-дискавери ребёнок делает **свой**: заново коннектится и запрашивает `tools/list`,
результат родителя не переиспользуется. Для stdio-серверов это отдельный процесс на
каждый запуск сабагента.

## Инструменты

### Имена пишутся полностью

```yaml
tools:
  - fs_read_file                  # встроенный
  - mcp_jira_search_issues        # MCP: mcp_<сервер>_<тул>, с префиксом
```

Это отличается от whitelist'а внутри MCP-сервера, где имена базовые
(`search_issues`, без префикса) — там список описывает ответ конкретного сервера, а
здесь пространство имён сквозное.

Неизвестное имя не роняет старт — будет варнинг со списком нераспознанных.

### Три состояния `tools`

| В файле | Что у сабагента |
|---|---|
| ключа нет | всё: встроенные + скиллы + MCP |
| `tools: [fs_read_file]` | перечисленное + служебное ядро |
| `tools: []` | только служебное ядро — сабагент без инструментов |

Фильтр применяется **после** сборки всех источников. То есть `tools` без имён `mcp_*`
убирает MCP-инструменты из набора, но коннект к серверам к этому моменту уже
произошёл: экономии на дискавери такой список не даёт, только сужение того, что видит
модель.

### Два служебных инструмента выдаются всегда

`turn_finish` и `session_read_stored_tool_output` сабагент получает **всегда**.
Перечислять их в `tools` не нужно, и `stop_tools` их не отбирает — это гарантия, а не
предпочтение. Попытка запретить их через `stop_tools` не исполняется, но пишется в
варнинг `subagent_required_tools_kept`, чтобы указание не игнорировалось молча.

Причина в том, что без них сабагент ломается не сразу, а позже и незаметно:

- без `turn_finish` он физически не может сдать отчёт — докрутит до `subagent_max_steps`
  и вернёт что попало;
- без `session_read_stored_tool_output` он на первом же большом выводе получит
  инструкцию «продолжи через session_read_stored_tool_output», которого у него нет.

Оба выглядят как «модель тупит», поэтому набор инструментов файлу здесь не доверяется.

### `stop_tools` только добавляет

Глобальный `agent.stop_tools` из основного конфига применяется всегда. `stop_tools` в
файле **дополняет** его, а не заменяет: снять глобальный запрет из файла сабагента
нельзя. Иначе кастомный файл мог бы ослабить периметр, заданный оператором.

Область действия у них при этом разная, и это стоит знать: глобальный
`agent.stop_tools` режет только **встроенные** инструменты (он применяется до того,
как подмешиваются скиллы и MCP), а `stop_tools` из файла — любые, включая `mcp_*` и
`skills_*`. Ограничить MCP глобально можно через `whitelist` внутри
`mcp.servers.<name>`, но там имена базовые и правило действует на один сервер.

### Ловушка: запись на диск возможна не одним инструментом

Записать файл можно **восемью** разными инструментами, поэтому `stop_tools` для
ограничения записи — ненадёжный путь. Это проверено живыми прогонами дважды: сабагент
с запретом `fs_write_file` создал файл через `fs_append_file`, а после добавления
`fs_append_file` в запрет — нашёл `fs_save_base64_file`.

**Для read-only сабагента задавайте `tools` (allowlist)** — всё, что не перечислено,
недоступно по построению, и новый инструмент в будущих версиях дыру не откроет:

```yaml
tools:
  - fs_read_file
  - fs_list_files
  - fs_search_files
  - fs_file_info
```

Blocklist работает, но требует перечислить все восемь и обновлять список при появлении
новых инструментов:

```yaml
stop_tools:
  - fs_write_file
  - fs_append_file
  - fs_apply_file_edits
  - fs_search_and_replace
  - fs_save_base64_file
  - exec_command
  - exec_python
  - download_file
```

### Про `turn_ask_human`

В дефолтном конфиге он уже отключён (`stop_tools: [turn_ask_human]`). Это влияет на
модерацию команд: если `security.command_moderation.mode: ask`, а спросить человека
нечем, решение схлопывается в отказ. То есть `ask` фактически работает как `deny`.
Поведение осмысленное, но знать о нём стоит.

## Коллизии, лимит и битые файлы

- Файлы читаются по порядку **имени файла**, без рекурсии, только первый уровень.
- Встроенные считаются прочитанными раньше кастомных: файл с `name: subagent_worker`
  проиграет встроенному и будет пропущен с варнингом.
- Два файла с одним `name` — побеждает первый по имени файла, второй пропускается.
- Валидных файлов больше `subagents_max_count` — берутся первые, остальные
  перечисляются в варнинге. Молча ничего не отбрасывается.
- Битый файл (нет обязательного поля, сломанный YAML, плохой `name`) пропускается с
  варнингом и не мешает остальным.

Ни один из этих случаев не роняет старт: кастомные сабагенты целиком построены на
варнингах, а не на отказах.

## Ограничения

- **Аргументы фиксированы.** У любого сабагента ровно два параметра: `reason` и `task`.
  Свою схему аргументов задать нельзя.
- **Глубина 1.** Сабагент не может вызывать сабагентов; `subagent_*` в `tools`
  игнорируется.
- **Модель одна.** Сабагент всегда работает на модели родителя; задать свою в файле нельзя.
- **Лимиты общие.** `subagent_max_steps` и `subagent_finish_gate_max_iterations` — одни
  на всех, на роль не настраиваются.
- **Одна папка.** Слоёв `project > user > system`, как у скиллов, нет.
- **Без горячей перезагрузки.** Файлы читаются на старте рана.
- **Контракт сдачи общий.** К любой роли автоматически приклеивается требование
  вернуть результат JSON-отчётом через `turn_finish` (`status`, `report_summary`,
  `artifacts_created`, `checks`). Отменить его из файла нельзя.
