# Кастомные сабагенты

## Что это

Сабагент — отдельный агент, которому оркестратор делегирует подзадачу: у него свой
системный промпт (роль), свой лог-файл и свой набор инструментов. Встроенных семь
(`subagent_worker`, `subagent_coder`, `subagent_planner`, `subagent_critic`,
`subagent_code_planner`, `subagent_code_reviewer`, `subagent_special_agent`).

Кастомные добавляются файлами: кладёте `.md` в папку, указываете путь в конфиге —
и агент видит их как обычные инструменты рядом со встроенными.

Работает только при `agent.use_local_subagents: true` и
`backend_api_mode: chat_completions`. Без них папка не читается вовсе.

## Конфиг основного агента

```yaml
agent:
  use_local_subagents: true       # без этого сабагентов нет вообще
  subagents_dir: /absolute/path/agents         # папка с определениями; нет ключа → только встроенные
  subagents_max_count: 20         # опционально, дефолт 20
  subagent_max_steps: 100         # общий лимит шагов на любого сабагента
  stop_tools: [turn_ask_human]    # глобальный запрет; файлы могут только добавить к нему

backend_api_mode: chat_completions
```

Если `subagents_dir` не задан или папки нет — ничего не ломается, работают встроенные
семь. Про отсутствующую папку будет один варнинг на старте.

## Файл сабагента

`<subagents_dir>/db-migrator.md` — имя файла произвольное, важно только расширение:

```markdown
---
name: subagent_db_migrator
description: Пишет и проверяет миграции БД. Вызывать, когда нужна схема или откат.
tools:
  - fs_read_file
  - fs_write_file
  - exec_command
  - turn_finish
  - session_read_stored_tool_output
stop_tools:
  - exec_python
---
Ты — инженер по миграциям базы данных.

Работаешь по шагам:
1. Читаешь текущую схему и последние миграции.
2. Пишешь миграцию и обратный откат.
3. Проверяешь, что откат возвращает схему в исходное состояние.

Никогда не удаляй данные без явного указания в задаче.
```

Минимальный валидный файл — три строки frontmatter и тело:

```markdown
---
name: subagent_doc_writer
description: Пишет и правит документацию по коду.
---
Ты — технический писатель. Пишешь кратко, по делу, с примерами.
```

### Поля

| Поле | Обяз. | Смысл |
|---|---|---|
| `name` | да | Имя инструмента. Должно матчить `^subagent_[a-z0-9_]+$` |
| `description` | да | По нему модель решает, звать ли этого сабагента. Пишите, **когда** его вызывать |
| `tools` | нет | Allowlist инструментов. Ключа нет → доступны все |
| `stop_tools` | нет | Blocklist. Применяется после `tools` |
| тело | да | Системная роль. Пустое тело — файл отвергается |

Неизвестный ключ во frontmatter — ошибка, файл пропускается с варнингом. Так опечатка
`discription:` не проглатывается молча.

## Инструменты

### Имена пишутся полностью

```yaml
tools:
  - fs_read_file                  # встроенный
  - mcp_jira_search_issues        # MCP: mcp_<сервер>_<тул>, с префиксом
```

Это отличается от whitelist'а внутри MCP-сервера, где имена базовые
(`search_issues`, без префикса) — там список описывает ответ конкретного сервера, а
здесь пространство имён сквозное.

Неизвестное имя не роняет старт — будет варнинг со списком нераспознанных.

### Два инструмента убрать нельзя

`turn_finish` и `session_read_stored_tool_output` обязаны остаться доступными. Если их
нет в `tools` или они попали в `stop_tools` — **агент не стартует** с ошибкой, где
указан файл и все проблемные инструменты сразу:

```
/path/agents/db.md: обязательные инструменты — отсутствуют в списке tools:
session_read_stored_tool_output, turn_finish
```

Причина в том, что без них сабагент ломается не сразу, а позже и незаметно:

- без `turn_finish` он физически не может сдать отчёт — докрутит до `subagent_max_steps`
  и вернёт что попало;
- без `session_read_stored_tool_output` он на первом же большом выводе получит
  инструкцию «продолжи через session_read_stored_tool_output», которого у него нет.

Оба выглядят как «модель тупит», поэтому проверка стоит на старте.

### `stop_tools` только добавляет

Глобальный `agent.stop_tools` из основного конфига применяется всегда. `stop_tools` в
файле **дополняет** его, а не заменяет: снять глобальный запрет из файла сабагента
нельзя. Иначе кастомный файл мог бы ослабить периметр, заданный оператором.

### Про `turn_ask_human`

В дефолтном конфиге он уже отключён (`stop_tools: [turn_ask_human]`). Это влияет на
модерацию команд: если `security.command_moderation.mode: ask`, а спросить человека
нечем, решение схлопывается в отказ. То есть `ask` фактически работает как `deny`.
Поведение осмысленное, но знать о нём стоит.

## Коллизии, лимит и битые файлы

- Файлы читаются по порядку **имени файла**, без рекурсии, только первый уровень.
- Встроенные считаются прочитанными раньше кастомных: файл с `name: subagent_worker`
  проиграет встроенному и будет пропущен с варнингом.
- Два файла с одним `name` — побеждает первый по имени файла, второй пропускается.
- Валидных файлов больше `subagents_max_count` — берутся первые, остальные
  перечисляются в варнинге. Молча ничего не отбрасывается.
- Битый файл (нет обязательного поля, сломанный YAML, плохой `name`) пропускается с
  варнингом и не мешает остальным.

Единственный случай, когда агент не стартует, — отсутствие обязательных инструментов.
Всё остальное деградирует до варнинга.

## Ограничения

- **Аргументы фиксированы.** У любого сабагента ровно два параметра: `reason` и `task`.
  Свою схему аргументов задать нельзя.
- **Глубина 1.** Сабагент не может вызывать сабагентов; `subagent_*` в `tools`
  игнорируется.
- **Модель одна.** Сабагент всегда работает на модели родителя; задать свою в файле нельзя.
- **Лимиты общие.** `subagent_max_steps` и `subagent_finish_gate_max_iterations` — одни
  на всех, на роль не настраиваются.
- **Одна папка.** Слоёв `project > user > system`, как у скиллов, нет.
- **Без горячей перезагрузки.** Файлы читаются на старте рана.
- **Контракт сдачи общий.** К любой роли автоматически приклеивается требование
  вернуть результат JSON-отчётом через `turn_finish` (`status`, `report_summary`,
  `artifacts_created`, `checks`). Отменить его из файла нельзя.
