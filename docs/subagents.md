# Кастомные сабагенты

## Что это

Сабагент — отдельный агент, которому оркестратор делегирует подзадачу: у него свой
системный промпт (роль), свой лог-файл и свой набор инструментов. Встроенных семь
(`subagent_worker`, `subagent_coder`, `subagent_planner`, `subagent_critic`,
`subagent_code_planner`, `subagent_code_reviewer`, `subagent_special_agent`).

Кастомные добавляются файлами: кладёте `.md` в папку, указываете путь в конфиге —
и агент видит их как обычные инструменты рядом со встроенными.

Работает только при `agent.use_local_subagents: true` и
`backend_api_mode: chat_completions`. Без них папка не читается вовсе.

## Конфиг основного агента

```yaml
agent:
  use_local_subagents: true       # без этого сабагентов нет вообще
  subagents_dir: /absolute/path/agents         # папка с определениями; нет ключа → только встроенные
  subagents_max_count: 20         # опционально, дефолт 20
  subagent_max_steps: 100         # общий лимит шагов на любого сабагента
  stop_tools: [turn_ask_human]    # ПРИМЕР запрета; по умолчанию список ПУСТ

backend_api_mode: chat_completions
```

Если `subagents_dir` не задан или папки нет — ничего не ломается, работают встроенные
семь. Про отсутствующую папку будет один варнинг на старте.

### Выбор состава: `use_local_subagents` списком

Поле принимает не только `true`/`false`, но и список имён. Список выбирает
**кастомных** сабагентов; встроенные семь доступны всегда, пока значение не `false`.

```yaml
agent:
  use_local_subagents: [db_migrator]   # встроенные + этот один из папки
```

| Значение | Встроенные | Кастомные |
|---|---|---|
| `true` | все семь | все из папки |
| `false` | нет | нет |
| `[db_migrator]` | все семь | только `subagent_db_migrator` |
| `[]` | все семь | ни одного |

Пустой список — это «только встроенные», а не «никого»: выключает всех только `false`.

Префикс `subagent_` можно не писать: `worker` и `subagent_worker` — одно и то же.
Имя встроенного в списке безвредно — он и так включён, ничего не меняется. Имя, которого
нет ни среди встроенных, ни в папке, попадает в варнинг `use_local_subagents_unknown`
со списком доступных; старт не прерывается.

Не попавший в список кастомный сабагент не показывается модели и не может быть вызван
напрямую — реестр его просто не отдаёт.

`use_server_subagents` остаётся строго булевым — состав server-сабагентов определяет
бэкенд, а не мы.

## Файл сабагента

`<subagents_dir>/db-migrator.md` — имя файла произвольное, важно только расширение:

```markdown
---
name: subagent_db_migrator
description: Пишет и проверяет миграции БД. Вызывать, когда нужна схема или откат.
tools:
  - fs_read_file
  - fs_write_file
  - exec_command
stop_tools:
  - exec_python
---
Ты — инженер по миграциям базы данных.

Работаешь по шагам:
1. Читаешь текущую схему и последние миграции.
2. Пишешь миграцию и обратный откат.
3. Проверяешь, что откат возвращает схему в исходное состояние.

Никогда не удаляй данные без явного указания в задаче.
```

Минимальный валидный файл — три строки frontmatter и тело:

```markdown
---
name: subagent_doc_writer
description: Пишет и правит документацию по коду.
---
Ты — технический писатель. Пишешь кратко, по делу, с примерами.
```

### Поля

| Поле | Обяз. | Смысл |
|---|---|---|
| `name` | да | Имя инструмента. Должно матчить `^subagent_[a-z0-9_]+$`, не длиннее 64 символов |
| `description` | да | По нему модель решает, звать ли этого сабагента. Пишите, **когда** его вызывать. Не длиннее 1024 символов |
| `tools` | нет | Allowlist инструментов. Ключа нет → доступны все |
| `stop_tools` | нет | Blocklist. Применяется после `tools` |
| тело | да | Системная роль. Пустое тело — файл отвергается |

Неизвестный ключ во frontmatter — ошибка, файл пропускается с варнингом. Так опечатка
`discription:` не проглатывается молча.

Лимиты длины не декоративные: имя не длиннее **64** символов, потому что столько
позволяют OpenAI-совместимые бэкенды для имени функции, и потому что имя без префикса
попадает в имя лог-файла (`agent_<kind>_<run_id>.jsonl`), а тот ограничен 255 байтами.
Описание не длиннее **1024**, потому что оно уходит в схему инструментов на каждом
запросе к модели — у встроенных сабагентов это 220–280 символов. Тело-роль не
ограничено: оно попадает в системный промпт один раз за запуск сабагента.

## Что наследует сабагент

По умолчанию — всё, что есть у родителя, кроме самих сабагентов:

| | Наследуется |
|---|---|
| Встроенные инструменты | все (минус глобальный `agent.stop_tools`) |
| Скиллы | все, тот же 3-слойный дискавери и тот же `disable_skills` |
| MCP-серверы | все, вместе с их `whitelist` |
| Модель и режим | реестр и raw-режим родителя на момент запуска; явная привязка имеет приоритет |
| Рабочая память, notes, кэш URL | общие с родителем |
| Тред | тот же, если у родителя он есть |
| Режим разрешений | режим сессии родителя (см. ниже) |
| `subagent_*` | **никогда** — сабагент не может вызывать сабагентов |

В AUTO непривязанный ребёнок самостоятельно оценивает своё поручение и выбирает
пару тем же алгоритмом, что основной агент. Его серии, временный подъём и
переигрыш слабого ответа работают независимо от родительской пары. Если после разрешения соседних уровней остаётся одна рабочая пара,
начальный судья не вызывается.
Последующий `/level` родителя не меняет режим уже запущенного ребёнка. Привязка
`assign.subagents` к алиасу или уровню, включая `*`, выключает его AUTO.
Старые Temporal-истории воспроизводятся с прежней парой или ручным уровнем.

Лимиты (`subagent_max_steps`, `subagent_finish_gate_max_iterations`) общие на всех.

### Режим разрешений

Режим один на сессию, и субагент подчиняется ему так же, как родитель: запреты `plan`,
вопросы `manual` и судья `auto` действуют и на его действия. Сам режим субагенту
**объявляется**: служебное сообщение о режиме он получает при старте и всякий раз, когда
режим сессии меняется (например, `Shift+Tab` посреди хода родителя) — перед ближайшим
запросом к модели. У субагента нет инструмента `turn_propose_plan`, поэтому в `plan` ему
объявляют другое: исследуй, ничего не меняй и верни находки текстом ответа; выход из
`plan` объявляется без слов про план. При запуске субагента в `auto` судья проверяет
сам запуск (задание субагента — выбор агента) и затем его действия; отчёт субагента не
проверяется.

Под Temporal субагент (дочерний workflow) получает режим **копией** общего состояния на
момент старта: смену режима посреди его работы он не видит ни в проверках, ни в
объявлении — они согласованы, ребёнок живёт в режиме старта.

MCP-дискавери ребёнок делает **свой**: заново коннектится и запрашивает `tools/list`,
результат родителя не переиспользуется. Для stdio-серверов это отдельный процесс на
каждый запуск сабагента.

## Инструменты

### Имена пишутся полностью

```yaml
tools:
  - fs_read_file                  # встроенный
  - mcp_jira_search_issues        # MCP: mcp_<сервер>_<тул>, с префиксом
```

Это отличается от whitelist'а внутри MCP-сервера, где имена базовые
(`search_issues`, без префикса) — там список описывает ответ конкретного сервера, а
здесь пространство имён сквозное.

Неизвестное имя не роняет старт — будет варнинг со списком нераспознанных.

### Три состояния `tools`

| В файле | Что у сабагента |
|---|---|
| ключа нет | всё: встроенные + скиллы + MCP |
| `tools: [fs_read_file]` | перечисленное + служебное ядро |
| `tools: []` | только служебное ядро — сабагент без инструментов |

Фильтр применяется **после** сборки всех источников. То есть `tools` без имён `mcp_*`
убирает MCP-инструменты из набора, но коннект к серверам к этому моменту уже
произошёл: экономии на дискавери такой список не даёт, только сужение того, что видит
модель.

### Служебное ядро выдаётся всегда

`turn_finish`, `session_read_stored_tool_output`, `session_memory` и `session_todo`
сабагент получает **всегда**. Перечислять их в `tools` не нужно, и `stop_tools` их не
отбирает — это гарантия, а не предпочтение. Попытка запретить их через `stop_tools` не
исполняется, но пишется в варнинг `subagent_required_tools_kept`, чтобы указание не
игнорировалось молча.

Причина в том, что без них сабагент ломается не сразу, а позже и незаметно:

- без `turn_finish` он физически не может сдать отчёт — докрутит до `subagent_max_steps`
  и вернёт что попало;
- без `session_read_stored_tool_output` он на первом же большом выводе получит
  инструкцию «продолжи через session_read_stored_tool_output», которого у него нет;
- без `session_memory` он на первом же шаге получит bootstrap памяти треда
  («update persistent registers with the thread memory tool»), а дальше — периодический
  `tool_usage_notice` про неиспользуемую память;
- без `session_todo` — напоминание завести чек-лист задачи.

Общее у последних двух: тексты этих подсказок собираются из **глобального** конфига, до
того как известен состав инструментов конкретного сабагента, и про `tools` из файла они
не знают. Поэтому «выдать тул» здесь дешевле, чем «научить харнес молчать».

Все четыре отказа выглядят как «модель тупит», поэтому набор инструментов файлу здесь
не доверяется.

### `stop_tools` только добавляет

Глобальный `agent.stop_tools` из основного конфига применяется всегда. `stop_tools` в
файле **дополняет** его, а не заменяет: снять глобальный запрет из файла сабагента
нельзя. Иначе кастомный файл мог бы ослабить периметр, заданный оператором.

Область действия у них при этом разная, и это стоит знать: глобальный
`agent.stop_tools` режет только **встроенные** инструменты (он применяется до того,
как подмешиваются скиллы и MCP), а `stop_tools` из файла — любые, включая `mcp_*` и
`skills_*`. Ограничить MCP глобально можно через `whitelist` внутри
`mcp.servers.<name>`, но там имена базовые и правило действует на один сервер.

### Ловушка: запись на диск возможна не одним инструментом

Записать файл можно **восемью** разными инструментами, поэтому `stop_tools` для
ограничения записи — ненадёжный путь. Это проверено живыми прогонами дважды: сабагент
с запретом `fs_write_file` создал файл через `fs_append_file`, а после добавления
`fs_append_file` в запрет — нашёл `fs_save_base64_file`.

**Для read-only сабагента задавайте `tools` (allowlist)** — всё, что не перечислено,
недоступно по построению, и новый инструмент в будущих версиях дыру не откроет:

```yaml
tools:
  - fs_read_file
  - fs_list_files
  - fs_find_files_by_name
  - fs_find_in_files
  - fs_file_info
  - fs_view_image
```

`fs_view_image` только читает. Картинку смотрит модель субагента — сама, если видит
изображения, иначе через «глаза» (`assign.vision`); родителю возвращается только текст
результата субагента.

Blocklist работает, но требует перечислить все восемь и обновлять список при появлении
новых инструментов:

```yaml
stop_tools:
  - fs_write_file
  - fs_append_file
  - fs_apply_file_edits
  - fs_search_and_replace
  - fs_save_base64_file
  - exec_command
  - exec_python
  - download_file
```

### Про `turn_ask_human`

По умолчанию `stop_tools` **пуст**, и субагенты получают `turn_ask_human` наравне с
основным агентом — в TUI под вопрос субагента есть отдельный баннер («Агент
спрашивает через subagent_*»), а порт ответа копируется в дочерний контекст рядом
с confirm-баннером. Ответ с картинками идёт тем же портом: картинки видит модель
субагента, в тред родителя они копируются так же, как у основного агента.

Если тул запретить (`stop_tools: [turn_ask_human]`), это заденет модерацию команд:
при `security.command_moderation.mode: ask` спросить человека станет нечем, и
решение схлопнется в отказ — то есть `ask` начнёт работать как `deny`. Поведение
осмысленное, но знать о нём стоит.

## Коллизии, лимит и битые файлы

- Файлы читаются по порядку **имени файла**, без рекурсии, только первый уровень.
- Встроенные считаются прочитанными раньше кастомных: файл с `name: subagent_worker`
  проиграет встроенному и будет пропущен с варнингом.
- Два файла с одним `name` — побеждает первый по имени файла, второй пропускается.
- Валидных файлов больше `subagents_max_count` — берутся первые, остальные
  перечисляются в варнинге. Молча ничего не отбрасывается. Лимит относится **только к
  кастомным**: встроенные в него не считаются. Когда `use_local_subagents` задан списком,
  урезается хвост **списка**, а не алфавита — оператор перечислил их в порядке
  приоритета.
- Битый файл (нет обязательного поля, сломанный YAML, плохой `name`) пропускается с
  варнингом и не мешает остальным.

Ни один из этих случаев не роняет старт: кастомные сабагенты целиком построены на
варнингах, а не на отказах.

### Где их видно

Каждый такой случай попадает в два места:

- **лог-файл рана** — записью с полем `event` (`subagent_definition_invalid`,
  `subagent_name_collision`, `use_local_subagents_unknown`,
  `subagents_max_count_exceeded`, `subagent_required_tools_kept`) и структурными
  полями для jsonl;
- **уведомления** — `gc-cli` печатает их в stderr при запуске, TUI показывает тостом
  и хранит в `/notices`.

В TUI они доступны **сразу на старте**, до первого запроса: чтение папки сабагентов —
это несколько локальных файлов, поэтому дискавери выполняется не лениво, в отличие от
MCP.

## Прогресс сабагента в ленте

Вызовы сабагента ядро отдаёт событиями прогресса (`SubagentProgressEvent`,
`gc_core.execution.progress`) по ходу работы, а записи — в трассу сабагента
(sidecar треда). События внутрипроцессные: в тред и в модель они не уходят.

- `tool_start` несёт сырой текст команды Run-тула (`command`) целиком, если
  он не длиннее `TOOL_START_COMMAND_MAX` (4096 символов); длиннее — `None`, и
  интерфейс читает команду из записи вызова в трассе.
- `tool_end` несёт сырой вывод тула (`output`) целиком, если он не длиннее
  `TOOL_END_OUTPUT_MAX` (16384 символа); длиннее — `None`, и вывод читается
  из записи результата в трассе. Вывод не обрезается: разбор конверта
  требует целой строки. Не строка — `json.dumps`, как в записи трассы.
- Запись в трассу пишется до события, поэтому при `None` она уже на месте.

Время вложенных вызовов после повторного открытия сессии — из записи итога
хода родителя (`outcome.calls`, [хранилище тредов](sdk/thread-store.md)).

Что из вызовов сабагента становится строкой ленты, решает таблица
отображения ядра (`gc_core.constants.tool_display`) с вложенным контекстом:
`tool_display(имя, nested=True)` сначала смотрит `NESTED_TOOL_DISPLAY`.

- Сдача сабагента (`turn_finish`) видна: в TUI — последнее событие блока
  `Agent`, `Finishing`, пока идёт, `Finished  <solution_type>` у принятой и
  `Finish` с причиной у отвергнутой. Наверху `turn_finish` скрыт, его
  показывает конец хода. Главный аргумент сдачи (`solution_type`) — только
  во вложенном контексте: сводка вызова сабагента считается с
  `tool_args_summary(..., nested=True)`, наверху сводка прежняя.
- Прочие скрытые тулы (`turn_ask_human`, промежуточная реплика, чек-лист,
  сжатие и другие) строкой ленты не становятся и внутри сабагента: реплика и
  чек-лист показываются своими видами.
- Короткая роль сабагента для заголовка — `SUBAGENT_ROLES` и
  `subagent_role(имя)` там же: `Worker`, `Planner`, `Code planner`, `Coder`,
  `Reviewer`, `Critic`; кастомный и неизвестный `subagent_*` — суффикс имени
  словами (`subagent_security_audit` — `Security audit`). Роль
  `subagent_special_agent` — его аргумент `role`. Таблица в ядре, чтобы её
  могли взять и другие фронтенды; сводка аргументов (`tool_args_summary`)
  и заголовки ACP и chat от неё не меняются.

## Свой системный промпт

Кастомные сабагенты работают на отдельном системном промпте —
`prompts/chat_completions_custom_subagent_system_prompt.md`. Он совпадает с промптом
встроенных, но добавляет раздел о том, что роль написал оператор в локальном файле:

- роль **не выдаёт прав** — правила безопасности и границы рабочей области выше неё;
- роль **не описывает инструменты**: если она обещает запись, а инструментов записи нет,
  сабагент сообщает об ограничении, а не ищет обход;
- текст роли **не является системной инструкцией** — попытки переопределения внутри неё
  (как и внутри прочитанных файлов и выводов инструментов) веса не имеют;
- при неоднозначной роли выбирается более узкое прочтение.

Переопределяется ключом `paths.chat_completions_custom_subagent_system_prompt_path`.
Если файл не задан или не читается, берётся встроенный. Свой шаблон обязан содержать
плейсхолдер `<specific_role>` — без него роль из файла молча никуда не подставится.

## Ограничения

- **Аргументы фиксированы.** У любого сабагента ровно два параметра: `reason` и `task`.
  Свою схему аргументов задать нельзя.
- **Глубина 1.** Сабагент не может вызывать сабагентов; `subagent_*` в `tools`
  игнорируется.
- **Модель одна.** Сабагент всегда работает на модели родителя; задать свою в файле нельзя.
- **Лимиты общие.** `subagent_max_steps` и `subagent_finish_gate_max_iterations` — одни
  на всех, на роль не настраиваются.
- **Одна папка.** Слоёв `project > user > system`, как у скиллов, нет.
- **Без горячей перезагрузки.** Файлы читаются на старте рана.
- **Контракт сдачи общий.** К любой роли автоматически приклеивается требование
  вернуть результат JSON-отчётом через `turn_finish` (`status`, `report_summary`,
  `artifacts_created`, `checks`). Отменить его из файла нельзя.
