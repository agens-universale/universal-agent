# Ручные тесты

Здесь то, что автоматический набор проверить **не может**: живые MCP-серверы,
настоящий браузер, реальная модель, поведение процессов во времени. Всё
остальное закрыто `uv run pytest` — см. [testing.md](testing.md).

Правило отбора: если проверку можно написать на `ScriptedBackend`, ей здесь не
место, она идёт в pytest. Сюда попадает ровно то, где отказ проявляется только
на живом внешнем участнике.

Стенд — `gc-core-acceptence`, конфиг у него свой.

---

## MCP: три случая, на которых мы обожглись

Каждый из трёх стоил половины дня и не ловится юнит-тестом на моках.

### M-1. Бюджет времени на `initialize`

**Зачем.** Объявление capabilities, которых мы не реализуем, заставляет сервер
ждать свой таймаут. Замерено: `{}` → **1,1 с**, `roots` → **61,2 с**,
`roots` + `sampling` → **64,2 с**. До того, как причина нашлась, были проверены
и отброшены три неверные гипотезы: недоступность сети, `--timeout-navigation`,
параметры spawn.

```bash
cd gc-core-acceptence
time uv run python -c "
import asyncio, time
from gc_core.tools.connect_mcp.transport import ...  # поднять сессию к playwright
"
```

**Ожидание.** Handshake живого сервера — меньше 5 секунд.
**Провал.** Десятки секунд ⇒ смотреть `capabilities` в `initialize`
(`transport.py`): там должно быть `{}`, а не то, что мы не реализуем.

Автоматическая часть закрыта `test_mcp_declared_capabilities.py` — она следит
за составом объявленного. Живой замер времени остаётся здесь.

### M-2. Persistent-сессия: браузер не открывается и закрывается

**Зачем.** При `persistent: false` процесс stdio поднимается **на каждый
вызов**, и браузер видимо мигает. При `true` — один процесс на всё время.

| Конфиг | Ожидание |
|---|---|
| `persistent: false` | окно открывается и закрывается на каждый шаг |
| `persistent: true` | окно открывается один раз, живёт до конца прогона |

**Провал.** При `true` браузер всё равно мигает ⇒ сессия не переиспользуется.

### M-3. Три агента на общей сессии браузера

**Зачем.** Владение сессией: закрытие из чужой задачи рвёт не тот cancel scope
anyio. Понадобился `ContextVar`-токен владельца через три реестра.

```bash
cd gc-core-acceptence
uv run parallel_agents.py --browser
```

**Ожидание.** Все три агента реально ходят в браузер (не подменяют его на
`exec_fetch_url` — первый прогон именно этим и обманул), каждый отвечает,
процесс не падает. Замерено: параллелизм **1,89×** на общем браузере,
**2,82×** на изолированных `stream_http`.

**Провал.** Падение с cancel scope, либо один агент отвечает, а двое молчат.

### M-4. Шесть транспортов поднимаются

stdio, stream_http, sse, ws, mtls, headers — по одному серверу каждого вида,
проверить, что дискавери отдаёт список тулов.

## Хранилище тредов: чужая реализация

Контракт и обе наши реализации закрыты pytest
(`test_thread_store_protocol.py`, `test_thread_store_async.py`,
`test_acceptance_sdk_thread_store.py`). Ручного здесь — только настоящая база.

### S-1. Реализация поверх настоящего Redis

**Зачем.** In-memory двойник не воспроизводит сетевую задержку, повторные
подключения и потерю соединения.

```python
from gc_testkit.thread_store_conformance import assert_conforms_async

assert_conforms_async(lambda: RedisThreadStore(url="redis://localhost:6379"))
```

**Ожидание.** Пятнадцать проверок пройдены.

Затем — прогон агента на этом хранилище и проверка, что в каталоге тредов не
появилось ни одного файла.

### S-2. Предупреждение о блокирующем хранилище

**Зачем.** Синхронный сетевой клиент статически не отличить от быстрого
локального, а разница в лаге цикла — на порядок.

Поднять агента с **синхронным** Redis-клиентом (`redis-py`), прогнать один ход.

**Ожидание.** В логе один раз появляется `thread_store_blocking_loop` с именем
метода и подсказкой про `AsyncThreadStore`.
**Провал.** Тишина ⇒ детектор не работает; предупреждение на каждый вызов ⇒
не однократное.

### S-3. Второй прогон того же треда

**Зачем.** Расхождение «номер `seq` против количества» и незаштампованная meta
проявляются **только на втором прогоне** — первый проходит нормально.

Прогнать агента дважды с одним `thread_id`.

**Ожидание.** История продолжена, `id` не задвоились, `StateSchemaError` нет.

## Суммаризация под async

Автоматическая часть — `test_thread_store_async.py::test_sync_and_async_paths_agree`
и набор `summarize/`. Здесь — то, что требует живой модели.

### C-1. Компакция по порогу на живой модели

Опустить `summary.chat_completions_summary_trigger_chars` до значения, которое
реальный диалог перешагнёт за два-три хода.

**Ожидание.** В логе `summary_triggered reason=pre_run|pre_backend`, история
схлопнулась в `[system?, m_sum_*]`, появились архивы
`data_<tid>__pre_summary__<ts>.jsonl`, в meta — `last_summarized_at` и
`last_summary_archive_suffix`.

### C-2. Индикаторы TUI во время компакции

**Зачем.** Именно они молча не загорались на асинхронном хранилище: возврат
`patch_runtime_flag` нигде не используется, и корутина просто выбрасывалась.

**Ожидание.** Во время компакции в TUI горит «сжимаю контекст», после —
гаснет; секция `runtime` из meta исчезает целиком.

### C-3. Отмена посреди компакции

**Зачем.** Единственное место, где я жду сюрприза: отмена посреди двухфазной
записи (архив + новая история) на файловом хранилище не атомарна.

Прервать прогон (Ctrl-C / закрытие TUI) в момент, когда идёт компакция.

**Ожидание.** Тред не порван, meta консистентна, следующий запуск читает тред
без ошибки и снимает протухший флаг `summarizing`.

### C-4. Многобатчевая сводка не обновляет рабочую память

**Зачем.** Побочный эффект, о котором легко забыть: при числе батчей `N > 1`
шаг memory-patch **не выполняется**.

Задать `summary.incremental_batch_chars` заведомо меньше объёма диалога.

**Ожидание.** В трассе `memory_patch = {executed: false, reason:
"skipped_multi_batch"}`, в логе `summary_memory_patch_skipped_multi_batch`,
`working_memory` из сводки не обновилась.

## Что сюда не входит и почему

| Проверка | Где закрыта |
|---|---|
| контракт хранилища, 15 свойств | `thread_store_conformance` |
| async-хранилище доезжает целиком | `test_thread_store_async.py` |
| SDK не пишет файлы треда | `test_acceptance_sdk_thread_store.py` |
| неблокирование цикла, параллелизм | `test_acceptance_non_blocking.py` |
| состав объявленных MCP-capabilities | `test_mcp_declared_capabilities.py` |
| владение MCP-сессией | `test_mcp_session_owner.py` |
| равенство sync- и async-путей компакции | `test_thread_store_async.py` |

Проверка, которую можно перенести отсюда в pytest, **должна** быть перенесена:
ручной тест исполняется тогда, когда о нём вспомнят.
