# Плагины

Плагин — готовый набор для агента: skills, команды, субагенты,
MCP-серверы и хуки в одном каталоге. Агент читает плагины в формате
Claude Code и в формате Agent Plugins (agent-plugins.org) как есть, без
перекладки файлов, поэтому готовые наборы вроде
[superpowers](https://github.com/obra/superpowers) ставятся одной командой.

Без плагинов поведение агента не меняется: по умолчанию их нет.

Что работает в первой версии:

| Компонент | Как виден агенту |
|---|---|
| skills (`skills/`) | skills с id `<плагин>:<skill>` |
| команды (`commands/`) | `/<плагин>:<команда> аргументы` — шаблон запроса |
| субагенты (`agents/`) | кастомные субагенты `subagent_<плагин>_<имя>` |
| MCP-серверы (`.mcp.json`) | серверы `<плагин>_<сервер>` рядом с серверами конфига |
| хуки `SessionStart`, `UserPromptSubmit` | добавляют контекст; только у доверенных плагинов |

Поведение одинаковое в `gc-cli`, TUI (`gc-ua`) и ACP. Сервер по умолчанию
установленные плагины не берёт ([ниже](#сервер)).

## Быстрый старт

```bash
gc-plugin install obra/superpowers   # показывает, что плагин запускает, и спрашивает
gc-plugin list                       # что установлено
```

Установленный плагин работает сразу, править конфиг не нужно. В TUI его
состав и неполадки показывает `/plugins`.

## Откуда агент берёт плагины

Набор плагинов складывается из трёх источников:

1. **Каталоги** из `plugins.paths` — удобно, когда вы пишете свой плагин.
2. **Git-источники** из `plugins.sources` — агент сам клонирует репозиторий
   в кеш.
3. **Установленные** командой `gc-plugin install` — постоянное хранилище
   `<gc_data>/plugins/installed/<имя>/` (на Linux и macOS
   `~/.local/share/gc/plugins/installed/`).

```yaml
plugins:
  paths:
    - /абсолютный/путь/к/my-plugin
  sources:
    - git: obra/superpowers        # owner/repo (GitHub) или полный URL
      ref: v5.0.0                  # ветка, тег или хеш коммита (необязательно)
      subdir: null                 # каталог плагина в репозитории (необязательно)
  use_installed: true              # подключать установленные (по умолчанию да)
  hook_timeout_sec: 30             # таймаут хука, если в hooks.json свой не задан
```

- Автопоиска нет: плагин работает, только если он установлен или указан в
  конфиге.
- Плагин с одним именем, заданный в нескольких местах, загружается один раз:
  берётся первый по порядку списка выше.
- Относительный путь в `plugins.paths` считается от каталога основного
  `config.yml`. В конфиге проекта (`<проект>/.gc/config.yml`) пишите
  абсолютный путь: относительный тоже отсчитается от основного конфига, а не
  от проекта.
- `plugins.use_installed: false` выключает все компоненты установленных
  плагинов (skills, команды, субагенты, MCP, хуки); `paths` и `sources`
  при этом работают. Бенчи Harbor ставят `false`, чтобы прогон не зависел
  от того, что установлено на машине. Разово — флагом:
  `gc-cli --plugins.use_installed false`.

### Git-источники

Репозиторий клонируется в `<gc_cache>/plugins/<имя>-<хеш>` один раз при
запуске агента, дальше агент работает из кеша без сети. Тег или хеш коммита
в `ref` фиксируют версию. Если клон не удался или в репозитории нет
`subdir`, плагин пропускается, а причина видна в уведомлениях при старте.
Источник, добавленный в конфиг во время работы TUI, клонируется при
следующем запуске.

Обновить кеш:

```bash
gc-plugin sources update
```

Команда обновляет только клоны на ветке (или без `ref`). Клоны, закреплённые
на теге или коммите, не трогаются. Работающий агент видит обновление после
перезапуска.

## Команда `gc-plugin`

```bash
gc-plugin install obra/superpowers               # owner/repo, URL или локальный путь
gc-plugin install obra/superpowers --ref v5.0.0  # зафиксировать версию (тег или хеш)
gc-plugin install owner/repo --subdir plugins/x  # плагин не в корне репозитория
gc-plugin list                                   # on/off, имя, версия, источник, коммит
gc-plugin disable superpowers                    # файлы остаются, плагин не грузится
gc-plugin enable superpowers
gc-plugin update superpowers                     # переустановить из источника
gc-plugin uninstall superpowers
gc-plugin sources update                         # обновить кеш plugins.sources
```

Команда входит в дистрибутив `gc-mcp` (вместе с `gc-mcp` и `gc-mcp-install`)
и в полный `gc-ua` ([packaging.md](packaging.md)).

**Подтверждение.** `install` и `update` сначала показывают, что плагин
запускает: хуки и адреса или команды MCP-серверов так, как они записаны в
файлах плагина, переменные окружения, которые читают MCP-серверы, права
каждого субагента (правит файлы, запускает команды, все инструменты, MCP
своего плагина) и то, что из плагина не заработает. Подстановки `${VAR}` и
`${CLAUDE_PLUGIN_ROOT}` не раскрываются, чтобы секреты из окружения не
попали в вывод. Затем спрашивается `Установить? [y/N]`. Флаг `--yes` (`-y`)
пропускает вопрос; без терминала и без `--yes` установка отклоняется.
`update` спрашивает, если в плагине изменилось хоть что-то (хуки, MCP, любой
файл); без изменений обновляет молча.

`update` переустанавливает плагин из того же источника с тем же `ref`:
плагин на ветке уходит вперёд, закреплённый остаётся на месте. Выключенный
плагин после обновления остаётся выключенным. Если в источнике сменилось
имя плагина, `update` отказывает с причиной: старый плагин удаляют и ставят
заново (`uninstall` и `install`).

`uninstall` удаляет только плагин из хранилища и только внутри него;
незнакомое имя — ошибка с ненулевым кодом, ничего не удаляется.

## Формат плагина

Формат определяется по манифесту:

- `.claude-plugin/plugin.json` или манифеста нет вовсе — формат Claude Code;
- только `plugin.json` в корне — формат Agent Plugins.

Если в пакете есть оба манифеста, читается Claude Code. Манифесты для других
агентов (`.codex-plugin`, `.cursor-plugin` и подобные) не читаются.

```
my-plugin/
  .claude-plugin/plugin.json   # имя и версия (необязательно)
  skills/<id>/SKILL.md         # skills
  commands/<имя>.md            # команды
  agents/<имя>.md              # субагенты
  hooks/hooks.json             # хуки
  .mcp.json                    # MCP-серверы (или mcp.json; .mcp.json главнее)
```

Без манифеста имя плагина — имя каталога.

Пути к компонентам в `plugin.json` формата Claude Code (`skills`, `commands`,
`agents`, `mcpServers`) **дополняют** стандартные каталоги. Каждый путь
проверяется после раскрытия ссылок: путь за пределы плагина отбрасывается с
предупреждением в логе. `mcpServers` может быть и самим описанием серверов.
Путь `hooks` из манифеста не читается — только `hooks/hooks.json`.

Вложенные папки в `commands/` и `agents/` не обходятся.

### Agent Plugins

- Манифест читается строго: обязательны `$schema`
  (`https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`) и `name`
  (строчные латиница, цифры, `.` и `-`, до 64 символов). Неверный плагин не
  загружается, `gc-plugin install` его отклоняет. Неизвестные поля
  игнорируются с предупреждением в логе.
- Из пакета берутся только `skills/` и `mcp.json`; `hooks/hooks.json`,
  `commands/` и `agents/` игнорируются.
- Skills, выходящие ссылкой за корень плагина, пропускаются.

## Skills

Skills плагина видны агенту как `<плагин>:<skill>` и работают как обычные
skills ([skills.md](skills.md)): модель видит их в списке и загружает сама,
в TUI их можно запустить из палитры.

## Команды

Команда — файл `commands/<имя>.md`: необязательная YAML-шапка (`description`)
и текст запроса. Команда — **шаблон**: `$ARGUMENTS` заменяется всеми
аргументами, `$1`…`$9` — отдельными словами аргументов (кавычки группируют
слова, как в оболочке).

```markdown
---
description: Проверить файл на ошибки
---
Прочитай файл $1 и найди в нём ошибки.
```

Как вызвать: в начале сообщения написать `/плагин:команда аргументы`.
Короткое `/команда` тоже работает, если имя однозначно. Агент добавляет к
запросу техническое сообщение с текстом команды, где аргументы уже
подставлены; как намерение пользователя (для проверки финала и сводки)
учитывается раскрытая команда. Полное имя работает одинаково во всех
режимах: `gc-cli -q "/review:check app.py"`, TUI, ACP. Короткое в TUI
уступает командам TUI — см. ниже.

- **Общее имя с skills.** Команды и skills делят одно пространство имён.
  Короткое имя однозначно, только если оно одно по обоим спискам; иначе
  команда не подставляется, и модель просит указать полное имя. Если у
  команды и skill одного плагина одинаковый id, работает skill, а команда
  отбрасывается с уведомлением.
- **В списке skills команд нет.** Модель не видит команды и сама их не
  вызывает — только пользователь.
- **TUI.** Короткое `/команда` доходит до команды плагина, только если
  это слово не занято командой TUI или её алиасом: алиасы тоже считаются
  словами TUI (`/clear` — алиас `/new`). При совпадении работает команда
  TUI, а команда плагина доступна по полному `/плагин:команда` и из
  палитры. Палитра показывает команды плагинов цветом skills с пометкой
  `· <плагин>` справа и описанием из `description`; строка находится и по
  короткому слову, и по полному имени. В строке короткое имя, если оно
  однозначно и не занято словом TUI, иначе полное. По Enter строка уходит
  агенту как обычный запрос. Команда в другой раскладке тоже работает:
  `/кумшуц` — это `/review`.
- Из шапки не применяются `allowed-tools`, `model` и `argument-hint`.
  Инструкции `` !`команда` `` в тексте не выполняются — модель получает их
  как текст.

## Субагенты

Файл `agents/<имя>.md` — готовый субагент: YAML-шапка (`name`,
`description`, `tools`, иногда `model`) и системный промпт. Он подключается
кастомным субагентом `subagent_<плагин>_<имя>` и живёт по тем же правилам,
что определения из `agent.subagents_dir` ([subagents.md](subagents.md)):

- нужны `agent.use_local_subagents` и `backend.api_mode: chat_completions`;
- действуют лимит `agent.subagents_max_count` и список имён в
  `agent.use_local_subagents`;
- при совпадении имён встроенный субагент и определение из `subagents_dir`
  главнее.

Почему субагент сейчас недоступен, показывает карточка плагина в
`/plugins`.

**Модель.** Поле `model` не переносится: модель субагента задаёт реестр
моделей (`assign.subagents.<имя>`, [configuration.md](configuration.md)).
Если в шапке указана модель (кроме `inherit`), в уведомлениях — «поле model
проигнорировано».

### Инструменты субагента

| Шапка субагента | Что получает субагент |
|---|---|
| ключа `tools` нет | все инструменты |
| `tools: []`, `tools: ""` | только служебные: завершение хода, память сессии, todo, чтение сохранённых выводов |
| `tools:` с неверным значением (`null`, словарь, число) | только служебные, с уведомлением |
| непустой список, перевелось хоть что-то | переведённые инструменты; отброшенные — в уведомлениях |
| непустой список, не перевелось ничего | субагент не подключается, причина — в уведомлениях |
| битая YAML-шапка | субагент не подключается |

Субагент не получает больше прав, чем задумал автор. Обратная сторона:
субагент `[Read, WebSearch]` подключится только с чтением файлов и может
справиться хуже, если его работа держалась на отброшенном инструменте.
Это видно в уведомлениях.

### Перевод имён инструментов

Имена переводятся только во встроенные инструменты агента и в
MCP-инструменты этого же плагина.

| В файле плагина | У агента |
|---|---|
| `Read` | `fs_read_file` |
| `Write` | `fs_write_file` |
| `Edit`, `MultiEdit` | `fs_apply_file_edits` |
| `Grep` | `fs_find_in_files` |
| `Glob` | `fs_find_files_by_name` |
| `LS` | `fs_list_files` |
| `Bash` | `exec_command` |
| `WebFetch` | `exec_fetch_url` |
| `TodoWrite` | `session_todo` |
| `mcp__<сервер>__<тул>`, `mcp__plugin_<плагин>_<сервер>__<тул>` | инструмент `<тул>` сервера `<сервер>` этого плагина |
| `mcp__<сервер>`, `mcp__<сервер>__*` | все инструменты сервера `<сервер>` этого плагина |
| имя агента (`fs_read_file`) | как есть, если такой встроенный инструмент есть |
| остальное (`WebSearch`, `Task`, ноутбуки…) | отбрасывается |
| MCP-сервер другого плагина или из `mcp.servers` | отбрасывается |

Если MCP-сервер плагина недоступен во время работы, субагент только с его
инструментами получит одни служебные — как любой кастомный субагент с
MCP-инструментами.

## MCP-серверы

Серверы плагина — **отдельный источник** рядом с `mcp.servers`, в ваш
конфиг они не записываются. Агент подключает серверы конфига и серверы
включённых плагинов вместе; в `/mcp` видны и те и другие.

- Ключ сервера — `<плагин>_<сервер>`, а сервер с именем самого плагина —
  просто `<плагин>` (`context7`, а не `context7_context7`). Инструменты
  видны модели как `mcp_<ключ>_<тул>`; имя длиннее 64 символов сокращается
  с хешем, вызов идёт по исходному имени.
- **Своя запись побеждает.** Запись с тем же ключом в `mcp.servers` (личного
  или проектного конфига) целиком заменяет сервер плагина, например чтобы
  задать свой адрес или токен. Замена видна в `/plugins`.
- **Столкновение ключей.** Если ключи двух серверов совпали (`a_b` + `c` и
  `a` + `b_c`, или `a.b` и `a_b` в одном плагине), подключается первый,
  второй пропускается с уведомлением.
- **Как выключить.** `--mcp.servers '{}'` выключает только серверы конфига.
  Серверы плагина выключаются вместе с плагином: `gc-plugin disable`,
  `plugins.use_installed: false`, правка `plugins.paths` / `plugins.sources`.
  Если прогону нужен «ни одного MCP», задайте и `--mcp.servers '{}'`, и
  `--plugins.use_installed false`, и пустые `plugins.paths` и
  `plugins.sources`.

### `.mcp.json` формата Claude Code

`{"mcpServers": {имя: {...}}}` или сразу `{имя: {...}}`. Поддержаны `stdio`
(`command`, `args`, `env`, `cwd`), streamable HTTP (`type: http`,
`streamable-http` или `url` без `type`) и `sse` (`url`, `headers`).

- `${CLAUDE_PLUGIN_ROOT}` (и `${GC_PLUGIN_ROOT}`) заменяется путём плагина.
- `${VAR}` и `${VAR:-по_умолчанию}` берутся из окружения процесса во всех
  полях записи. Так передаются секреты:
  `"Authorization": "Bearer ${GITHUB_PERSONAL_ACCESS_TOKEN}"`. Если
  переменная без значения по умолчанию не задана, сервер пропускается с
  уведомлением (значение не пишется). Установке это не мешает: сводка
  `gc-plugin install` показывает, какие переменные нужны.
- Битый сервер пропускается с уведомлением, остальные подключаются; значения
  из файла в лог не пишутся.
- Серверы со входом по OAuth (например, облачный context7) не подключаются и
  показывают 401 в `/mcp`. Обход — ключ через `${VAR}` или своя запись в
  `mcp.servers`.

### `mcp.json` формата Agent Plugins

Обязательны `$schema` и `mcpServers`; у сервера один из видов `stdio`,
`streamable-http`, `sse`. `${PLUGIN_ROOT}` и `${PLUGIN_DATA}` раскрываются
только в `args`, `env`, `cwd`. Серверу `stdio` в окружение передаются
`PLUGIN_ROOT` и `PLUGIN_DATA`; каталог данных —
`<gc_data>/plugins/data/<имя>`. Для адресов вне loopback нужен HTTPS.

## Хуки

В первой версии работают два события, оба только добавляют контекст:

| Событие | Когда | Что даёт |
|---|---|---|
| `SessionStart` | перед запросом к модели, один раз на контекст; снова — после сжатия истории (`source: compact`), в том числе посреди хода | текст хука добавляется техническим сообщением |
| `UserPromptSubmit` | на сообщении пользователя (не на технических); в stdin есть `prompt` | текст хука добавляется техническим сообщением; `decision: block` или код 2 — модель получает сообщение с причиной (запрос уже в истории). Сжатие посреди шага сохраняет это сообщение вместе с запросом: повтор запроса хук не перезапускает |

- `SessionStart` идёт для каждого плагина отдельно: плагин, включённый
  посреди треда, получает свой запуск. Хук, который ничего не вывел,
  запускается снова на следующем ходе (не чаще раза на ход).
- `matcher`: `*` или пустая строка подходят всегда, иначе регулярное
  выражение, которое должно совпасть целиком. Для `SessionStart`
  сверяется источник: `startup` или `compact`. У `UserPromptSubmit`
  сверять не с чем: условие не применяется, хук срабатывает на каждый
  запрос (как в Claude Code).
- Субагентам хуки не запускаются.
- Хуки `PreToolUse`, `PostToolUse`, `PostToolUseFailure` и `Stop`
  пропускаются: сводка установки и `/plugins` пишут «будут поддержаны
  после middleware». Хуки других событий пропускаются молча.

### Чьи хуки запускаются

Хук — внешняя команда с вашими правами, поэтому хуки запускаются только у
**доверенных** плагинов:

- установленных `gc-plugin install` (вы подтвердили их при установке);
- подключённых в личном конфиге (основной `config.yml` и профили рядом с
  ним) или в управляемом конфиге.

У плагинов из конфига проекта (`<проект>/.gc/config.yml`) и из профиля,
лежащего в проекте (`<проект>/.gc/profiles/…`), хуки не запускаются: чужой
репозиторий не должен запускать команды без вашего согласия. Skills,
команды, субагенты и MCP таких плагинов работают. При старте один раз
показывается: «Хуки плагина X из конфига проекта не запускаются. Чтобы
включить, установите плагин командой `gc-plugin install` или добавьте его в
личный конфиг». Если тот же плагин есть и в личном конфиге, он доверенный.

### Контракт хука

- **Запуск:** команда из `hooks.json` исполняется через `bash -c`
  (на Windows — `bash` из PATH; нет его — хук считается сбоем). Таймаут —
  поле `timeout` хука в секундах, иначе `plugins.hook_timeout_sec`. По
  таймауту и при остановке агента убивается вся группа процессов хука
  (на Windows — только `bash`, его потомки могут доработать). Агент не
  ждёт хук дольше 2 секунд после этого, даже если вывод держит открытым
  отвязанный потомок. Стоп хода (`/stop`) снимает идущий хук сразу и
  сбоем не считается; после стопа хуки этого хода не запускаются.
- **Окружение:** окружение агента плюс `GC_PLUGIN_ROOT` и
  `CLAUDE_PLUGIN_ROOT` (каталог плагина) и `GC_PROJECT_DIR` (рабочий
  каталог).
- **Вход:** JSON на stdin: `hook_event_name`, `session_id`, `cwd` и поля
  события (`source` у `SessionStart`, `prompt` у `UserPromptSubmit`).
- **Выход:** код 0 и JSON — берётся `additionalContext` (верхнего уровня или
  в `hookSpecificOutput`); код 0 и не JSON — весь текст идёт в контекст.
  Контекст длиннее 10 000 символов обрезается с пометкой.
- **Сбой** — другой код выхода, таймаут, код 2 у `SessionStart`. Агент
  продолжает работу. Один раз на плагин и событие за запуск: в TUI —
  уведомление, в `gc-cli` — строка в stderr; в ACP и на сервере — только
  запись в лог.

```json
{
  "hooks": {
    "SessionStart": [
      { "matcher": "startup|compact",
        "hooks": [{ "type": "command",
                    "command": "python3 \"${CLAUDE_PLUGIN_ROOT}/hooks/start.py\"" }] }
    ]
  }
}
```

## Когда изменения вступают в силу

Агент берёт набор плагинов целиком и работает на нём, чтобы компоненты
одного запуска не оказались из разных версий набора.

- **`gc-cli`** — каждый запуск читает набор заново.
- **TUI** — после `gc-plugin install`, `update`, `enable`, `disable` или
  `uninstall` в другом терминале следующий ход идёт на новом наборе целиком:
  skills, команды, субагенты, MCP, хуки и палитра. Набор сверяется с диском и
  при отправке ввода, открытии палитры и `/plugins`, поэтому команда нового
  плагина работает с первой попытки; идущий ход набор не меняет. Правка
  `plugins.*` в конфиге
  применяется, когда TUI перечитывает настройки (смена профиля, сохранение
  в `/settings`), или после перезапуска.
- **ACP и сервер** — набор читается при старте процесса; изменения
  вступают в силу после перезапуска.
- Правки файлов внутри каталога из `plugins.paths` (когда вы пишете плагин)
  и `gc-plugin sources update` видны после перезапуска.

## Где плагины не работают

В этих режимах плагины в первой версии выключены целиком — все компоненты;
причина показывается в уведомлениях при старте и в `/plugins`:

- задан `paths.skills_data_path` (единый источник skills);
- ресурсы агента в своём хранилище (`storage` для агента — не файлы). Треды
  в базе при ресурсах агента на диске плагинам не мешают;
- удалённый OS-бэкенд (`harbor`, `docker`, `ssh`, `exec`);
- durable-режим (Temporal): воркер и `AgentActivity` собирают настройки без
  плагинов, даже если приложение передало готовый снимок; если в профиле
  заданы плагины, они пишут об этом в лог.

## Сервер

`gc-serve` по умолчанию не подхватывает плагины, установленные на хосте:
в `demo_config_server.yml` в общих `agent_overrides` стоит
`plugins.use_installed: false`. Плагины из `plugins.paths` и
`plugins.sources` в `config.yml` работают. Подробнее и предупреждение для
уже развёрнутых конфигов — в [server.md](server.md#плагины).

## Что не входит в первую версию

- Хуки `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Stop` — придут
  вместе с middleware.
- Хуки плагинов из конфига проекта и проектных профилей не запускаются;
  чтобы включить, установите плагин или подключите его в личном конфиге.
- `/плагин:команда`, введённая как ответ на вопрос агента, не раскрывается:
  ответ уходит модели как есть.
- Режимы без плагинов — [выше](#где-плагины-не-работают).
- Из формата Claude Code не поддерживаются: `marketplace.json` и установка
  `плагин@маркетплейс` (ставьте через `--subdir`), хуки типов `http`,
  `prompt`, `agent`, выполнение `` !`команда` `` в командах, `model`
  у субагентов, `userConfig`, LSP-серверы, стили вывода, OAuth для MCP.
  `extensions` Agent Plugins игнорируются.
- Инструменты, которых у агента нет (`WebSearch` и другие), не заменяются
  MCP-инструментами пользователя.

## Где смотреть, что не работает

- **Сводка `gc-plugin install` и `update`** — до установки.
- **Уведомления при старте** — `gc-cli` пишет их в stderr, TUI показывает
  уведомлениями, `gc-serve` — в консоль: пропущенные субагенты и MCP-серверы,
  отброшенные инструменты, хуки, которые не запускаются, неполученные
  git-источники, режим без плагинов.
- **`/plugins` в TUI** — состав каждого плагина, его неполадки, права
  субагентов и почему субагент недоступен при текущих настройках. Экран
  только показывает.
- **Лог агента** — подробности сбоев хуков и разбора файлов.
