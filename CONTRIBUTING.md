# Участие в разработке

Мы принимаем сообщения об ошибках, предложения по улучшению, исправления
документации и изменения исходного кода GigaCode Universal Agent (`gc-ua`).

Перед началом работы ознакомьтесь с настоящими правилами.

## Как можно помочь проекту

Вы можете:

- сообщить об ошибке;
- предложить улучшение;
- исправить документацию;
- добавить или исправить тесты;
- исправить ошибку в коде;
- реализовать согласованную функциональность;
- улучшить совместимость с моделями, провайдерами и инструментами.

Крупные изменения желательно предварительно обсудить в Issue. Это позволяет
избежать работы над изменением, которое не соответствует направлению проекта
или уже реализуется другим участником.

Обратная связь также принимается в каналах поддержки (см. [readme.md](readme.md)).

## Сообщения об ошибках

Перед созданием Issue:

1. Проверьте, не была ли проблема уже зарегистрирована.
2. Убедитесь, что она воспроизводится на актуальной версии проекта.
3. Подготовьте минимальный пример воспроизведения.

В сообщении укажите:

- версию проекта или хеш коммита;
- операционную систему и версию Python;
- используемую модель и провайдера;
- конфигурацию запуска (`--config`, профиль, уровень модели);
- последовательность действий;
- ожидаемое поведение;
- фактическое поведение;
- логи или traceback.

Удалите из логов токены, пароли, персональные данные и другую
конфиденциальную информацию.

Если проблема связана с уязвимостью, не создавайте публичный Issue.
Следуйте инструкциям из [SECURITY.md](SECURITY.md).

## Предложения новых возможностей

Опишите:

- какую практическую проблему решает изменение;
- для кого оно предназначено;
- почему существующих возможностей недостаточно;
- предполагаемый сценарий использования;
- возможные альтернативы;
- влияние на обратную совместимость.

Само наличие реализации не гарантирует принятия функции. Мы оцениваем
соответствие архитектуре проекта, стоимость сопровождения и применимость
для других пользователей.

## Настройка окружения разработки

Клонирование, установка через `uv` и структура пакетов описаны в
[readme.md](readme.md), [docs/usage.md](docs/usage.md) и
[docs/packaging.md](docs/packaging.md). Зависимости ставьте только через `uv`.

Практическая памятка — карта репозитория, запуск из исходников, частые
грабли — в [docs/for_developers](docs/for_developers/README.md).

Для разработки достаточно двух команд в корне клона:

```bash
uv sync                        # зависимости, тесты и инструменты проверок
uv run pre-commit install      # хуки проверок — один раз на клон
```

`uv sync` ставит группу `dev`: тестовые зависимости и инструменты гейта качества
(ruff, complexipy, vulture, pylint, pre-commit). Сам хук git пакетный менеджер
поставить не может — git не даёт репозиторию устанавливать исполняемые хуки, —
поэтому `pre-commit install` остаётся отдельным шагом. Ставятся два хука:
`pre-commit` и `pre-push`.

Чтобы хук появлялся в каждом новом клоне сам, один раз на машину:

```bash
git config --global init.templateDir ~/.git-template
uvx pre-commit init-templatedir ~/.git-template
```

Вместо pre-commit подойдёт [prek](https://github.com/j178/prek) — та же
конфигурация, быстрее и без Python: `uvx prek install`.

## Ветки и Pull Request

Модель веток:

- **`develop`** — основная ветка разработки; nightly может быть нестабилен;
- **`master`** — стабильные релизы; в неё мержат только из `develop` (и hotfix
  релизов по согласованию с мейнтейнерами);
- фичи — в ветках вида `feat/<краткое-имя>` от актуального `develop`.

**Все Pull Request принимаются только в ветку `develop`.**

PR в `master` и другие ветки не рассматриваются, если иное явно не согласовано
с мейнтейнерами (например, срочный hotfix релиза).

Перед открытием PR:

1. Обновите свою ветку от актуального `develop`.
2. Убедитесь, что изменение сфокусировано: один PR — одна тема.
3. Добавьте или обновите тесты, если меняется поведение.
4. Прогоните релевантные тесты локально.
5. Прогоните проверки качества: `scripts/lint.sh` (он же стоит хуком
   pre-commit, см. [docs/code-quality.md](docs/code-quality.md)).
6. Не включайте в PR токены, локальные конфиги с секретами, артефакты
   (`threads/`, `*.bak`, отчёты и т.п.).

В описании PR укажите:

- какую проблему решает изменение;
- как проверить;
- влияние на совместимость конфигов, CLI и API, если есть.

## Качество кода

Проверки запускаются сами: на `git commit` — по изменённым файлам, на
`git push` — дополнительно поиск дублирования по всему коду. Всё сразу, как в
CI: `scripts/lint.sh`.

| Проверка | Что ловит |
| --- | --- |
| гигиена файлов | маркеры конфликтов, битый YAML/TOML, приватные ключи, забытый `breakpoint()`, файлы больше 1 МБ, пробелы в конце строк |
| `ruff check` | линтер: ошибки, порядок импортов, упрощения, правила Sonar (неиспользуемые параметры, вложенные `if`, `raise Exception` и др.) |
| `ruff format` | единый стиль кода (Black-совместимый, строка до 120 символов) |
| complexipy | функция сложнее 15 по когнитивной сложности (правило Sonar S3776) |
| `scripts/sonar_like_check.py` | правила Sonar, которых нет в ruff: строка повторена 3+ раз, лишний класс в `except`, вложенный тернарник, одинаковые функции, сложные регулярки |
| `scripts/dead_code_check.py` | мёртвый код: недостижимые строки, неиспользуемые импорты и приватные функции |
| pylint `duplicate-code` (на push) | блоки кода от 10 строк, повторённые в другом месте |

Если проверка не пропускает:

- **ruff исправил файлы сам** («files were modified by this hook») —
  посмотрите правки, добавьте их (`git add`) и повторите коммит;
- **слишком сложная функция** — вынесите части в хелперы; хук называет файл,
  функцию и её сложность;
- **строка повторяется** — вынесите её в константу модуля;
- **мёртвый код** — удалите; если код жив по причине, которую анализ не видит
  (вызов по имени из строки, сигнатура чужого колбэка), добавьте имя в
  `scripts/dead_code_whitelist.py` с пояснением;
- **дублирование** — вынесите общее в функцию или базовый класс.

Заглушить находку можно только с обоснованием в той же строке:
`# noqa: <КОД>  # почему` для ruff, `# NOSONAR: почему` для нашего чекера и
Sonar. `git commit --no-verify` пропускает хуки, но CI прогонит те же проверки.

Как устроен гейт, какие правила Sonar чем ловятся и что выключено — в
[docs/code-quality.md](docs/code-quality.md).

## Коммиты

- Сообщение — по-русски, в форме `тип(область): что изменилось`: `fix(core): …`,
  `feat(tui): …`, `refactor: …`, `test(cli): …`, `docs: …`, `chore(lint): …`.
  Область — пакет или подсистема (`core`, `cli`, `tui`, `server`, `mcp`,
  `testkit`), через запятую, если затронуто несколько; `!` после области —
  ломающее изменение.
- В теле — почему, а не только что: какая была проблема и почему решение такое.
- Одно логическое изменение — один коммит. Массовая механика (форматирование,
  переименование по всему коду) — отдельным коммитом, его хеш добавляется в
  `.git-blame-ignore-revs`. Включить у себя:
  `git config blame.ignoreRevsFile .git-blame-ignore-revs`.
- Заметные для пользователя изменения — в `CHANGELOG.md`, раздел `Unreleased`.
- Смена версии — `python scripts/bump_version.py X.Y.Z`: скрипт синхронно
  правит манифесты всех пакетов и `uv.lock`.

## Стиль изменений

- Следуйте существующему стилю кода в затрагиваемом пакете.
- Не раздувайте diff: без рефакторинга «заодно» и правок несвязанных файлов.
- Крупную архитектуру и новые зависимости согласуйте заранее.
- Документацию обновляйте вместе с поведением, если меняется пользовательский
  контракт (CLI, конфиг, публичные API).
