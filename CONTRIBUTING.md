# Участие в разработке

Мы принимаем сообщения об ошибках, предложения по улучшению, исправления
документации и изменения исходного кода GigaCode Universal Agent (`gc-ua`).

Перед началом работы ознакомьтесь с настоящими правилами.

## Как можно помочь проекту

Вы можете:

- сообщить об ошибке;
- предложить улучшение;
- исправить документацию;
- добавить или исправить тесты;
- исправить ошибку в коде;
- реализовать согласованную функциональность;
- улучшить совместимость с моделями, провайдерами и инструментами.

Крупные изменения желательно предварительно обсудить в Issue. Это позволяет
избежать работы над изменением, которое не соответствует направлению проекта
или уже реализуется другим участником.

Обратная связь также принимается в каналах поддержки (см. [readme.md](readme.md)).

## Сообщения об ошибках

Перед созданием Issue:

1. Проверьте, не была ли проблема уже зарегистрирована.
2. Убедитесь, что она воспроизводится на актуальной версии проекта.
3. Подготовьте минимальный пример воспроизведения.

В сообщении укажите:

- версию проекта или хеш коммита;
- операционную систему и версию Python;
- используемую модель и провайдера;
- конфигурацию запуска (`--config`, профиль, уровень модели);
- последовательность действий;
- ожидаемое поведение;
- фактическое поведение;
- логи или traceback.

Удалите из логов токены, пароли, персональные данные и другую
конфиденциальную информацию.

Если проблема связана с уязвимостью, не создавайте публичный Issue.
Следуйте инструкциям из [SECURITY.md](SECURITY.md).

## Предложения новых возможностей

Опишите:

- какую практическую проблему решает изменение;
- для кого оно предназначено;
- почему существующих возможностей недостаточно;
- предполагаемый сценарий использования;
- возможные альтернативы;
- влияние на обратную совместимость.

Само наличие реализации не гарантирует принятия функции. Мы оцениваем
соответствие архитектуре проекта, стоимость сопровождения и применимость
для других пользователей.

## Настройка окружения разработки

Клонирование, установка через `uv` и структура пакетов описаны в
[readme.md](readme.md), [docs/usage.md](docs/usage.md) и

## Ветки и Pull Request

Модель веток:

- **`develop`** — основная ветка разработки; nightly может быть нестабилен;
- **`master`** — стабильные релизы; в неё мержат только из `develop` (и hotfix
  релизов по согласованию с мейнтейнерами);
- фичи — в ветках вида `feat/<краткое-имя>` от актуального `develop`.

**Все Pull Request принимаются только в ветку `develop`.**

PR в `master` и другие ветки не рассматриваются, если иное явно не согласовано
с мейнтейнерами (например, срочный hotfix релиза).

Перед открытием PR:

1. Обновите свою ветку от актуального `develop`.
2. Убедитесь, что изменение сфокусировано: один PR — одна тема.
3. Добавьте или обновите тесты, если меняется поведение.
4. Прогоните релевантные тесты локально.
5. Прогоните проверки качества: `scripts/lint.sh` (он же стоит хуком
   pre-commit, см. [docs/code-quality.md](docs/code-quality.md)).
6. Не включайте в PR токены, локальные конфиги с секретами, артефакты
   (`threads/`, `*.bak`, отчёты и т.п.).

В описании PR укажите:

- какую проблему решает изменение;
- как проверить;
- влияние на совместимость конфигов, CLI и API, если есть.

## Тесты

Как запускать наборы — в [docs/testing.md](docs/testing.md). Кратко:
`uv run pytest` из корня репозитория.

## Качество кода

Линтер, форматтер, порог когнитивной сложности и локальный аналог правил
Sonar — в [docs/code-quality.md](docs/code-quality.md). Поставить хуки:
`uv sync --group lint && uv run --group lint pre-commit install`.

## Стиль изменений

- Следуйте существующему стилю кода в затрагиваемом пакете.
- Не раздувайте diff: без рефакторинга «заодно» и правок несвязанных файлов.
- Крупную архитектуру и новые зависимости согласуйте заранее.
- Документацию обновляйте вместе с поведением, если меняется пользовательский
  контракт (CLI, конфиг, публичные API).

## Лицензия

Отправляя Pull Request, вы подтверждаете, что ваш вклад распространяется на
условиях лицензии проекта — см. [LICENSE.md](LICENSE.md).
