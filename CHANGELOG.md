# Changelog

## Unreleased

### Breaking — типизированные настройки вместо плоского `config_dict`

- Конфиг загружается в неизменяемые pydantic-модели: `gc_core.config.load_settings(path, profile_override=...)` → `LoadedSettings(settings: AppConfig, runtime: RuntimeEnv, provenance, profile_meta)`. Плоского словаря больше нет: удалены `load_config`, `load_config_ex`, `flatten_app_config`, `flat_config` и поле `RunContext.config_dict`.
- SDK: `AsyncAgent.create(settings)` и `acreate_run_context(settings)` принимают `LoadedSettings`/`AppConfig`; словарь — `TypeError`. Правка — новым объектом: `loaded.with_overrides({"agent.max_steps": 5})`, `override_settings(app_cfg, {...})`. Чтение — `ctx.settings` / `ctx.runtime` (`gc_core.settings.settings_of`/`runtime_of`).
- `gc-cli config` и `gc-ua config`: `explain` (значение и источник каждой настройки — файл, профиль, managed, `${ENV}`, CLI; секреты замаскированы), `validate` (проверка без запуска агента), `schema` (JSON Schema).
- `${ENV:VAR}`/`${FILE:path}` строгие: незаданный источник — ошибка при старте с файлом и ключом; необязательное значение — `${ENV:VAR:-умолчание}`. Отказ — только если значение дошло до итогового конфига: ключ, перекрытый проектом или профилем, загрузку не роняет. Исключение — правило пары адрес+токен записи реестра: оно проверяется по каждому документу, и незаданная переменная в половине пары остаётся ошибкой. `gc-cli --update` работает и со сломанным конфигом.
- Плоские имена прежнего `config_dict` удалены отовсюду: `--param` (`--max_steps 50` → `--agent.max_steps 50`), `agent_overrides` сервера (webhook и swarm), `gc config explain`, профили бенча (`agent_kwargs.gc_cli_config`) и тестовые хелперы принимают только путь настройки через точку (или вложенную секцию — в `agent_overrides` и профилях бенча). Неизвестное имя — ошибка; если у схемы есть настройка с тем же последним сегментом, сообщение подсказывает путь: `неизвестная настройка --max_steps (возможно, --agent.max_steps)`. Объявленные флаги CLI (`--model`, `--completions_url`, `--profile`, `--level`, `--write-guard`, `--trace-id`…) остаются флагами. `gc-acp` и `gc-chat` принимают те же настройки: путь через точку и флаги `--model`, `--completions_url`, `--level` (общий разбор — `gc_core.config_modules.cli_args`). Незнакомый путь — ошибка, код 2; флаги клиента без точки (JetBrains `--experimental`) `gc-acp` пропускает с пометкой в stderr, `gc-chat` отвечает ошибкой.
- Правки из CLI (`--param`), `agent_overrides` сервера и сессионные правки TUI **заменяют** значение по своему пути, как прежний `config_dict.update`: `--mcp.servers '{}'` отключает серверы, список `allowed_read_roots` сужается, `--models` заменяет запись вместе с адресом и токеном. Секция-словарь раскладывается на поля (не сбрасывает остальные поля секции), адрес записи реестра без токена — ошибка правила пары; swarm ведёт себя так же и проверяет каждое раскрытое поле (опечатка внутри секции — ошибка). Флаги CLI не сокращаются (`allow_abbrev=False`). Объединение списков — только у файловых слоёв.
- Негодное значение `--param`/`agent_overrides` — сообщение с ключом и причиной без самого значения (`hide_input_in_errors`): токен не печатается в трейсбеке. Секреты внутри словарей без схемы (`*_kwargs`, `extra_body`) маскируются по имени ключа в TUI `/config` и `gc config explain`. Невалидное сессионное значение в мете треда снимается при открытии с уведомлением.
- Лишний ключ в YAML — уведомление (файл, ключ, подсказка «возможно, …») вместо отказа загрузки; в `--param` — по-прежнему ошибка. `config_version` и реестр миграций; межполевые проверки.
- Метаданные полей (`secret`, `worker_only`, `expert`, `restart`) — рядом с полями модели; токены — `SecretStr`, `repr` настроек секретов не показывает.
- `models.<alias>.backend` больше не принимает `api_mode`, `stream` и `chat_completion_kwargs` — на уровне модели они никогда не применялись (теперь уведомление). `send_tool_strict` и `openai_strict_tools_schema` на алиасе по-прежнему принимаются и применяются в режиме chat_completions.
- Ссылка на сохранённый вывод инструмента (`output_ref`) теперь `out_<sha>` — от содержимого вывода, а не случайный uuid.
- В `${FILE:путь:-умолчание}` умолчание отделяет последний `:-`: путь с `:-` внутри записывается только вместе с умолчанием.
- Прежнее имя `--agent_url` подсказывает `--backend.completions_url`.
- Относительные пути из `--paths.*` и `agent_overrides` (а также `*_prompt_path`, `security.write_guard.extra_paths`) считаются от текущего каталога, как раньше, а не от каталога конфига.
- `gc-ua` и `gc-acp`: сокращённый или незнакомый флаг (`--conf`, `--prof`, `--init`) — ошибка с кодом 2, а не тихий запуск на конфиге по умолчанию (флаги клиента ACP вроде `--experimental` по-прежнему пропускаются). `gc-ua --help` — справка.
- Незнакомый ключ в секции `logging:` у `config_server.yml` отбрасывается с предупреждением (как в YAML агента), а не роняет старт сервера.
- Старые записи треда без `id` больше не дописываются в тред повторно, когда история уходит в ход целиком (Responses без `previous_response_id`).
- Гвард команд защищает `security.protected_paths.extra`; каталоги `security.write_guard.extra_paths` (разрешённые для записи) идут обычной модерацией команд.
- `backend.chat_completion_headers` и `backend.chat_completion_kwargs` строкой (не словарём) — ошибка валидации; раньше значение молча становилось `{}` и запрос уходил без заголовков. Пустая строка — «не задано».
- `logging.propagate` из YAML теперь действует. TUI `/config` показывает настройки документом. Перечитка конфига в TUI атомарна.
- Тестам: `gc_testkit.settings.make_settings` / `fake_ctx` / `update_ctx`, `gc_testkit.helpers.tool_ctx.tool_settings`, `gc_testkit.tui_support.tui_settings` — ключи только путями через точку (`{"agent.max_steps": 3}`) или секциями; `settings_from_flat` удалён.

### Feature — нативный Temporal backend

- **API как у Pydantic AI**: воркер — нативные `temporalio` `Client`/`Worker` с `AgentPlugin` (`SimplePlugin`): агенты — те же настройки, что у `AsyncAgent` (`LoadedSettings` вместе с рантаймом), хранилище тредов — объектом, таймауты и повторы — нативные `ActivityConfig`/`RetryPolicy` (у модели — своя `task_queue`), versioning — нативный `deployment_config` с `default_build_id()`. Приложение — `AsyncAgent.create(settings, durable=TemporalDurability(client, task_queue=…, agent=…))` (ядро знает только протокол `gc_core.aio.durable`) или `AgentSession` (`ask`/`send`/`wait`/`answer_human`/`stop`/`close`); query `message_state` — состояние сообщения и ответ хода, который его обработал (`AgentSession.wait` опрашивает его). `gc-temporal-worker --config` собирает тот же плагин (`run_worker`); `profiles.<имя>.runtime` — рантайм агента (`text_answer_mode` и др.). Очереди `RunRequest` необязательны: по умолчанию — очередь workflow.
- Сверка настроек приложения и воркера: `AsyncAgent(durable=…)` и `AgentSession(settings=…)` передают отпечаток настроек по секциям (`settings_fingerprint`, только хэши), воркер сравнивает его с профилем на подготовке хода; расхождение — `SessionFailed` с перечнем секций (`paths`, `logging` и рантайм не сравниваются). Упавшая сессия у `AgentSession.wait` — `SessionFailed` с исходной причиной; ожидание ответа не держит упавшую сессию.
- Ревью пакета (07.10): пределы считаются в байтах истории Temporal (кириллица — 6 байт на символ); промах кэша ссылок больше не шлёт тред одной записью (шаги хода — в тред, повтор со ссылками); вход activity или субагента больше лимита записи — отказ хода, а не вечный сбой задачи; субагенту — облегчённое состояние родителя; ожидание ответа — опрос query (не занимает лимит update), ответ — своего хода; `AsyncAgent.run([...])` — один ход, без `thread_id` сессия одноразовая; нативный `RetryPolicy` у инструмента не включает бесконечных повторов эффекта; ответы модели — ссылками; параметры подключения `os_backend` (`ssh`, `exec`, `docker`) — только для воркера; предупреждения о непроверенных `os_backend`, общих очередях по умолчанию и размере истории посреди хода.
- **Несовместимо: ID сессии включает агента** (`session_workflow_id(agent, store_id, system_id, thread_id)`). Сессия, открытая прежней версией, под новым ID не находится: новое сообщение откроет новую сессию, а старая держит тред, пока её не закроют (`AgentSession.close` по старому ID, `temporal workflow terminate`) или не снимут владение (`gc-temporal unlock`).
- Ревью r6 (07.10): **meta треда в истории Temporal — разницей, как сообщения — ссылками**: запись несёт изменённые ключи и хвост журнала намерений с номера, длинные тексты — ссылкой на сообщение или на строку meta; квитанция — без meta (только то, что хранилище поменяло само); чтение — частями, если meta больше половины страницы. Хранилище и локальный режим получают полную meta, журнал намерений **больше не урезается** (до этого под Temporal обрезались длинные записи и старые записи журнала); кэш `fetch_url` локального режима в meta не стирается. Повтор записи после падения воркера собирает ту же операцию — хранилище отвечает исходной квитанцией. Значение больше записи истории (ответ модели, вход activity или субагента) — **отказ хода, а не сессии**: `wait` возвращает `turn_error`, `AgentSession.ask` и durable `AsyncAgent.run` поднимают `TurnFailed` (это `ExecutionFailure`, как отказ хода локально), сессия принимает следующие сообщения. Состояние для Continue-As-New и результат workflow укладываются в запись (длинный ответ — с пометкой `answer_truncated`, полный — в треде). `wait(timeout=…)`; задача workflow падает раз за разом — `SessionStuck` вместо вечного ожидания. Отпечаток настроек сверяется при каждой отправке (`SettingsMismatch` — сообщение не принято, сессия работает дальше) и не учитывает пути промптов, `tui` (кроме `agentsmd_override`), `acp`, `pricing`. Трасса сжатия уходит частями. `agent_step` проверяет размер промпта до запуска и принимает параметры дочернего workflow (`parent_close_policy`, `execution_timeout`, `retry_policy`…); `AgentSession(workflow_id=…)` подключается к идущему workflow и не запускает новый. `maximum_attempts=0` нативного `RetryPolicy` на любом уровне — «не задано» (предел уровня остаётся). Снимок настроек с `os_backend.kind: docker|ssh|exec` собирается обратно (регрессия прошлого ревью). Вопрос человеку под Temporal не печатается в stderr воркера (печать повторялась при replay; в журнале прогона он есть).
- Ревью r7 (07.10): разница meta не зависит от порядка ключей (журнал больше не уходит в историю целиком после чтения из SQLite или истории Temporal); итог сборки meta сверяется по хэшу, при расхождении (чужая правка meta, повтор после записи) запись повторяется с полной meta — повтор после падения воркера получает исходную квитанцию, а чужая запись даёт конфликт ревизии, который ядро повторяет, а не отказ сессии; трасса субагента не перечитывает meta родителя; ответ последнего хода переживает Continue-As-New целиком до ~1 МБ, больше — `AnswerTruncated` (а не тихая обрезка); служебный запрос к модели (сводка при лимите шагов) больше записи истории укорачивается посередине с пометкой, а не роняет ход; meta не читается второй раз в начале хода; отпечаток настроек из сообщений переживает Continue-As-New.
- Ревью r8 (08.10): запасной путь полной meta укладывается в запись — записи журнала, разделы и короткие тексты идут ссылками по содержимому текущей meta хранилища (meta 3 МБ с чужой правкой `tui` посреди хода больше не роняет ход), не собирается — конфликт ревизии; кэш `fetch_url` при этом не стирается. Версия meta — ревизия и хэш содержимого (правка `tui` без смены ревизии видна). Ответ сессии не дублируется в состоянии Continue-As-New (ответ и форматированный ответ по ~600 КБ доходят целиком), `status()` несёт `answer_truncated`, `wait` возвращает одинаковый вид до и после Continue-As-New.
- **Файлы треда в хранилище тредов** (необязательная способность: `write_thread_file`/`read_thread_file`, удаление — в `reset`): снимки `fs_view_image`, картинки сообщений и медиа из ответов MCP ложатся в хранилище (SQLite, S3-модуль, `MemoryThreadStore`), а не на диск процесса; путь — ссылка `thread-file://…`, reset треда удаляет их вместе с историей. Файловое хранилище и локальный режим не меняются. Временный каталог `gc-images-<uid>` создаётся только при записи, а не при сборке контекста. Под Temporal: `fs_view_image` больше не падает (`state_id` в срезе зрения, адрес треда в запросе эффекта), а при хранилище без файлов треда выключается; лог прогона по умолчанию — в `logging` процесса (`save_logs: false`, `propagate: true`, маскировка секретов включена), трасса сжатия — записью лога; `AgentPlugin(log_handlers=…)`. Ссылка `thread-file://` читается только для своего треда: `fs_view_image` и охрана чтения отказывают ссылке на чужой тред.
- **Без человека по умолчанию** (`AgentPlugin(human_input=False)`, `WorkerConfig.human_input`): под Temporal у агента нет `turn_ask_human`, режим `ask` охраны (`write_guard`, `read_guard` и `binary_read_policy`, `url_policy`, `command_moderation`) — `deny`, а случайный запрос к человеку сразу получает отказ вместо вечного ожидания. Вопросы и подтверждения — `human_input=True`. В документации `agent_step` — где настраивается агент (плагин воркера) и что шаг запускает агента сам.
- Тред, которым владеет сессия Temporal, локальный TUI/CLI не открывает на запись, если каталог тредов общий с воркером; владение снимает закрытие сессии или `gc-temporal unlock`.
- **Перед обновлением** завершите (`temporal workflow terminate`) сессии, запущенные под прежним типом `NativeAgentWorkflow`: новые воркеры их не исполняют, а они держат свои треды (снять владение — `gc-temporal unlock`).
- `AsyncAgent` в durable-режиме: `send()` следует локальной семантике — вне хода сообщение ждёт следующего `run()` (раньше сразу запускало ход в фоне, его ответ терялся), во время хода `run()` дожидается хода, обработавшего присланное («хвост»); сбой фоновой отправки поднимается следующим `run()`.
- Агент шагом своего workflow: `await agent_step("shop", prompt, thread_id=…)` в коде workflow — ход в дочернем `AgentWorkflow` с предсказуемым ID (`step_workflow_id`) для ответа человека и stop.
- Своё хранилище тредов в Temporal обязано объявить `protected_paths()` (пути данных на диске воркера или `[]`): без этого воркер не стартует, а не оставляет данные незащищёнными от агента.
- Документация Temporal — один файл [docs/temporal.md](docs/temporal.md) про использование; `temporal-configuration.md` и `temporal-architecture.md` удалены.
- Защита от ввода-вывода ядра мимо Temporal: `gc_core.execution.ports.port(ctx, name)` — в durable-исполнении отсутствие порта роняет ход, а не исполняет локальный запасной путь в коде workflow; `test_port_contract` требует решения для Temporal по каждому необязательному атрибуту контекста ядра; песочница воркера запрещает создавать HTTP- и MCP-клиенты в коде workflow, а нарушение песочницы больше не превращается в «ошибку инструмента»; под Temporal гоняются 26 из 30 эталонных сценариев ядра (было 19), остальные — в списке с причинами, новый сценарий без решения роняет тест; `REQUIRE_TEMPORAL=1` превращает отсутствие `temporal` CLI в ошибку живых тестов.
- Серверный Temporal-режим удалён: `execution_backend`, `temporal_config`, `temporal_profile`, `temporal_store` в `config_server.yml` и маршруты `/temporal/{system}/{thread}/…` больше не существуют; gc-server работает только локально. Сессии Temporal — через `AgentClient` или `gc-temporal`.
- **Переименование**: пакет `gc-ua-temporalio` → `gc-core-temporalio` (модуль `gc_core_temporalio`), префикс `native_` убран из файлов и классов (`AgentWorkflow`, `SubagentWorkflow`, `AgentClient`, `WorkerConfig`, `AgentActivities`, `WorkflowOperations`, `RunRequest`…), команды `gc-temporal-worker` и `gc-temporal`, очереди по умолчанию `ua-workflow`, `ua-model`, `ua-resource-local`. Старые имена не поддерживаются: сессии, начатые под типом `NativeAgentWorkflow`, не продолжатся.
- Добавлен опциональный пакет `gc-core-temporalio`: штатные `AgentExecutor` и `ThreadSession` работают через workflow, а обращения к модели, внешние эффекты инструментов и операции хранилища выполняются в activities. Локальное исполнение остаётся режимом по умолчанию.
- Добавлены worker и client (`gc-temporal-worker`, `gc-temporal`, `AgentClient`), подтверждения, stop, дочерние workflow и управление persistent MCP-ресурсами.
- FileThreadStore и SQLite поддерживают квитанции операций хранилища и восстановление записи. Continue-As-New сохраняет очередь доставки, включая большие checkpoint.
- Конфигурация, архитектура и ограничения текущего deployment описаны в [документации Temporal](docs/temporal.md). Legacy workflow сохранён отдельно; автоматическая миграция его истории не выполняется.
- Профиль native-воркера без `revision`: workflow знает профиль по имени, настройки и токены берутся из текущего процесса воркера. Смена конфигурации или ротация токена — перезапуск воркера; живые сессии продолжают работу. Ключ `revision` в JSON воркера и флаг `--revision` клиента удалены.
- **У воркера нет своей базы**: `receipts_database` (SQLite с результатами activities и предпросмотром) удалён — результаты activities хранит история Temporal, повторы — «хотя бы раз», как у Pydantic AI и интеграций Temporal. Запрос к модели после падения воркера может повториться (и оплатиться второй раз). Эффект инструмента (запись, команда, MCP, project memory) исполняется одной попыткой: после падения модель получает «исход неизвестен, проверьте состояние»; повторы эффекта включаются явно в `activities.tools.<имя>.retry`. Удалены потоковый предпросмотр (`profiles.<имя>.preview_stream`) и эндпоинты `GET /temporal/{system}/{thread}/events` и `/stream`. Новый ключ `state_dir` — каталог служебного состояния (треды по умолчанию; по умолчанию — каталог конфига воркера); конфиги с `receipts_database` или `preview_stream` не загружаются.
- **Без хранилища payload**: `payload_storage` (наш файловый драйвер, каталог `payloads`, `prune_after_days`) удалён — всё лежит в истории Temporal и удаляется по retention, как у Pydantic AI. Лимиты истории (2 МБ на запись, 50 МБ на run) держат: Continue-As-New после хода; чтение треда и трассы субагента страницами по 400 КБ (ниже порога предупреждения сервера); вход activity модели — новые сообщения целиком, уже переданные и прочитанные из треда — хэш-ссылкой (воркер держит сообщения хода в памяти, на промахе ищет в треде, иначе workflow повторяет запрос целиком); потолок вывода инструмента через границу activity — 1 МБ (обрезка с пометкой, нужна ответам MCP); при `persist: turn` шаги хода пишутся в тред частями по 400 КБ (ядро делит запись, если хранилище объявляет `max_operation_bytes`; у локальных хранилищ потолка нет — одна операция, как раньше). Замер: тред 6 МБ и ход из 30 шагов — вход модели 40–45 КБ на шаг вместо 6–7 МБ. Свой external storage подключается через `DataConverter` клиента Temporal (API библиотеки). Ключ `--config` клиента нужен только `unlock`.
- **Сменился путь тредов по умолчанию**: без `thread_stores` воркер берёт каталог `threads` в `state_dir`, а не `threads` от cwd (workspace агента). Установка, полагавшаяся на умолчание, откроет пустые треды — задайте прежний путь явно (`"thread_stores": {"files": {"kind": "file", "path": "<workspace>/threads"}}`) или перенесите каталог.
- `gc-temporal unlock` снимает владение тредом у сессии, которой больше нет.
- Секция `activities` конфига воркера: таймауты и повторы activities по уровням (`default`, `model`, `resource`, `thread_store`, `tools.<имя>`), как `ActivityConfig` у Pydantic AI. Сбой провайдера модели (обрыв, 5xx, 408/425/429) теперь повторяет Temporal — по умолчанию без ограничения, с паузой до минуты: ход ждёт провайдера, а не завершается FAILED. Неразрешимое имя хоста, отказ TLS-сертификата и неверный URL не повторяются. `stop` отменяет ожидающий запрос к модели: ход завершается остановленным, не дожидаясь провайдера. `AgentClient.start` принимает `retry_policy` и `execution_timeout` для всего workflow (по умолчанию не заданы).
- Worker Versioning (секция `versioning` воркера, по умолчанию выключен): ход закреплён за сборкой, на которой начался, Continue-As-New переводит сессию на текущую сборку, простаивающая сессия переходит на новую сборку сразу после её объявления. Номер сборки — версия пакета `gc-core-temporalio` и хэш исходников (`0.4.0+a1b2c3d4e5f6`); без versioning воркер предупреждает на старте.
- В ядре — базовый класс доменного отказа хода `TurnFailure` (`ExecutionFailure`, ошибка провайдера, `ContextWindowExceeded`): durable-исполнитель переводит его в FAILED, прочие исключения кода workflow — в повтор workflow task.
- Сессия снимает владение тредом при закрытии после Continue-As-New и при падении; сбой коммита в режиме `persist: turn` не теряет шаги хода; сбой закрытия MCP не подменяет готовый ответ.
- Слит develop 0.4.0 (`os_backend`, параметры запроса на алиасе `models.<алиас>.main`/`.auxiliary`, `strip_think` на алиасе, схема тулов под алиас, повтор авторизации другой формой токена на 401): код develop переведён на типизированные настройки. В снимок конфига, который уходит в историю Temporal, `models.*.main`/`.auxiliary` проходят ту же схему, что и `backend.chat_completion_kwargs` (неизвестный ключ — отказ без значения в тексте ошибки); `os_backend.env` — секрет и только для воркера. Под Temporal проверены `os_backend.kind: local` и `harbor`; `docker`/`ssh`/`exec`/`sandbox` в native-воркере не прогонялись.
- Кэш страниц `fetch_url` под Temporal живёт в памяти воркера по сессии (до 64 МБ на все сессии), а не в состоянии workflow: страница в мегабайты больше не идёт во вход и результат activity, checkpoint субагента и meta треда (лимит записи 2 МБ). Кэш из meta треда, который вёл локальный режим, воркер в workflow не отдаёт.
- Повторы модели: ошибка в стриме или пустой ответ без кода повторяются, как в ядре (раньше ход завершался FAILED); незнакомый сбой провайдера без кода больше не повторяется без ограничения — повторяется только явный сбой транспорта.
- Субагент: если ход ребёнка упал, а сигнал родителю не дошёл, наружу выходит ошибка ребёнка, а не сбой сигнала.
- SQLite-хранилище тредов: снимок читается без блокировки записи и не создаёт пустых строк для незнакомого треда (статус и история по любому ID).
- Снимок конфига принимает рантайм-вид `os_backend` из схемы (`docker`, `ssh`, `exec`, `sandbox`), а не только `local`/`harbor`.
- Предел текста сообщения native-сессии — 1 000 000 байт UTF-8, а не символов: без хранилища payload миллион символов кириллицы (2 МБ) не помещался во вход activity модели.
- `TrackingFsBackend` пробрасывает `isolates_exec`: без этого обёртка учёта правок скрывала изоляцию `os_backend.kind: sandbox`, и MCP-сервер с `execute_on: os_backend` поднимался в процессе агента вне песочницы.

### Feature — limit trace summary (LIMIT_TRACE_SUMMARY_SPEC)

- When the main agent or a subagent hits a limit (`step_limit` / `tool_call_limit` / `token_limit`), the trace is now summarized by a single auxiliary LLM call and returned as a JSON envelope `{ok:false, status, message, raw_trace_summary}` instead of a flat string.
- `build_limit_envelope(state, reason, ctx)` in `src/summarize/limit_trace_summary.py` serializes `state.messages` (system prompt stripped; full trace, no truncation), calls `request_auxiliary_completion_text`, and returns the envelope. On LLM failure the envelope is still returned with an empty `raw_trace_summary`.
- The auxiliary LLM call does NOT count as `state.steps` and does NOT turn the agent loop (spec §5.3). Finish detection keeps priority over limit (spec §6.3).
- `SubagentRunner` limit branch is pure pass-through: it returns the child envelope unchanged (spec §6.2).
- Config kill-switch: `agent.limit_trace_summary` (default `true`). Весь трейс обрабатывается целиком, без искусственных лимитов на размер входа или выхода; `max_tokens` ответа берётся из `chat_completions.auxiliary_llm.max_tokens` (как у прочих aux-вызовов).
- Prompt: `prompts/limit_trace_summary.md`.
- Old spec `docs_md/done/2026-07-31-step-limit-forced-finish-spec.md` marked **superseded**.

### Breaking — tool namespaces (TOOL_NAMESPACES_SPEC v1.1)

- Builtin API names now use prefixes: `fs_*`, `exec_*`, `turn_*`, `session_*`, `project_*`; MCP `mcp_*`; subagent `subagent_*` (e.g. `subagent_special_agent`).
- Notable renames: `submit_solution` → `turn_finish`, `working_memory` → `session_memory`, `long_memory` → `project_memory`, `ask_human` → `turn_ask_human`.
- Config keys: `project_memory`, `strict_turn_finish_validation`, `intent_scope.tools` / `stop_tools` / `tool_usage_notice` use to-be tool names.
- Project file: `.gc/project_memory.md` (no automigrate from `long_memory.md`).
- No runtime alias for old tool or config names.

Internal unchanged: `state.shared.working_memory`, XML `<working_memory>` in summarizer payloads, yaml section `working_memory:` (summarize params).

Tool JSON envelopes now use to-be `"tool"` field names (e.g. `fs_read_file`, `exec_command`). `project_memory` domain API renamed (`build_project_memory_status`, `ProjectMemoryError`, …). Compaction prompt: `prompts/project_memory_compaction_prompt.md`.
